## TL;DR

분산 시스템에서 가장 다루기 까다로운 실패 유형은 "성공/실패가 아닌 **불확실(Unknown Outcome)**"이다. [[HTTP]] 요청은 서버에서 처리되었으나 응답이 클라이언트에 도달하지 못하는 경우, [[RPC Node]]로 보낸 [[sendRawTransaction]]이 타임아웃됐지만 실제로는 멤풀에 들어간 경우가 대표적이다. 해법의 골자는 세 가지다 — (1) [[Idempotency Key]]로 동일 요청의 중복 처리를 서버가 흡수하고, (2) [[Nonce Manager]]로 [[Treasury Wallet]]의 nonce를 중앙에서 직렬 할당하며, (3) 서명된 [[Raw Transaction]]과 [[txHash]]를 **전송 전에** DB에 영속화하여 재시도 시 동일 트랜잭션을 그대로 재방송(rebroadcast)한다. 이 세 가지가 결합되면 "처리되었는지 모르겠다"는 상태도 안전하게 수렴 가능한 상태로 바뀐다.

> [!tip] 핵심 원칙
> **불확실을 없애려 하지 말고, 불확실해도 같은 결과로 수렴하게 설계하라.** 멱등성은 "재시도해도 안전하다"의 다른 이름이며, 블록체인에서는 **nonce + rawTx 영속화**가 그 멱등성을 구성하는 물리적 기반이다. 자세한 메커니즘은 [[HTTP Unknown Outcome 문제]], [[멱등성 키로 해결하기]], [[Treasury 단일 지갑 재시도 문제 (nonce & txHash)]], [[Nonce Manager + Treasury Queue 패턴]]에서 다룬다.

## HTTP Unknown Outcome 문제

> [!note] 핵심 명제
> [[HTTP]]는 본질적으로 "요청을 보냄"과 "응답을 받음" 사이에 **원자성 보장이 없다**. 클라이언트가 받는 에러는 "서버가 실패했음"이 아니라 "결과를 알 수 없음(Unknown Outcome)"이다.

### 1. 왜 "실패"가 아니라 "모름"인가

전통적으로 우리는 [[HTTP]] 통신을 다음 두 결과 중 하나로 분류한다.

```
요청 → 서버 → 응답 200 OK   ✅ 성공
요청 → 서버 → 응답 500       ❌ 실패
```

하지만 현실의 분산 시스템에서는 **세 번째 상태**가 존재한다.

```
요청 → 서버 → (처리 완료) → 응답 → ⚡ 네트워크 단절 → 클라 timeout
                ↑                                            ↑
            DB commit 됨                          클라는 "실패"로 인식
```

이때 **클라이언트가 보유한 정보**는 단 하나, "응답이 안 왔다"는 사실뿐이다. 서버 입장에서 그 요청이:

- 도달하지 못했는지 (요청 패킷 손실)
- 도달했지만 처리 전에 죽었는지
- 처리 중에 죽었는지
- **처리 완료 후 응답 직전/도중에 단절됐는지**

—를 클라이언트가 구분할 방법이 **원리적으로 없다**. 이게 [[Unknown Outcome]] 문제다.

### 2. 단절이 발생할 수 있는 모든 지점

요청 한 번의 라이프사이클 동안 네트워크가 끊길 수 있는 지점은 생각보다 많다.

```
[Client]                                              [Server]
   |                                                     |
   |---(1) SYN ---------------------------------------> |  ← TCP 핸드셰이크 단절 가능
   |<--(2) SYN/ACK ------------------------------------ |
   |---(3) ACK + HTTP Request ------------------------> |  ← 요청 패킷 손실 가능
   |                                                     |
   |                                  [process request]  ← 여기서 서버 crash 가능
   |                                  [DB COMMIT]        ← ★ 가장 위험한 구간 시작
   |                                                     |
   |<--(4) HTTP Response ------------------------------- |  ← 응답 패킷 손실 가능
   |                                                     |
   |---(5) ACK ---------------------------------------> |  ← 클라가 받기 전 단절 가능
   |                                                     |
   ?  ← timeout / connection reset                       |  서버는 정상 처리 완료
```

> [!warning] 위험 구간
> **DB COMMIT 이후 ~ 클라이언트가 응답을 ACK하기 전**까지가 모호한 구간이다. 이 구간에 단절이 일어나면 서버 측 상태는 변경됐지만 클라이언트는 변경 사실을 모른다.

### 3. 구체적인 시나리오 — 결제 API

> [!example] 결제 요청에서 일어나는 Unknown Outcome
> ```
> POST /payments  { amount: 10000, userId: 42 }
> ```
> 1. 서버가 요청을 받아 PG사에 결제 승인 호출
> 2. PG 응답 OK, DB에 `payment_id = 12345, status = PAID` 저장 (COMMIT)
> 3. 서버가 `200 OK { payment_id: 12345 }` 응답 전송
> 4. 응답이 클라이언트의 모바일 네트워크에서 손실됨 (지하철 진입, LTE→3G 전환 등)
> 5. 클라이언트: 30초 후 timeout → "결제 실패" 표시
> 6. 사용자가 재시도 버튼 클릭 → 같은 요청 재전송
> 7. 서버는 **다시 PG 호출 → 또 결제 → 중복 청구** 💥

여기서 두 가지 손해가 발생한다.

| 측면 | 결과 |
|------|------|
| 사용자 경험 | "성공한 거 같은데 실패라고 떠서 한 번 더 눌렀다" |
| 비즈니스 임팩트 | 동일 주문에 2회 청구, CS 대응, 환불 비용 |
| 회계 정합성 | DB의 payment 레코드와 PG의 거래 내역이 N:1로 어긋남 |

### 4. 단순 재시도가 "사고의 원인"이 되는 구조

대부분의 [[HTTP client]] 라이브러리(axios, retrofit, OkHttp 등)는 기본적으로 **네트워크 에러나 5xx에 대해 자동 재시도** 옵션을 제공한다. 그런데 이건 다음과 같은 가정 위에서만 안전하다.

> [!tip] 자동 재시도가 안전하려면
> 1. 해당 요청이 [[Idempotent]]하거나
> 2. 서버가 [[중복 감지]] 메커니즘을 갖고 있어야 한다.
>
> 둘 다 아니면, 재시도는 **데이터 손상을 자동화**하는 장치가 된다.

GET, PUT, DELETE는 [[HTTP 메서드]] 정의상 멱등이지만 POST는 그렇지 않다. 그래서 "결제 생성", "송금", "주문 생성" 같은 [[POST]] 엔드포인트가 가장 큰 위험 지대다.

### 5. 본질: "최소 한 번"인가 "최대 한 번"인가

분산 시스템 교과서에서 말하는 [[메시지 전달 보장]]은 보통 셋 중 하나다.

```
At-most-once   : 재시도 안 함. 손실 가능. 중복 없음.
At-least-once  : 재시도 함. 손실 없음. 중복 가능.
Exactly-once   : 손실도 중복도 없음. 일반적으로 불가능, 시뮬레이션만 가능.
```

> [!note] HTTP의 디폴트 위치
> [[HTTP]]는 트랜스포트 레벨에서 **at-most-once에 가깝다** — 응답이 안 오면 그걸로 끝이다. 하지만 클라이언트가 재시도 로직을 붙이는 순간 [[at-least-once]]가 되고, 그때부터 **중복 처리**에 대한 책임은 서버로 넘어온다. [[Exactly-once]]는 [[Idempotency Key]]로 시뮬레이션한다([[멱등성 키로 해결하기]] 참조).

### 6. 클라이언트가 할 수 있는 것 / 못 하는 것

| 할 수 있는 것 | 못 하는 것 |
|--------------|-----------|
| 같은 요청을 다시 보낸다 | 서버의 처리 여부를 안다 |
| 서버에 "이전 요청 결과 알려줘"라고 묻는다 (단, 식별자 필요) | 응답 손실과 처리 실패를 구분한다 |
| 사용자에게 "결과 확인 중"이라고 표시한다 | 두 번째 요청이 첫 번째의 재시도인지 새 요청인지 서버에 알린다 (단, 키 없으면) |

> [!warning] 핵심 결론
> Unknown Outcome은 [[HTTP]]를 "더 잘 쓰는 것"으로는 해결되지 않는다. **서버와 클라이언트가 함께 합의한 식별자**(= [[Idempotency Key]])를 통해 "이 요청은 우리가 봤던 그 요청인가?"를 서버가 판정할 수 있도록 만들어야 한다. 어떻게 푸는지는 [[멱등성 키로 해결하기]] 섹션에서 다룬다.

## 멱등성 키로 해결하기

[[HTTP Unknown Outcome 문제]]를 해결하는 핵심 도구가 **Idempotency Key**(또는 **Request ID**) 패턴이다. 아이디어는 단순하다 — 클라이언트가 요청마다 고유 식별자를 만들어서 같이 보내고, 서버는 그 키를 기준으로 "이 요청은 처음인가? 이미 처리했나?"를 판단한다. 같은 키로 N번 와도 부작용은 1번만 발생하도록 보장하는 것이 목표다.

### 동작 원리

```
Client                              Server
  |                                   |
  | 1. UUID v4 생성: req_id = abc-123 |
  |---- POST /transfer ------------>  |
  |     Idempotency-Key: abc-123      |
  |     { amount: 100, to: X }        | 2. SELECT * FROM idempotency
  |                                   |    WHERE key = 'abc-123'
  |                                   |    → NOT FOUND
  |                                   |
  |                                   | 3. INSERT idempotency(key, status='IN_PROGRESS')
  |                                   | 4. 실제 처리 (DB 트랜잭션, 이체 등)
  |                                   | 5. UPDATE idempotency
  |                                   |    SET status='DONE', response=...
  |                                   |
  |  <---- 200 OK { txId: 999 } ----  |
  |                                   |
  |  ※ 네트워크 단절, 클라이언트는 timeout  |
  |                                   |
  | 6. 재시도 (같은 키!)              |
  |---- POST /transfer ------------>  |
  |     Idempotency-Key: abc-123      | 7. SELECT → status='DONE' 발견
  |                                   | 8. 저장된 response 그대로 반환
  |  <---- 200 OK { txId: 999 } ----  |  (실제 처리 안 함)
```

> [!note] 키는 **클라이언트**가 만든다
> 서버가 ID를 만들면 "요청을 받아야만 ID가 생긴다" — Unknown Outcome 상황에서 클라이언트는 같은 ID로 재시도할 방법이 없다. 그래서 [[Stripe API|Stripe]], [[PayPal]] 등 결제 API는 모두 클라이언트가 UUID/ULID를 생성해 헤더로 넣는 방식을 강제한다.

### 키 생성 규칙

| 잘못된 예 | 올바른 예 | 이유 |
|---|---|---|
| `userId + timestamp` | `UUIDv4` / `ULID` | 동시 요청 시 충돌 가능 |
| 매 재시도마다 새로 생성 | 한 번 만들면 재시도 내내 고정 | 재시도가 새 요청으로 보임 |
| 서버가 생성해서 반환 | 클라가 미리 생성 | Unknown Outcome에서 키 분실 |

### 서버 측 저장 — Current State Table + Event Log

멱등성 키만 따로 저장하는 별도 [[Redis]] 캐시로도 가능하지만, **트랜잭션 무결성** 때문에 보통은 [[Current State Table]]에 함께 박는다.

```sql
-- 현재 상태 테이블 (Idempotency 컬럼 포함)
CREATE TABLE transfers (
  id            BIGSERIAL PRIMARY KEY,
  idempotency_key TEXT UNIQUE NOT NULL,  -- ← 이게 핵심
  user_id       BIGINT,
  amount        NUMERIC,
  status        TEXT,  -- IN_PROGRESS | DONE | FAILED
  response_body JSONB, -- 재시도 시 그대로 돌려줄 응답
  created_at    TIMESTAMPTZ DEFAULT NOW(),
  updated_at    TIMESTAMPTZ
);

CREATE UNIQUE INDEX ON transfers(idempotency_key);
```

```sql
-- 이벤트 로그 테이블 (감사/재생용, append-only)
CREATE TABLE transfer_events (
  id            BIGSERIAL PRIMARY KEY,
  transfer_id   BIGINT REFERENCES transfers(id),
  event_type    TEXT,  -- CREATED | TX_BROADCAST | CONFIRMED | FAILED
  payload       JSONB,
  occurred_at   TIMESTAMPTZ DEFAULT NOW()
);
```

> [!tip] 두 테이블을 한 DB 트랜잭션으로 묶어라
> `INSERT INTO transfers(...) ... ON CONFLICT (idempotency_key) DO NOTHING RETURNING *` 와 이벤트 로그 `INSERT`를 **같은 transaction** 안에서 실행하면, "처리는 됐는데 멱등성 키 저장에 실패" 같은 어긋남이 원천 차단된다.

### 코드 패턴 (NestJS 예시)

```typescript
@Post('/transfer')
async transfer(
  @Headers('idempotency-key') key: string,
  @Body() dto: TransferDto,
) {
  return this.db.transaction(async (tx) => {
    // 1. UPSERT: 새 행이면 IN_PROGRESS로 잡고, 이미 있으면 그 행을 가져온다
    const [row, created] = await tx.transfer.upsertReturning({
      idempotency_key: key,
      status: 'IN_PROGRESS',
      ...dto,
    });

    // 2. 이미 끝난 요청이면 저장된 응답 그대로
    if (!created && row.status === 'DONE') {
      return row.response_body;
    }

    // 3. 같은 키인데 IN_PROGRESS면 → 동시 재시도 (409 또는 대기)
    if (!created && row.status === 'IN_PROGRESS') {
      throw new ConflictException('Request already in progress');
    }

    // 4. 처음이면 실제 처리
    const result = await this.doTransfer(row);
    await tx.transfer.update({ 
      where: { id: row.id }, 
      data: { status: 'DONE', response_body: result } 
    });
    await tx.transferEvent.create({ 
      data: { transfer_id: row.id, event_type: 'CONFIRMED', payload: result } 
    });
    return result;
  });
}
```

> [!warning] IN_PROGRESS 상태에 TTL을 걸어야 한다
> 처리 도중 서버가 죽으면 그 키는 영원히 IN_PROGRESS로 남는다. 보통 _N분 이상 IN_PROGRESS인 행을 FAILED로 옮기고 다시 시도할 수 있게_ 백그라운드 워커를 둔다 — 이게 [[비동기 워크플로우]]와 [[상태 머신|state machine]] 패턴이 자연스럽게 따라붙는 이유다.

### 요청 본문의 일관성도 검증해야 한다

같은 키로 **다른 본문**이 오면 어떻게 할까? Stripe는 본문 해시를 같이 저장해 두고, 키는 같은데 해시가 다르면 422를 던진다. 안 그러면 "키 abc-123으로 100원 송금했는데 같은 키로 1000원 재시도가 통과"하는 사고가 난다.

```typescript
const bodyHash = sha256(canonicalJson(dto));
if (row.body_hash !== bodyHash) {
  throw new UnprocessableEntityException('Idempotency-Key reused with different body');
}
```

### 한계 — 이게 모든 곳에서 통하지는 않는다

멱등성 키는 **자기 서버 안에서 같은 DB에 쓰는 작업**에는 완벽하다. 그러나 다음 섹션에서 다룰 **[[RPC 노드에서의 Unknown Outcome|RPC 노드 호출]]** 처럼 외부 시스템 — 특히 블록체인 노드 — 은 우리가 멱등성 테이블을 강제할 수 없다. 거기선 다른 도구(nonce, txHash, raw transaction 보존)가 필요하다.

## RPC 노드에서의 Unknown Outcome

[[멱등성 키]]는 우리가 만든 서버 끼리의 약속이라서 통하지만, [[RPC 노드]]는 그 약속 밖에 있다. Ethereum/EVM 계열의 `eth_sendRawTransaction`은 표준 JSON-RPC 메서드일 뿐, 우리가 보낸 요청에 idempotency-key 같은 헤더를 끼워 넣어도 **노드가 그것을 보고 중복을 막아주지 않는다**. 그래서 [[HTTP Unknown Outcome]]에서 이야기한 같은 클래스의 문제가, 한 계층 더 깊은 곳에서 다시 나타난다.

> [!warning] 핵심 문장
> 멱등성 키는 "내가 만든 API 계약" 안에서만 작동한다. RPC 노드처럼 **외부 시스템과의 경계**에서는 키 자체가 의미를 잃고, 우리는 다시 "노드가 받았는지조차 모르는" 원초적 Unknown Outcome으로 돌아간다.

### 1. sendRawTransaction이 타임아웃되면 일어나는 일

서버가 트랜잭션을 서명해서 [[Infura]] / [[Alchemy]] / 자체 [[geth]] 노드로 broadcast 하는 흐름은 이렇게 생겼다.

```
                    ┌────────────────────────────────┐
                    │           Our Backend          │
                    │  signedTx = wallet.sign(tx)    │
                    │  POST eth_sendRawTransaction   │
                    └──────────────┬─────────────────┘
                                   │  (HTTPS, 30s timeout)
                                   ▼
                    ┌────────────────────────────────┐
                    │       RPC Node (Infura)        │
                    │   1. parse + verify signature  │
                    │   2. admit to local mempool    │
                    │   3. gossip to peers           │
                    │   4. return txHash             │
                    └──────────────┬─────────────────┘
                                   │
                            ❌ TIMEOUT ❌
                       (어디서 끊겼는지 알 수 없음)
```

타임아웃이 떨어졌을 때 실제로 가능한 상태는 최소 5가지다.

| # | 실제 상태 | 우리가 보는 것 |
|---|----------|---------------|
| A | 노드까지 가지도 못함 (네트워크 단절) | timeout |
| B | 노드가 받았지만 reject (nonce too low 등) | timeout (응답 못 받음) |
| C | 노드가 받아서 mempool에 admit, 응답이 유실됨 | timeout |
| D | mempool admit + peer gossip 중 응답 유실 | timeout |
| E | 이미 채굴까지 됐는데 응답 유실 | timeout |

**전부 동일하게 timeout이라는 한 가지 신호로 들어온다.** 멱등성 키를 추가해본들, 이 5가지 중 어느 상태인지 구분해주지 않는다.

### 2. 멱등성 키가 무력해지는 이유

[[멱등성 키로 해결하기]]에서 우리가 만든 패턴은 "같은 키로 두 번 오면 첫 결과를 그대로 반환한다"였다. 이게 성립하려면 **수신자가 키를 기억하고, 같은 키의 부작용은 한 번만 일으켜야** 한다.

RPC 노드는 둘 다 안 해준다.

```ts
// 우리 머릿속의 모델 (틀림)
await rpc.sendRawTransaction(signedTx, {
  idempotencyKey: 'order-42-payout',  // ← 이런 거 없음
});

// 실제 JSON-RPC
{
  "jsonrpc": "2.0",
  "method": "eth_sendRawTransaction",
  "params": ["0xf86c80..."],   // signed tx 만 받음
  "id": 1
}
```

게다가 우리가 "같은 요청"이라고 생각하는 재시도를 그대로 다시 보내봐도, **mempool은 같은 nonce·같은 from의 tx를 새 트랜잭션으로 인지하지 않는다** — 이미 들어가 있으면 `ALREADY_KNOWN`을 돌려주고, 안 들어가 있었다면 새로 admit 한다. 일견 멱등해 보이지만, "어떤 signedTx 바이트가 같으냐"에만 멱등하다는 점이 함정이다. 같은 의미(같은 비즈니스 의도)지만 다른 nonce·다른 gas로 다시 서명해서 보내면, 그건 노드 입장에서 **완전히 별개의 트랜잭션**이고, 두 개 다 채굴될 수 있다.

> [!warning] 두 번 결제 시나리오
> Treasury 지갑에서 100 USDC를 보내는 tx가 타임아웃 → 안전한 줄 알고 nonce를 다시 따와 재서명·재전송 → 둘 다 mempool에 들어감 → **두 번 다 confirm**. 멱등성 키는 우리 DB 안에 있어서, 체인에는 200 USDC가 빠져나간 사실을 막을 방법이 없다.

### 3. 진짜 진실의 원천: txHash와 체인 상태

RPC 노드 너머에는 우리가 만든 게 아닌 진실의 원천이 하나 있다 — **블록체인 자체**. 그래서 분산 시스템에서 외부 서비스의 Unknown Outcome을 처리하는 일반 원칙이 여기서도 똑같이 적용된다:

> [!tip] 원칙
> **응답을 못 믿을 때는, 우리가 만든 식별자(txHash)로 외부 상태를 직접 조회한다.** 멱등성 키는 *클라이언트→서버* 경계용이고, txHash는 *서버→체인* 경계용이다.

`txHash`는 signedTx의 keccak256 해시라서, **서명한 순간 클라이언트가 미리 계산할 수 있다.** 노드가 응답을 주지 않아도 우리는 이미 hash를 알고 있다.

```ts
// 노드에 보내기 전에 hash를 먼저 계산해서 DB에 저장
const signedTx = await wallet.signTransaction(tx);
const txHash   = keccak256(signedTx);   // ethers: ethers.keccak256(signedTx)

await db.transactions.insert({
  id: requestId,
  txHash,                  // ← 미리 안다
  rawTx: signedTx,         // ← 재전송용으로 보관
  nonce: tx.nonce,
  status: 'BROADCASTING',
});

try {
  await rpc.sendRawTransaction(signedTx);   // 타임아웃 나도 OK
  await db.transactions.update(requestId, { status: 'BROADCASTED' });
} catch (e) {
  // 응답을 못 받았다 ≠ 실패다. 상태를 UNKNOWN으로만 표시.
  await db.transactions.update(requestId, { status: 'BROADCAST_UNKNOWN' });
}
```

이렇게 해두면, 타임아웃이 떨어진 뒤 reconciler가 **체인을 직접 본다**:

```ts
// 잠시 후 reconciler 잡
const onChain = await rpc.getTransactionReceipt(txHash);

if (onChain?.status === 1)      → CONFIRMED
else if (onChain?.status === 0) → REVERTED
else if (await inMempool(txHash)) → PENDING (그냥 기다린다)
else                            → DROPPED → 재전송 또는 재서명
```

상태 전이도를 명시하면 다음과 같다.

```
                   sendRawTx
   BROADCASTING ───────────────► BROADCASTED ──► CONFIRMED
        │                            │             │
        │ timeout                    │ getReceipt  │
        ▼                            ▼  status=0   ▼
 BROADCAST_UNKNOWN ──poll txHash─► PENDING     REVERTED
        │                            │
        │ not in mempool +           │ stuck (N blocks)
        │ no receipt                 ▼
        ▼                          BUMP_FEE (replace-by-fee)
     DROPPED ──► resubmit same rawTx
```

> [!example] 왜 rawTx를 통째로 저장하나
> 같은 `signedTx`를 다시 broadcast 하면 **txHash가 동일**해서, 중복 채굴이 절대 일어날 수 없다. 새로 서명하면 다른 hash → 다른 tx → 이중 지급 위험. 그래서 [[Treasury Queue 패턴]]의 핵심 인프라가 "rawTx + txHash를 DB에 박제해두는 것"이다.

### 4. HTTP Unknown Outcome과의 대응 관계

같은 문제, 다른 계층, 다른 식별자다.

| 계층 | Unknown Outcome 트리거 | 클라이언트가 미리 정하는 식별자 | 진실의 원천 |
|------|----------------------|-------------------------------|------------|
| HTTP API | request timeout | `Idempotency-Key` 헤더 | 우리 DB의 결과 테이블 |
| RPC → Chain | `sendRawTransaction` timeout | `txHash` (서명에서 도출) | 블록체인 (`getTransactionReceipt`) |

> [!note] 일반화
> **Unknown Outcome은 어느 분산 시스템 경계에서나 다시 나타난다.** 경계마다 (a) 클라이언트가 결정론적으로 만드는 식별자, (b) 외부 진실을 조회할 reconciliation 경로 — 이 두 가지를 함께 설계해야 한다. 하나만 있으면 안 된다.

이렇게 txHash까지 확보하면 "노드가 받았는지조차 모르는" 문제는 풀린다. 하지만 끝이 아니다 — 다음 문제는 [[Treasury 단일 지갑 재시도 문제]]: 재시도 사이에 **다른 요청이 nonce를 올려버리면** 그 rawTx를 다시 보내봤자 `nonce too low`로 거절된다. 그건 다음 섹션에서 다룬다.

## Treasury 단일 지갑 재시도 문제 (nonce & txHash)

[[Treasury]] 지갑이 **단 하나**라는 점은 운영적으론 깔끔하지만, 재시도 관점에선 **공유 자원에 대한 직렬화 문제**를 정면으로 만든다. 핵심 원인은 [[EVM]] 계열 체인의 [[nonce]]가 **계정별 순차 카운터**라는 사실이다.

> [!warning] 한 줄 요약
> "Replay 했더니 txHash가 달라졌다"는 건 *그 사이 다른 요청이 nonce를 먹어버렸기 때문*이다. 해결의 핵심은 **재서명하지 말고 원본 rawTx를 그대로 다시 쏘는 것**이다.

### 1. 왜 hash가 달라지는가 — nonce가 서명의 입력값이기 때문

EVM 트랜잭션의 [[txHash]]는 RLP 인코딩된 **서명된 트랜잭션 전체**의 keccak256이다. 서명의 입력에는 다음이 들어간다:

```
tx = { nonce, gasPrice (or maxFee/maxPriorityFee), gasLimit,
       to, value, data, chainId }
rawTx = RLP(tx, v, r, s)        // 서명 포함
txHash = keccak256(rawTx)
```

→ **nonce가 1만 바뀌어도 서명이 바뀌고, 서명이 바뀌면 txHash가 완전히 달라진다.**

따라서 서버 코드가 매번 "현재 nonce를 조회해서 새로 서명"하는 식이면, 재시도 때 다른 txHash가 나오는 건 *피할 수 없는 결과*다.

### 2. 문제가 터지는 시나리오 — 단일 지갑 race

요청 A가 실패해서 재시도하려는 그 짧은 사이, 요청 B가 같은 지갑을 사용해 처리되어 nonce가 올라간다.

```
시각  요청   동작                        지갑 nonce   txHash 추적 상태
─────────────────────────────────────────────────────────────────────
t0    A     서명(nonce=42) → 전송       42 → ?       hashA 기록
t1    A     RPC 타임아웃 (Unknown)       ?            hashA, 결과 모름
t2    B     서명(nonce=43) → 전송 → 채굴 43 → 44      hashB 성공
t3    A     "재시도" → 현재 nonce=44     ↑            
              로 다시 서명 → 전송         
                                          → hashA' (전혀 다른 해시)
```

문제 상황 정리:

| 상태 | 원본 hashA | 재서명 hashA' |
|---|---|---|
| 체인에 있나? | **모름** (mempool에서 drop? 이미 채굴?) | 새 트랜잭션으로 broadcast 됨 |
| nonce | 42 | 44 |
| 중복 결제 위험 | — | **있음** (둘 다 채굴되면 두 번 송금) |
| 추적성 | hashA로는 더 이상 못 찾음 | 새 hash라 [[이벤트 로그]]와 연결 끊김 |

> [!danger] 단순 재시도의 함정
> "현재 nonce 다시 가져와서 다시 서명한다"는 코드는 **사실상 새 트랜잭션을 만드는 것**이다. 원본이 mempool에 살아있거나 이미 채굴됐다면 **두 번 결제**가 일어난다. [[멱등성]] 보장이 완전히 깨진다.

### 3. 해결책 — rawTx 사전 저장 + sendRawTransaction 재전송

핵심 아이디어는 **서명을 *상태로* 저장**해 두는 것이다. 서명은 commit, broadcast는 retry-able.

```
[ Build & Sign ] ─────► (DB) raw_transactions
       │                  ─ id, intent_id (idempotency key)
       │                  ─ nonce
       │                  ─ rawTx (bytes)
       │                  ─ txHash (계산된 값)
       │                  ─ status: SIGNED | BROADCAST | CONFIRMED
       ▼
[ Broadcast ] ──► eth_sendRawTransaction(rawTx)
       │
       │   타임아웃/네트워크 에러?
       ▼
[ Retry ] ──► **같은 rawTx를 다시 sendRawTransaction**
              → 같은 nonce, 같은 서명 → 같은 txHash
              → 노드는 "already known" / "nonce too low" 응답
              → 그래도 OK, 이미 받아들였다는 뜻
```

> [!tip] 핵심 불변식
> **(intent_id) → (rawTx, txHash) 매핑이 DB에 1:1로 고정**된 순간, 그 intent는 영원히 같은 txHash로만 추적된다. RPC가 몇 번 죽든 상관없다.

#### 의사 코드

```typescript
async function sendFromTreasury(intent: TransferIntent) {
  // 1) idempotency key로 기존 서명 있는지 확인
  let row = await db.rawTx.findByIntentId(intent.id);

  if (!row) {
    // 2) 없으면: nonce 할당 + 서명까지 한 트랜잭션 안에서 커밋
    const nonce = await nonceManager.acquire(treasuryAddress); // [[Nonce Manager]]
    const tx = buildTx({ ...intent, nonce });
    const { rawTx, txHash } = await signer.sign(tx);
    row = await db.rawTx.insert({
      intentId: intent.id, nonce, rawTx, txHash, status: 'SIGNED',
    });
  }

  // 3) 항상 같은 rawTx를 broadcast (재시도여도)
  try {
    await rpc.sendRawTransaction(row.rawTx);
  } catch (e) {
    // "already known", "nonce too low (already mined)" 는 사실상 성공
    if (!isBenignBroadcastError(e)) throw e;
  }

  // 4) txHash로 채굴 여부 확인 (별도 reconciler가 polling)
  return row.txHash;
}
```

### 4. 왜 이게 정답인가 — 3가지 보장

> [!example] rawTx 사전 저장이 사주는 것들
> 1. **결정론적 txHash** — 같은 (nonce, payload, key)면 무조건 같은 hash. [[이벤트 로그 테이블]]과 1:1 매칭.
> 2. **재전송 안전성** — `eth_sendRawTransaction`은 같은 rawTx에 대해 멱등이다. "already known"은 에러처럼 보여도 *성공*으로 처리해야 한다.
> 3. **장애 회복성** — 서버가 broadcast 직전에 죽어도 다음 부팅 시 `SIGNED` 상태인 row를 발견해 그대로 쏘면 된다.

### 5. 그래도 남는 함정 — nonce gap

rawTx를 만들었는데 broadcast 전에 *그 nonce를 건너뛰고* 더 큰 nonce가 먼저 채굴되면 어떻게 될까?

→ 그럴 일이 없도록 **nonce 발급을 직렬화**해야 한다. 이게 다음 섹션에서 다룰 [[Nonce Manager]] + [[Treasury Queue]] 패턴의 존재 이유다.

```
nonce 42 가 SIGNED 상태로 DB에만 있고 broadcast 안 됨
nonce 43, 44, 45 가 먼저 broadcast → mempool에서 "42 대기" 상태로 멈춤
  → 42를 빨리 쏘거나, 같은 nonce로 cancel-tx(높은 gas, value=0 self-transfer)로 덮어써야 풀림
```

> [!note] 요약
> - **단일 지갑 = 단일 nonce 카운터** → 모든 retry는 *이 카운터를 공유*한다.
> - **서명을 먼저, broadcast는 나중에** — rawTx를 DB에 박아두는 순간 trxn id (= txHash)가 freeze 된다.
> - **재시도 ≠ 재서명**. 재시도는 *동일 rawTx 재전송*이다. 이 한 줄 차이가 "두 번 송금" 사고를 막는다.

## Nonce Manager + Treasury Queue 패턴

단일 Treasury 지갑에서 [[nonce]] 충돌과 [[Unknown Outcome]] 문제를 동시에 해결하려면, **nonce 발급을 직렬화**하고 **서명된 rawTx를 영속화**해서 재시도 시 **동일한 txHash를 그대로 재브로드캐스트**하는 구조가 필요하다. 이 두 가지 — Nonce Manager와 Treasury Queue — 가 한 세트로 묶인다.

### 왜 이 조합이어야 하는가

> [!warning] 단순 재시도의 함정
> "실패하면 다시 sendTransaction" 은 가장 흔한 안티패턴이다. 같은 비즈니스 요청이라도 nonce가 바뀌면 [[txHash]]가 달라지고, 운이 나쁘면 **두 트랜잭션이 모두 체인에 올라가** 이중 송금이 발생한다. [[idempotency key]] 만으로는 부족하다 — 서명 자체가 멱등적이어야 한다.

핵심 통찰: **서명된 rawTx는 그 자체로 멱등 토큰이다.** 같은 (from, nonce, to, value, data, gas, chainId, signature) 튜플을 몇 번을 브로드캐스트하든 체인은 단 한 번만 채택한다. 따라서 "한 번 서명한 rawTx를 잃지 않는 것" 이 전부다.

### 전체 워크플로우

```
 ┌─────────────┐   1. enqueue(jobId, payload)    ┌──────────────────┐
 │  API / BFF  │ ──────────────────────────────► │ Treasury Queue   │
 └─────────────┘                                  │   (FIFO, single  │
        ▲                                         │   consumer)      │
        │ 5. status(jobId)                        └────────┬─────────┘
        │                                                  │
        │                                  2. claim job    ▼
        │                                  ┌──────────────────────────┐
        │                                  │   Treasury Worker        │
        │                                  │   (single-flight)        │
        │                                  └────────┬─────────────────┘
        │                                           │
        │                3. allocateNonce(addr) ◄───┤
        │                                           │
        │                                  ┌────────▼─────────────────┐
        │                                  │   Nonce Manager          │
        │                                  │   (Redis INCR /          │
        │                                  │    Postgres advisory     │
        │                                  │    lock + counter)       │
        │                                  └────────┬─────────────────┘
        │                                           │
        │            4. sign + persist(rawTx,       │
        │                              txHash,      │
        │                              nonce)       ▼
        │                                  ┌──────────────────────────┐
        │                                  │   tx_outbox (Postgres)   │
        │                                  │   pending → sent →       │
        │                                  │   mined / dropped        │
        │                                  └────────┬─────────────────┘
        │                                           │
        │                                  5. eth_sendRawTransaction
        │                                           │
        └───────────── 6. confirmer ◄───────────────┘
                       (poll receipt by txHash,
                        rebroadcast on timeout,
                        bump-fee on stuck)
```

### 단계별 책임 분해

> [!example] 6단계 흐름
> 1. **Enqueue** — 비즈니스 핸들러는 [[idempotency key]](= `jobId`)와 함께 큐에 작업을 넣고 즉시 `202 Accepted` 반환.
> 2. **Claim** — Treasury Worker는 큐에서 **단일 컨슈머**로 작업을 꺼낸다. 동시성은 정확히 1.
> 3. **Allocate nonce** — Nonce Manager가 해당 주소의 다음 nonce를 원자적으로 발급.
> 4. **Sign & persist** — rawTx를 만들고 **DB에 먼저 저장한 뒤** 브로드캐스트.
> 5. **Broadcast** — `eth_sendRawTransaction`. 실패하든 타임아웃이든 rawTx는 이미 DB에 있다.
> 6. **Confirm / retry** — 별도 컨퍼머가 영수증을 폴링하고, 안 잡히면 **같은 rawTx**를 다시 쏘거나 fee를 bump한다.

### Nonce Manager — 직렬화된 발급

[[Ethereum]] 의 nonce는 주소별로 0부터 단조 증가하는 정수이고, **gap이 생기면 그 뒤 모든 트랜잭션이 mempool에 멈춘다.** 그래서 발급은 반드시 직렬화돼야 한다.

```typescript
// Redis 기반 — 가장 흔한 구현
class NonceManager {
  async allocate(address: string): Promise<number> {
    const key = `nonce:${address}`;
    // Lua 스크립트로 원자성 보장
    const next = await redis.eval(`
      local cur = redis.call('GET', KEYS[1])
      if not cur then
        local onchain = tonumber(ARGV[1])
        redis.call('SET', KEYS[1], onchain)
        return onchain
      end
      return redis.call('INCR', KEYS[1]) - 1
    `, 1, key, await provider.getTransactionCount(address, 'pending'));
    return Number(next);
  }

  async reset(address: string) {
    // 드리프트가 의심될 때 on-chain 값으로 강제 복구
    const onchain = await provider.getTransactionCount(address, 'pending');
    await redis.set(`nonce:${address}`, onchain);
  }
}
```

> [!tip] On-chain `getTransactionCount` 만 믿지 말 것
> `pending` 카운트는 노드마다 다르고, 우리가 방금 쏜 tx가 아직 mempool에 안 보일 수도 있다. **로컬 카운터를 source of truth로 두고**, on-chain 값은 부팅 시 / 드리프트 감지 시에만 참조한다.

| 구현 옵션 | 직렬화 메커니즘 | 장점 | 단점 |
|---|---|---|---|
| Redis `INCR` | 싱글 스레드 보장 | 빠름 (μs) | Redis 장애 시 드리프트 |
| Postgres `SELECT ... FOR UPDATE` | row lock | 트랜잭션과 한 묶음 가능 | 느림 (ms) |
| Postgres advisory lock | `pg_advisory_xact_lock` | DB 트랜잭션 자연 통합 | 락 키 관리 필요 |
| In-process Mutex | 워커 1개일 때만 | 가장 단순 | 스케일 아웃 불가 |

### Treasury Queue — 단일 컨슈머의 이유

Treasury가 지갑 하나라면 **그 지갑에 대한 nonce 발급도 한 곳에서만 일어나야 한다.** 큐의 의미는 throughput이 아니라 **순서 보장**이다.

```typescript
// BullMQ 예시 — concurrency: 1 이 핵심
const treasuryWorker = new Worker('treasury', async (job) => {
  const { jobId, to, value, data } = job.data;

  // 이미 처리된 job인가? (idempotency)
  const existing = await db.tx_outbox.findUnique({ where: { jobId } });
  if (existing?.txHash) {
    // 재시도라면 같은 rawTx를 다시 쏜다
    return rebroadcast(existing.rawTx, existing.txHash);
  }

  // 신규 처리
  const nonce = await nonceManager.allocate(TREASURY_ADDR);
  const tx = await signer.populateTransaction({ to, value, data, nonce });
  const signed = await signer.signTransaction(tx);
  const txHash = ethers.keccak256(signed);

  // ★ 브로드캐스트 전에 DB 저장
  await db.tx_outbox.create({
    data: { jobId, nonce, rawTx: signed, txHash, status: 'pending' },
  });

  try {
    await provider.broadcastTransaction(signed);
    await db.tx_outbox.update({
      where: { jobId },
      data: { status: 'sent' },
    });
  } catch (e) {
    // 네트워크 에러여도 OK — rawTx는 이미 저장됨
    // confirmer가 알아서 재브로드캐스트
  }
}, { connection: redis, concurrency: 1 });  // ◄ 반드시 1
```

> [!note] 왜 concurrency=1인가
> 워커가 둘이면 둘 다 동시에 nonce를 발급받을 수 있고, 발급 자체는 직렬화돼도 **누가 먼저 sendRawTransaction을 호출할지는 보장되지 않는다.** 빠른 워커가 nonce=11을 먼저 쏘고 느린 워커가 nonce=10에서 멈추면 — gap. concurrency=1은 이걸 원천 차단한다. 진짜로 처리량이 필요하면 [[multi-treasury sharding]] (지갑을 N개로 분할) 으로 가야 한다.

### rawTx 영속화 — 멱등성의 진짜 무기

`tx_outbox` 테이블 스키마:

```sql
CREATE TABLE tx_outbox (
  job_id        TEXT PRIMARY KEY,           -- 비즈니스 idempotency key
  nonce         BIGINT NOT NULL,
  raw_tx        BYTEA NOT NULL,             -- 서명 완료된 rawTx
  tx_hash       TEXT NOT NULL UNIQUE,       -- keccak256(rawTx)
  status        TEXT NOT NULL,              -- pending|sent|mined|dropped|replaced
  attempts      INT NOT NULL DEFAULT 0,
  last_error    TEXT,
  created_at    TIMESTAMPTZ DEFAULT now(),
  mined_at      TIMESTAMPTZ,
  block_number  BIGINT
);

CREATE INDEX ON tx_outbox (status, created_at);
CREATE UNIQUE INDEX ON tx_outbox (nonce);  -- 같은 nonce 두 번 금지
```

> [!warning] 서명 → 저장 → 브로드캐스트, 순서가 전부다
> "브로드캐스트하고 성공하면 저장" 은 틀린 순서다. 브로드캐스트는 성공했는데 DB 저장 직전 프로세스가 죽으면 — Unknown Outcome. nonce는 소비됐고 우리는 무슨 tx를 쐈는지 모른다. 반드시 **DB 저장이 먼저**, 브로드캐스트가 나중. ([[outbox pattern]])

### Confirmer — 재브로드캐스트 루프

```typescript
// 별도 워커로 분리. 큐와 무관하게 주기적으로 돈다.
setInterval(async () => {
  const pending = await db.tx_outbox.findMany({
    where: { status: { in: ['pending', 'sent'] } },
    orderBy: { nonce: 'asc' },
  });

  for (const row of pending) {
    const receipt = await provider.getTransactionReceipt(row.tx_hash);
    if (receipt) {
      await db.tx_outbox.update({
        where: { job_id: row.job_id },
        data: {
          status: receipt.status === 1 ? 'mined' : 'reverted',
          block_number: receipt.blockNumber,
          mined_at: new Date(),
        },
      });
      continue;
    }

    const age = Date.now() - row.created_at.getTime();
    if (age > 30_000) {
      // 같은 rawTx 그대로 재전송 — txHash 변하지 않음, 멱등
      await provider.broadcastTransaction(row.raw_tx).catch(() => {});
      await db.tx_outbox.update({
        where: { job_id: row.job_id },
        data: { attempts: { increment: 1 } },
      });
    }

    if (age > 5 * 60_000) {
      // 5분 이상 stuck → fee bump (replacement tx, 같은 nonce)
      await bumpFee(row);
    }
  }
}, 5_000);
```

### 사용자 질문에 직접 답하기

> [!example] "트레저리 지갑 하나, 실패해서 replay 할 때 txHash 재계산 안 되지 않냐?"
> 정답이다. **그래서 재계산을 안 한다.** 최초 1회 서명된 rawTx와 그 txHash를 `tx_outbox` 에 박아두고, 재시도는 `provider.broadcastTransaction(row.raw_tx)` 로 **같은 바이트 시퀀스를 다시 쏘는 것**으로 끝낸다. nonce가 이미 박혀 있으니 그 사이 다른 요청이 더 높은 nonce를 써도 무관하다 — 우리 tx는 자기 자리(nonce=N)에서 채굴되기를 기다린다.

> [!example] "그 사이 다른 요청이 nonce 올렸으면?"
> Nonce는 **이미 발급 시점에 fix됐다.** Job A가 nonce=10을 할당받아 서명까지 끝낸 뒤 브로드캐스트만 실패한 상황에서, Job B가 nonce=11로 먼저 채굴돼도 — 체인은 nonce=10이 들어올 때까지 nonce=11 이후의 tx들을 **mempool에 보류**한다. Job A의 rawTx를 다시 쏘면 nonce=10이 채워지고 줄줄이 채굴된다. 만약 Job A가 영원히 못 들어가면 (예: 잘못된 데이터로 항상 revert) — fee bump로 같은 nonce의 **dummy tx로 덮어쓰기**가 최후의 수단이다.

### 운영상 주의점

- **Drop 감지**: mempool에서 떨어진 tx (`getTransaction` 이 null) 는 그냥 다시 쏘면 된다. rawTx가 살아있으니까.
- **Reorg 처리**: `mined` 상태여도 N블록 확정 전엔 다시 `pending`으로 돌릴 수 있어야 한다.
- **Fee bump = replacement**: 같은 nonce + 더 높은 gas price로 새 rawTx 서명. 이전 rawTx는 `replaced` 로 마킹.
- **모니터링**: oldest pending tx의 age, nonce drift (`localCounter - onchainCount`), attempts 분포를 [[Datadog]] 으로 추적.

이 패턴은 [[Tigris]], [[Coinbase]] 같은 곳의 wallet infrastructure 글에서 [[Treasury Worker]] / [[Wallet Service]] 라는 이름으로 반복적으로 등장한다. 핵심은 변하지 않는다 — **서명을 한 번만 하고, 영속화하고, 같은 바이트를 재전송하라.**

## English

### TL;DR

The hardest failure mode in distributed systems is not success-or-failure but **Unknown Outcome**: an [[HTTP]] request that the server processed but whose response never reached the client, or a [[sendRawTransaction]] call to an [[RPC Node]] that timed out yet still landed in the mempool. The remedy has three pillars — (1) an [[Idempotency Key]] lets the server absorb duplicate retries of the same logical request, (2) a [[Nonce Manager]] centrally serializes nonce assignment for the shared [[Treasury Wallet]], and (3) the signed [[Raw Transaction]] together with its [[txHash]] is persisted **before** broadcast, so retries simply re-broadcast the *same* transaction instead of recomputing a new hash. Together, these turn "I don't know whether it happened" into a state that safely converges.

> [!tip] Core principle
> **Don't try to eliminate uncertainty — design so the system converges to the same result despite it.** Idempotency is just another word for "safe to retry," and on-chain that safety is physically grounded in **nonce + persisted rawTx**. The mechanisms are unpacked in [[HTTP Unknown Outcome 문제]], [[멱등성 키로 해결하기]], [[Treasury 단일 지갑 재시도 문제 (nonce & txHash)]], and [[Nonce Manager + Treasury Queue 패턴]].

### The HTTP Unknown Outcome Problem

> [!note] Core claim
> [[HTTP]] gives **no atomicity guarantee** between "request sent" and "response received." The error a client sees is not "the server failed" — it's "the outcome is unknown."

#### 1. Why it's "unknown," not "failed"

The naive mental model of [[HTTP]] has two outcomes:

```
request → server → 200 OK   ✅ success
request → server → 500       ❌ failure
```

But in real distributed systems there is a **third state**:

```
request → server → (processed) → response → ⚡ network drop → client timeout
              ↑                                                     ↑
        DB commit done                                  client thinks "failed"
```

The only fact the client actually possesses is "no response came back." It has **no way in principle** to distinguish whether the request:

- never arrived (request packet lost),
- arrived but the server died before processing,
- died mid-processing, or
- **completed processing and then died just before/during sending the response.**

That is the [[Unknown Outcome]] problem.

#### 2. Every point where the wire can drop

Within a single request lifecycle, there are surprisingly many places the network can break.

```
[Client]                                              [Server]
   |                                                     |
   |---(1) SYN ---------------------------------------> |  ← TCP handshake can drop
   |<--(2) SYN/ACK ------------------------------------ |
   |---(3) ACK + HTTP Request ------------------------> |  ← request packet can be lost
   |                                                     |
   |                                  [process request]  ← server may crash here
   |                                  [DB COMMIT]        ← ★ danger zone begins
   |                                                     |
   |<--(4) HTTP Response ------------------------------- |  ← response packet can be lost
   |                                                     |
   |---(5) ACK ---------------------------------------> |  ← can drop before client acks
   |                                                     |
   ?  ← timeout / connection reset                       |  server completed normally
```

> [!warning] The danger zone
> **From DB COMMIT until the client ACKs the response** is the ambiguous window. If the drop happens in this window the server-side state has changed but the client doesn't know it.

#### 3. A concrete scenario — payment API

> [!example] Unknown Outcome in a payment flow
> ```
> POST /payments  { amount: 10000, userId: 42 }
> ```
> 1. Server receives the request and calls the PG (payment gateway) to authorize.
> 2. PG returns OK, server writes `payment_id = 12345, status = PAID` and COMMITs.
> 3. Server sends `200 OK { payment_id: 12345 }`.
> 4. The response is lost on the client's mobile network (subway tunnel, LTE→3G switch, etc.).
> 5. Client times out after 30s → shows "payment failed."
> 6. User taps "retry" → identical request goes out again.
> 7. Server **calls the PG again → charges again → duplicate charge.** 💥

Two kinds of damage follow.

| Aspect | Outcome |
|--------|---------|
| UX | "It looked like it worked but said failed, so I tapped again." |
| Business impact | Same order charged twice, support tickets, refund cost |
| Accounting integrity | DB payment records and PG transaction records diverge N:1 |

#### 4. Why naive retries become the cause of incidents

Most [[HTTP client]] libraries (axios, retrofit, OkHttp, …) ship with automatic retry on network errors or 5xx. That is safe **only** under these assumptions:

> [!tip] When auto-retry is safe
> 1. The request is [[Idempotent]], **or**
> 2. The server implements [[중복 감지]] (duplicate detection).
>
> If neither holds, retry becomes a mechanism for **automating data corruption**.

GET, PUT, DELETE are idempotent by [[HTTP 메서드]] definition, but POST is not. So `POST` endpoints like "create payment," "send money," "create order" are the highest-risk surface area.

#### 5. The essence: at-least-once vs at-most-once

Distributed systems textbooks define three [[메시지 전달 보장]] (delivery guarantees):

```
At-most-once   : no retries. loss possible. no duplicates.
At-least-once  : retries. no loss. duplicates possible.
Exactly-once   : neither loss nor duplicates. impossible in general; only simulable.
```

> [!note] HTTP's default position
> [[HTTP]] at the transport level is close to **at-most-once** — if the response doesn't come back, that's it. The moment the client adds retry logic it becomes [[at-least-once]], and **responsibility for handling duplicates shifts to the server**. [[Exactly-once]] is simulated via an [[Idempotency Key]] (see [[멱등성 키로 해결하기]]).

#### 6. What the client can vs cannot do

| Can do | Cannot do |
|--------|-----------|
| Re-send the same request | Know whether the server processed it |
| Ask "what was the result of my last request?" (if it has an ID) | Distinguish response-loss from processing-failure |
| Show "checking result…" UX | Tell the server whether this is a retry or a new request (without a key) |

> [!warning] Bottom line
> Unknown Outcome cannot be solved by "using [[HTTP]] better." You need an **identifier the client and server agree on** (= [[Idempotency Key]]) so the server can answer: "Is this the same request I've already seen?" How to actually do that is the topic of [[멱등성 키로 해결하기]].

### Solving It with Idempotency Keys

The canonical tool for the [[HTTP Unknown Outcome 문제|HTTP Unknown Outcome problem]] is the **Idempotency Key** (a.k.a. **Request ID**) pattern. The idea is simple — the client generates a unique identifier for each logical request and sends it along; the server uses that key to decide "is this a first-time request, or one I've already processed?". The guarantee: even if the same key arrives N times, the side effect happens exactly once.

### How it works

```
Client                              Server
  |                                   |
  | 1. Generate UUID v4: req_id = abc-123
  |---- POST /transfer ------------>  |
  |     Idempotency-Key: abc-123      |
  |     { amount: 100, to: X }        | 2. SELECT * FROM idempotency
  |                                   |    WHERE key = 'abc-123'
  |                                   |    → NOT FOUND
  |                                   |
  |                                   | 3. INSERT idempotency(key, status='IN_PROGRESS')
  |                                   | 4. Do the actual work (DB tx, transfer, …)
  |                                   | 5. UPDATE idempotency
  |                                   |    SET status='DONE', response=...
  |                                   |
  |  <---- 200 OK { txId: 999 } ----  |
  |                                   |
  |  ※ Network drops, client times out
  |                                   |
  | 6. Retry (same key!)              |
  |---- POST /transfer ------------>  |
  |     Idempotency-Key: abc-123      | 7. SELECT → finds status='DONE'
  |                                   | 8. Returns the stored response verbatim
  |  <---- 200 OK { txId: 999 } ----  |  (no real processing)
```

> [!note] The **client** generates the key
> If the server generated it, "no ID exists until the request lands" — in an Unknown Outcome scenario the client has no way to retry with the same ID. That's why [[Stripe API|Stripe]], [[PayPal]], and other payment APIs require the client to mint a UUID/ULID and send it as a header.

### Key generation rules

| Wrong | Right | Why |
|---|---|---|
| `userId + timestamp` | `UUIDv4` / `ULID` | Concurrent requests collide |
| New key on every retry | Mint once, freeze for the retry loop | Retry looks like a new request |
| Server-generated, returned to client | Client mints in advance | Key is lost on Unknown Outcome |

### Server-side storage — Current State Table + Event Log

You could keep idempotency keys in a separate [[Redis]] cache, but for **transactional integrity** you usually nail them into the [[Current State Table]] itself.

```sql
-- Current state table (with idempotency column)
CREATE TABLE transfers (
  id            BIGSERIAL PRIMARY KEY,
  idempotency_key TEXT UNIQUE NOT NULL,  -- ← the linchpin
  user_id       BIGINT,
  amount        NUMERIC,
  status        TEXT,  -- IN_PROGRESS | DONE | FAILED
  response_body JSONB, -- response to return verbatim on retry
  created_at    TIMESTAMPTZ DEFAULT NOW(),
  updated_at    TIMESTAMPTZ
);

CREATE UNIQUE INDEX ON transfers(idempotency_key);
```

```sql
-- Event log table (audit / replay, append-only)
CREATE TABLE transfer_events (
  id            BIGSERIAL PRIMARY KEY,
  transfer_id   BIGINT REFERENCES transfers(id),
  event_type    TEXT,  -- CREATED | TX_BROADCAST | CONFIRMED | FAILED
  payload       JSONB,
  occurred_at   TIMESTAMPTZ DEFAULT NOW()
);
```

> [!tip] Wrap both tables in a single DB transaction
> Run `INSERT INTO transfers(...) ... ON CONFLICT (idempotency_key) DO NOTHING RETURNING *` and the event-log `INSERT` inside **one transaction**. That eliminates the "work happened but idempotency key wasn't saved" skew at the root.

### Code pattern (NestJS example)

```typescript
@Post('/transfer')
async transfer(
  @Headers('idempotency-key') key: string,
  @Body() dto: TransferDto,
) {
  return this.db.transaction(async (tx) => {
    // 1. UPSERT: new row → IN_PROGRESS; existing row → return it
    const [row, created] = await tx.transfer.upsertReturning({
      idempotency_key: key,
      status: 'IN_PROGRESS',
      ...dto,
    });

    // 2. Already finished → return the stored response
    if (!created && row.status === 'DONE') {
      return row.response_body;
    }

    // 3. Same key, still IN_PROGRESS → concurrent retry (409 or wait)
    if (!created && row.status === 'IN_PROGRESS') {
      throw new ConflictException('Request already in progress');
    }

    // 4. First time → actually do the work
    const result = await this.doTransfer(row);
    await tx.transfer.update({ 
      where: { id: row.id }, 
      data: { status: 'DONE', response_body: result } 
    });
    await tx.transferEvent.create({ 
      data: { transfer_id: row.id, event_type: 'CONFIRMED', payload: result } 
    });
    return result;
  });
}
```

> [!warning] Give IN_PROGRESS a TTL
> If the server dies mid-processing, that key sits as IN_PROGRESS forever. The usual fix is a background worker that _flips rows IN_PROGRESS for more than N minutes into FAILED so a retry can claim them_ — which is exactly why [[비동기 워크플로우|async workflows]] and the [[상태 머신|state machine]] pattern fall out of this naturally.

### You also have to validate request-body consistency

What if the same key arrives with a **different body**? Stripe stores a hash of the body alongside the key; if the key matches but the hash doesn't, they return 422. Without this check, "key abc-123 sent 100 won, same key retried with 1000 won" would silently slip through.

```typescript
const bodyHash = sha256(canonicalJson(dto));
if (row.body_hash !== bodyHash) {
  throw new UnprocessableEntityException('Idempotency-Key reused with different body');
}
```

### Limits — this doesn't work everywhere

Idempotency keys are perfect for **work inside your own server, writing to your own DB**. But for external systems — covered in the next section, **[[RPC 노드에서의 Unknown Outcome|RPC node calls]]**, especially blockchain nodes — you can't force the remote side to honor an idempotency table. There you need different tooling (nonces, txHash, preserved raw transactions).

### Unknown Outcome at the RPC Node

[[Idempotency keys]] are a contract we make between our own services. The [[RPC node]] sits outside that contract. Ethereum/EVM-family `eth_sendRawTransaction` is just a standard JSON-RPC method — even if we stuff an idempotency-key header into the request, **the node will not look at it and will not deduplicate on our behalf**. So the same class of problem we discussed in [[HTTP Unknown Outcome]] reappears one layer deeper.

> [!warning] Core claim
> Idempotency keys only work inside an API contract we control. At a boundary with an external system like an RPC node, the key becomes meaningless and we are back to the primal Unknown Outcome — "we don't even know if the node received it."

### 1. What actually happens when sendRawTransaction times out

The flow when our backend signs a transaction and broadcasts it to [[Infura]] / [[Alchemy]] / a self-hosted [[geth]] node looks like this:

```
                    ┌────────────────────────────────┐
                    │           Our Backend          │
                    │  signedTx = wallet.sign(tx)    │
                    │  POST eth_sendRawTransaction   │
                    └──────────────┬─────────────────┘
                                   │  (HTTPS, 30s timeout)
                                   ▼
                    ┌────────────────────────────────┐
                    │       RPC Node (Infura)        │
                    │   1. parse + verify signature  │
                    │   2. admit to local mempool    │
                    │   3. gossip to peers           │
                    │   4. return txHash             │
                    └──────────────┬─────────────────┘
                                   │
                            ❌ TIMEOUT ❌
                     (we have no idea where it broke)
```

When the timeout fires, at least 5 real states are possible:

| # | Actual state | What we observe |
|---|-------------|-----------------|
| A | Never reached the node (network cut) | timeout |
| B | Node received but rejected (nonce too low etc.) | timeout (lost response) |
| C | Admitted to mempool, response lost | timeout |
| D | Admitted + gossiped to peers, response lost | timeout |
| E | Already mined, response lost | timeout |

**All five collapse into the same single signal: timeout.** Adding an idempotency key does nothing to distinguish them.

### 2. Why idempotency keys are powerless here

The pattern from [[Solving with idempotency keys]] was: "if the same key comes in twice, replay the first result." For that to hold, **the receiver has to remember the key, and the side effect must happen only once per key**.

The RPC node does neither.

```ts
// Our mental model (wrong)
await rpc.sendRawTransaction(signedTx, {
  idempotencyKey: 'order-42-payout',  // ← does not exist
});

// Actual JSON-RPC
{
  "jsonrpc": "2.0",
  "method": "eth_sendRawTransaction",
  "params": ["0xf86c80..."],   // signed tx only
  "id": 1
}
```

Worse: re-broadcasting what we *think* is the same request doesn't behave the way we want. The **mempool does not treat the same nonce+from combination as a new transaction** — if the exact bytes are already in, it returns `ALREADY_KNOWN`; if not, it admits as new. It *appears* idempotent, but the idempotency is keyed on "same signedTx bytes," not "same business intent." If we re-sign with a different nonce or different gas, **the node sees a completely separate transaction** and both can mine.

> [!warning] Double-payment scenario
> A Treasury tx sending 100 USDC times out → we think it's safe to retry, grab a fresh nonce, re-sign and re-broadcast → both land in the mempool → **both confirm**. The idempotency key lives in our DB; it can't undo 200 USDC having left the chain.

### 3. The real source of truth: txHash and chain state

Beyond the RPC node there's a source of truth we didn't build — **the blockchain itself**. The general principle for Unknown Outcomes against external systems applies here too:

> [!tip] Principle
> **When you can't trust the response, use a client-side identifier to query external state directly.** The idempotency key is for the *client→server* boundary. The txHash is for the *server→chain* boundary.

`txHash` is the keccak256 of the signedTx, which means **the client can compute it before sending**. Even if the node never replies, we already know the hash.

```ts
// Compute the hash before broadcasting, persist immediately
const signedTx = await wallet.signTransaction(tx);
const txHash   = keccak256(signedTx);   // ethers: ethers.keccak256(signedTx)

await db.transactions.insert({
  id: requestId,
  txHash,                  // ← known up front
  rawTx: signedTx,         // ← kept for safe re-broadcast
  nonce: tx.nonce,
  status: 'BROADCASTING',
});

try {
  await rpc.sendRawTransaction(signedTx);   // timeout is fine
  await db.transactions.update(requestId, { status: 'BROADCASTED' });
} catch (e) {
  // No response ≠ failure. Mark only as UNKNOWN.
  await db.transactions.update(requestId, { status: 'BROADCAST_UNKNOWN' });
}
```

Later, a reconciler **asks the chain directly**:

```ts
// reconciler job, run on a tick
const onChain = await rpc.getTransactionReceipt(txHash);

if (onChain?.status === 1)      → CONFIRMED
else if (onChain?.status === 0) → REVERTED
else if (await inMempool(txHash)) → PENDING (just wait)
else                            → DROPPED → re-broadcast or re-sign
```

The state machine:

```
                   sendRawTx
   BROADCASTING ───────────────► BROADCASTED ──► CONFIRMED
        │                            │             │
        │ timeout                    │ getReceipt  │
        ▼                            ▼  status=0   ▼
 BROADCAST_UNKNOWN ──poll txHash─► PENDING     REVERTED
        │                            │
        │ not in mempool +           │ stuck (N blocks)
        │ no receipt                 ▼
        ▼                          BUMP_FEE (replace-by-fee)
     DROPPED ──► resubmit same rawTx
```

> [!example] Why store the whole rawTx
> Re-broadcasting **the same signedTx** yields the **same txHash**, so duplicate confirmation is impossible. Re-signing produces a different hash → different tx → double-spend risk. That's why pinning `rawTx + txHash` into the DB is the core infrastructure behind the [[Treasury Queue pattern]].

### 4. Mapping back to HTTP Unknown Outcome

Same problem, different layer, different identifier.

| Layer | Unknown Outcome trigger | Client-chosen identifier | Source of truth |
|-------|------------------------|--------------------------|-----------------|
| HTTP API | request timeout | `Idempotency-Key` header | our DB's result table |
| RPC → Chain | `sendRawTransaction` timeout | `txHash` (derived from signature) | the blockchain (`getTransactionReceipt`) |

> [!note] Generalization
> **Unknown Outcome reappears at every distributed-system boundary.** At each boundary, design two things together: (a) a deterministic client-side identifier, and (b) a reconciliation path to query the external truth. One without the other is not enough.

Securing the txHash solves "did the node even receive it?" But we're not done — the next problem is the [[Treasury single-wallet retry problem]]: if other requests bump the nonce between our retries, re-broadcasting that rawTx will be rejected with `nonce too low`. That's the next section.

### Treasury Single-Wallet Retry Problem (nonce & txHash)

Having **a single** [[Treasury]] wallet is operationally clean, but from a retry standpoint it forces you head-on into a **serialization-of-shared-resource** problem. The root cause is that the [[nonce]] in [[EVM]]-family chains is a **per-account sequential counter**.

> [!warning] One-line summary
> "Replayed the request and the txHash changed" means *another request consumed the nonce in between*. The fix is to **stop re-signing, and instead re-broadcast the original rawTx as-is**.

### 1. Why the hash changes — nonce is an input to the signature

The [[txHash]] of an EVM transaction is the keccak256 of the **RLP-encoded signed transaction**. The signature is computed over:

```
tx = { nonce, gasPrice (or maxFee/maxPriorityFee), gasLimit,
       to, value, data, chainId }
rawTx = RLP(tx, v, r, s)        // includes signature
txHash = keccak256(rawTx)
```

→ **Change the nonce by even 1 and the signature changes; change the signature and the txHash changes entirely.**

So if server code "fetches current nonce and re-signs" on every attempt, getting a different txHash on retry is *unavoidable*.

### 2. The failure scenario — single-wallet race

Between request A failing and being retried, request B uses the same wallet and advances the nonce.

```
time  req   action                       wallet nonce  txHash tracking
─────────────────────────────────────────────────────────────────────
t0    A     sign(nonce=42) → send         42 → ?       hashA recorded
t1    A     RPC timeout (Unknown)         ?            hashA, outcome unknown
t2    B     sign(nonce=43) → send → mined 43 → 44      hashB success
t3    A     "retry" → current nonce=44   ↑
              re-sign → send
                                          → hashA' (a completely different hash)
```

What you're left with:

| State | original hashA | re-signed hashA' |
|---|---|---|
| On chain? | **unknown** (dropped from mempool? already mined?) | broadcast as a brand-new tx |
| nonce | 42 | 44 |
| Double-spend risk | — | **yes** (both mine → paid twice) |
| Traceability | hashA no longer locatable | new hash → broken link to [[event log]] |

> [!danger] The trap of naive retry
> Code that "fetches current nonce and signs again" is **effectively creating a new transaction**. If the original is still in the mempool or already mined, you **pay twice**. [[Idempotency]] is completely broken.

### 3. The fix — pre-store rawTx + re-call sendRawTransaction

The core idea: **treat the signature as state**. Signing is a commit; broadcasting is retry-able.

```
[ Build & Sign ] ─────► (DB) raw_transactions
       │                  ─ id, intent_id (idempotency key)
       │                  ─ nonce
       │                  ─ rawTx (bytes)
       │                  ─ txHash (computed)
       │                  ─ status: SIGNED | BROADCAST | CONFIRMED
       ▼
[ Broadcast ] ──► eth_sendRawTransaction(rawTx)
       │
       │   timeout / network error?
       ▼
[ Retry ] ──► **send the SAME rawTx again**
              → same nonce, same signature → same txHash
              → node replies "already known" / "nonce too low"
              → that's fine — it means it was already accepted
```

> [!tip] The key invariant
> Once **(intent_id) → (rawTx, txHash) is pinned 1:1 in the DB**, that intent is forever tracked under one and only one txHash, no matter how many times the RPC dies.

#### Pseudo-code

```typescript
async function sendFromTreasury(intent: TransferIntent) {
  // 1) check if we've already signed for this idempotency key
  let row = await db.rawTx.findByIntentId(intent.id);

  if (!row) {
    // 2) if not: acquire nonce + sign, persist in one transaction
    const nonce = await nonceManager.acquire(treasuryAddress); // [[Nonce Manager]]
    const tx = buildTx({ ...intent, nonce });
    const { rawTx, txHash } = await signer.sign(tx);
    row = await db.rawTx.insert({
      intentId: intent.id, nonce, rawTx, txHash, status: 'SIGNED',
    });
  }

  // 3) always broadcast the same rawTx (even on retry)
  try {
    await rpc.sendRawTransaction(row.rawTx);
  } catch (e) {
    // "already known", "nonce too low (already mined)" are effectively success
    if (!isBenignBroadcastError(e)) throw e;
  }

  // 4) confirm via txHash later (a separate reconciler polls)
  return row.txHash;
}
```

### 4. What this buys you — three guarantees

> [!example] What pre-storing rawTx gives you
> 1. **Deterministic txHash** — same (nonce, payload, key) ⇒ same hash, always. 1:1 mapping to the [[event log table]].
> 2. **Safe re-broadcast** — `eth_sendRawTransaction` is idempotent for the same rawTx. "already known" looks like an error but is *actually success*.
> 3. **Crash recovery** — if the server dies right before broadcast, on restart it finds the `SIGNED` row and just sends it.

### 5. The remaining trap — nonce gaps

What if you've signed a rawTx but never broadcast it, and *later* nonces get mined first?

→ You must **serialize nonce allocation** so this doesn't happen. That's exactly why the next section discusses the [[Nonce Manager]] + [[Treasury Queue]] pattern.

```
nonce 42 sits SIGNED in DB, never broadcast
nonces 43, 44, 45 get broadcast → mempool stuck "waiting on 42"
  → either ship 42 fast, or overwrite it with a cancel-tx
    (same nonce, higher gas, value=0 self-transfer)
```

> [!note] Recap
> - **Single wallet = single nonce counter** → every retry *shares this counter*.
> - **Sign first, broadcast later** — the moment rawTx is pinned in the DB, the trxn id (= txHash) is frozen.
> - **Retry ≠ re-sign**. Retry = *re-broadcast the same rawTx*. That one-line distinction is what stops the "paid twice" incident.

### Nonce Manager + Treasury Queue Pattern

To solve [[nonce]] collisions and the [[Unknown Outcome]] problem on a single Treasury wallet at the same time, you need a structure that **serializes nonce allocation** and **persists the signed rawTx**, so retries can **rebroadcast the exact same txHash**. These two pieces — Nonce Manager and Treasury Queue — come as one set.

### Why this combination?

> [!warning] The naive-retry trap
> "On failure, call sendTransaction again" is the most common anti-pattern. Even for the same business request, if the nonce changes the [[txHash]] changes too, and if you're unlucky **both transactions land on chain** — double spend. [[idempotency key]] alone isn't enough; the signature itself must be idempotent.

The key insight: **a signed rawTx is itself an idempotency token.** No matter how many times you broadcast the same `(from, nonce, to, value, data, gas, chainId, signature)` tuple, the chain accepts it exactly once. So the entire problem reduces to "never lose the rawTx once signed."

### Full workflow

```
 ┌─────────────┐   1. enqueue(jobId, payload)    ┌──────────────────┐
 │  API / BFF  │ ──────────────────────────────► │ Treasury Queue   │
 └─────────────┘                                  │   (FIFO, single  │
        ▲                                         │   consumer)      │
        │ 5. status(jobId)                        └────────┬─────────┘
        │                                                  │
        │                                  2. claim job    ▼
        │                                  ┌──────────────────────────┐
        │                                  │   Treasury Worker        │
        │                                  │   (single-flight)        │
        │                                  └────────┬─────────────────┘
        │                                           │
        │                3. allocateNonce(addr) ◄───┤
        │                                           │
        │                                  ┌────────▼─────────────────┐
        │                                  │   Nonce Manager          │
        │                                  │   (Redis INCR /          │
        │                                  │    Postgres advisory     │
        │                                  │    lock + counter)       │
        │                                  └────────┬─────────────────┘
        │                                           │
        │            4. sign + persist(rawTx,       │
        │                              txHash,      │
        │                              nonce)       ▼
        │                                  ┌──────────────────────────┐
        │                                  │   tx_outbox (Postgres)   │
        │                                  │   pending → sent →       │
        │                                  │   mined / dropped        │
        │                                  └────────┬─────────────────┘
        │                                           │
        │                                  5. eth_sendRawTransaction
        │                                           │
        └───────────── 6. confirmer ◄───────────────┘
                       (poll receipt by txHash,
                        rebroadcast on timeout,
                        bump-fee on stuck)
```

### Step-by-step responsibilities

> [!example] The six stages
> 1. **Enqueue** — business handler pushes the job with an [[idempotency key]] (`jobId`) and returns `202 Accepted` immediately.
> 2. **Claim** — Treasury Worker pulls work from the queue as a **single consumer**. Concurrency is exactly 1.
> 3. **Allocate nonce** — Nonce Manager atomically issues the next nonce for that address.
> 4. **Sign & persist** — build the rawTx and **save it to DB first**, then broadcast.
> 5. **Broadcast** — `eth_sendRawTransaction`. Even if it fails or times out, the rawTx is already in DB.
> 6. **Confirm / retry** — a separate confirmer polls receipts and, if nothing lands, rebroadcasts **the same rawTx** or bumps fee.

### Nonce Manager — serialized allocation

[[Ethereum]] nonces are per-address monotonically increasing integers starting at 0, and **a gap stalls every later transaction in the mempool.** So allocation must be serialized.

```typescript
// Redis-based — the most common implementation
class NonceManager {
  async allocate(address: string): Promise<number> {
    const key = `nonce:${address}`;
    // Lua script for atomicity
    const next = await redis.eval(`
      local cur = redis.call('GET', KEYS[1])
      if not cur then
        local onchain = tonumber(ARGV[1])
        redis.call('SET', KEYS[1], onchain)
        return onchain
      end
      return redis.call('INCR', KEYS[1]) - 1
    `, 1, key, await provider.getTransactionCount(address, 'pending'));
    return Number(next);
  }

  async reset(address: string) {
    // Force-recover to on-chain value when drift is suspected
    const onchain = await provider.getTransactionCount(address, 'pending');
    await redis.set(`nonce:${address}`, onchain);
  }
}
```

> [!tip] Don't trust on-chain `getTransactionCount` alone
> The `pending` count differs per node, and a tx you just sent may not show up in mempool yet. **Keep the local counter as source of truth**, and consult the on-chain value only at boot or when drift is detected.

| Option | Serialization | Pros | Cons |
|---|---|---|---|
| Redis `INCR` | single-threaded by design | fast (μs) | drift on Redis outage |
| Postgres `SELECT ... FOR UPDATE` | row lock | bundles with tx | slow (ms) |
| Postgres advisory lock | `pg_advisory_xact_lock` | natural DB-tx integration | lock-key bookkeeping |
| In-process Mutex | only with 1 worker | simplest | can't scale out |

### Treasury Queue — why single consumer

If Treasury is a single wallet, **nonce allocation for that wallet must happen in exactly one place too.** The queue's purpose isn't throughput — it's **ordering**.

```typescript
// BullMQ example — concurrency: 1 is the point
const treasuryWorker = new Worker('treasury', async (job) => {
  const { jobId, to, value, data } = job.data;

  // Already processed? (idempotency)
  const existing = await db.tx_outbox.findUnique({ where: { jobId } });
  if (existing?.txHash) {
    // On retry, rebroadcast the same rawTx
    return rebroadcast(existing.rawTx, existing.txHash);
  }

  // New work
  const nonce = await nonceManager.allocate(TREASURY_ADDR);
  const tx = await signer.populateTransaction({ to, value, data, nonce });
  const signed = await signer.signTransaction(tx);
  const txHash = ethers.keccak256(signed);

  // ★ Save to DB BEFORE broadcasting
  await db.tx_outbox.create({
    data: { jobId, nonce, rawTx: signed, txHash, status: 'pending' },
  });

  try {
    await provider.broadcastTransaction(signed);
    await db.tx_outbox.update({
      where: { jobId },
      data: { status: 'sent' },
    });
  } catch (e) {
    // Network error is fine — rawTx is already persisted
    // confirmer will rebroadcast
  }
}, { connection: redis, concurrency: 1 });  // ◄ must be 1
```

> [!note] Why concurrency=1
> With two workers, both can pull nonces concurrently, and even if allocation is serialized **the order of `sendRawTransaction` calls isn't.** If the fast worker fires nonce=11 first and the slow one stalls at nonce=10 — gap. concurrency=1 prevents this at the source. If you genuinely need throughput, go to [[multi-treasury sharding]] (partition into N wallets).

### Persisting rawTx — the real idempotency weapon

`tx_outbox` schema:

```sql
CREATE TABLE tx_outbox (
  job_id        TEXT PRIMARY KEY,           -- business idempotency key
  nonce         BIGINT NOT NULL,
  raw_tx        BYTEA NOT NULL,             -- fully signed rawTx
  tx_hash       TEXT NOT NULL UNIQUE,       -- keccak256(rawTx)
  status        TEXT NOT NULL,              -- pending|sent|mined|dropped|replaced
  attempts      INT NOT NULL DEFAULT 0,
  last_error    TEXT,
  created_at    TIMESTAMPTZ DEFAULT now(),
  mined_at      TIMESTAMPTZ,
  block_number  BIGINT
);

CREATE INDEX ON tx_outbox (status, created_at);
CREATE UNIQUE INDEX ON tx_outbox (nonce);  -- forbid duplicate nonce
```

> [!warning] Sign → persist → broadcast — the order is everything
> "Broadcast first, save on success" is the wrong order. If broadcast succeeds but the process dies before the DB write — Unknown Outcome. The nonce is burned and you don't know what you sent. **Save first**, broadcast second. ([[outbox pattern]])

### Confirmer — the rebroadcast loop

```typescript
// Separate worker. Runs on its own cadence, independent of the queue.
setInterval(async () => {
  const pending = await db.tx_outbox.findMany({
    where: { status: { in: ['pending', 'sent'] } },
    orderBy: { nonce: 'asc' },
  });

  for (const row of pending) {
    const receipt = await provider.getTransactionReceipt(row.tx_hash);
    if (receipt) {
      await db.tx_outbox.update({
        where: { job_id: row.job_id },
        data: {
          status: receipt.status === 1 ? 'mined' : 'reverted',
          block_number: receipt.blockNumber,
          mined_at: new Date(),
        },
      });
      continue;
    }

    const age = Date.now() - row.created_at.getTime();
    if (age > 30_000) {
      // Resend the same rawTx — txHash unchanged, idempotent
      await provider.broadcastTransaction(row.raw_tx).catch(() => {});
      await db.tx_outbox.update({
        where: { job_id: row.job_id },
        data: { attempts: { increment: 1 } },
      });
    }

    if (age > 5 * 60_000) {
      // Stuck for 5+ min → fee bump (replacement tx, same nonce)
      await bumpFee(row);
    }
  }
}, 5_000);
```

### Answering the user's questions directly

> [!example] "Single Treasury wallet — on retry, txHash can't be recomputed, right?"
> Exactly. **So we don't recompute it.** Sign the rawTx exactly once, pin it (with its txHash) into `tx_outbox`, and let retries be `provider.broadcastTransaction(row.raw_tx)` — **resending the same byte sequence**. Because the nonce is already baked in, it doesn't matter that other requests took higher nonces in the meantime — our tx waits in its assigned slot (nonce=N) to be mined.

> [!example] "What if another request bumped the nonce in between?"
> The nonce is **fixed at allocation time.** If Job A got nonce=10 and finished signing but the broadcast failed, and Job B then mined first with nonce=11 — the chain **holds nonce=11 and beyond in mempool** until nonce=10 arrives. Resend Job A's rawTx; nonce=10 fills in and the rest mine in order. If Job A can never land (e.g. always reverts with bad data) — fee-bumping a **dummy tx with the same nonce** is the last resort to unblock the queue.

### Operational notes

- **Drop detection**: a tx that fell out of mempool (`getTransaction` returns null) just gets rebroadcast — the rawTx is still on disk.
- **Reorg handling**: even after `mined`, you must be able to roll back to `pending` before N-block finality.
- **Fee bump = replacement**: sign a new rawTx with the same nonce + higher gas price. Mark the old row `replaced`.
- **Monitoring**: track oldest pending tx age, nonce drift (`localCounter - onchainCount`), and attempts distribution in [[Datadog]].

This pattern shows up under names like [[Treasury Worker]] / [[Wallet Service]] in wallet-infrastructure writeups from [[Tigris]], [[Coinbase]], and others. The essence doesn't change — **sign once, persist, and resend the same bytes.**
