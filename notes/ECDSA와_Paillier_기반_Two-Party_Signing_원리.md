## TL;DR

> [!tip] 한 문단 요약
> [[ECDSA]] 2PC + [[Paillier]]의 핵심은 **곱셈 분할**입니다. 개인키 `x = key1·key2`, 1회용 난수 `k = k1·k2`로 쪼개서 main/sub 두 서버에 흩어 두면, 공개키 `Q = x·G`와 서명의 `r = (k·G).x`는 **점 곱셈**만으로 합쳐집니다(이산로그 덕에 점을 봐도 스칼라는 안 샘). 문제는 `s = k⁻¹·(hm + r·x)`의 `r·key1·key2` **교차항** 한 곳뿐 — main의 `key1`과 sub의 `key2`를 평문 노출 없이 곱해야 합니다. 이 한 줄을 [[Paillier]] 동형암호로 처리합니다: main이 `Enc_pk1(key1)`을 보내면 sub가 자기 `key2`를 **암호문 위에서** 곱하고(`⊗`), `k2⁻¹·hm` 항과 동형 덧셈(`⊕`)으로 합쳐 partial-S를 만들어 돌려주고, main이 복호화 후 `k1⁻¹`을 곱해 `s`를 완성. 결과적으로 **`x`도 `k`도 어디에도 통째로 존재하지 않으며**, sub는 `key1`을 평문으로 본 적이 없고 main은 `key2`·`k2`를 본 적이 없습니다.

## ECDSA 기초 — G, n, 개인키 x와 공개키 Q

[[ECDSA]]의 모든 마법은 결국 **타원곡선 위 점들의 그룹**과 그 위에서의 **점 곱셈**에 기댑니다. 2PC 분할이든 [[Paillier]] 동형 연산이든, 그 아래 기반은 다 이 한 층이에요. 이 절에서는 [[secp256k1]] 곡선의 `G`와 `n`이 무엇인지, 점 곱셈과 [[ECDLP|이산로그 문제]]가 왜 키쌍을 안전하게 만드는지, 그리고 "개인키 `x`"와 "공개키 `Q`"가 갑자기 튀어나오는 게 아니라 어떻게 자연스럽게 정의되는지 차례로 잡습니다.

### 1. 곡선과 그 위의 그룹

이 sign-service는 비트코인/이더리움과 동일한 [[secp256k1]] 곡선을 씁니다. 코드 진입점은 한 줄이에요 (`ec.ts:8-9`).

```ts
import { ec as EC } from 'elliptic'
const ec = new EC('secp256k1')
export const G = ec.g     // 생성원
export const n = ec.n     // 차수
```

곡선 위의 "점들"은 특별한 덧셈 규칙으로 하나의 **그룹(group)** 을 이룹니다. 곡선식 자체(`y² = x³ + 7 mod p`)는 일단 잊고, **"점 + 점 = 점"이라는 연산이 정의된 세계**라고만 생각해도 됩니다.

> [!note] 알아둘 것은 3가지
> - **`G` (Generator, 생성원)** — 모두가 공유하는 곡선 위의 고정된 한 점. "시작점".
> - **`n` (Order, 차수)** — `n·G = O`(무한원점, 항등원)이 되는 가장 작은 양의 정수. secp256k1에서 `n ≈ 2²⁵⁶`인 소수.
> - **점 곱셈 `k·G`** — `G + G + … + G` (k번). 숫자 곱이 아니라 곡선 위 점들의 덧셈을 k번 반복.

`n`이 차수라는 말은 곧 **"스칼라 연산은 전부 `mod n`으로 돈다"** 는 뜻이에요. `(n+1)·G = 1·G`, `(n+2)·G = 2·G`처럼 지수가 `n`을 한 바퀴 돌면 원위치로 돌아옵니다. 그래서 ECDSA의 모든 `mod n`은 사실 "n번 돌면 제자리"라는 곡선의 주기성에서 옵니다.

### 2. 점 곱셈이라는 일방향 함수

암호의 진짜 토대는 다음 비대칭성입니다.

```
k 를 알면 → k·G  계산:  쉬움 ✅  (256비트라도 마이크로초)
k·G 만 보고 → k  역산:  사실상 불가능 ❌  (Elliptic Curve Discrete Log Problem)
```

곱셈은 빠른데 그 역(나눗셈, "주어진 점에서 G를 몇 번 더했는지 알아내기")이 **지수적으로 어렵다** — 이게 [[ECDLP]], 즉 **타원곡선 이산로그 문제**입니다. secp256k1에서 이걸 푸는 가장 좋은 알려진 알고리즘조차 약 `2¹²⁸` 연산을 요구합니다. 우주가 끝날 때까지 못 풀어요.

> [!tip] 비유로 잡기
> 페인트 두 색을 섞는 건 쉽지만, 섞인 색을 보고 원래 비율을 분리하는 건 사실상 불가능합니다. `k → k·G`는 색을 섞는 쪽, `k·G → k`는 분리하는 쪽이에요.

이 비대칭성 한 가지로부터 공개키 암호 전체가 굴러갑니다. **"비밀로 만든 결과는 보여줘도 비밀이 안 새는"** 기적이 가능한 거죠.

### 3. 개인키 `x` — 그냥 무작위로 고른 큰 정수

개인키는 거창한 게 아닙니다. **1부터 `n−1` 사이에서 균등하게 뽑은 한 개의 정수**일 뿐이에요. 코드도 정확히 그렇게 합니다 (`two-party-player.ts:39-41`).

```ts
private generateKey() {
  return new BN(randomBytes(n.byteLength() / 2))   // 그냥 큰 랜덤 숫자
}
```

작은 비유 숫자로:

```
x = 27   ← 이게 개인키. 256비트 정수. 절대 공개 안 함.
```

> [!warning] 개인키 = 정말 "그냥 숫자"
> 비밀번호도 시드 문구도 아닙니다. **하나의 정수**예요. 시드 문구(BIP39)나 keystore는 결국 이 정수 `x`를 도출/저장하기 위한 포장일 뿐입니다.

### 4. 공개키 `Q` — `x`로 만든 점

공개키는 그 정수만큼 `G`를 곱한 **점**입니다.

```
Q = x · G
```

`x=27`이면 `Q = 27·G` = "G를 27번 더한 점". 이 sign-service에서 한 조각의 공개키 계산이 바로 이 한 줄이에요 (`two-party-player.ts:59-61`).

```ts
public returnPartialQ(): curve.base.BasePoint {
  return G.mul(this.key)     // Q(조각) = key · G
}
```

`Q`는 곡선 위의 점이라 `(x_Q, y_Q)` 좌표 쌍으로 표현되고, 직렬화하면 65바이트(비압축) 또는 33바이트(압축) hex가 됩니다. [[EVM]] 지갑 주소는 이 `Q`의 keccak256 해시 뒤 20바이트예요.

### 5. 두 짝의 관계 — 한 방향만 쉬움

이제 키 "쌍"이 왜 쌍인지 명확해집니다.

```
개인키 x  ──── x·G ────►  공개키 Q   (앞으로: 쉬움)
공개키 Q  ──── ???? ────►  개인키 x   (뒤로: ECDLP, 불가능)
```

| 키 | 정체 | 누가 보나 | 역할 |
|---|---|---|---|
| `x` | 무작위 큰 정수 | 본인만 (혹은 2PC에선 누구도 통째로 안 봄) | **서명 생성** |
| `Q = x·G` | 곡선 위 한 점 | 전 세계 공개 OK | **서명 검증** |

> [!example] 서명/검증에서 두 짝이 만나는 지점
> 서명자는 비밀 `x`로 `s = k⁻¹·(hm + r·x)` 를 만듭니다. 검증자는 공개 `Q`로 `P = u1·G + u2·Q` 를 만듭니다. 검증식을 전개할 때 `Q = x·G`를 대입하는 순간 `x`가 식 안으로 들어와서 양쪽이 곡선 위에서 맞물리고, **`x` 자체는 한 번도 전송되지 않은 채** 서명이 검증됩니다. (자세한 전개는 [[서명식의 의미 — r, s가 왜 그 꼴인가|다음 절]]에서.)

### 6. 2PC로 향하는 다리

이 절의 마지막 한 걸음. `x = key1 · key2 (mod n)` 로 쪼개면 [[two-party-player.ts|two-party-player]]에서 공개키가 이렇게 만들어집니다.

```
main: partialQ = key1·G                       ← key1 만 안다
sub:  Q = partialQ · key2 = (key1·key2)·G    ← key2 만 안다
                          = x·G              ✓ 정상적인 ECDSA 공개키
```

> [!note] 핵심 — `x` 라는 숫자는 어디에도 존재한 적이 없다
> 두 조각 `key1`, `key2`는 각자 다른 서버 DB에 [[AWS KMS]]로 암호화돼 보관되지만, **그 곱(=진짜 개인키 `x`)은 메모리에서도 만들어진 적이 없습니다.** 점 곱셈의 결합성(`(key1·key2)·G = key2·(key1·G)`) 덕분에 곡선 위에서만 합쳐져 `Q`가 나옵니다. 한 서버가 통째로 털려도 단독 서명 불가, `x` 복원 불가.

여기까지 잡으면 다음 절들이 자연스럽게 따라옵니다 — `r`, `s`의 의미([[서명식의 의미 — r, s가 왜 그 꼴인가]]), 검증식([[검증 메커니즘 — u1, u2, P]]), 그리고 `x = key1·key2` 교차항 때문에 [[Paillier]]가 왜 필요해지는지([[Paillier가 등장하는 지점 — s 계산의 교차항 문제]]).

## 서명식의 의미 — r, s가 왜 그 꼴인가

ECDSA의 `(r, s)`는 임의로 정해진 두 숫자가 아니라, **하나의 "증명(proof)"을 구성하는 두 조각**입니다. 서명자가 검증자에게 다음을 말하고 있다고 보면 됩니다:

> [!note] 서명이 진짜 말하는 것
> "나는 공개키 `Q`에 대응하는 비밀 `x`를 안다. 그리고 **바로 이 메시지** `hm`에 대해 그걸 안다. 단, `x`도 `k`도 절대 보여주지 않는다."

이 증명은 보통의 영지식 증명처럼 **커밋(commitment) → 응답(response)** 의 2박자 구조를 가집니다. r과 s를 그 틀로 보면 정체가 깔끔히 떨어집니다.

## r — "1회용 임시 공개키의 x좌표" = 커밋

서명자는 매번 새 난수 `k`를 뽑아 점 `R = k·G`를 만듭니다. 이 `R`은 사실상 **이번 서명 한 번만 쓰는 임시 키쌍의 공개키**예요. (`k`가 임시 개인키, `R`이 임시 공개키.) `r`은 거기서 x좌표만 떼어낸 것:

```
r = R.x mod n = (k·G).x mod n
```

의미는 **"이번에 어떤 난수 k를 골랐는지에 대한 공개 약속"** — 즉 [[ecdsa-commitment-r|커밋]]입니다.

- `k` 자체는 영원히 비밀로 둔다 (유출되면 [[private-key-x-vs-nonce-k|개인키 즉시 복원]]).
- 대신 `k`에 대응하는 흔적 `r`만 공개해서 "나 이 난수 골랐다"고 못 박는다.
- 검증자가 나중에 이 커밋을 거꾸로 재현(`P = u1·G + u2·Q`)할 때, 그 결과의 x좌표가 `r`과 일치하는지로 진위가 판가름난다.

> [!tip] 왜 점 전체가 아니라 x좌표만 쓰나
> 두 가지 이유. ① 서명을 256비트로 압축하기 위해. ② DSA 계보의 설계 선택. 점의 핵심 정보는 x좌표에 다 들어있고, 검증식이 x좌표 비교 하나로 닫히게 설계됐습니다. (대신 같은 x좌표를 가진 점이 두 개라 EVM은 `v`를 보조로 둡니다 — [[ecdsa-v-recovery]].)

## s — "비밀·메시지·커밋을 묶은 봉인" = 응답

```
s = k⁻¹ · (hm + r·x)   mod n
```

이 한 줄에 **세 가지가 묶여** 있고, 각 항이 하는 일이 다 다릅니다:

| 조각 | 의미론적 역할 | 빠지면? |
|---|---|---|
| `hm` | **무엇에** 서명했나 (메시지 바인딩) | 같은 서명을 아무 메시지에나 갖다 붙임 (위조) |
| `r·x` | **누가** 서명했나 (신원 바인딩) + 커밋과 결합 | `x` 없으면 누구나 서명, `r` 없으면 커밋과 안 묶여 검증식 안 닫힘 |
| `k⁻¹` | **블라인딩 + 일회성** | 없으면 `x`가 그대로 노출되고, 같은 메시지에 매번 같은 서명 |

> [!note] 의미 한 줄
> `s` = "내 비밀 `x`를, 이번 커밋 `r`과 이 메시지 `hm`에 묶어, 1회용 난수 `k`로 가린 응답값." 세 가지 중 하나라도 바뀌면 `s`가 깨지도록 한 식에 봉인한 것.

## 왜 "하필 그 꼴"인가 — 검증식에서 (hm + r·x)가 약분되도록 역설계

`s`의 모양은 임의가 아니라, **검증자가 `r`(커밋)을 다시 복원할 수 있어야 한다**는 제약에서 거꾸로 강제됩니다.

검증자가 가진 재료는 공개값뿐: `Q, hm, r, s`. 검증자는 [[ecdsa-verification-u1-u2-P|계수 u1, u2를 만들어 점 P]]를 조립합니다. 그 P를 `Q = x·G`로 전개하면:

```
P = u1·G + u2·Q
  = (hm·s⁻¹)·G + (r·s⁻¹)·Q
  = (hm·s⁻¹)·G + (r·s⁻¹)·(x·G)      ← Q = x·G 대입
  = s⁻¹·(hm + r·x)·G                  ← G로 묶기
```

여기서 서명자가 `s = k⁻¹·(hm + r·x)`로 정의했다면 `s⁻¹ = k·(hm + r·x)⁻¹` 이므로:

```
P = k·(hm + r·x)⁻¹·(hm + r·x)·G
  = k·G
  = R                                  ← 서명자의 커밋이 정확히 부활
```

> [!example] 역설계의 심장
> `(hm + r·x)`라는 **곱셈 덩어리** 하나로 묶고, 그 앞에 `k⁻¹`을 둔다 — 이러면 검증식에서 `s⁻¹`이 곱해지면서 `(hm + r·x)`가 **통째로 약분**되어 사라지고, `k`만 남아 `k·G = R`이 되살아남. 다른 꼴(예: `hm + r·x⁻¹`, `k·(hm + r·x)` 등)이면 이 약분이 일어나지 않아 검증식이 닫히지 않음.

ASCII로 한 줄 더 보면 명확합니다:

```
서명자: s = k⁻¹ · (hm + r·x)            ← 비밀 x로 잠근다
검증자: P = s⁻¹ · (hm + r·x) · G        ← 공개 Q로 다시 푼다
                  └─약분─┘
        P = k·G = R   →   P.x == r ?
```

비밀 `x`는 `Q` 안에 점으로 숨어 들어가고, 곱셈 덩어리 `(hm + r·x)`는 검증 도중 `s⁻¹`과 만나 깨끗이 소거 — **그래서 검증자는 `x`를 한 번도 보지 않고도 "이 사람이 `x`를 안다"를 확인**할 수 있습니다.

## 각 항의 역할 한 번 더, 검증식과 짝지어서

| s 안의 항 | 서명에서 하는 일 | 검증식에서 만나는 짝 |
|---|---|---|
| `hm` | 메시지 바인딩 | `u1 = hm·s⁻¹` → `u1·G` 에서 `G`에 곱해진다 |
| `r·x` | 신원·커밋 바인딩 | `u2 = r·s⁻¹` → `u2·Q` 에서 `Q(=x·G)`에 곱해진다 |
| `k⁻¹` | 블라인딩·일회성 | `s⁻¹`을 통해 풀려서 최종적으로 `k`로 되돌아온다 (`P = k·G`) |

직관:
- `hm`은 `G` 쪽으로(공개 기준점),
- `r·x`는 `Q` 쪽으로(숨은 비밀이 박힌 점),
- `k⁻¹`은 검증 도중 `s⁻¹`에 의해 풀려나 `k`로 환원 — 셋이 검증식에서 각자 제자리를 찾아갑니다.

## "유일한" 꼴은 아니다 — Schnorr와의 대비

s가 굳이 이 곱셈/역원 꼴인 건 ECDSA(=DSA 계보)의 선택일 뿐, 서명의 본질은 아닙니다. [[schnorr-vs-ecdsa|Schnorr 서명]]은 같은 의미(커밋 + 바인딩 + 블라인딩)를 훨씬 선형적으로 표현합니다:

```
ECDSA:    s = k⁻¹·(hm + r·x)              ← 곱셈·역원, 비선형
Schnorr:  s = k + e·x   (e = H(R, m))     ← 덧셈만, 선형
```

> [!warning] 이 꼴이 2PC를 어렵게 만든다
> ECDSA의 `k⁻¹·(...)` 곱셈 꼴은 2PC로 쪼개면 `(k1·k2)⁻¹·(hm + r·key1·key2)`가 되어, **`key1·key2` 교차 곱셈**이 등장합니다. 평문 교환 없이 이걸 만들려고 [[paillier-homomorphic-encryption|Paillier 동형암호]]가 끌어와집니다. Schnorr였다면 덧셈만 있어 멀티파티가 훨씬 쉬웠을 일 — 이 sign-service가 Paillier까지 동원하는 **근본 이유는 결국 s의 이 곱셈 꼴**입니다.

## 정리

- **r** = "이번 1회용 난수 `k`에 대한 공개 커밋" — 임시 공개키 `R = k·G`의 x좌표.
- **s** = "내 비밀 `x`를, 그 커밋 `r`과 메시지 `hm`에 묶어, 난수 `k`로 가린 응답" — 메시지/신원/일회성 세 가지를 한 식에 봉인.
- **그 꼴인 이유** = 검증식에서 `s⁻¹`이 곱해질 때 **`(hm + r·x)`가 통째로 약분**되어 커밋 `R = k·G`가 정확히 되살아나도록, **역에서 거꾸로 설계**됐기 때문. 다른 모양이면 약분이 일어나지 않아 검증식이 닫히지 않음.

## 검증 메커니즘 — u1, u2, P

검증자가 손에 든 건 **공개값 4개**뿐입니다: 공개키 `[[Q]]`, 메시지 해시 `[[hm]]`, 서명 `(r, s)`. 비밀 `[[x]]`도 `[[k]]`도 모릅니다. 이 재료로 점 하나를 조립해서 서명자가 만든 커밋 `R = k·G`와 같은지 확인하는 게 전부예요. 그 조립 과정에 등장하는 게 `u1`, `u2`, 그리고 결과점 `P`입니다.

### u1, u2 — 검증자가 G와 Q에 곱할 두 배율

정의는 단순합니다:

```
u1 = hm · s⁻¹   (mod n)
u2 = r  · s⁻¹   (mod n)
```

- `hm`, `r`, `s` 모두 공개 → 검증자 혼자 계산 가능.
- `s⁻¹`은 나눗셈이 아니라 **모듈러 역원** — `s · s⁻¹ ≡ 1 (mod n)`을 만족하는 정수. 확장 유클리드로 항상 구해짐. ([[ec.ts]]의 `.invm(n)`).

> [!note] u1과 u2의 의미론
> - **`u1`** = "**G** 자체에 얼마나 기여하는가" — 메시지 해시 `hm`에서 온 몫
> - **`u2`** = "**Q**(=숨겨진 x)에 얼마나 기여하는가" — 커밋 `r`에서 온 몫
>
> 둘 다 `s⁻¹`을 공유하는데, 이건 서명자가 s에 박아둔 `k⁻¹`을 "되돌리는" 역할입니다.

### k = u1 + u2·x — u1/u2가 왜 그 모양인가

`s`의 정의에서 거꾸로 `k`를 끄집어내면 u1, u2의 정체가 드러납니다:

```
s    = k⁻¹·(hm + r·x)
k·s  = hm + r·x                  ← 양변에 k
k    = s⁻¹·(hm + r·x)            ← 양변에 s⁻¹
k    = s⁻¹·hm + s⁻¹·r·x          ← 분배
k    = (hm·s⁻¹) + (r·s⁻¹)·x
       └──┬──┘    └──┬──┘
          u1         u2
k    = u1 + u2·x                 ★
```

> [!tip] 핵심 한 줄
> 진짜 `k`는 **`u1 + u2·x`로 쪼개진다**. 검증자는 `x`를 모르니 숫자로는 못 구하지만, **`x` 대신 점 `Q = x·G`를 쓰면 점 위에서 같은 계산이 가능**합니다.

### P — 양변에 G를 곱하고 x·G=Q를 대입

★식의 양변에 `G`를 점으로 곱합니다 (양변에 같은 걸 곱해도 등식은 유지, 점 곱셈도 분배법칙 성립):

```
k·G = (u1 + u2·x)·G
    = u1·G + u2·x·G            ← 분배
    = u1·G + u2·(x·G)          ← 결합 (u2·x)·G = u2·(x·G)
    = u1·G + u2·Q              ← x·G = Q (공개키 정의) 대입
```

여기서 정의되는 것이 검증자의 재현점 `P`입니다:

```
P  ≜  u1·G + u2·Q
```

서명이 정직했다면 위 전개로 `P = k·G = R`. 즉:

```
┌─────────────────────────────────────────────────────────┐
│   서명자가 만든 커밋  R = k·G                            │
│              ‖ (같은 점)                                 │
│   검증자가 재현한 점  P = u1·G + u2·Q                    │
└─────────────────────────────────────────────────────────┘
```

> [!example] x를 모르는데 어떻게 u2·Q가 u2·(x·G)와 정확히 같은 점이 되나
> 스칼라 곱의 결합법칙 때문입니다: `u2·Q = u2·(x·G) = (u2·x)·G`. 검증자는 `x`라는 숫자는 모르지만, 그 숫자만큼 G를 곱한 결과인 `Q`는 손에 들고 있습니다. 곡선 위에서 "x로 한 번, u2로 또 한 번" 점을 늘리는 것과 "u2로 늘리고 x·G를 통째로 u2배 하는 것"이 같은 점에 도달해요. 이게 [[이산로그]]가 만들어준 비대칭의 또 다른 얼굴입니다.

### 검증식 — P.x == r ?

검증자가 실제로 하는 일은 딱 세 줄:

```
1. u1 = hm·s⁻¹ mod n,  u2 = r·s⁻¹ mod n
2. P  = u1·G + u2·Q                       ← 공개값만으로 점 조립
3. P.x mod n == r ?                       ← 그 점의 x좌표 비교
       같으면 → 서명 진짜 ✓
       다르면 → 가짜 ✗
```

| 입력 | 출처 | 비밀? |
|---|---|---|
| `Q` | 공개키 | ❌ 공개 |
| `G` | secp256k1 상수 | ❌ 공개 |
| `hm` | 메시지 해시 | ❌ 공개 |
| `r`, `s` | 서명 | ❌ 공개 |
| `x`, `k` | — | ✅ 끝까지 안 씀 |

> [!warning] r은 입력이자 정답지
> `r`은 **u2를 만들 때 입력**으로 들어가고(`u2 = r·s⁻¹`), **마지막에 비교 대상**으로도 쓰입니다(`P.x == r`). 즉 "넣은 r → 나온 r"의 자기일관성(self-consistency)을 확인하는 구조. 올바른 서명만이 이 루프를 닫습니다.

### 직관 — 한 문장으로

> [!note] 검증의 본질
> 검증자는 **공개키 `Q`** 라는 점 안에 "숨어 있는" `x`를, 직접 꺼내지 않고 점 위에서만 다뤄서 서명자의 1회용 커밋 `R = k·G`를 **재현**해 봅니다. `s`가 약분 장치 역할을 해서, **정직한 서명자**가 만든 `(r, s)`만 이 재현을 정확히 닫아 `P.x = r`이 됩니다.

이게 [[ECDSA]]가 영지식 증명의 가족인 이유이기도 합니다: 검증 전 과정에 **비밀이 단 하나도 안 들어가요**. 비밀은 서명 만들 때만, 검증은 100% 공개값. 그래서 누구나, 언제든, 서명자의 협조 없이 검증할 수 있습니다 — 이게 공개키 서명의 정의 그 자체죠.

> [!tip] [[2PC]]에서도 검증식은 그대로
> 서명이 main/sub 두 서버의 협력으로 만들어졌든, 한 서버가 만들었든, 결과 `(r, s)`는 똑같은 ECDSA 서명입니다. 체인 상의 검증자(이더리움 노드, 메타마스크 등)는 분할 사실을 알 필요도, 알 수도 없습니다. [[Paillier]] 마법은 모두 서명 **생성** 쪽 이야기고, 검증식은 `P = u1·G + u2·Q`로 변함없이 동작합니다.

## 비밀의 안전성 — G/k/x가 털리면?

지금까지 등장한 값들은 보안 등급이 **완전히 다릅니다**. "다 같은 암호 값"처럼 묶이지만, 실제로는 공개 전제인 것과 한 번만 새도 끝장나는 것이 섞여 있어요. 하나씩 분리해서 봅시다.

### 1. G — 애초에 "털린다"는 개념이 없는 공개 상수

[[G]]는 비밀이 아닙니다. **[[secp256k1]] 표준에 박혀서 전 세계가 똑같이 쓰는 공개 상수**예요. 비트코인, 이더리움, 이 [[sign-service]]까지 전부 같은 G를 씁니다. 코드도 그냥 라이브러리에서 끌어다 쓰는 한 줄입니다 (`ec.ts:9`):

```ts
export const G = ec.g;   // 누구나 아는 값
```

보안은 "G를 모르는 것"이 아니라 **`Q = x·G`에서 `x`를 역산 못 하는 것**, 즉 [[이산로그 문제 (ECDLP)]]의 난해성에 걸려 있습니다. G는 처음부터 공개를 전제로 설계됐어요.

> [!note] 자물쇠 비유
> 자물쇠 **브랜드**(G)는 누구나 알아도 됩니다. 비밀은 **열쇠**(x)지 모델명이 아니죠. 같은 G로 전 세계 수십억 개의 키쌍이 만들어지지만, 각자의 `x`는 서로 무관합니다.

### 2. k — 한 번만 새도 개인키가 즉시 복원되는 치명값

[[1회용 난수 k (nonce)]]는 정반대입니다. **k가 새면 개인키 `x`가 곧장 계산됩니다.**

서명식이 이거였죠:
```
s = k⁻¹·(hm + r·x)
```
공격자는 서명을 보면 `s, r, hm`을 이미 압니다(전부 공개). 여기서 `k`까지 알면 미지수가 `x` 하나뿐이라 한 줄에 풀려요:

```
s · k        = hm + r · x          (양변에 k 곱)
s · k − hm   = r · x
x = r⁻¹ · (s · k − hm)   (mod n)   ← 개인키 끝
```

> [!warning] k 유출 = 개인키 유출
> 서명 하나 + 새어 나간 `k` 하나면, **공격자는 그 지갑의 모든 미래 트랜잭션을 위조할 수 있는 `x`를 얻습니다.** 복구 불가, 자산 이전 외에 방법이 없습니다.

### 2-1. 더 무서운 변종 — k를 "재사용"만 해도 털린다

`k` 값 자체를 몰라도, **같은 `k`로 두 번 서명하면** 공격자가 두 식을 빼서 `k`를 구하고, 그걸로 `x`까지 구합니다. `r = (k·G).x`니까 같은 `k`면 `r`도 같다는 점이 결정타예요:

```
서명1:  s1 = k⁻¹·(hm1 + r·x)
서명2:  s2 = k⁻¹·(hm2 + r·x)     ← 같은 k → r도 동일
────────────────────────────────
s1 − s2 = k⁻¹·(hm1 − hm2)
   ⇒  k = (hm1 − hm2) · (s1 − s2)⁻¹   (mod n)
   ⇒  그다음 위의 x 복원 식으로 끝
```

### 2-2. 실제 사례 — [[Sony PS3 사건]]과 초기 안드로이드 지갑

> [!example] 2010, Sony PlayStation 3
> [[fail0verflow]]가 PS3 펌웨어 서명을 분석하다가, Sony가 **모든 서명에 같은 상수 `k`를 박아 썼다**는 걸 발견. 위의 두-식-빼기 공격을 그대로 적용해서 **PS3의 마스터 ECDSA 개인키를 통째로 복원**했습니다. 그 뒤로는 누구나 자기가 만든 코드에 Sony 서명을 붙일 수 있었어요.

> [!example] 2013, Android Bitcoin Wallets
> Android의 `SecureRandom` 구현 결함으로 일부 지갑 앱이 **`k`를 중복 생성**. 같은 주소가 같은 `k`로 두 번 서명하는 트랜잭션이 블록체인에 그대로 박혔고, 이걸 자동으로 스캔해 `x`를 뽑아낸 공격자가 코인을 가져갔습니다. 공개 원장이라 누구나 사후 검증 가능했어요.

그래서 코드에서 **매 서명마다 새 `k`를 무작위로** 뽑습니다 (`two-party-player.ts:47-49`):

```ts
public createRandomK() {
  this.k = new BN(randomBytes(n.byteLength() / 2)).umod(n);  // 매번 새 난수
}
```

### 3. 그런데 이 서비스(2PC)는 k 위험을 한 단계 더 막는다

여기가 [[2PC ECDSA]]의 또 다른 장점입니다. 일반 지갑은 한 서버가 `k` 전체를 갖지만, [[sign-service]]는 `k`도 곱셈으로 쪼개져 있어요:

```
k = k1 · k2         (k1은 main만, k2는 sub만)
```

- main의 RNG가 고장 나서 `k1`이 새거나 중복돼도, **sub의 `k2`를 모르면 진짜 `k`를 복원 못 합니다.**
- 한쪽 서버가 통째로 털려도 노출되는 건 그쪽 조각(`k1` 또는 `k2`)뿐 → 개인키 복원 불가.
- sub의 `k2`는 [[Redis]]에 `(walletAddress, randomRequestId)` 키로 **partial-S 단계까지만** 살아 있다 폐기되어, 세션 간 재사용도 구조적으로 막힙니다 (`return-partial-r.usecase.ts`, `return-partial-s.usecase.ts`).

> [!tip] 왜 "곱셈 분할"이 결정적인가
> RNG 결함은 보통 **한쪽 시스템**(라이브러리, OS, 드라이버)에서 일어납니다. `k`를 한 서버가 통째로 만들면 그 한 결함이 곧 개인키 누출이에요. 곱셈으로 쪼개면 두 서버의 RNG가 **동시에** 같은 방식으로 고장 나야 같은 `k`가 재현되는데, 다른 호스트·다른 시드·다른 프로세스라 사실상 독립 → 한쪽 RNG 결함 단독으로는 PS3·Android 패턴이 발동하지 못합니다.

### 4. 한눈에 — 무엇이 비밀이고 무엇이 공개인가

| 값 | 털리면? | 이유 |
|---|---|---|
| **G** | 괜찮음 ✅ | 원래 공개 상수. 보안은 G가 아니라 [[이산로그 문제 (ECDLP)]] 난해성 |
| **Q** (공개키) | 괜찮음 ✅ | 공개 전제. `Q → x` 역산 불가 |
| **r, s, hm** | 괜찮음 ✅ | 서명·메시지의 일부, 검증을 위해 공개돼야 함 |
| **k** (nonce) | 치명적 ❌ | 한 번 누출·재사용 → 위의 한 줄로 `x` 즉시 복원 |
| **x** (개인키) | 끝장 ❌ | 말 그대로 개인키 |

> [!note] 결론
> **비밀로 지켜야 하는 건 `x`와 `k` 둘 뿐**, G·Q·r·s·hm은 다 공개돼도 됩니다. 그리고 [[sign-service]]의 2PC 설계는 `x`와 `k` **둘 다** 한 곳에 모이지 않게 곱셈으로 쪼개서, **한 서버 탈취만으로는 어느 쪽도 복원 못 하게** 만든 구조입니다.

## 2PC 분할 — x=key1·key2, k=k1·k2를 어떻게 합치나

이제 단일 서명자의 ECDSA를 두 서버(main = player1, sub = player2)로 쪼갭니다. 핵심 결정 하나가 모든 걸 정합니다: **덧셈이 아니라 곱셈으로 쪼갠다.**

```
x = key1 · key2   (mod n)        ← 진짜 개인키. 어디에도 통째로 존재하지 않음
k = k1   · k2     (mod n)        ← 1회용 난수도 마찬가지
```
- main만 `key1, k1`을 갖고
- sub만 `key2, k2`를 갖습니다
- 곱 `x`와 `k`는 **누구도 모름**

> [!note] 왜 곱셈인가
> 덧셈 분할(`x = a+b`)도 가능은 합니다. 다만 ECDSA의 `s = k⁻¹·(hm + r·x)`엔 **곱셈 항**이 자연스럽게 들어 있어서, 같은 모양으로 쪼개면 점 곱셈/[[paillier-homomorphic]]의 평문-스칼라 곱과 깔끔하게 맞물립니다.

## 공개키 Q는 "점 곱셈"으로 합친다

공개키는 평문 `x`를 합치지 않고도 두 단계 점 곱셈만으로 완성됩니다 (`two-party-player.ts:59-66`):

```
main: partialQ = key1 · G              ← main만 자기 key1을 곱함
       ───────► sub로 점을 전달
sub : Q        = key2 · partialQ
              = key2 · (key1 · G)
              = (key1·key2) · G
              = x · G       ✓
```

요점: **숫자 `x = key1·key2`는 한 번도 만들어진 적이 없습니다.** 두 조각이 곡선 위 점 곱셈으로만 합쳐져 `Q`가 나옵니다. 두 서버가 각자 `Q`를 독립적으로 계산해 일치 여부를 검증한 뒤 저장합니다 (`create-signer.usecase.ts`).

> [!tip] 스칼라 곱의 결합법칙이 다 한다
> `key2 · (key1·G) = (key2·key1) · G` — 점 위의 스칼라 곱은 결합법칙이 성립하므로, 누가 먼저 곱하든 결과 점은 같습니다. 이게 곱셈 분할이 점 위에서 자연스럽게 합쳐지는 이유입니다.

## r은 "k2·G를 받아 내 k1을 점에 곱해서" 만든다

서명할 때 r을 만드는 단계는 공개키 합치기와 구조가 똑같습니다 (`returnPartialR`, `returnR` — `two-party-player.ts:71-84`):

```
main: 자기 k1 새로 뽑음 →  k1·G 보유
sub : 자기 k2 새로 뽑음 →  k2·G 를 응답으로 보냄
                          ───────►
main: R = k1 · (k2·G) = k1·k2·G = k·G
      r = R.x mod n           ✓
```

이 한 줄이 2PC의 절반을 떠받칩니다. **main은 sub의 평문 `k2`를 본 적이 없고, 그럴 필요도 없습니다.** sub가 보낸 건 점 `k2·G`지 숫자 `k2`가 아니거든요.

```
┌─────────────┐                       ┌─────────────┐
│   main      │                       │     sub     │
│  key1, k1   │                       │  key2, k2   │
└─────────────┘                       └─────────────┘
       │     POST /v1/signer/get-part-r       │
       │ ───────────────────────────────────► │
       │            ◄─── k2·G ─────           │
       │                                      │
       │ r = (k1·(k2·G)).x                    │
       │                                      │
```

## 왜 상대 k를 몰라도 되는가 — 이산로그가 가려준다

여기가 직관이 잘 안 잡히는 곳인데, 결정적 사실은 [[ecdlp-discrete-log]]입니다:

```
k2 를 알면  →  k2·G  계산:  쉬움 ✅
k2·G 만 보고 →  k2   역산:  불가능 ❌  (n ≈ 2²⁵⁶)
```

> [!warning] 이게 보안 기능이다, 버그가 아니다
> main이 sub의 `k2`를 모르는 건 **불편함이 아니라 의도**입니다. 만약 main이 완전한 `k = k1·k2`를 안다면, 공개된 `(r,s)`만 있으면 `x = r⁻¹·(s·k − hm)`로 개인키를 즉시 복원할 수 있어요. 그래서 `k`도 `x`처럼 한쪽에 절대 모이면 안 되는 값이고, 2PC는 이걸 **구조적으로** 막은 겁니다.

비유로 정리하면:

> [!example] 잠긴 상자 비유
> sub가 잠긴 상자(`k2·G`)를 보냅니다. main은 상자 안 숫자(`k2`)는 못 보지만, 상자째로 자기 배율(`k1`)만큼 키울 수는 있어요. 결과 상자는 정확히 `k1·k2`짜리 — 그게 `R = k·G`이고, x좌표가 `r`입니다.

## 점에서 합쳐지는 항 vs 숫자에서 합쳐야 하는 항

여기까지가 곱셈 분할이 **공짜로** 작동하는 영역입니다. 정리하면:

| 합쳐야 할 것 | 어떻게 | Paillier 필요? |
|---|---|---|
| `Q = key1·key2·G` | 점 곱셈만으로 (sub가 main의 점에 자기 key2 곱함) | ❌ |
| `R = k1·k2·G` (→ `r`) | 점 곱셈만으로 (main이 sub의 점에 자기 k1 곱함) | ❌ |
| `s = (k1·k2)⁻¹·(hm + r·key1·key2)` | **숫자에서 `key1·key2` 교차항** 발생 | ✅ |

> [!note] s만 까다로운 이유
> `Q`와 `r`은 결과가 **점**이라서, 한쪽 평문 스칼라를 다른 쪽 점에 곱하면 끝납니다. 반면 `s`는 결과가 **`mod n`의 숫자**고, 그 안에 `key1·key2`라는 두 평문의 곱이 그대로 들어가요. 점 곱셈처럼 "한쪽을 점으로 위장"하는 트릭이 안 통하니까, 다음 섹션의 [[paillier-homomorphic|Paillier 동형암호]]가 필요해지는 겁니다.

요약: **곱셈으로 쪼갰기 때문에 `Q`와 `r`은 점 곱셈의 결합법칙만으로 합쳐지고, 상대의 스칼라는 이산로그 뒤에 숨어 절대 노출되지 않습니다.** s 한 줄만 빼고요 — 그 한 줄이 다음 섹션의 모든 복잡함을 부릅니다.

## Paillier가 등장하는 지점 — s 계산의 교차항 문제

[[ECDSA]] 2PC에서 `r`까지는 [[타원곡선 점 곱셈]]만으로 처리됩니다. 진짜 막히는 곳은 `s`예요. 이 한 줄에서 **딱 한 항**이 평문 교환을 거부하고, 그 한 항을 풀려고 [[Paillier]]가 끌려 들어옵니다.

### 1. 분할된 비밀로 s를 다시 써 보기

[[ECDSA]] 본래의 `s`:
```
s = k⁻¹ · (hm + r·x)
```

2PC에서는 `x = key1·key2`, `k = k1·k2`로 곱셈 분할되어 있으니 그대로 대입:
```
s = (k1·k2)⁻¹ · (hm + r · key1·key2)
  = k1⁻¹ · k2⁻¹ · (hm + r · key1·key2)
```

이걸 항별로 "누가 무엇을 아는가" 표로 정리해 보면 막히는 지점이 한눈에 보입니다:

| 항 | 들어 있는 비밀 | main(key1, k1) | sub(key2, k2) | 평문 교환 가능? |
|---|---|---|---|---|
| `hm` | (없음, 공개) | ✓ | ✓ | 공개값이라 무관 |
| `r` | (없음, 공개) | ✓ | ✓ | 공개값이라 무관 |
| `k1⁻¹` | k1 | ✓ 혼자 계산 | ✗ | 안 보내면 됨 |
| `k2⁻¹` | k2 | ✗ | ✓ 혼자 계산 | 안 보내면 됨 |
| `r · key1·key2` | **key1 + key2** | key1만 | key2만 | ❌ **둘이 곱해야 함** |

> [!warning] 막히는 지점
> `key1·key2` 교차항 — main은 `key1`만, sub는 `key2`만 안다. 그런데 곱해야 한다. 평문으로 주고받으면 **개인키 `x = key1·key2`가 즉시 노출**된다.

`hm`은 공개, `r`은 공개, `k1⁻¹`과 `k2⁻¹`은 각자 혼자 계산해서 자기 단계에만 곱하면 됩니다([[k는 양측이 몰라도 된다]] 참고). **오직 `key1·key2` 한 항만이 "남의 비밀과 내 비밀을 곱해야 하는데 평문 노출은 안 됨"이라는 진짜 벽**입니다.

### 2. 왜 점 곱셈 트릭이 여기선 안 통하나

`r` 만들 때는 [[이산로그]] 덕분에 점 `k2·G`를 보내도 `k2`가 안 새었습니다(점에 내 `k1` 곱하면 끝). 그런데 `s`는 **그냥 정수 등식**입니다 — 점 위가 아니라 `mod n` 정수 세계에서의 곱셈. 점으로 들고 올라가면 결과가 점이 되어버려서 `s`라는 스칼라가 나오지 않습니다.

> [!note] 핵심 차이
> - `r`: 점 위 연산 → [[ECDLP]]가 비밀을 가려준다 → 평문 교환 불필요
> - `s`: 정수 곱셈/역원 → 점 위로 못 올림 → **다른 종류의 "암호화된 채로 곱하기" 도구가 필요**

[[ECDSA]] `s`의 `k⁻¹·(hm + r·x)` 곱셈/역원 꼴이 이 어려움을 만든 장본인이에요. [[Schnorr 서명]]은 `s = k + e·x`라는 **덧셈** 꼴이라 멀티파티가 훨씬 쉽고, Paillier 같은 추가 도구 없이도 2PC가 됩니다. [[ECDSA]]가 곱셈/역원을 택한 대가가 바로 이 한 줄에서 청구되는 거예요.

### 3. Paillier의 두 초능력

[[Paillier]]는 **암호문 상태로** 두 가지 연산이 가능한 [[부분 동형암호 (Partially Homomorphic Encryption)]]입니다.

```
┌─────────────────────────────────────────────────────────────┐
│  ① 덧셈 동형 (⊕):  Enc(a) ⊕ Enc(b) = Enc(a + b)             │
│     실제 연산:     암호문끼리 곱한다  (c1 · c2 mod N²)       │
│                                                              │
│  ② 평문 스칼라 곱 (⊗):  Enc(a) ⊗ b = Enc(a · b)              │
│     실제 연산:          암호문을 b제곱한다  (c^b mod N²)     │
└─────────────────────────────────────────────────────────────┘
```

코드에서는 그대로 메서드로 노출돼 있습니다 (`apps/sign-service/.../two-party-player.ts`):

```ts
publicKey.addition(c1, c2)     // ⊕  암호문 + 암호문 → 평문 합 암호문
publicKey.multiply(c, scalar)  // ⊗  암호문 + 평문 스칼라 → 평문 곱 암호문
```

> [!tip] 두 초능력이 정확히 무엇을 가능케 하나
> - ⊕ 덕분에: `Enc(A) ⊕ Enc(B) = Enc(A+B)` → 두 부분 합을 **암호문 상태로 합칠 수 있다**.
> - ⊗ 덕분에: `Enc(key1) ⊗ (k2⁻¹·r·key2) = Enc(k2⁻¹·r·key1·key2)` → sub가 **`key1`을 평문으로 보지 않고** 자기 평문(`k2⁻¹·r·key2`)을 곱해 넣을 수 있다.

이 둘만 있으면 `s`의 문제 부분이 풀립니다. main이 자기 `key1`을 자기 [[Paillier]] 공개키로 미리 한 번 암호화해서 sub에 보내면, sub는 그 암호문에 ⊗로 자기 평문을 곱하고 ⊕로 `k2⁻¹·hm` 부분을 더해서 `Enc(k2⁻¹·hm + k2⁻¹·r·key1·key2)`를 만들어 돌려보냅니다. main은 자기 [[Paillier]] 개인키로 복호화한 뒤 `k1⁻¹`만 더 곱하면 `s` 완성.

### 4. 왜 이게 "안전"한가 — 비대칭 키 배치

```
┌────────── main ──────────┐         ┌────────── sub ───────────┐
│  ECDSA:   key1, k1       │         │  ECDSA:   key2, k2       │
│  Paillier: pk1, sk1 ✓    │         │  Paillier: pk1만 (sk1 ✗) │
│  ─────────────────────   │         │  ─────────────────────   │
│  Enc(key1) 만들어 송신   │ ──cKey─▶│  cKey ⊗/⊕ 로 partialS    │
│                          │◀─partialS│  암호문 응답              │
│  sk1으로 복호화 → ·k1⁻¹  │         │  (복호화 영원히 불가)     │
└──────────────────────────┘         └──────────────────────────┘
```

> [!note] 비대칭의 핵심
> [[Paillier]] **개인키 `sk1`은 main만** 가집니다. sub는 [[Paillier]] 공개키 `pk1`로 ⊕/⊗ 연산은 할 수 있어도, **복호화는 영원히 불가능**. 그래서 sub는 `Enc(key1)`을 어떻게 만져도 `key1`을 못 봅니다.

여기서 [[ECDSA]] 분할 비밀(key1/key2)과 [[Paillier]] 키쌍(pk1/sk1)이 **서로 다른 축**으로 작동한다는 점이 중요해요:
- [[ECDSA]] 키는 둘로 **쪼개져** 있고 (대칭적, 둘 다 조각만 가짐),
- [[Paillier]] 키는 main에 **몰려** 있다 (비대칭적, sub는 공개키만).

이 조합 덕분에 sub는 main의 비밀에 손댈 수 있지만 늘 자물쇠 안에서, main은 sk1을 가져도 복호 결과에서 `key2`나 `k2`를 분리해낼 수 없습니다(둘이 한 식에 섞여 있음).

### 5. 다음 섹션으로 가는 다리

정리하면:

> [!example] s = (k1·k2)⁻¹·(hm + r·key1·key2) 의 항별 처리 전략
> - `hm`, `r` → 공개, 그대로 사용
> - `k1⁻¹`, `k2⁻¹` → 각자 자기 단계에 혼자 곱함
> - `key1·key2` 교차항 ← **여기에만 [[Paillier]] 동원**
>   - ⊗ 로 sub가 암호문 상태의 `key1`에 자기 평문 곱셈
>   - ⊕ 로 부분합 합치기
>   - 최종 복호화는 sk1을 쥔 main만 가능

다음 섹션([[sign-service 실제 흐름 — 저장과 서명 오케스트레이션]])에서 이 ⊕/⊗가 `returnCKey` → `returnPartialS` → `returnS`의 세 단계에 어떻게 정확히 박혀 있는지, 그리고 그 다음 [[Paillier 동형 연산 숫자 예시 — N=143으로 따라가기]]에서 실제 정수로 432¹⁰ 같은 거듭제곱이 어떻게 `Enc(평문 곱)`이 되는지 따라갑니다.

## sign-service 실제 흐름 — 저장과 서명 오케스트레이션

지금까지의 수식이 실제로 어떻게 **서버 두 대**와 **데이터베이스 두 개**에 펼쳐져 돌아가는지를 봅니다. 핵심은 단순합니다: **"개인키 전체가 한 곳에 모이지 않고, 두 번의 HTTP 왕복으로 서명이 완성된다."**

### A. DB가 저장하는 것 — "조각 하나"를 KMS로 또 한 번 잠금

`Wallet` 스키마는 의외로 평범합니다 (`prisma/schema.prisma:18-29`):

```prisma
model Wallet {
  address    String
  network    String
  publicKey  String   // Q (공개키 점, hex)
  privateKey Bytes    // ⚠️ "조각 하나"를 KMS로 암호화한 바이트
}
```

여기서 가장 중요한 두 가지:

> [!warning] `privateKey` 컬럼은 **개인키가 아니라 개인키의 절반**이다
> - **main 서버 DB**에는 `key1`만, **sub 서버 DB**에는 `key2`만 들어간다. 두 DB는 물리적으로 분리되어 있고 sub는 `.sub.env`로 다른 connection을 쓴다.
> - 진짜 개인키 `x = key1 · key2` 는 **어떤 DB에도, 어떤 메모리에도, 어떤 순간에도** 통째로 존재한 적이 없다.
> - 따라서 main DB만 통째로 덤프 되어도 → 나오는 건 `key1` 뿐 → 서명 불가, [[ecdsa-private-key-x]] 복원 불가.

그리고 **그 조각마저도** 평문이 아니라 AWS [[kms-envelope-encryption]]으로 한 번 더 잠가서 저장합니다 (`key.repository.ts:77-94`):

```ts
const encrypted = await this.kmsService.encrypt(key);   // AWS KMS 호출
privateKey: Buffer.from(encrypted.CiphertextBlob),      // DB에는 암호문만
```

- 복호화 키는 AWS KMS 안에 있고(`AWS_KMS_KEY_ID`), 풀려면 IAM 권한이 필요.
- 즉 DB가 털려도 → 나오는 건 "암호화된 key1" → KMS 권한까지 같이 털려야 비로소 `key1` 평문 → **그래도 `key2`가 없으면 서명 불가.**

> [!note] 이중 방어 = (조각 분리) × (KMS 봉투 암호화)
> 한 지갑 = `{address, network, Q, KMS(key_share)}`. main이 털리려면 main DB **+** main KMS 권한 **+** sub DB **+** sub KMS 권한이 **동시에** 깨져야 한다.

> [!tip] [[paillier-keypair]]는 DB에 저장하지 않는다
> Paillier 키쌍은 영속화 대상이 아니다. 서명 요청이 올 때마다 `TwoPartyPlayer` 생성자에서 새로 만들고, 그 요청이 끝나면 메모리에서 같이 사라진다. 즉 **요청-스코프 1회용**. 그래서 `two-party-player.ts:20-28`의 `while (N.bitLength() < n.bitLength()*2)` 루프가 매 요청마다 돈다.

### B. 요청이 들어왔을 때 — 두 번의 HTTP 왕복

`POST /v1/transaction/transfer` 가 main에 도착하는 순간부터 체인에 트랜잭션이 들어가기까지의 흐름입니다.

```
client → main(:host)                               sub(:host)
   │ POST /v1/transaction/transfer
   │
   ▼
[1] 자기 key1 로드 & KMS 복호화
    DB(privateKey ciphertext) → KMS.decrypt() → key1 (평문, 메모리 only)
    new TwoPartyPlayer(key1)  ──► Paillier 키쌍도 메모리에서 새로 생성
   │
   ▼
[2] 1차 왕복 ─ r 만들기
    main: k1 ← random;  partialR = k1·G
   ──────► POST /v1/signer/get-part-r   (walletAddress, randomRequestId, k1·G)
                                          sub: k2 ← random
                                          sub: partialR2 = k2·G
                                          sub: Redis.SET(walletAddress:randomRequestId → k2, TTL)
                                       ◄──── 응답: k2·G
    main: r = (k1 · (k2·G)).x mod n     ← 두 점을 곡선 위에서 곱함
   │
   ▼
[3] 2차 왕복 ─ s 만들기
    main: cKey = Enc_pk1(key1)                       (자기 Paillier 키로 자기 조각 암호화)
   ──────► POST /v1/signer/get-part-s   (cKey, pk1, r, hm, randomRequestId)
                                          sub: k2 ← Redis.GET(walletAddress:randomRequestId)
                                          sub: partialS = Enc_pk1(k2⁻¹·hm + k2⁻¹·r·key1·key2)
                                              (cKey ⊗ scalar, ⊕ 동형 연산만 사용)
                                          sub: Redis.DEL(...)   ← k2 즉시 폐기
                                       ◄──── 응답: partialS (암호문)
    main: dec = Dec_sk1(partialS)        (자기 Paillier 개인키로만 가능)
    main: s   = dec · k1⁻¹ mod n
   │
   ▼
[4] canonical s 검사 → (필요 시) 재시도 → 서명 조립 → 체인 전송
    if (s == 0 || r == 0 || s > n/2) ⇒  k 새로 뽑아서 [2]부터 다시 (low-S form)
    sig = 0x{r}{s}{v}
    publicClient.sendRawTransaction(sig) → receipt → response
```

각 단계의 코드 참조 위치:

| 단계 | 파일 | 함수/줄 |
|---|---|---|
| [1] DB→KMS 복호화 | `key.repository.ts:25-75` | `findOne()` |
| [2] partial-R 교환 | `two-party-player.ts:71-84`, `return-partial-r.usecase.ts` | `returnPartialR`, `returnR` |
| [2] sub의 k2 캐싱 | `return-partial-r.usecase.ts` | Redis `randomRequestId` 키 |
| [3] cKey 생성 | `two-party-player.ts:89-92` | `returnCKey` |
| [3] sub partial-S | `two-party-player.ts:94-112` | `returnPartialS` |
| [3] main 복호화 | `two-party-player.ts:114-121` | `returnS` |
| [4] canonical 재시도 | `two-party-evm-signer.ts:167-243` | `signHash` 루프 (188-237) |
| [4] 체인 전송 | `evm.service.ts:215-247` | `sendRawTransaction` |
| 인증 | `two-party.strategy.ts` | sub가 player 복원할 때 검증 |

> [!example] [[redis-k2-cache]] — sub의 `k2`가 잠깐 머무는 유일한 곳
> sub의 처리가 **HTTP 2번**으로 쪼개져 있기 때문에 (get-part-r, get-part-s), [2]에서 만든 `k2`를 [3]에서 다시 써야 한다. 그 사이를 잇는 게 Redis. 키는 `(walletAddress, randomRequestId)`로 잡고, 짧은 TTL + partial-S 응답 직후 명시적 `DEL`. 이게 있어서:
> - **세션 간 nonce 재사용을 구조적으로 차단** ([[k-reuse-attack]] 방어)
> - main의 retry 호출이 같은 `randomRequestId`로 들어와도 같은 `k2`를 다시 못 꺼냄 → 매번 새 nonce 강제

### C. canonical `s` 재시도 — `s ≤ n/2` 강제 (EIP-2 / low-S)

EVM은 같은 메시지에 두 개의 유효한 `s`(원래 `s`와 `n−s`)가 있는 [[ecdsa-signature-malleability]]를 막으려고 **`s ≤ n/2`만 허용**합니다 (EIP-2). `two-party-evm-signer.ts:188-237`은 이걸 보장하려고 루프를 돕니다:

```
do {
    k1 ← random;   randomRequestId ← uuid()
    [get-part-r] → r
    if (r == 0) continue
    [get-part-s] → s
    if (s == 0) continue
    if (s > n/2) continue        // low-S 위반 → 새 k로 재시도
    break
} while (true)
v ← recoveryId (27/28)
```

> [!note] 왜 `n−s`를 그냥 쓰면 안 되나
> 사실 단일 키 ECDSA라면 `s > n/2`일 때 `s ← n − s` 한 줄로 끝낸다. 하지만 **2PC에선 `s`가 `k1⁻¹ · Dec(partialS)` 의 산물**이라 함부로 뒤집으면 `(r, s)` 쌍의 일관성이 깨질 수 있고, 무엇보다 sub의 Redis `k2`가 한 번의 partial-S로 폐기되기 때문에 **그냥 새 k로 재시도**하는 게 코드 흐름에 맞는다.

### D. 네트워크에 흐르는 것 vs **절대** 안 흐르는 것

이 표가 이 섹션 전체 요약입니다.

| 분류 | 네트워크에 흐른다 | 절대 안 흐른다 |
|---|---|---|
| **개인키 영역** | — | 평문 `key1`, 평문 `key2`, 완성된 `x = key1·key2` |
| **난수 영역** | `k1·G`, `k2·G` (점, 이산로그로 보호) | 평문 `k1`, 평문 `k2`, 완성된 `k = k1·k2` |
| **Paillier 영역** | `cKey = Enc_pk1(key1)`, `partialS`, 공개키 `pk1` | Paillier 개인키 `sk1` (main 메모리 only) |
| **공개 입력** | `r`, `hm`, `walletAddress`, `randomRequestId` | — |
| **저장소 영역** | — | DB의 `privateKey` 컬럼(KMS 암호문), KMS의 마스터키 |

> [!warning] 한 서버 탈취만으로는 어느 비밀도 복원되지 않는다
> - main 탈취 → `key1`, `k1`, Paillier sk1 노출. 하지만 sub의 `key2`/`k2` 없이는 `x`, `k`, 어느 것도 못 구함.
> - sub 탈취 → `key2`, `k2`(짧게) 노출. main의 `key1`은 sub 입장에선 **`cKey` 암호문으로만** 본 적 있고, `sk1`이 없어서 풀 수 없음.
> - DB 두 개를 동시에 털어도 → KMS 복호화 권한이 없으면 ciphertext만 손에 들림.

### 한 줄 요약

sign-service는 지갑마다 **개인키의 절반 조각을 KMS로 한 번 더 봉인해** 각자 다른 서버·DB에 두고, 서명 요청이 오면 main이 자기 조각을 메모리로 복호화한 뒤 **두 번의 HTTP 왕복(`/v1/signer/get-part-r`, `/v1/signer/get-part-s`)**으로 sub와 협력해 `(r, s)`를 만들고, low-S면 새 `k`로 재시도해서 체인에 쏜다. 그 과정 어디서도 완전한 [[ecdsa-private-key-x]] 나 [[ecdsa-nonce-k]] 가 한 곳에 모이거나 네트워크를 타지 않는다.

## Paillier 동형 연산 숫자 예시 — N=143으로 따라가기

추상 수식만 보면 "정말 평문 노출 없이 s가 나오나?" 싶죠. 작은 곡선(`nc=11`)과 작은 Paillier 모듈러스(`N=143`)로 끝까지 직접 굴려보면, 손에 잡히는 숫자로 맞아떨어집니다.

### 1. 무대 설정 — 작은 곡선·작은 Paillier

[[ecdsa-curve-params]] 쪽 (스칼라는 전부 `mod nc`):

| 값 | 숫자 | 누가 보유 |
|---|---|---|
| `nc` (곡선 차수) | 11 | 공개 상수 |
| `key1` | 3 | main만 |
| `key2` | 5 | sub만 |
| `x = key1·key2 mod 11` | 15 mod 11 = **4** | **아무도 통째로 모름** |
| `k1` | 2 | main만 |
| `k2` | 3 | sub만 |
| `k = k1·k2 mod 11` | 6 | **아무도 통째로 모름** |
| `r` (커밋 점의 x좌표라 치고) | 6 | 공개 |
| `hm` (메시지 해시) | 5 | 공개 |

[[paillier-keys]] 쪽 (전부 `mod N²`):

| 값 | 숫자 | 비고 |
|---|---|---|
| `p, q` | 11, 13 | Paillier용 소수 (곡선 소수와 무관) |
| `N = p·q` | **143** | Paillier 모듈러스 |
| `N²` | **20449** | 암호문이 사는 세계 |
| `g = N+1` | 144 | 표준 선택 |
| 설명용 난수 r | 1로 고정 | 실제론 매번 랜덤 — 같은 평문이 매번 다른 암호문이 됨 |

> [!note] 난수 r 고정은 설명용일 뿐
> 실제 [[paillier-encryption]]은 `Enc(m) = gᵐ·rᴺ mod N²`로 매번 새 r을 뽑아 **의미론적 보안(semantic security)** 을 얻습니다. 여기선 산수를 따라가기 쉽게 r=1로 두고 `Enc(m) = 1 + 143·m mod 20449`로 단순화했습니다. 동형 연산 결과가 항상 같은 평문으로 복호화된다는 점은 둘 다 동일합니다.

### 2. 정답지 — 일반 ECDSA로 직접 계산한 s

[[two-party-split]] 없이 한 명이 다 안다고 가정하고 [[ecdsa-signing-formula|s = k⁻¹·(hm + r·x)]]를 계산:

```
k⁻¹ mod 11 = 2          (6·2 = 12 ≡ 1)
hm + r·x   = 5 + 6·4 = 29 ≡ 7  (mod 11)
s          = 2·7 = 14 ≡ 3      (mod 11)
                         ━━━━━━
                          정답 s = 3
```

각 조각의 역원도 미리 뽑아둡니다 (`mod 11`):

```
k1⁻¹ = 6   (2·6 = 12 ≡ 1)
k2⁻¹ = 4   (3·4 = 12 ≡ 1)
검산:  k1⁻¹·k2⁻¹ = 6·4 = 24 ≡ 2 = k⁻¹  ✓
```

이제 main과 sub가 서로의 비밀을 **평문으로 한 번도 안 본 채로** 정확히 이 `s=3`을 만들어내는지 따라갑니다.

### 3. main → sub: `cKey = Enc(key1)`

main이 자기 [[paillier-keypair|Paillier 공개키 pk1]]로 [[private-key-share|key1]]을 암호화:

```
cKey = Enc_pk1(key1) = 1 + 143·3 = 430
```

main은 sub에게 `(cKey, pk1, r, hm)`을 보냅니다. 평문 key1=3은 절대 보내지 않습니다.

> [!warning] 여기서 sub가 보는 것
> sub의 손에 들어온 건 숫자 `430`뿐입니다. `430`을 보고 평문 3을 역산하려면 [[paillier-decisional-composite-residuosity|DCR 가정]] 아래에서 `N=143`의 인수분해(`p=11, q=13`)를 풀거나 [[paillier-private-key|λ]]를 알아야 합니다. sub에겐 둘 다 없음 → **key1은 봉인된 상태.**

### 4. sub의 평문 사전 계산 (자기 것만)

[[partial-s-computation]]에 들어가기 전, sub가 자기 비밀 `(k2, key2)`와 공개값 `(hm, r)`만으로 두 개의 평문을 만듭니다 (`mod 11`):

```
result1 = k2⁻¹ · hm        = 4·5     = 20 ≡  9
result2 = k2⁻¹ · r · key2  = 4·6·5   = 120 ≡ 10
```

`result1`은 "메시지에서 온 몫", `result2`는 "커밋·내 키조각에서 온 몫"입니다. 둘 다 **key1을 전혀 안 씁니다** — 다음 단계에서 암호문 `cKey`가 그 역할을 해줄 거니까요.

### 5. 동형 연산 — 암호문 위에서 곱하고 더하기

[[paillier-homomorphism|Paillier의 두 초능력]]을 그대로 적용합니다 (`mod N² = mod 20449`):

```
①  Enc(a) ⊗ b   :=  cipherᵇ mod N²       →  Enc(a·b)
②  Enc(a) ⊕ Enc(b) := c_a · c_b mod N²    →  Enc(a+b)
```

**(1) eResult1 — 새 암호화** (평문 result1=9):
```
eResult1 = Enc_pk1(9) = 1 + 143·9 = 1288
```

**(2) eResult2 — `cKey` 를 result2 제곱** (`Enc(key1) ⊗ result2`):
```
eResult2 = cKey^result2 mod N²
         = 430¹⁰ mod 20449
         = 4291
검산: Enc(key1·result2) = Enc(3·10) = Enc(30) = 1 + 143·30 = 4291  ✓
```

→ sub는 `430`을 10제곱했을 뿐인데, 그 결과는 `Enc(3·10) = Enc(30)`. **key1=3은 평문으로 한 번도 안 봤습니다.** 이게 `(1+N)ᵃᵇ ≡ 1+abN (mod N²)` 덕분이고, 자세한 이항정리 전개는 다음 섹션에서 다룹니다.

**(3) partialS — 두 암호문 곱하기** (`eResult1 ⊕ eResult2`):
```
partialS = (1288 · 4291) mod 20449
         = 5527408 mod 20449
         = 5578
검산: Enc(9 + 30) = Enc(39) = 1 + 143·39 = 5578  ✓
```

이게 `partialS = Enc_pk1(k2⁻¹·hm + k2⁻¹·r·key1·key2)`의 정체입니다. 평문 `39 = 9 + 30 = k2⁻¹·hm + k2⁻¹·r·key1·key2 (mod ...)`이 암호문 안에 봉인된 셈.

> [!example] 흐름도
> ```
> main                                    sub
> ───                                     ───
> cKey = Enc(3) = 430        ──cKey──▶    
>                                         result1 = 9       (평문)
>                                         result2 = 10      (평문)
>                                         eResult1 = Enc(9) = 1288
>                                         eResult2 = 430¹⁰ = 4291  (= Enc(30))
>                                         partialS = 1288·4291 = 5578  (= Enc(39))
>                            ◀─partialS──
> ```

### 6. main의 복호화 + k1⁻¹ 곱 → s 완성

[[partial-s-decrypt]] 단계. main은 자기 [[paillier-private-key|개인키 sk1]]로 `partialS`를 풀고, 자기 `k1⁻¹`을 곱합니다:

```
dec = Dec_sk1(5578) = 39                    ← main만 가능 (sk1 보유)
s   = dec · k1⁻¹ mod 11
    = 39 · 6 mod 11
    = 234 mod 11
    = 3                                      ✓ 정답 s=3 과 일치!
```

복호화로 나온 `dec=39`의 의미도 정확히 맞아떨어집니다:

```
39 mod 11 = 6
         = k2⁻¹·hm + k2⁻¹·r·key1·key2  mod 11
         = 4·5  +  4·6·3·5  mod 11
         = 20 + 360 mod 11
         = 9 + 8 mod 11
         = 17 ≡ 6                            ✓
```

여기에 `k1⁻¹=6`을 곱해 `k⁻¹ = k1⁻¹·k2⁻¹`을 완성 → 정확히 ECDSA의 `s = k⁻¹·(hm + r·x)`가 재현됩니다.

### 7. 누가 무엇을 평문으로 봤나 — 최종 점검

| 누가 | key1=3 | key2=5 | k1=2 | k2=3 | x=4 | k=6 | s=3 |
|---|:---:|:---:|:---:|:---:|:---:|:---:|:---:|
| main | ✅ | ❌ (영원히) | ✅ | ❌ | ❌ | ❌ | ✅ (최종) |
| sub | ❌ (cKey만) | ✅ | ❌ | ✅ | ❌ | ❌ | ❌ |
| 네트워크 위 | ❌ | ❌ | ❌ | ❌ | ❌ | ❌ | ❌ |

네트워크에는 `cKey=430`, `partialS=5578`, 공개값 `r=6, hm=5`만 흘렀습니다. **`x = key1·key2 = 4`라는 진짜 개인키, `k = k1·k2 = 6`이라는 진짜 난수는 어디에도 조립된 적이 없습니다.**

> [!tip] 왜 [[two-party-player-constructor|`TwoPartyPlayer` 생성자 루프]]가 `N > nc²`을 요구하나
> 복호화 직전 main이 보는 평문은 `dec = k2⁻¹·hm + k2⁻¹·r·key1·key2` — **`mod 11`로 줄이기 전의 정수**입니다. 우리 예시에선 39였죠. 만약 `N < 39`였다면 `dec mod N`으로 깎여서 `s` 복원이 망가집니다. 일반적으로 이 합의 최대 크기는 대략 `nc + nc²` (교차항 `key1·key2` 때문) → `N > nc²` 필요. 코드는 `generateRandomKeysSync(nc.bitLength() * 2)`로 **곡선 차수의 2배 비트수** Paillier 키를 뽑고, `nc ≤ N` 조건이 맞을 때까지 `while` 루프를 돕니다. 우리 예시도 `N=143 > nc²=121`이라 39가 무사히 살아남았습니다. 실제 [[secp256k1]]은 `nc ≈ 2²⁵⁶`이라 `N ≈ 2⁵¹²`이 됩니다.

> [!note] 한 줄 요약
> `cKey=430` → sub가 평문 `key1` 없이 `430¹⁰ = Enc(30)` → `1288·4291 = Enc(39) = 5578` → main이 복호화로 `39` → `·k1⁻¹=6` → **s=3**. 정답과 일치, 평문 비밀 노출 0. [[paillier-homomorphism|⊕와 ⊗]]가 정확히 [[ecdsa-s-cross-term|s의 교차항]]을 채우는 도구로 쓰였습니다.

## 왜 (1+N)^a ≡ 1+aN (mod N²) — 이항정리로 본 동형성

[[Paillier]] 동형암호가 "암호문 위 곱셈"이라는 마법을 부릴 수 있는 이유는, 사실 고등학교에서 배운 **이항정리** 한 줄에서 나옵니다. 이 절에선 그 한 줄을 직접 펼쳐서, 왜 `(1+N)^a ≡ 1+aN (mod N²)`이 성립하는지, 그게 어떻게 ⊗(평문곱)의 작동 원리가 되는지, 그리고 왜 [[sign-service]]의 `TwoPartyPlayer` 생성자에 `while` 루프가 박혀 있는지를 한 줄기로 잇겠습니다.

### 1. 왜 `g = N+1`을 고르나 — 의도된 선택

[[Paillier]] 암호화 식은 일반적으로 이렇습니다 (설명용으로 난수 `r=1` 고정):

```
Enc(m) = g^m · r^N mod N²        // 일반형
       = g^m mod N²              // r=1로 단순화
```

여기서 `g`는 아무거나 쓸 수 있는 게 아니라 **`N²` 위에서 차수가 `N`의 배수**인 원소여야 합니다. 가장 단순하면서 계산이 깔끔한 선택이 바로:

```
g = N + 1
```

> [!note] g = N+1을 고른 이유
> 이 선택은 우연이 아닙니다. `(1+N)^a`를 [[이항정리]]로 펼쳤을 때 **`N²` 이상 항이 mod N²에서 전부 사라지는 구조**가 되도록 의도적으로 설계된 거예요. 그래서 암호화·복호화가 "지수=평문"이라는 직관적인 모양으로 떨어집니다.

이 선택 덕분에 **모든 암호문이 `(1+N)^m` 꼴**이 됩니다. 평문 `m`은 그냥 `(1+N)`의 지수로 들어가 있을 뿐이에요.

### 2. 보조정리 — 이항정리를 직접 펼치기

핵심 등식부터 적고, 왜 성립하는지 한 줄씩 가겠습니다:

```
(1 + N)^a  ≡  1 + aN   (mod N²)
```

[[이항정리]]로 `(1+N)^a`를 펼치면 — `(x+y)^a = Σ C(a,k)·x^(a-k)·y^k` 공식에 `x=1, y=N` 대입:

```
(1 + N)^a  =  Σ_{k=0}^{a} C(a,k)·N^k
           =  C(a,0)·N^0  +  C(a,1)·N^1  +  C(a,2)·N^2  +  C(a,3)·N^3  + ...
           =      1       +      aN      +  C(a,2)·N²   +  C(a,3)·N³   + ...
                                          └──────────────┬───────────────┘
                                                  k ≥ 2  →  N^k 안에 N² 들어있음
```

이제 양변에 **`mod N²`** 를 씌웁니다. `k ≥ 2`인 모든 항은 `N^k = N^(k-2) · N²` 라서 **N²의 배수 → mod N²에서 0**:

```
(1 + N)^a  ≡  1 + aN  +  0  +  0  +  ...   (mod N²)
           ≡  1 + aN                        (mod N²)   ✓
```

> [!tip] 직관 한 줄
> "`(1+N)`을 a번 곱하면 항이 잔뜩 생기는데, mod N²에선 1차항(`aN`)만 살아남고 나머지는 다 죽는다." → 그래서 **지수 `a`가 1차항 계수로 그대로 살아남는다.** 이게 [[Paillier]]가 "지수=평문"으로 동작하는 비결입니다.

### 3. 우리 예시 — `(1+3N)^10` 직접 펼치기

[[Paillier 동형 연산 숫자 예시]] 절에서 `N=143`, `N²=20449`, `cKey = Enc(3) = 1 + 3N = 430`이었죠. sub가 `cKey^10`을 계산해서 `Enc(30)`을 만든 그 단계를 이항정리로 펼쳐봅니다.

`430 = 1 + 3N` 이므로, `(3N)`을 한 덩어리로 보고 이항정리:

```
(1 + 3N)^10  =  Σ_{k=0}^{10} C(10,k)·(3N)^k

  k=0:  C(10,0)·(3N)^0  =  1·1               =  1
  k=1:  C(10,1)·(3N)^1  =  10·3N             =  30N
  k=2:  C(10,2)·(3N)^2  =  45·9·N²           =  405·N²    ← N² 들어감
  k=3:  C(10,3)·(3N)^3  =  120·27·N³         =  3240·N³   ← N³
  ...
  k=10: C(10,10)·(3N)^10 = 1·3^10·N^10        = 59049·N^10
```

**mod N² 취하면 k ≥ 2 항은 전부 0**:

```
(1 + 3N)^10  ≡  1 + 30N   (mod N²)
             =  1 + 30·143
             =  1 + 4290
             =  4291
```

그리고 `4291 = 1 + 143·30 = Enc(30) = Enc(3·10)` ✓

> [!example] 한 눈에 보기
> ```
> cKey       = Enc(3)        = (1+N)^3       = 1 + 3N   = 430
> cKey^10    = ((1+N)^3)^10  = (1+N)^(3·10)  = (1+N)^30
>            ≡ 1 + 30N       (mod N²)         = 4291
>            = Enc(30)       = Enc(3 · 10)   ← key1(3) × 평문 10!
> ```
> sub는 `key1=3`을 **단 한 번도 평문으로 보지 않고** 암호문 `430`을 10제곱했을 뿐인데, 결과는 정확히 `Enc(3·10)=Enc(30)`. 이게 ⊗(평문곱)의 정체입니다.

### 4. 이게 곧 ⊗(평문곱)의 근원

지수 법칙 `(g^a)^b = g^(a·b)`를 [[Paillier]] 암호화에 그대로 적용하면:

```
Enc(a)^b  =  (g^a)^b  =  g^(a·b)  =  Enc(a · b)
```

즉 **암호문을 평문 `b`로 거듭제곱하면 평문이 `a·b`로 곱해집니다.** [[two-party-player.ts]]의 `publicKey.multiply(cipher, scalar)`가 정확히 이 연산이에요. 코드 한 줄로 보면:

```ts
// sub가 평문 key1을 못 본 채로 key1·result2 의 암호문을 만드는 마법
eResult2 = pk1.multiply(cKey, result2)
//        = Enc(key1) ⊗ result2
//        = Enc(key1 · result2)
```

> [!note] ⊕(덧셈)도 같은 원리
> 같은 이항정리로 ⊕도 풀립니다:
> ```
> Enc(a) · Enc(b) = (1+N)^a · (1+N)^b = (1+N)^(a+b) ≡ 1 + (a+b)N = Enc(a+b)
> ```
> 즉 **암호문끼리 곱하면 평문은 더해진다.** ⊗는 거듭제곱, ⊕는 곱셈 — 둘 다 `(1+N)^m` 표현에서 자동으로 나옵니다.

### 5. 왜 `N > nc²` 키 크기 조건이 필요한가 — 생성자 `while` 루프의 정체

여기서 [[sign-service]] 코드의 한 의문이 풀립니다. `TwoPartyPlayer` 생성자(`two-party-player.ts:20-28`)에 이런 루프가 있어요:

```ts
do {
  const keys = generateRandomKeysSync(nc.bitLength() * 2)  // nc의 2배 비트수
  this.publicKey = keys.publicKey
  this.privateKey = keys.privateKey
} while (this.publicKey.n.lte(nc))   // n > nc 조건
```

왜 곡선 차수 `nc`의 **2배 비트수**로 [[Paillier]] 키를 만들고, 조건이 맞을 때까지 재생성할까요?

복호화 직전 평문은 **mod `nc`로 줄이기 전의 정수**입니다. [[Paillier 동형 연산 숫자 예시]]에서 본 그 `dec = 39`를 다시 보면:

```
dec = k2⁻¹·hm + k2⁻¹·r·key1·key2
                       └────┬────┘
                       이 교차항이 최대 nc² 크기까지 커짐
```

`k2⁻¹`, `hm`, `r`은 각각 mod `nc`라 최대 `nc` 정도, 그런데 `key1·key2`는 **두 개의 mod `nc` 수의 곱**이라 최대 `nc²` 크기까지 갑니다. 전체 합도 대략 `nc + nc²` 수준.

> [!warning] N이 작으면 평문이 잘려서 답이 망가진다
> 만약 `N < nc²`라면, 합 `k2⁻¹·hm + k2⁻¹·r·key1·key2`가 복호화 단계에서 **`mod N`으로 잘려 나갑니다.** 그러면 main이 받은 `dec`는 진짜 값이 아니라 잘린 쓰레기 값이 되고, 거기에 `k1⁻¹`을 곱한 `s`도 ECDSA 검증에 실패합니다. 즉 **`N > nc²`** 가 정확성의 필요조건.

그래서:

```
필요한 조건:  N > nc²
비트수로 옮기면:  log₂(N) > 2·log₂(nc)
                 즉:  N의 비트수  >  nc의 비트수 × 2
```

코드의 `nc.bitLength() * 2`가 정확히 이거예요. secp256k1은 `nc ≈ 2²⁵⁶`이므로 `N ≈ 2⁵¹²` 짜리 [[Paillier]] 키를 만듭니다. 하지만 `generateRandomKeysSync(512)`가 항상 정확히 512비트 `N`을 내놓는다는 보장은 없고(소수 두 개의 곱이라 511비트가 나올 수도 있음), 그래서 **`N > nc`가 확실히 만족될 때까지 `while`로 재시도**하는 겁니다.

> [!example] 우리 예시에서도 조건이 지켜짐
> 작은 예시에선 `nc = 11`(곡선 차수), `nc² = 121`, `N = 143`. → `N > nc²` 확인 ✓
> 그래서 복호화 단계의 평문 `39`가 `mod 143`에 안 잘리고 그대로 살아남았고, `mod 11`로 줄이는 건 main이 마지막 단계에서 의도적으로 하는 거예요.

### 6. 한 줄기로 정리

```
g = N+1 선택
     │
     ▼
모든 암호문이 (1+N)^m 꼴
     │
     ▼
이항정리: (1+N)^a = 1 + aN + C(a,2)·N² + ...
     │
     ├─ mod N²로 N² 이상 항 소멸 ──▶ (1+N)^a ≡ 1 + aN
     │
     ▼
지수 법칙으로 ⊗·⊕ 동형성 도출
     ├─ Enc(a)^b = Enc(a·b)  (⊗)
     └─ Enc(a)·Enc(b) = Enc(a+b)  (⊕)
     │
     ▼
교차항 key1·key2 (최대 nc²)를 암호문 위에서 계산 가능
     │
     ▼
하지만 평문이 안 잘리려면  N > nc²
     │
     ▼
생성자 while 루프: nc.bitLength() * 2 비트로 키 생성, 조건 충족까지 재시도
```

> [!tip] 한 줄 요약
> `g=N+1`은 **이항정리에서 `N²` 이상 항이 mod N²로 깨끗이 죽도록** 의도적으로 고른 값이고, 그 결과 `(1+N)^a ≡ 1+aN`이 성립해 [[Paillier]]가 "지수=평문" 구조가 됩니다. 이게 ⊗(평문곱)의 근원이고, 교차항 `key1·key2`(최대 `nc²` 크기)를 잘리지 않고 처리하려면 `N > nc²`가 필수 — 그래서 [[sign-service]] 생성자의 `while` 루프가 곡선 차수의 2배 비트수로 키를 재생성하며 이 조건을 보장합니다. 수학적 우아함과 코드의 한 줄이 정확히 같은 이유를 가리키고 있어요.

## English

### TL;DR

> [!tip] One-paragraph summary
> The heart of [[ECDSA]] 2PC + [[Paillier]] is **multiplicative splitting**. The private key `x = key1·key2` and the one-shot nonce `k = k1·k2` are shattered across two servers (main/sub). The public key `Q = x·G` and the signature's `r = (k·G).x` recombine via **point multiplication** alone (the discrete log keeps scalars hidden even when points travel). The only sticking point is the `r·key1·key2` **cross-term** inside `s = k⁻¹·(hm + r·x)` — main's `key1` and sub's `key2` must be multiplied without either side seeing the other's plaintext. That single line is handled by [[Paillier]] homomorphic encryption: main sends `Enc_pk1(key1)`, sub multiplies its own `key2` **on top of the ciphertext** (`⊗`), folds in the `k2⁻¹·hm` term via homomorphic addition (`⊕`), and returns partial-S; main decrypts and multiplies by `k1⁻¹` to finalize `s`. Net result: **neither `x` nor `k` ever exists in one place**, sub never sees `key1` in plaintext, and main never sees `key2` or `k2`.

### ECDSA Fundamentals — G, n, Private Key x, and Public Key Q

All of [[ECDSA]]'s magic rests on one foundation: **a group of points on an elliptic curve**, and **scalar multiplication** on that group. Whether it's 2PC splitting or [[Paillier]] homomorphic operations, that's the layer underneath. This section pins down what `G` and `n` are on the [[secp256k1]] curve, why scalar multiplication and the [[ECDLP|elliptic-curve discrete-log problem]] make a key pair safe, and how the "private key `x`" and "public key `Q`" aren't pulled out of thin air but defined very naturally.

### 1. The Curve and Its Group

This sign-service uses [[secp256k1]], the same curve as Bitcoin and Ethereum. The code entry point is one line (`ec.ts:8-9`):

```ts
import { ec as EC } from 'elliptic'
const ec = new EC('secp256k1')
export const G = ec.g     // generator
export const n = ec.n     // order
```

The "points" on the curve form a **group** under a special addition rule. You can forget the curve equation itself (`y² = x³ + 7 mod p`) and just think of it as **a world where "point + point = point" is defined**.

> [!note] Three things to know
> - **`G` (generator)** — a fixed, publicly agreed-upon point on the curve. The "starting point".
> - **`n` (order)** — the smallest positive integer such that `n·G = O` (the point at infinity, the identity). On secp256k1, `n ≈ 2²⁵⁶`, a prime.
> - **Scalar multiplication `k·G`** — `G + G + … + G` (k times). Not numeric multiplication, but the curve's point-addition repeated k times.

Saying `n` is the order means **"all scalar arithmetic happens mod n"**. `(n+1)·G = 1·G`, `(n+2)·G = 2·G` — exponents wrap. So every `mod n` you see in ECDSA traces back to this periodicity.

### 2. Scalar Multiplication as a One-Way Function

The real foundation of the crypto is this asymmetry:

```
Know k → compute k·G:   easy ✅   (microseconds, even for 256-bit k)
See k·G  → recover k:    infeasible ❌   (Elliptic Curve Discrete Log Problem)
```

Multiplication is fast; its inverse ("given the point, figure out how many G's were added") is **exponentially hard**. That's the [[ECDLP]], the **Elliptic Curve Discrete Logarithm Problem**. On secp256k1, the best known algorithm needs roughly `2¹²⁸` operations. The universe ends first.

> [!tip] Analogy
> Mixing two paint colors is easy; separating a mixed color back into its original ratios is essentially impossible. `k → k·G` is the mixing direction; `k·G → k` is the separation direction.

This single asymmetry is what makes the whole edifice of public-key crypto possible — **"a result computed from a secret can be published without leaking the secret"**.

### 3. Private Key `x` — Just a Random Large Integer

The private key isn't anything exotic. It's **one integer, picked uniformly at random from 1 to `n−1`**. The code does exactly that (`two-party-player.ts:39-41`):

```ts
private generateKey() {
  return new BN(randomBytes(n.byteLength() / 2))   // just a big random number
}
```

With a tiny illustrative number:

```
x = 27   ← the private key. A 256-bit integer in real life. Never published.
```

> [!warning] The private key is literally "just a number"
> Not a password, not a seed phrase. **One integer.** Seed phrases (BIP39) and keystores are just packaging used to derive or store this integer `x`.

### 4. Public Key `Q` — A Point Built From `x`

The public key is the point you get by adding `G` to itself `x` times.

```
Q = x · G
```

If `x=27`, then `Q = 27·G`. In this sign-service, one shard's public-key computation is exactly this line (`two-party-player.ts:59-61`):

```ts
public returnPartialQ(): curve.base.BasePoint {
  return G.mul(this.key)     // Q(shard) = key · G
}
```

`Q` is a point on the curve, so it's an `(x_Q, y_Q)` coordinate pair; serialized it becomes 65 bytes (uncompressed) or 33 bytes (compressed) hex. An [[EVM]] wallet address is the keccak256 hash of `Q`, truncated to its last 20 bytes.

### 5. The Pair — Easy One Way, Impossible the Other

Now it's clear why it's called a key "pair":

```
Private x  ──── x·G ────►  Public Q     (forward: easy)
Public  Q  ──── ???? ────►  Private x   (backward: ECDLP, infeasible)
```

| Key | What it is | Who sees it | Role |
|---|---|---|---|
| `x` | A random large integer | Only the owner (or in 2PC, nobody as a whole) | **Create signatures** |
| `Q = x·G` | A point on the curve | Anyone, by design | **Verify signatures** |

> [!example] Where the two meet — in signing & verifying
> The signer builds `s = k⁻¹·(hm + r·x)` with the secret `x`. The verifier builds `P = u1·G + u2·Q` with the public `Q`. When you expand the verification identity, substituting `Q = x·G` pulls `x` into the equation, the two sides line up on the curve, and the signature verifies — **without `x` ever being transmitted**. (Full derivation in the [[서명식의 의미 — r, s가 왜 그 꼴인가|next section]].)

### 6. The Bridge to 2PC

One last step in this section. Split `x = key1 · key2 (mod n)`, and in [[two-party-player.ts|two-party-player]] the public key is assembled like this:

```
main: partialQ = key1·G                       ← only main knows key1
sub:  Q = partialQ · key2 = (key1·key2)·G    ← only sub knows key2
                          = x·G              ✓ a normal ECDSA public key
```

> [!note] The point — the number `x` has never existed anywhere
> The two shards `key1` and `key2` are stored in different server DBs, each encrypted with [[AWS KMS]]. But **their product (the real private key `x`) was never materialized, not even in memory.** Thanks to scalar-multiplication associativity (`(key1·key2)·G = key2·(key1·G)`), the shards combine only on the curve to produce `Q`. Even if one server is fully compromised, it can neither sign alone nor recover `x`.

With this in hand, the rest follows naturally — the meaning of `r` and `s` ([[서명식의 의미 — r, s가 왜 그 꼴인가]]), the verification identity ([[검증 메커니즘 — u1, u2, P]]), and why the cross-term in `x = key1·key2` forces us to bring in [[Paillier]] ([[Paillier가 등장하는 지점 — s 계산의 교차항 문제]]).

### What the signing equation means — why r and s take that shape

ECDSA's `(r, s)` is not two arbitrary numbers but **two pieces that together form a proof**. The signer is saying to the verifier:

> [!note] What a signature actually claims
> "I know the secret `x` corresponding to public key `Q`, and I know it **for this specific message** `hm`. But I will never reveal either `x` or `k`."

Like a standard zero-knowledge proof, this has a **commit → response** structure. Viewing r and s through that lens makes their roles fall into place.

## r — "x-coordinate of a one-time ephemeral public key" = the commitment

For each signature the signer draws a fresh nonce `k` and forms the point `R = k·G`. `R` is effectively **the public key of an ephemeral keypair used only for this one signature** (`k` is the ephemeral private key, `R` the ephemeral public key). `r` is just its x-coordinate:

```
r = R.x mod n = (k·G).x mod n
```

Semantically, `r` is **"a public commitment to which nonce k I chose this round"** — i.e. the [[ecdsa-commitment-r|commitment]].

- `k` itself stays secret forever (leaking it leads to [[private-key-x-vs-nonce-k|immediate private-key recovery]]).
- Only its trace `r` is published, locking in "I chose this nonce."
- Later, when the verifier reconstructs the commitment (`P = u1·G + u2·Q`), the authenticity check is whether that point's x-coordinate matches `r`.

> [!tip] Why only the x-coordinate, not the whole point
> Two reasons. (1) To compress the signature to 256 bits. (2) Historical DSA-lineage design choice. The essential information sits in the x-coordinate, and the verification equation closes on a single x-coordinate comparison. (Since two points share each x-coordinate, EVM keeps `v` as a recovery hint — [[ecdsa-v-recovery]].)

## s — "a seal binding secret, message, and commitment" = the response

```
s = k⁻¹ · (hm + r·x)   mod n
```

This one line bundles **three things**, each playing a distinct role:

| Piece | Semantic role | If removed? |
|---|---|---|
| `hm` | **What** was signed (message binding) | Same signature reusable on any message (forgery) |
| `r·x` | **Who** signed it (identity binding) + coupling to the commitment | Without `x`, anyone could sign; without `r`, no link to the commit, verification can't close |
| `k⁻¹` | **Blinding + one-time-ness** | Without it, `x` leaks directly; same message would yield same signature every time |

> [!note] One-line meaning
> `s` = "my secret `x`, tied to this commitment `r` and this message `hm`, blinded by the one-time nonce `k`." All three are sealed into one expression so that altering any one breaks `s`.

## Why *exactly* this shape — reverse-engineered so (hm + r·x) cancels in verification

The form of `s` isn't arbitrary; it's forced backwards by the constraint that **the verifier must be able to reconstruct `r` (the commitment) from public values alone.**

The verifier has only `Q, hm, r, s`. They build [[ecdsa-verification-u1-u2-P|coefficients u1, u2 and a point P]]. Expanding P using `Q = x·G`:

```
P = u1·G + u2·Q
  = (hm·s⁻¹)·G + (r·s⁻¹)·Q
  = (hm·s⁻¹)·G + (r·s⁻¹)·(x·G)      ← substitute Q = x·G
  = s⁻¹·(hm + r·x)·G                  ← factor out G
```

If the signer chose `s = k⁻¹·(hm + r·x)`, then `s⁻¹ = k·(hm + r·x)⁻¹`, and:

```
P = k·(hm + r·x)⁻¹·(hm + r·x)·G
  = k·G
  = R                                  ← the signer's commitment, exactly resurrected
```

> [!example] The heart of the reverse-engineering
> Bundle `(hm + r·x)` as **one multiplicative block** and prepend `k⁻¹`. Then in verification, multiplying by `s⁻¹` makes `(hm + r·x)` **cancel cleanly as a whole**, leaving only `k`, which yields `k·G = R`. Any other shape (e.g. `hm + r·x⁻¹`, or `k·(hm + r·x)`) breaks this cancellation and the verification equation no longer closes.

One ASCII line makes it crisp:

```
Signer:    s = k⁻¹ · (hm + r·x)         ← locked with secret x
Verifier:  P = s⁻¹ · (hm + r·x) · G     ← unlocked with public Q
                     └ cancels ┘
           P = k·G = R   →   P.x == r ?
```

The secret `x` hides inside `Q` as a point, the bundle `(hm + r·x)` meets `s⁻¹` in verification and dissolves — **so the verifier confirms "this person knows `x`" without ever seeing `x`**.

## Roles of each term, paired with the verification side

| Term in s | Job at signing time | Counterpart on the verification side |
|---|---|---|
| `hm` | Message binding | `u1 = hm·s⁻¹` → multiplied with `G` in `u1·G` |
| `r·x` | Identity + commitment binding | `u2 = r·s⁻¹` → multiplied with `Q (= x·G)` in `u2·Q` |
| `k⁻¹` | Blinding / one-time-ness | Unwound by `s⁻¹` and ultimately returns as `k` in `P = k·G` |

Intuitively:
- `hm` lands on the `G` side (the public anchor),
- `r·x` lands on the `Q` side (the point with the hidden secret),
- `k⁻¹` is unwound by `s⁻¹` and reverts to `k` — each finds its place in verification.

## It's not the *only* possible shape — contrast with Schnorr

This multiplicative/inverse form is an ECDSA (DSA-lineage) choice, not a fundamental requirement of signatures. [[schnorr-vs-ecdsa|Schnorr signatures]] express the same meaning (commit + binding + blinding) far more linearly:

```
ECDSA:    s = k⁻¹·(hm + r·x)              ← multiplication & inverse, nonlinear
Schnorr:  s = k + e·x   (e = H(R, m))     ← purely additive, linear
```

> [!warning] This shape is exactly what makes 2PC hard
> ECDSA's `k⁻¹·(...)` multiplicative form, once split for 2PC, becomes `(k1·k2)⁻¹·(hm + r·key1·key2)`, surfacing a **`key1·key2` cross-term**. Computing that without exchanging plaintext secrets is precisely why [[paillier-homomorphic-encryption|Paillier homomorphic encryption]] is dragged in. With Schnorr, only addition would be needed and multi-party signing would be far simpler — **the root reason this sign-service needs Paillier at all is the multiplicative shape of `s`.**

## Summary

- **r** = "public commitment to the one-time nonce `k` for this signature" — the x-coordinate of the ephemeral public key `R = k·G`.
- **s** = "my secret `x`, bound to commitment `r` and message `hm`, blinded by `k`" — message / identity / one-time-ness sealed into a single expression.
- **Why that shape** = because the verification equation must reconstruct the commitment `R = k·G`. The form is reverse-engineered so that when `s⁻¹` is multiplied in, **`(hm + r·x)` cancels as a single block**, leaving exactly `k·G`. Any other shape breaks that cancellation and verification no longer closes.

### Verification Mechanics — u1, u2, P

The verifier has only **four public values** in hand: the public key `[[Q]]`, the message hash `[[hm]]`, and the signature `(r, s)`. They know neither `[[x]]` nor `[[k]]`. The whole job is to assemble one point from these inputs and check whether it matches the signer's commit `R = k·G`. That assembly is where `u1`, `u2`, and the resulting point `P` show up.

### u1, u2 — Two Scalars the Verifier Applies to G and Q

The definitions are simple:

```
u1 = hm · s⁻¹   (mod n)
u2 = r  · s⁻¹   (mod n)
```

- `hm`, `r`, `s` are all public → the verifier computes these alone.
- `s⁻¹` isn't division but the **modular inverse** — the integer satisfying `s · s⁻¹ ≡ 1 (mod n)`. Always computable via the extended Euclidean algorithm (`.invm(n)` in [[ec.ts]]).

> [!note] What u1 and u2 mean semantically
> - **`u1`** = "how much weight goes on **G** itself" — the share coming from message hash `hm`
> - **`u2`** = "how much weight goes on **Q** (=the hidden x)" — the share coming from commit `r`
>
> Both carry `s⁻¹`, whose job is to "undo" the `k⁻¹` the signer baked into s.

### k = u1 + u2·x — Where the Shape Comes From

Solving the definition of `s` backwards for `k` reveals the identity of u1 and u2:

```
s    = k⁻¹·(hm + r·x)
k·s  = hm + r·x                  ← multiply both sides by k
k    = s⁻¹·(hm + r·x)            ← multiply both sides by s⁻¹
k    = s⁻¹·hm + s⁻¹·r·x          ← distribute
k    = (hm·s⁻¹) + (r·s⁻¹)·x
       └──┬──┘    └──┬──┘
          u1         u2
k    = u1 + u2·x                 ★
```

> [!tip] The key one-liner
> The real `k` **decomposes as `u1 + u2·x`**. The verifier doesn't know `x` and can't compute that as a number — but **swap `x` for the point `Q = x·G` and the same computation works on the curve**.

### P — Multiply Both Sides by G and Substitute x·G = Q

Multiply both sides of ★ by the point `G` (the equation stays valid; point multiplication distributes):

```
k·G = (u1 + u2·x)·G
    = u1·G + u2·x·G            ← distribute
    = u1·G + u2·(x·G)          ← associate: (u2·x)·G = u2·(x·G)
    = u1·G + u2·Q              ← substitute x·G = Q (public-key definition)
```

This is exactly how the verifier's reconstructed point `P` is defined:

```
P  ≜  u1·G + u2·Q
```

If the signature is honest, the chain above gives `P = k·G = R`. In other words:

```
┌─────────────────────────────────────────────────────────┐
│   Signer's commit       R = k·G                          │
│              ‖ (same point)                              │
│   Verifier's rebuild    P = u1·G + u2·Q                  │
└─────────────────────────────────────────────────────────┘
```

> [!example] How can u2·Q equal u2·(x·G) if the verifier doesn't know x?
> Scalar-multiplication associativity: `u2·Q = u2·(x·G) = (u2·x)·G`. The verifier doesn't know the integer `x`, but they hold `Q`, which is G scaled by exactly that integer. On the curve, "stretch by x, then by u2" lands on the same point as "stretch the x·G bundle u2 times." This is another face of the asymmetry that [[discrete-log]] hands you.

### The Verification Check — P.x == r ?

What the verifier actually runs is three lines:

```
1. u1 = hm·s⁻¹ mod n,  u2 = r·s⁻¹ mod n
2. P  = u1·G + u2·Q                       ← assemble point from public values only
3. P.x mod n == r ?                       ← compare its x-coordinate
       match     → signature valid ✓
       mismatch  → forgery ✗
```

| Input | Source | Secret? |
|---|---|---|
| `Q` | public key | ❌ public |
| `G` | secp256k1 constant | ❌ public |
| `hm` | message hash | ❌ public |
| `r`, `s` | the signature | ❌ public |
| `x`, `k` | — | ✅ never used |

> [!warning] r is both an input and the answer key
> `r` enters **as an input** when building u2 (`u2 = r·s⁻¹`) **and** as the **comparison target** at the end (`P.x == r`). The check is really a self-consistency loop: "fed-in r → recovered r". Only an honest signature closes that loop.

### Intuition — In One Sentence

> [!note] What verification really is
> The verifier takes the `x` that is "hiding" inside the **public key `Q`** and, without ever pulling it out as a number, **reconstructs the signer's one-shot commit `R = k·G`** purely on the curve. `s` acts as the cancellation device: only an **honest signer's** `(r, s)` makes this reconstruction close cleanly so that `P.x = r`.

That's why [[ECDSA]] sits in the same family as zero-knowledge proofs: **no secret enters the verification path at any point**. Secrets are used only during signing; verification is 100% public values. So anyone, anytime, can verify without the signer's cooperation — which is the very definition of a public-key signature.

> [!tip] The same check holds in [[2PC]]
> Whether the signature was produced by two cooperating servers (main + sub) or by one, the result `(r, s)` is just an ECDSA signature. The on-chain verifier (an Ethereum node, MetaMask, etc.) neither knows nor needs to know about the split. The [[Paillier]] magic lives entirely on the **signing** side; the verification equation `P = u1·G + u2·Q` is unchanged.

### Secret Safety — What if G/k/x Leaks?

The values we've used so far have **wildly different security grades**. They look like a uniform set of "crypto values," but in reality some are public by design and others end the game the moment they slip out. Let's separate them.

### 1. G — there's no such thing as "leaking" it; it's a public constant

[[G]] is not secret. It's a **public constant baked into the [[secp256k1]] standard, identical across the entire world** — Bitcoin, Ethereum, this [[sign-service]] all use the same G. The code just pulls it from a library (`ec.ts:9`):

```ts
export const G = ec.g;   // anyone knows this
```

Security does not come from "not knowing G." It comes from **not being able to reverse `Q = x·G` to recover `x`** — the hardness of [[Discrete Log Problem (ECDLP)]]. G was designed for full public exposure from day one.

> [!note] Lock analogy
> The **brand** of the lock (G) can be public — the secret is the **key** (x), not the model name. Billions of keypairs share the same G worldwide, yet each `x` is independent.

### 2. k — leak it once and the private key is instantly recovered

The [[ephemeral nonce k]] is the polar opposite. **If `k` leaks, the private key `x` falls out in one line.**

Recall the signing equation:
```
s = k⁻¹·(hm + r·x)
```
The attacker already sees `s, r, hm` from any signature (all public). Add `k` and there's only one unknown left — `x`:

```
s · k       = hm + r · x          (multiply both sides by k)
s · k − hm  = r · x
x = r⁻¹ · (s · k − hm)   (mod n)  ← private key, done
```

> [!warning] k leak = private key leak
> One signature + one leaked `k` and the attacker holds the `x` needed to **forge every future transaction from that wallet.** No recovery — only moving the funds out before they do.

### 2-1. The scarier variant — even *reusing* `k` is fatal

Even if `k` itself never leaks, **signing twice with the same `k`** lets the attacker subtract the two equations to recover `k`, and then `x`. Since `r = (k·G).x`, reusing `k` means `r` repeats too — that's the giveaway:

```
sig1:  s1 = k⁻¹·(hm1 + r·x)
sig2:  s2 = k⁻¹·(hm2 + r·x)     ← same k ⇒ same r
────────────────────────────────
s1 − s2 = k⁻¹·(hm1 − hm2)
   ⇒  k = (hm1 − hm2) · (s1 − s2)⁻¹   (mod n)
   ⇒  then the x-recovery line above
```

### 2-2. Real incidents — [[Sony PS3 incident]] and early Android wallets

> [!example] 2010, Sony PlayStation 3
> [[fail0verflow]] reverse-engineered PS3 firmware signatures and discovered that Sony had **embedded the same constant `k` in every signature.** Applying the two-equation subtraction above, they **recovered Sony's master ECDSA private key wholesale.** From that point on, anyone could sign their own code as if it came from Sony.

> [!example] 2013, Android Bitcoin Wallets
> A flaw in Android's `SecureRandom` implementation caused some wallet apps to **emit duplicate `k` values.** Two transactions from the same address sharing a `k` ended up on a public ledger; attackers scanned for the pattern, extracted `x`, and drained the coins. The whole thing was independently verifiable on-chain.

That's why the code generates a **fresh random `k` on every signature** (`two-party-player.ts:47-49`):

```ts
public createRandomK() {
  this.k = new BN(randomBytes(n.byteLength() / 2)).umod(n);  // new randomness each time
}
```

### 3. And this service (2PC) defuses the `k` risk one level deeper

Here's another payoff of [[2PC ECDSA]]. In a regular wallet, one server holds the entire `k`. In [[sign-service]], **`k` itself is multiplicatively split**:

```
k = k1 · k2         (k1 only on main, k2 only on sub)
```

- Even if main's RNG breaks and `k1` leaks or repeats, **without sub's `k2` the attacker cannot reconstruct the real `k`.**
- A full takeover of one server only exposes its share (`k1` or `k2`) → private key still unrecoverable.
- sub's `k2` lives in [[Redis]] under `(walletAddress, randomRequestId)` **only until partial-S is computed**, then is discarded — structurally preventing cross-session reuse (`return-partial-r.usecase.ts`, `return-partial-s.usecase.ts`).

> [!tip] Why "multiplicative split" is the decisive trick
> RNG flaws usually originate on **one** system (a library, an OS, a driver). If one server alone produces `k`, that one flaw is a private-key leak. With a multiplicative split, both servers' RNGs would have to fail **in the same way at the same moment** to reproduce a `k` — and they're different hosts, different seeds, different processes, effectively independent. A unilateral RNG failure on one side cannot, by itself, trigger the PS3/Android attack pattern.

### 4. At a glance — what is secret, what is public

| Value | If leaked? | Why |
|---|---|---|
| **G** | Fine ✅ | Public constant by design. Security rests on [[Discrete Log Problem (ECDLP)]] hardness, not on G |
| **Q** (public key) | Fine ✅ | Public by design. `Q → x` is infeasible |
| **r, s, hm** | Fine ✅ | Part of the signature/message; must be public for verification |
| **k** (nonce) | Catastrophic ❌ | One leak or reuse → `x` recovered in a single line |
| **x** (private key) | Game over ❌ | Literally the private key |

> [!note] Bottom line
> **The only values that must stay secret are `x` and `k`** — G·Q·r·s·hm can all be public. And [[sign-service]]'s 2PC design splits **both** `x` and `k` so neither ever assembles in one place, ensuring that **compromising a single server cannot recover either one.**

### 2PC split — combining x = key1·key2 and k = k1·k2

We now split single-signer ECDSA across two servers (main = player1, sub = player2). One design choice drives everything: **split multiplicatively, not additively.**

```
x = key1 · key2   (mod n)        ← the real private key. Never assembled anywhere.
k = k1   · k2     (mod n)        ← same for the one-shot nonce.
```
- main holds `key1, k1`
- sub holds `key2, k2`
- the products `x` and `k` are known **to no one**

> [!note] Why multiplicative?
> Additive splits (`x = a+b`) are possible too. But ECDSA's `s = k⁻¹·(hm + r·x)` already contains a **product** term, so a multiplicative split lines up cleanly with both point multiplication and [[paillier-homomorphic]]'s plaintext-scalar multiply.

### The public key Q combines via point multiplication

The public key is built without ever assembling plaintext `x` — just two stages of point multiplication (`two-party-player.ts:59-66`):

```
main: partialQ = key1 · G              ← main multiplies in only its key1
       ───────► sends the point to sub
sub : Q        = key2 · partialQ
              = key2 · (key1 · G)
              = (key1·key2) · G
              = x · G       ✓
```

Key point: **the scalar `x = key1·key2` is never formed.** The two shares meet only as a point on the curve. Both servers compute `Q` independently and check they agree before storing it (`create-signer.usecase.ts`).

> [!tip] Associativity of scalar multiplication does the work
> `key2 · (key1·G) = (key2·key1) · G` — scalar multiplication on the curve is associative, so it doesn't matter who multiplies first; the resulting point is the same. That's why a multiplicative split combines naturally on the curve.

### r is built by "receiving k2·G and multiplying your own k1 onto the point"

The r-generation step mirrors public-key combination exactly (`returnPartialR`, `returnR` — `two-party-player.ts:71-84`):

```
main: fresh k1 →  holds k1·G
sub : fresh k2 →  responds with k2·G
                          ───────►
main: R = k1 · (k2·G) = k1·k2·G = k·G
      r = R.x mod n           ✓
```

This single line carries half of 2PC. **main has never seen sub's plaintext `k2`, and doesn't need to.** What crossed the wire is the point `k2·G`, not the scalar `k2`.

```
┌─────────────┐                       ┌─────────────┐
│   main      │                       │     sub     │
│  key1, k1   │                       │  key2, k2   │
└─────────────┘                       └─────────────┘
       │     POST /v1/signer/get-part-r       │
       │ ───────────────────────────────────► │
       │            ◄─── k2·G ─────           │
       │                                      │
       │ r = (k1·(k2·G)).x                    │
       │                                      │
```

### Why not knowing the other side's k is fine — discrete log hides it

This is the spot where intuition fights you. The decisive fact is [[ecdlp-discrete-log]]:

```
know k2  →  computing k2·G:   easy ✅
see k2·G →  recovering k2:    infeasible ❌  (n ≈ 2²⁵⁶)
```

> [!warning] This is a security feature, not a bug
> main *not* knowing sub's `k2` is **intentional, not inconvenient**. If main knew the full `k = k1·k2`, the published `(r,s)` would instantly leak the private key via `x = r⁻¹·(s·k − hm)`. So `k`, like `x`, must never gather in one place — and 2PC enforces that **structurally**.

A picture for the intuition:

> [!example] Locked-box analogy
> sub sends a locked box (`k2·G`). main can't see the number inside (`k2`), but can scale the whole box by its own factor (`k1`). The result is a box that holds exactly `k1·k2` — that's `R = k·G`, and `r` is its x-coordinate.

### Terms that combine on the curve vs. terms that must combine as scalars

This is where the multiplicative split works **for free**. To summarize:

| What must combine | How | Paillier needed? |
|---|---|---|
| `Q = key1·key2·G` | Pure point multiplication (sub multiplies key2 onto main's point) | ❌ |
| `R = k1·k2·G` (→ `r`) | Pure point multiplication (main multiplies k1 onto sub's point) | ❌ |
| `s = (k1·k2)⁻¹·(hm + r·key1·key2)` | **Scalar product `key1·key2` appears inside numbers** | ✅ |

> [!note] Why s is the only tricky one
> `Q` and `r` end up as **points**, so multiplying one side's plaintext scalar onto the other side's point closes the deal. `s` lives in `mod n` as a number, with `key1·key2` as a raw product of two plaintexts. The "disguise the scalar as a point" trick no longer applies — and that's exactly what pulls in the [[paillier-homomorphic|Paillier homomorphic encryption]] in the next section.

Bottom line: **the multiplicative split makes `Q` and `r` combine via the associativity of point multiplication alone, and discrete log keeps each side's scalar hidden behind its point.** Everything except the single line for `s` — and that one line is what motivates everything in the next section.

### Where Paillier Enters — The Cross-Term Problem in Computing s

In [[ECDSA]] 2PC, everything up to `r` is handled by [[elliptic curve point multiplication]] alone. The real wall is `s`. In that one line, **exactly one term** refuses plaintext exchange, and that single term is what drags [[Paillier]] into the picture.

### 1. Rewriting s with Split Secrets

The original [[ECDSA]] `s`:
```
s = k⁻¹ · (hm + r·x)
```

In 2PC we have `x = key1·key2` and `k = k1·k2` (multiplicative split), so substitute:
```
s = (k1·k2)⁻¹ · (hm + r · key1·key2)
  = k1⁻¹ · k2⁻¹ · (hm + r · key1·key2)
```

Lay out a "who knows what" table per term and the bottleneck pops out:

| Term | Secrets inside | main (key1, k1) | sub (key2, k2) | Plaintext exchange OK? |
|---|---|---|---|---|
| `hm` | (none, public) | ✓ | ✓ | irrelevant (public) |
| `r` | (none, public) | ✓ | ✓ | irrelevant (public) |
| `k1⁻¹` | k1 | ✓ alone | ✗ | just don't send it |
| `k2⁻¹` | k2 | ✗ | ✓ alone | just don't send it |
| `r · key1·key2` | **key1 + key2** | key1 only | key2 only | ❌ **must be multiplied together** |

> [!warning] The choke point
> The `key1·key2` cross term — main has only `key1`, sub has only `key2`, yet they must multiply. Exchanging them as plaintext **immediately leaks the private key `x = key1·key2`**.

`hm` is public, `r` is public, and `k1⁻¹`/`k2⁻¹` are each multiplied in by their owner during their own step (see [[k is fine for neither party to know]]). **The single wall is the `key1·key2` cross term: "I must multiply your secret with mine, but plaintext is off-limits."**

### 2. Why the Point-Multiplication Trick Doesn't Help Here

For `r`, the [[discrete log problem]] saved us — sending the point `k2·G` revealed nothing about `k2`, and main just multiplied that point by its own `k1`. But `s` is **just an integer equation** — multiplication in `mod n`, not on the curve. If you lift it to the curve, the result becomes a point, not the scalar `s` we need.

> [!note] The key difference
> - `r`: curve-side operation → [[ECDLP]] hides the secret → no plaintext exchange needed
> - `s`: integer multiplication and inverse → can't be lifted to the curve → **needs a different "multiply-while-encrypted" tool**

[[ECDSA]]'s `k⁻¹·(hm + r·x)` shape — multiplications and a modular inverse — is what creates this difficulty. [[Schnorr signatures]] use `s = k + e·x`, an **additive** shape that makes multiparty signing far easier with no Paillier-like tool needed. The price [[ECDSA]] pays for choosing the multiplicative/inverse form gets billed precisely on this one line.

### 3. Paillier's Two Superpowers

[[Paillier]] is a [[partially homomorphic encryption]] scheme that supports **two operations on ciphertexts**:

```
┌─────────────────────────────────────────────────────────────┐
│  ① Additive (⊕):  Enc(a) ⊕ Enc(b) = Enc(a + b)              │
│     concretely:   multiply the ciphertexts  (c1 · c2 mod N²)│
│                                                              │
│  ② Plaintext scalar (⊗):  Enc(a) ⊗ b = Enc(a · b)            │
│     concretely:           raise ciphertext to b  (c^b mod N²)│
└─────────────────────────────────────────────────────────────┘
```

The code surfaces these directly (`apps/sign-service/.../two-party-player.ts`):

```ts
publicKey.addition(c1, c2)     // ⊕  ciphertext + ciphertext → enc of plaintext sum
publicKey.multiply(c, scalar)  // ⊗  ciphertext + plaintext scalar → enc of plaintext product
```

> [!tip] What each superpower buys you
> - With ⊕: `Enc(A) ⊕ Enc(B) = Enc(A+B)` → **two parts can be combined while still encrypted**.
> - With ⊗: `Enc(key1) ⊗ (k2⁻¹·r·key2) = Enc(k2⁻¹·r·key1·key2)` → sub can **multiply its own plaintext into `key1` without ever seeing `key1` in the clear**.

These two are exactly enough to unblock `s`. main pre-encrypts its `key1` under its own [[Paillier]] public key and sends that ciphertext to sub; sub uses ⊗ to fold its plaintext into the cross term, ⊕ to add the `k2⁻¹·hm` piece, and returns `Enc(k2⁻¹·hm + k2⁻¹·r·key1·key2)`. main decrypts with its [[Paillier]] private key, multiplies by `k1⁻¹`, and `s` is done.

### 4. Why This Stays Secure — Asymmetric Key Placement

```
┌────────── main ──────────┐         ┌────────── sub ───────────┐
│  ECDSA:   key1, k1       │         │  ECDSA:   key2, k2       │
│  Paillier: pk1, sk1 ✓    │         │  Paillier: pk1 only (✗sk1)│
│  ─────────────────────   │         │  ─────────────────────   │
│  Make Enc(key1), send    │ ──cKey─▶│  Apply ⊗ / ⊕ to cKey      │
│                          │◀─partialS│  Return ciphertext        │
│  Decrypt with sk1 → ·k1⁻¹│         │  (decryption forever      │
│                          │         │   impossible)             │
└──────────────────────────┘         └──────────────────────────┘
```

> [!note] The asymmetry that makes it work
> The [[Paillier]] **private key `sk1` lives only on main**. sub holds the [[Paillier]] public key `pk1` and can do ⊕/⊗ all day, but **can never decrypt**. So whatever sub does to `Enc(key1)`, it never sees `key1`.

Notice two **orthogonal axes** at play here:
- [[ECDSA]] keys are **split** across the two servers (symmetric — each holds a share),
- [[Paillier]] keys are **concentrated** on main (asymmetric — sub gets only the public half).

This combination lets sub touch main's secret only inside the Paillier "vault," while main, even with `sk1`, can't isolate `key2` or `k2` from the decryption output (both are entangled in one expression).

### 5. Bridge to the Next Section

Putting it together:

> [!example] Per-term strategy for s = (k1·k2)⁻¹·(hm + r·key1·key2)
> - `hm`, `r` → public, use as-is
> - `k1⁻¹`, `k2⁻¹` → each party multiplies its own in during its own step
> - `key1·key2` cross term ← **[[Paillier]] is invoked here and only here**
>   - ⊗ lets sub multiply its plaintext into a still-encrypted `key1`
>   - ⊕ stitches the partial sums together
>   - Final decryption is performed by main, who alone holds `sk1`

The next section ([[sign-service 실제 흐름 — 저장과 서명 오케스트레이션]]) shows exactly how these ⊕/⊗ operations are wired through `returnCKey` → `returnPartialS` → `returnS`, and after that [[Paillier 동형 연산 숫자 예시 — N=143으로 따라가기]] walks the integers — e.g. why a raw exponentiation like `430¹⁰` turns into `Enc(plaintext product)`.

### sign-service in practice — storage & signing orchestration

This section grounds all the math in **two servers** and **two databases**. The core property is simple: **the full private key never lives in one place, and a signature is produced by two HTTP round-trips.**

### A. What the DB stores — "one shard," re-locked by KMS

The `Wallet` schema is surprisingly mundane (`prisma/schema.prisma:18-29`):

```prisma
model Wallet {
  address    String
  network    String
  publicKey  String   // Q (public-key point, hex)
  privateKey Bytes    // ⚠️ "ONE shard" encrypted under KMS
}
```

Two things matter most here:

> [!warning] The `privateKey` column is **not the private key — it's half of it**
> - The **main server's DB** holds only `key1`; the **sub server's DB** holds only `key2`. The two DBs are physically separated and sub uses a different connection via `.sub.env`.
> - The real private key `x = key1 · key2` has **never** existed whole — in any DB, in any memory, at any instant.
> - So even a full dump of main's DB yields only `key1` → no signing, no recovery of [[ecdsa-private-key-x]].

And **even that shard** isn't plaintext: it's wrapped once more with AWS [[kms-envelope-encryption]] (`key.repository.ts:77-94`):

```ts
const encrypted = await this.kmsService.encrypt(key);   // AWS KMS call
privateKey: Buffer.from(encrypted.CiphertextBlob),      // DB stores ciphertext only
```

- The unwrap key lives inside AWS KMS (`AWS_KMS_KEY_ID`); decrypting requires IAM permission.
- So a DB leak → "encrypted key1"; you'd need KMS permission too to recover plaintext `key1` → **and even then, no `key2` ⇒ no signature.**

> [!note] Defense in depth = (shard split) × (KMS envelope encryption)
> One wallet = `{address, network, Q, KMS(key_share)}`. A full break requires main DB **+** main KMS access **+** sub DB **+** sub KMS access — **all at once.**

> [!tip] The [[paillier-keypair]] is **not** persisted
> The Paillier keypair is not stored. It's freshly generated inside the `TwoPartyPlayer` constructor on every signing request, and dies with that request — **per-request, single-use.** That's why the `while (N.bitLength() < n.bitLength()*2)` loop at `two-party-player.ts:20-28` runs every time.

### B. When a request arrives — two HTTP round-trips

The path from `POST /v1/transaction/transfer` hitting main to the tx landing on chain:

```
client → main(:host)                               sub(:host)
   │ POST /v1/transaction/transfer
   │
   ▼
[1] Load my key1 & KMS-decrypt
    DB(privateKey ciphertext) → KMS.decrypt() → key1 (plaintext, memory only)
    new TwoPartyPlayer(key1)  ──► Paillier keypair born in memory
   │
   ▼
[2] Round-trip #1 ─ build r
    main: k1 ← random;  partialR = k1·G
   ──────► POST /v1/signer/get-part-r   (walletAddress, randomRequestId, k1·G)
                                          sub: k2 ← random
                                          sub: partialR2 = k2·G
                                          sub: Redis.SET(walletAddress:randomRequestId → k2, TTL)
                                       ◄──── reply: k2·G
    main: r = (k1 · (k2·G)).x mod n     ← multiply the two points on the curve
   │
   ▼
[3] Round-trip #2 ─ build s
    main: cKey = Enc_pk1(key1)                       (encrypt my own shard with my Paillier key)
   ──────► POST /v1/signer/get-part-s   (cKey, pk1, r, hm, randomRequestId)
                                          sub: k2 ← Redis.GET(walletAddress:randomRequestId)
                                          sub: partialS = Enc_pk1(k2⁻¹·hm + k2⁻¹·r·key1·key2)
                                              (uses only homomorphic ⊗ and ⊕ on cKey)
                                          sub: Redis.DEL(...)   ← k2 discarded immediately
                                       ◄──── reply: partialS (ciphertext)
    main: dec = Dec_sk1(partialS)        (only main can — only main has sk1)
    main: s   = dec · k1⁻¹ mod n
   │
   ▼
[4] canonical-s check → (maybe) retry → assemble signature → broadcast
    if (s == 0 || r == 0 || s > n/2) ⇒  resample k, GOTO [2]   (low-S form)
    sig = 0x{r}{s}{v}
    publicClient.sendRawTransaction(sig) → receipt → response
```

Code pointers for each step:

| Step | File | Function / lines |
|---|---|---|
| [1] DB→KMS decrypt | `key.repository.ts:25-75` | `findOne()` |
| [2] partial-R exchange | `two-party-player.ts:71-84`, `return-partial-r.usecase.ts` | `returnPartialR`, `returnR` |
| [2] sub caches k2 | `return-partial-r.usecase.ts` | Redis under `randomRequestId` |
| [3] cKey | `two-party-player.ts:89-92` | `returnCKey` |
| [3] sub partial-S | `two-party-player.ts:94-112` | `returnPartialS` |
| [3] main decrypt | `two-party-player.ts:114-121` | `returnS` |
| [4] canonical retry | `two-party-evm-signer.ts:167-243` | `signHash` loop (188-237) |
| [4] broadcast | `evm.service.ts:215-247` | `sendRawTransaction` |
| auth | `two-party.strategy.ts` | sub verifies before restoring its player |

> [!example] [[redis-k2-cache]] — the only place sub's `k2` lives, briefly
> Because sub's work is split across **two HTTP calls** (get-part-r, then get-part-s), the `k2` generated in [2] must be reused in [3]. Redis bridges them, keyed by `(walletAddress, randomRequestId)`, with a short TTL **and** an explicit `DEL` right after partial-S replies. The payoff:
> - **Structural prevention of nonce reuse across sessions** ([[k-reuse-attack]])
> - Even if main retries with the same `randomRequestId`, sub cannot fetch the same `k2` again → a fresh nonce is forced every time.

### C. Canonical `s` retry — enforcing `s ≤ n/2` (EIP-2 / low-S)

EVM rejects [[ecdsa-signature-malleability]] (a single message having two valid `s` values, `s` and `n−s`) by allowing **only `s ≤ n/2`** (EIP-2). `two-party-evm-signer.ts:188-237` loops to enforce this:

```
do {
    k1 ← random;   randomRequestId ← uuid()
    [get-part-r] → r
    if (r == 0) continue
    [get-part-s] → s
    if (s == 0) continue
    if (s > n/2) continue        // low-S violated → retry with fresh k
    break
} while (true)
v ← recoveryId (27/28)
```

> [!note] Why not just flip `s ← n − s`?
> A single-key ECDSA implementation would do exactly that one-liner. But in 2PC, `s` is the product of `k1⁻¹ · Dec(partialS)` — flipping it risks breaking the consistency of the `(r, s)` pair, and sub's Redis `k2` is already gone after one partial-S anyway. So **resampling `k`** lines up cleanly with the protocol's lifecycle.

### D. What flows over the wire vs what **never** does

This table summarizes the whole section.

| Category | Travels over the network | Never travels |
|---|---|---|
| **Private-key zone** | — | plaintext `key1`, plaintext `key2`, full `x = key1·key2` |
| **Nonce zone** | `k1·G`, `k2·G` (points, protected by ECDLP) | plaintext `k1`, plaintext `k2`, full `k = k1·k2` |
| **Paillier zone** | `cKey = Enc_pk1(key1)`, `partialS`, public key `pk1` | Paillier private key `sk1` (main's memory only) |
| **Public inputs** | `r`, `hm`, `walletAddress`, `randomRequestId` | — |
| **Storage zone** | — | DB `privateKey` column (KMS ciphertext), KMS master key |

> [!warning] Compromising one server alone recovers no secret
> - Main pwned → `key1`, `k1`, Paillier `sk1` leak. Without sub's `key2`/`k2`, none of `x`, `k` can be assembled.
> - Sub pwned → `key2`, `k2` (briefly) leak. Sub has only ever seen main's `key1` as **`cKey` ciphertext**, and lacks `sk1` to decrypt it.
> - Even dumping both DBs → only ciphertexts, useless without KMS decrypt rights.

### One-liner

sign-service stores **each wallet's half-shard, KMS-wrapped on top**, on two different servers/DBs; when a signing request arrives, main KMS-decrypts its half into memory and cooperates with sub over **two HTTP round-trips (`/v1/signer/get-part-r`, `/v1/signer/get-part-s`)** to produce `(r, s)`, retrying with a fresh `k` if low-S is violated, and broadcasts the result. At no point along the path does a full [[ecdsa-private-key-x]] or [[ecdsa-nonce-k]] sit in one place or cross the wire.

### Paillier Homomorphic Math by Numbers — Walking N=143 Through

The abstract formulas always raise the question: "is the plaintext really never exposed?" Cranking the whole thing by hand on a tiny curve (`nc=11`) and tiny Paillier modulus (`N=143`) makes it tangible — every number lines up.

### 1. Stage setup — small curve, small Paillier

[[ecdsa-curve-params]] side (all scalars `mod nc`):

| Value | Number | Who holds it |
|---|---|---|
| `nc` (curve order) | 11 | public constant |
| `key1` | 3 | main only |
| `key2` | 5 | sub only |
| `x = key1·key2 mod 11` | 15 mod 11 = **4** | **nobody knows it whole** |
| `k1` | 2 | main only |
| `k2` | 3 | sub only |
| `k = k1·k2 mod 11` | 6 | **nobody knows it whole** |
| `r` (assumed x-coord of commit) | 6 | public |
| `hm` (message hash) | 5 | public |

[[paillier-keys]] side (everything `mod N²`):

| Value | Number | Note |
|---|---|---|
| `p, q` | 11, 13 | Paillier primes (unrelated to curve primes) |
| `N = p·q` | **143** | Paillier modulus |
| `N²` | **20449** | where ciphertexts live |
| `g = N+1` | 144 | standard choice |
| Explanatory randomness r | fixed at 1 | real impl draws fresh r each time — same plaintext yields different ciphertext |

> [!note] Fixing the randomness is for exposition
> Real [[paillier-encryption]] computes `Enc(m) = gᵐ·rᴺ mod N²` with fresh r each call to get **semantic security**. We pin r=1 so the arithmetic is simple: `Enc(m) = 1 + 143·m mod 20449`. The point that homomorphic operations decrypt to the right plaintext is identical either way.

### 2. The answer key — s computed by plain ECDSA

Pretend one party knows everything and computes [[ecdsa-signing-formula|s = k⁻¹·(hm + r·x)]] directly, without [[two-party-split]]:

```
k⁻¹ mod 11 = 2          (6·2 = 12 ≡ 1)
hm + r·x   = 5 + 6·4 = 29 ≡ 7  (mod 11)
s          = 2·7 = 14 ≡ 3      (mod 11)
                         ━━━━━━
                          answer s = 3
```

Pre-compute the per-share inverses (`mod 11`):

```
k1⁻¹ = 6   (2·6 = 12 ≡ 1)
k2⁻¹ = 4   (3·4 = 12 ≡ 1)
check:  k1⁻¹·k2⁻¹ = 6·4 = 24 ≡ 2 = k⁻¹  ✓
```

Now we trace main and sub reaching that same `s=3` **without either ever seeing the other's plaintext secret.**

### 3. main → sub: `cKey = Enc(key1)`

main encrypts [[private-key-share|key1]] under its own [[paillier-keypair|Paillier public key pk1]]:

```
cKey = Enc_pk1(key1) = 1 + 143·3 = 430
```

main sends `(cKey, pk1, r, hm)` to sub. Plaintext key1=3 is never transmitted.

> [!warning] What sub actually sees
> All sub gets is the number `430`. Recovering plaintext 3 from `430` requires either factoring `N=143` (`p=11, q=13`) or knowing [[paillier-private-key|λ]], both protected by the [[paillier-decisional-composite-residuosity|DCR assumption]]. sub has neither → **key1 stays sealed.**

### 4. sub's plaintext pre-compute (its own values only)

Before entering [[partial-s-computation]], sub builds two plaintexts from its own secrets `(k2, key2)` plus the public `(hm, r)` (`mod 11`):

```
result1 = k2⁻¹ · hm        = 4·5     = 20 ≡  9
result2 = k2⁻¹ · r · key2  = 4·6·5   = 120 ≡ 10
```

`result1` is the "message-side share," `result2` is the "commit-and-my-key-share share." **Neither uses key1** — the ciphertext `cKey` will play that role in the next step.

### 5. Homomorphic ops — multiply and add over ciphertext

Apply [[paillier-homomorphism|Paillier's two superpowers]] directly (`mod N² = mod 20449`):

```
①  Enc(a) ⊗ b   :=  cipherᵇ mod N²       →  Enc(a·b)
②  Enc(a) ⊕ Enc(b) := c_a · c_b mod N²    →  Enc(a+b)
```

**(1) eResult1 — fresh encryption** (plaintext result1=9):
```
eResult1 = Enc_pk1(9) = 1 + 143·9 = 1288
```

**(2) eResult2 — `cKey` raised to result2** (`Enc(key1) ⊗ result2`):
```
eResult2 = cKey^result2 mod N²
         = 430¹⁰ mod 20449
         = 4291
check: Enc(key1·result2) = Enc(3·10) = Enc(30) = 1 + 143·30 = 4291  ✓
```

→ sub merely raised `430` to the 10th power, yet the result is `Enc(3·10) = Enc(30)`. **key1=3 was never seen in plaintext.** This works because `(1+N)ᵃᵇ ≡ 1+abN (mod N²)` — the binomial-theorem walkthrough is in the next section.

**(3) partialS — multiply the two ciphertexts** (`eResult1 ⊕ eResult2`):
```
partialS = (1288 · 4291) mod 20449
         = 5527408 mod 20449
         = 5578
check: Enc(9 + 30) = Enc(39) = 1 + 143·39 = 5578  ✓
```

This is `partialS = Enc_pk1(k2⁻¹·hm + k2⁻¹·r·key1·key2)` in concrete form. The plaintext `39 = 9 + 30 = k2⁻¹·hm + k2⁻¹·r·key1·key2` sits sealed inside.

> [!example] Flow diagram
> ```
> main                                    sub
> ───                                     ───
> cKey = Enc(3) = 430        ──cKey──▶    
>                                         result1 = 9       (plaintext)
>                                         result2 = 10      (plaintext)
>                                         eResult1 = Enc(9) = 1288
>                                         eResult2 = 430¹⁰ = 4291  (= Enc(30))
>                                         partialS = 1288·4291 = 5578  (= Enc(39))
>                            ◀─partialS──
> ```

### 6. main decrypts + multiplies by k1⁻¹ → s done

The [[partial-s-decrypt]] step. main decrypts `partialS` with its [[paillier-private-key|sk1]] and multiplies by its own `k1⁻¹`:

```
dec = Dec_sk1(5578) = 39                    ← only main can do this (holds sk1)
s   = dec · k1⁻¹ mod 11
    = 39 · 6 mod 11
    = 234 mod 11
    = 3                                      ✓ matches answer key s=3!
```

The meaning of `dec=39` also lines up perfectly:

```
39 mod 11 = 6
         = k2⁻¹·hm + k2⁻¹·r·key1·key2  mod 11
         = 4·5  +  4·6·3·5  mod 11
         = 20 + 360 mod 11
         = 9 + 8 mod 11
         = 17 ≡ 6                            ✓
```

Multiplying by `k1⁻¹=6` completes `k⁻¹ = k1⁻¹·k2⁻¹` → exactly ECDSA's `s = k⁻¹·(hm + r·x)` is reproduced.

### 7. Who saw what in plaintext — final audit

| Who | key1=3 | key2=5 | k1=2 | k2=3 | x=4 | k=6 | s=3 |
|---|:---:|:---:|:---:|:---:|:---:|:---:|:---:|
| main | ✅ | ❌ (ever) | ✅ | ❌ | ❌ | ❌ | ✅ (final) |
| sub | ❌ (cKey only) | ✅ | ❌ | ✅ | ❌ | ❌ | ❌ |
| on the wire | ❌ | ❌ | ❌ | ❌ | ❌ | ❌ | ❌ |

The wire carried only `cKey=430`, `partialS=5578`, and public `r=6, hm=5`. **The real private key `x = key1·key2 = 4` and the real nonce `k = k1·k2 = 6` were never assembled anywhere.**

> [!tip] Why the [[two-party-player-constructor|`TwoPartyPlayer` constructor loop]] demands `N > nc²`
> Just before decryption, main's plaintext is `dec = k2⁻¹·hm + k2⁻¹·r·key1·key2` — **the integer before reduction mod 11**. In our example that was 39. If `N < 39`, then `dec mod N` would clip and break `s` recovery. The worst-case size of this sum is roughly `nc + nc²` (driven by the `key1·key2` cross term), so we need `N > nc²`. The code calls `generateRandomKeysSync(nc.bitLength() * 2)` to get a Paillier key with **twice the bit-length** of the curve order, and loops with `while` until the `nc ≤ N` condition holds. Our toy satisfies it (`N=143 > nc²=121`), which is exactly why 39 survived. On [[secp256k1]] where `nc ≈ 2²⁵⁶`, this means `N ≈ 2⁵¹²`.

> [!note] One-line recap
> `cKey=430` → sub raises to `430¹⁰ = Enc(30)` without ever seeing plaintext `key1` → `1288·4291 = Enc(39) = 5578` → main decrypts to `39` → `·k1⁻¹=6` → **s=3**. Matches the answer key, zero plaintext leakage. [[paillier-homomorphism|⊕ and ⊗]] are deployed precisely to fill in [[ecdsa-s-cross-term|s's cross term]].

### Why (1+N)^a ≡ 1+aN (mod N²) — Homomorphism via the Binomial Theorem

The reason [[Paillier]] homomorphic encryption can perform "multiplication on ciphertext" comes down to a single line from high-school **binomial theorem**. This section unfolds that line directly — why `(1+N)^a ≡ 1+aN (mod N²)` holds, how it becomes the operational basis for ⊗ (plaintext multiplication), and why the `TwoPartyPlayer` constructor in [[sign-service]] has a `while` loop baked in. One continuous thread.

### 1. Why pick `g = N+1` — a deliberate choice

The [[Paillier]] encryption formula is generally (with explanatory randomness `r=1` fixed):

```
Enc(m) = g^m · r^N mod N²        // general form
       = g^m mod N²              // simplified with r=1
```

`g` can't be just anything — it must be an element whose order over `N²` is a multiple of `N`. The simplest and computationally cleanest choice is:

```
g = N + 1
```

> [!note] Why g = N+1 was chosen
> This isn't accidental. It's deliberately designed so that when `(1+N)^a` is expanded by the [[binomial theorem]], **every term involving N² or higher vanishes under mod N²**. That makes encryption and decryption fall into an intuitive "exponent = plaintext" shape.

Thanks to this choice, **every ciphertext takes the form `(1+N)^m`**. The plaintext `m` simply sits as the exponent of `(1+N)`.

### 2. The lemma — unfolding the binomial theorem directly

Start with the key equation, then justify it line by line:

```
(1 + N)^a  ≡  1 + aN   (mod N²)
```

Expanding `(1+N)^a` via the [[binomial theorem]] — `(x+y)^a = Σ C(a,k)·x^(a-k)·y^k` with `x=1, y=N`:

```
(1 + N)^a  =  Σ_{k=0}^{a} C(a,k)·N^k
           =  C(a,0)·N^0  +  C(a,1)·N^1  +  C(a,2)·N^2  +  C(a,3)·N^3  + ...
           =      1       +      aN      +  C(a,2)·N²   +  C(a,3)·N³   + ...
                                          └──────────────┬───────────────┘
                                              k ≥ 2  →  N^k contains N²
```

Now apply **`mod N²`** to both sides. Every term with `k ≥ 2` is `N^k = N^(k-2) · N²` → a **multiple of N² → zero under mod N²**:

```
(1 + N)^a  ≡  1 + aN  +  0  +  0  +  ...   (mod N²)
           ≡  1 + aN                        (mod N²)   ✓
```

> [!tip] One-line intuition
> "Multiplying `(1+N)` by itself a times produces a swarm of terms, but under mod N² only the linear term (`aN`) survives — the rest die." → So **the exponent `a` survives unchanged as the coefficient of the linear term.** This is the secret behind [[Paillier]] operating as "exponent = plaintext."

### 3. Our example — unfolding `(1+3N)^10` directly

In the [[Paillier 동형 연산 숫자 예시]] section we had `N=143`, `N²=20449`, `cKey = Enc(3) = 1 + 3N = 430`. Let's unfold the step where sub computed `cKey^10` to produce `Enc(30)`.

Since `430 = 1 + 3N`, treating `(3N)` as one unit, the binomial expansion:

```
(1 + 3N)^10  =  Σ_{k=0}^{10} C(10,k)·(3N)^k

  k=0:  C(10,0)·(3N)^0  =  1·1               =  1
  k=1:  C(10,1)·(3N)^1  =  10·3N             =  30N
  k=2:  C(10,2)·(3N)^2  =  45·9·N²           =  405·N²    ← contains N²
  k=3:  C(10,3)·(3N)^3  =  120·27·N³         =  3240·N³   ← N³
  ...
  k=10: C(10,10)·(3N)^10 = 1·3^10·N^10        = 59049·N^10
```

**Under mod N², all `k ≥ 2` terms zero out**:

```
(1 + 3N)^10  ≡  1 + 30N   (mod N²)
             =  1 + 30·143
             =  1 + 4290
             =  4291
```

And `4291 = 1 + 143·30 = Enc(30) = Enc(3·10)` ✓

> [!example] At a glance
> ```
> cKey       = Enc(3)        = (1+N)^3       = 1 + 3N   = 430
> cKey^10    = ((1+N)^3)^10  = (1+N)^(3·10)  = (1+N)^30
>            ≡ 1 + 30N       (mod N²)         = 4291
>            = Enc(30)       = Enc(3 · 10)   ← key1(3) × plaintext 10!
> ```
> sub **never saw `key1=3` in plaintext, not once** — it just raised ciphertext `430` to the 10th power — yet the result is exactly `Enc(3·10)=Enc(30)`. This is what ⊗ (plaintext multiplication) actually is.

### 4. This is exactly the origin of ⊗ (plaintext multiplication)

Apply the exponent law `(g^a)^b = g^(a·b)` directly to [[Paillier]] encryption:

```
Enc(a)^b  =  (g^a)^b  =  g^(a·b)  =  Enc(a · b)
```

That is, **raising a ciphertext to plaintext `b` multiplies the plaintext by `a·b`.** The `publicKey.multiply(cipher, scalar)` call in [[two-party-player.ts]] is precisely this operation. One line of code:

```ts
// sub crafts the ciphertext of key1·result2 WITHOUT ever seeing plaintext key1
eResult2 = pk1.multiply(cKey, result2)
//        = Enc(key1) ⊗ result2
//        = Enc(key1 · result2)
```

> [!note] ⊕ (addition) works by the same principle
> The same binomial theorem unfolds ⊕ too:
> ```
> Enc(a) · Enc(b) = (1+N)^a · (1+N)^b = (1+N)^(a+b) ≡ 1 + (a+b)N = Enc(a+b)
> ```
> That is, **multiplying ciphertexts adds the plaintexts.** ⊗ is exponentiation, ⊕ is multiplication — both fall out automatically from the `(1+N)^m` representation.

### 5. Why the `N > nc²` key-size condition — what the constructor `while` loop actually does

This is where a long-standing puzzle in the [[sign-service]] code resolves. The `TwoPartyPlayer` constructor (`two-party-player.ts:20-28`) has this loop:

```ts
do {
  const keys = generateRandomKeysSync(nc.bitLength() * 2)  // 2x the bitlength of nc
  this.publicKey = keys.publicKey
  this.privateKey = keys.privateKey
} while (this.publicKey.n.lte(nc))   // condition: n > nc
```

Why generate the [[Paillier]] key at **twice the bitlength** of the curve order `nc`, and regenerate until the condition holds?

The plaintext right before decryption is **an integer that has NOT yet been reduced mod `nc`**. Look at `dec = 39` from the [[Paillier 동형 연산 숫자 예시]]:

```
dec = k2⁻¹·hm + k2⁻¹·r·key1·key2
                       └────┬────┘
                  this cross term can grow as large as nc²
```

`k2⁻¹`, `hm`, `r` are each mod `nc`, so each at most `nc`-sized. But `key1·key2` is the **product of two mod-`nc` numbers**, so it can grow up to `nc²`. The whole sum sits around `nc + nc²`.

> [!warning] If N is too small, the plaintext gets truncated and the answer breaks
> If `N < nc²`, the sum `k2⁻¹·hm + k2⁻¹·r·key1·key2` **gets sliced off by `mod N`** at the decryption step. main then receives a garbage `dec` instead of the real value, and the `s` produced by multiplying with `k1⁻¹` fails ECDSA verification. So **`N > nc²`** is a hard correctness requirement.

So:

```
Required condition:  N > nc²
In terms of bits:    log₂(N) > 2·log₂(nc)
                     i.e.:  bitlength(N)  >  bitlength(nc) × 2
```

The `nc.bitLength() * 2` in the code is exactly this. secp256k1 has `nc ≈ 2²⁵⁶`, so we generate a [[Paillier]] key with `N ≈ 2⁵¹²`. But `generateRandomKeysSync(512)` doesn't guarantee exactly 512-bit `N` (it's a product of two primes, so could come out 511-bit), which is why the **`while` loop retries until `N > nc` is definitely satisfied**.

> [!example] Our example satisfies the condition too
> In the small example, `nc = 11` (curve order), `nc² = 121`, `N = 143`. → `N > nc²` confirmed ✓
> That's why the plaintext `39` at decryption time wasn't truncated by `mod 143` — and reducing `mod 11` is a deliberate final step that main performs.

### 6. One unified thread

```
Pick g = N+1
     │
     ▼
Every ciphertext takes the form (1+N)^m
     │
     ▼
Binomial theorem: (1+N)^a = 1 + aN + C(a,2)·N² + ...
     │
     ├─ mod N² kills all N²-or-higher terms ──▶ (1+N)^a ≡ 1 + aN
     │
     ▼
Exponent law gives ⊗ and ⊕ homomorphisms
     ├─ Enc(a)^b = Enc(a·b)  (⊗)
     └─ Enc(a)·Enc(b) = Enc(a+b)  (⊕)
     │
     ▼
Cross term key1·key2 (up to nc²) is now computable on ciphertext
     │
     ▼
But to keep the plaintext from being truncated:  N > nc²
     │
     ▼
Constructor while loop: generate keys at nc.bitLength()*2 bits, retry until condition holds
```

> [!tip] One-line takeaway
> `g=N+1` was chosen **deliberately so that the binomial theorem makes all N²-or-higher terms cleanly die under mod N²**, which gives `(1+N)^a ≡ 1+aN` — i.e. [[Paillier]] gets its "exponent = plaintext" structure. That's the origin of ⊗ (plaintext multiplication), and to handle the cross term `key1·key2` (up to `nc²` in size) without truncation, `N > nc²` becomes mandatory — which is exactly why the `while` loop in the [[sign-service]] constructor regenerates keys at twice the curve order's bitlength until the condition holds. Mathematical elegance and one line of code point to the same reason.
