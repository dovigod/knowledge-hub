## TL;DR

백엔드에서 "조건에 따라 다른 플로우를 타게 하는 것"은 **[[오케스트레이션 orchestration]]** 의 문제이며, 복잡도가 커질수록 **[[상태 머신 state machine]]**(예: [[XState]])이나 **[[워크플로우 엔진 workflow engine]]**([[Temporal]], [[AWS Step Functions]])으로 분기·재시도·타임아웃을 *데이터*로 모델링하는 것이 표준 해법이다. 상태는 결국 어딘가에 영속화되어야 하는데, 단순히 `status` 컬럼만 두면 "현재 어디까지 왔는가"는 보이지만 *왜·언제 그리 됐는가* 가 사라진다 — 이를 메우는 게 **[[이벤트 소싱 event sourcing]]** 의 **[[Current State Table]] + [[Event Log Table]]** 이중 구조다. [[Datadog]] 로그가 있어도 이벤트 테이블을 따로 두는 이유는 *로그는 관측(observability)용, 이벤트는 도메인 상태의 사실(source of truth)*이기 때문이며, 재처리·감사·결과가 불확실한 비동기 호출의 **[[Outcome Unknown]]** 처리(특히 `sendRawTransaction` 같은 블록체인 호출의 `txHash` 추적, **[[Idempotency Key]]** 기반 [[deposit_request]] 재시도)에서 그 차이가 결정적으로 드러난다.

> [!note] 한 줄 요약
> **오케스트레이션은 "어떻게 분기할지" 의 문제, 상태 머신/엔진은 "그 분기를 코드로 어떻게 표현할지" 의 답, 이벤트 소싱은 "그 모든 결정을 어떻게 잃지 않고 보존할지" 의 답이다.** 셋은 경쟁 관계가 아니라 *계층 관계*다.

```
┌────────────────────────────────────────────────────────────┐
│  Orchestration (분기·재시도·타임아웃을 누가 지휘?)         │
│     │                                                      │
│     ▼                                                      │
│  State Machine / Workflow Engine (XState, Temporal …)      │
│     │  ← 코드 모델                                         │
│     ▼                                                      │
│  Persistence Layer                                         │
│     ├─ Current State Table   ← "지금 어디"                │
│     └─ Event Log Table       ← "어떻게 여기까지" (ES)     │
│           │                                                │
│           ▼                                                │
│  Observability (Datadog, Sentry) ← 부차적 관측, 사실 X    │
└────────────────────────────────────────────────────────────┘
```

> [!tip] 이 노트를 읽는 순서
> 아래 섹션들은 위 다이어그램을 위→아래로 따라간다. *분기 패턴 → 코드 표현([[XState]]) → 저장 위치 → 이벤트 소싱 → 로그와의 차이 → 비동기/[[Idempotency]] 실전* 순으로 풀린다.

## 오케스트레이션이란? — 분기되는 플로우를 다루는 패턴

"입금 요청이 들어왔는데 KYC가 안 끝났네 → 그러면 KYC 플로우로 빠졌다가 → 다시 돌아와서 입금 처리" 같은 식으로, **하나의 비즈니스 요청이 여러 하위 플로우를 조건부로 엮으면서 진행**되는 걸 일반적으로 [[workflow-orchestration|오케스트레이션]]이라 부른다. 핵심 질문은 두 개다.

1. **누가 다음 단계를 결정하는가** (중앙 지휘자 vs 각자 알아서)
2. **현재 어디까지 왔는지 어떻게 추적하는가** (메모리/DB/이벤트 로그)

이 두 축에 따라 패턴이 갈린다.

### Orchestration vs Choreography — 누가 흐름을 쥐는가

> [!note] 두 가지 큰 갈래
> - **Orchestration**: 중앙 컨트롤러가 "다음은 B, 그 다음 C" 식으로 명시적으로 호출. 흐름이 코드에 한 곳에 모인다.
> - **Choreography**: 각 서비스가 이벤트만 발행하고, 다른 서비스가 알아서 구독해서 반응. 결합도는 낮지만 "전체 흐름이 어떻게 흘러가는지"가 코드에 안 적혀있다.

```
[Orchestration]                          [Choreography]
                                                            
   ┌──────────────┐                       ServiceA ── event ──▶ Bus
   │ Orchestrator │                                          │
   └───┬──────┬───┘                              ┌───────────┼───────────┐
       │      │                                  ▼           ▼           ▼
       ▼      ▼                              ServiceB    ServiceC    ServiceD
   ServiceA ServiceB
```

추적성만 놓고 보면 거의 항상 [[orchestration-pattern|Orchestration]]이 이긴다. "지금 이 요청 어디서 막혔어?" 라는 질문에 컨트롤러 코드 한 군데만 보면 되니까. Choreography는 production에서 디버깅이 지옥이 되기 쉽다.

### 패턴별 비교

분기 있는 플로우를 다루는 대표적인 4가지 구현 패턴이다.

| 패턴 | 분기 표현 | 상태 저장 | 적합한 복잡도 | 추적성 |
|---|---|---|---|---|
| **Pipeline / Chain of Responsibility** | `if/else`, early return | 보통 in-memory (요청 수명 내) | 낮음 (선형 + 한두 분기) | 낮음 (로그로만) |
| **State Machine ([[xstate]], statecharts)** | 상태별 transition 정의 | 메모리 + 외부 persist | 중간 (상태가 10~50개) | 중간 (현재 상태는 명시적) |
| **Saga (Choreography-based)** | 이벤트 + compensating action | 이벤트 로그 + 각 서비스 로컬 DB | 중~높음 (분산) | 낮음 (이벤트 추적 도구 필요) |
| **[[temporal|Workflow Engine]] (Temporal, Cadence, AWS Step Functions)** | 코드로 작성하되 엔진이 영속화 | 엔진이 자동 영속화 (event sourced) | 높음 (며칠~몇 달 걸리는 워크플로우) | 매우 높음 (replay 가능) |

#### 1. Pipeline — 가장 단순한 시작점

```typescript
async function handleDeposit(req: DepositRequest) {
  await validateRequest(req)
  if (!await isKycComplete(req.userId)) {
    await startKycFlow(req.userId)
    return { status: 'PENDING_KYC' }
  }
  await reserveBalance(req)
  await submitOnChain(req)
  return { status: 'SUBMITTED' }
}
```

> [!tip] Pipeline의 한계
> 분기가 2~3개일 때는 멀쩡한데, 단계가 늘어나고 각 단계가 비동기로 며칠씩 걸리기 시작하면 — 예: 입금 → KYC 대기 → 컴플라이언스 승인 대기 → 온체인 컨펌 대기 → 정산 — 더 이상 하나의 함수 호출로 안 묶인다. 단계 사이에 프로세스가 죽으면 어디까지 갔는지 복구 불가.

#### 2. State Machine — 상태를 1급 시민으로

각 상태에서 어떤 이벤트가 들어오면 어떤 상태로 가는지를 **데이터로 선언**한다. [[xstate]]가 대표적.

```
        ┌──────────┐  KYC_OK   ┌──────────┐  COMPLIANCE_OK  ┌─────────────┐
   ───▶ │ created  │──────────▶│ kyc_done │────────────────▶│ ready_to_tx │
        └────┬─────┘           └────┬─────┘                 └──────┬──────┘
             │ KYC_FAIL              │ COMPLIANCE_FAIL              │ SUBMIT
             ▼                       ▼                              ▼
         ┌───────┐               ┌─────────┐                   ┌──────────┐
         │rejected│               │rejected │                   │submitted │
         └───────┘               └─────────┘                   └────┬─────┘
                                                                    │ CONFIRMED
                                                                    ▼
                                                                ┌────────┐
                                                                │settled │
                                                                └────────┘
```

> [!example] State Machine이 이기는 지점
> "이 결제 요청이 `rejected` 상태인데 어떻게 거기 도착했지?"를 물을 때, transition이 명시적이라 가능한 경로가 유한하다. 그리고 누가 새 상태를 추가하면 PR 리뷰에서 "이 상태에서 들어올 수 있는 이벤트 다 처리됐어?"를 검토 가능하다.

다만 NestJS에서 [[xstate]]를 그대로 쓰면 **상태 영속화는 직접 해줘야 한다** — XState는 "지금 메모리에 있는 머신이 어느 상태인가"만 알지, "프로세스가 죽었다 살아나도 같은 자리에서 다시 돌게" 해주진 않는다. 다음 섹션([[nest-xstate-workflow]])에서 자세히 다룬다.

#### 3. Saga — 분산 트랜잭션을 흉내내는 보상 패턴

여러 서비스에 걸친 트랜잭션이 "전부 성공 or 전부 롤백"이 필요한데 분산 환경이라 진짜 2PC를 못 쓸 때. **각 단계마다 compensating action(되돌리기 액션)**을 정의해두고, 어딘가 실패하면 거꾸로 풀어준다.

```
Forward:    reserveBalance ──▶ deductFee ──▶ submitOnChain ──▶ markSettled
                                                │
                                                │ FAIL
                                                ▼
Compensate:                       refundFee ◀── releaseBalance
```

> [!warning] Saga의 함정
> Compensating action이 멱등(idempotent)이지 않으면 보상이 이중으로 돌 수 있다. 그리고 "이미 외부로 나간 액션"(예: 이메일 발송, 온체인 트랜잭션)은 진짜 못 되돌린다 — 그건 보상 트랜잭션을 따로 발생시켜서 회계적으로만 맞춰야 한다.

#### 4. Workflow Engine — 코드로 쓰지만 엔진이 영속화

[[temporal|Temporal]], Cadence, AWS Step Functions, Airflow 같은 부류. 핵심 마법은:

```typescript
// 이 함수가 며칠 동안 살아있을 수 있다. 프로세스가 죽었다 살아나도 같은 자리에서 재개.
async function depositWorkflow(req: DepositRequest) {
  await activities.validate(req)

  if (!await activities.isKycComplete(req.userId)) {
    await workflow.executeChildWorkflow(kycWorkflow, req.userId) // 며칠 대기 가능
  }

  const txHash = await activities.submitOnChain(req)
  await workflow.condition(() => activities.isConfirmed(txHash), '1 hour')

  return { status: 'SETTLED', txHash }
}
```

> [!note] 어떻게 이게 가능한가
> 워크플로우 엔진은 매 `await` 지점마다 **결과를 이벤트 로그에 기록**한다. 프로세스가 죽으면, 다시 시작할 때 처음부터 코드를 다시 돌리되 — 이미 로그에 결과가 있는 `await`은 "기록된 값"을 반환해주고, 아직 안 한 부분부터 실제 실행한다. 이것이 [[event-sourcing|이벤트 소싱]]의 직접적인 응용이다. 자세한 내용은 뒤 섹션에서.

### 어떻게 골라야 할까

> [!tip] 의사결정 가이드
> - **분기가 1~2개, 동기 처리, 단일 프로세스**: 그냥 Pipeline. 오버엔지니어링 금지.
> - **상태가 5개 이상이고 transition이 분명한 도메인** (주문, KYC, 청구): [[xstate|XState]] + DB persistence. 코드+다이어그램이 동기화된다는 장점이 크다.
> - **단계 사이에 며칠씩 걸림 + 외부 시스템 콜백 대기 + retry/timeout 처리가 복잡함**: [[temporal|Temporal]] 같은 엔진을 진지하게 검토. 직접 만들면 결국 절반쯤 엉성한 Temporal을 만들게 된다.
> - **마이크로서비스 여러 개를 가로지르는 트랜잭션, 각 팀이 자기 부분을 소유**: Saga + 이벤트 버스. 단, 추적 도구([[opentelemetry|OpenTelemetry]] trace)를 같이 깔아야 한다.

**복잡도/추적성 트레이드오프 요약**:

```
복잡도 ─────────────────────────────────────────▶
Pipeline  <  State Machine  <  Saga  <  Workflow Engine

추적성 가성비
                 State Machine (가장 좋은 가성비 구간)
                       ▲
                       │
Pipeline ──────────────┴──────────────── Workflow Engine
  (적게 투자, 적게 얻음)         (많이 투자, 매우 많이 얻음)
                 Saga
                 (투자 많이 하는데 추적 도구 없으면 손해)
```

핀테크/크립토 도메인처럼 **돈이 움직이고, 외부 시스템(체인, 은행, 카드사) 응답이 비동기이고, 감사가 필요한 경우** 는 거의 항상 [[state-machine|상태머신]] 이상으로 가야 한다. 그리고 그때부터는 "상태를 어디에 저장할까"라는 다음 질문이 따라온다 — 그게 다음 섹션의 주제다.

## NestJS + XState — 워크플로우를 코드로 모델링하기

[[NestJS]] 백엔드에서 [[XState]]를 쓰는 가장 솔직한 동기는 **"if/else 지옥을 명세화된 상태 머신으로 끌어올리고 싶다"** 이다. 결제·KYC·출금처럼 단계가 많고 외부 콜백을 기다리는 플로우는 핸들러 안에 분기를 늘릴수록 추적 불가능해진다. XState는 상태(state), 이벤트(event), 가드(guard), 액션(action), 서비스(invoke)를 객체 트리로 명시하고, **순수 함수**로 전이(transition)를 계산하기 때문에 Nest의 DI/Provider 위에 올리기 쉽다.

### 실제 사용 사례 — 출금(Withdrawal) 머신

> [!example] 시나리오
> 사용자가 출금 요청 → 사내 정책 검사 → [[nonce manager]]에서 nonce 발급 → rawTx 서명 → `sendRawTransaction` → txHash 수신 → 컨펌 대기 → 완료/실패. 어느 단계든 [[Outcome Unknown]]가 가능.

```ts
// withdrawal.machine.ts
import { setup, assign } from 'xstate';

export const withdrawalMachine = setup({
  types: {
    context: {} as {
      requestId: string;        // == deposit_request 와 동일한 의미의 idempotency key
      txHash?: string;
      rawTx?: string;
      lastError?: string;
      retries: number;
    },
    events: {} as
      | { type: 'POLICY_OK' }
      | { type: 'POLICY_REJECT'; reason: string }
      | { type: 'SIGNED'; rawTx: string }
      | { type: 'BROADCASTED'; txHash: string }
      | { type: 'BROADCAST_TIMEOUT' }
      | { type: 'CONFIRMED' }
      | { type: 'REVERTED' },
  },
  actors: {
    runPolicyCheck: /* fromPromise(...) */ undefined as any,
    signRawTx:      undefined as any,
    broadcastTx:    undefined as any,
    waitConfirm:    undefined as any,
  },
  guards: {
    canRetry: ({ context }) => context.retries < 3,
  },
}).createMachine({
  id: 'withdrawal',
  initial: 'policyCheck',
  context: { requestId: '', retries: 0 },
  states: {
    policyCheck: {
      invoke: { src: 'runPolicyCheck', onDone: 'signing', onError: 'rejected' },
    },
    signing: {
      invoke: { src: 'signRawTx', onDone: { target: 'broadcasting',
        actions: assign({ rawTx: ({ event }) => event.output }) } },
    },
    broadcasting: {
      invoke: {
        src: 'broadcastTx',
        onDone: { target: 'confirming',
          actions: assign({ txHash: ({ event }) => event.output }) },
        onError: 'outcomeUnknown',          // sendRawTransaction 타임아웃
      },
    },
    outcomeUnknown: {                       // 핵심 상태
      on: {
        BROADCASTED: { target: 'confirming',
          actions: assign({ txHash: ({ event }) => event.txHash }) },
        BROADCAST_TIMEOUT: { target: 'broadcasting',
          guard: 'canRetry',                // 같은 rawTx/nonce 재사용
          actions: assign({ retries: ({ context }) => context.retries + 1 }) },
      },
    },
    confirming: {
      invoke: { src: 'waitConfirm',
        onDone: 'completed', onError: 'reverted' },
    },
    completed: { type: 'final' },
    rejected:  { type: 'final' },
    reverted:  { type: 'final' },
  },
});
```

```
       ┌───────────┐  POLICY_OK   ┌─────────┐  SIGNED   ┌──────────────┐
 start │policyCheck│─────────────▶│ signing │──────────▶│ broadcasting │
       └─────┬─────┘              └─────────┘           └──────┬───────┘
             │ POLICY_REJECT                                   │ timeout
             ▼                                                 ▼
        ┌────────┐                                       ┌──────────────┐
        │rejected│                                       │outcomeUnknown│◀──BROADCAST_TIMEOUT (retry, canRetry)
        └────────┘                                       └──────┬───────┘
                                                                │ BROADCASTED(txHash)
                                                                ▼
                                                          ┌────────────┐ CONFIRMED  ┌──────────┐
                                                          │ confirming │───────────▶│ completed│
                                                          └─────┬──────┘            └──────────┘
                                                                │ REVERTED
                                                                ▼
                                                            ┌──────────┐
                                                            │ reverted │
                                                            └──────────┘
```

### Nest와 어떻게 합치는가

> [!note] 통합 패턴
> - **Machine 정의** = 순수 모듈(`*.machine.ts`). DI 없음.
> - **Actor 실행** = `WithdrawalOrchestrator` 같은 `@Injectable()` 서비스가 `createActor(machine)`로 인스턴스를 만들고, `invoke` 안의 `actors`를 Nest 프로바이더(레포지토리, RPC, 큐)로 주입.
> - **영속화** = 매 전이 직후 `actor.getPersistedSnapshot()`을 DB의 워크플로우 행에 저장하거나 [[Event Log]]에 append.
> - **이벤트 수신** = 컨트롤러/리스너가 들어온 콜백(예: 노드 RPC webhook)을 `actor.send({ type: 'BROADCASTED', txHash })`로 변환.

```ts
@Injectable()
export class WithdrawalOrchestrator {
  constructor(
    private repo: WorkflowRepo,
    private signer: SignerService,
    private rpc: RpcService,
    private nonce: NonceManager,
  ) {}

  async resume(requestId: string) {
    const row = await this.repo.find(requestId);
    const actor = createActor(withdrawalMachine.provide({
      actors: {
        signRawTx:   fromPromise(() => this.signer.sign(requestId)),
        broadcastTx: fromPromise(() => this.rpc.sendRaw(row.rawTx!)),
        // ...
      },
    }), { snapshot: row.snapshot });   // ← 재개

    actor.subscribe((s) => this.repo.save(requestId, s));
    actor.start();
    return actor;
  }
}
```

### 장점

| 항목 | 효과 |
|---|---|
| 시각화 | [[Stately]] 에디터/Inspector로 머신을 그대로 다이어그램으로 띄움. PR 리뷰가 쉬워짐. |
| 테스트 | 가드/액션이 순수 함수 → `transition(state, event)` 단위 테스트만으로 충분. 외부 의존성 없이 분기 100% 커버. |
| 명세화 | "이 상태에서는 이 이벤트만 받는다"가 코드로 강제됨. 잘못된 이벤트는 무시 또는 에러. [[invariant]] 보장. |
| 모델 체크 | `@xstate/test`로 경로(path) 생성기를 돌려 도달 불가능/데드락 상태를 미리 발견. |
| 점진 도입 | 한 도메인(출금)만 머신으로 만들고, 나머지는 기존 Nest 핸들러로 두는 게 가능. Temporal처럼 인프라가 안 따라옴. |

### 단점/주의점

> [!warning] XState만으로 부족한 영역
> - **영속성은 직접 해결**해야 함. 스냅샷을 어디에 저장할지, 충돌 시 어떻게 합칠지는 너희 몫. → [[Current State Table]] / [[Event Log]] 패턴 필요.
> - **타이머/리트라이도 직접 운용.** `after: { 5000: ... }`은 메모리 타이머라 프로세스 재시작 시 사라진다. 결국 외부 스케줄러([[BullMQ]], [[Redis]] delayed job, cron)가 필요.
> - **분산 락이 없다.** 같은 `requestId`로 두 인스턴스가 동시에 actor를 만들면 둘 다 진행된다. → DB 행 락이나 [[Outbox]]로 직렬화해야 함.
> - **롱런닝 워크플로우는 무겁다.** 컨펌 대기 30분짜리를 한 actor가 메모리에 들고 있을 수는 없으므로, "이벤트 들어올 때마다 hydrate → 한 스텝 진행 → 영속화 → 사라짐" 사이클이 정석.
> - **하위 호환 마이그레이션이 까다롭다.** 머신 정의를 바꿨는데 DB에 옛 스냅샷이 남아있으면 unknown state로 깨질 수 있다. 버전 필드를 같이 저장.

### Temporal 같은 외부 엔진과의 비교

| 축 | XState (in NestJS) | [[Temporal]] / [[AWS Step Functions]] / [[Cadence]] |
|---|---|---|
| 어디서 도는가 | 너희 Nest 프로세스 안 | 별도 클러스터(워커는 클라이언트) |
| 상태 저장 | 너희가 책임 (DB/Event Log) | 엔진이 책임 (Event History 내장) |
| 결정론(Determinism) | 권장이지만 강제 X | 워크플로우 코드는 **결정론적**이어야 함 (replay 기반) |
| 타이머/리트라이 | 직접 구현 | 엔진이 durable timer/retry 제공 |
| 시각화 | Stately Inspector | Temporal Web UI (실행 단위로 추적) |
| 운영 복잡도 | 거의 0 (라이브러리) | 클러스터/DB/UI/메트릭 별도 운영 |
| 가시성/감사 | 직접 [[Event Log]] 설계 | 모든 이벤트가 자동으로 Event History |
| 코드 표현력 | 머신 트리(선언적) | 일반 코드 + `await activity()`(명령형) |
| 적합한 규모 | 단일 서비스, 도메인 1~3개 | 회사 전체, 수십 도메인, 장기 실행 |

> [!tip] 한 줄 요약
> [[XState]]는 **"워크플로우를 코드 안에 명세로 박는 라이브러리"**, [[Temporal]]은 **"워크플로우 실행을 외부에 위탁하는 런타임"**. 가시성·재생(replay)·durable timer가 진짜 필요해지는 시점이 오면 Temporal로 넘어가지만, 그 전까지는 XState + Nest + DB만으로 7~80%를 커버한다.

> [!note] 실무 권고
> - 한 도메인이 **3개 이상 외부 시스템 콜백**을 기다리거나 **TTL이 30분+**이면 XState로 분리할 가치가 있다.
> - **금전이 움직이고**, **장기간 실행**되고, **여러 팀이 워크플로우를 공유**해야 한다면 Temporal을 검토. XState는 그 전 단계 보험.
> - 둘 다 [[Idempotency Key]]([[requestId]] / [[deposit_request]] id)를 시작점으로 잡아야 안전하다 — 머신을 어디서 돌리든 입력 키가 동일하면 결과가 동일해야 한다.

## 워크플로우 상태를 어디에 저장할까 — DB vs 워크플로우 엔진

워크플로우는 본질적으로 **장기 실행(long-running)** 이다. 사용자가 "출금 요청" 버튼을 누르는 순간부터 KYC 검증 → AML 스크리닝 → 블록체인 트랜잭션 → 컨펌 대기 → 알림까지 수 초~수 시간이 걸린다. 그 사이 서버는 재시작되고, 컨테이너는 OOM으로 죽고, Kubernetes가 Pod를 옮긴다. 메모리에 들고 있는 [[XState]] 인스턴스는 **그 순간 증발**한다.

> [!note] 상태 영속성이 필요한 본질적 이유
> "지금 이 요청이 어느 단계까지 진행됐는가?"를 프로세스 외부에 적어두지 않으면, 재시작 직후 시스템은 그 요청의 존재 자체를 잊는다. 워크플로우 엔진이든 DB든 — **결국 누군가는 디스크에 적어야 한다.**

### 선택지 1 — DB로 직접 관리하기

가장 직관적인 방법은 PostgreSQL 같은 [[Relational Database]]에 워크플로우 테이블을 만드는 것이다.

```sql
CREATE TABLE withdrawal_workflow (
    id              UUID PRIMARY KEY,
    user_id         BIGINT NOT NULL,
    amount          NUMERIC(36, 18),
    state           TEXT NOT NULL,  -- 'kyc_pending', 'aml_pending', 'broadcasting', ...
    context         JSONB NOT NULL, -- XState context 스냅샷
    tx_hash         TEXT,
    retry_count     INT DEFAULT 0,
    next_run_at     TIMESTAMPTZ,
    updated_at      TIMESTAMPTZ DEFAULT now()
);
```

이 접근은 처음엔 깔끔해 보인다. [[NestJS]] 서비스가 [[TypeORM]]/[[Prisma]]로 row를 읽고, transition을 돌리고, 새 state를 UPDATE 한다. 하지만 운영하다 보면 **세 가지 부담**이 누적된다.

#### 1. 커넥션 풀 압박

```
[Worker A] ──┐
[Worker B] ──┼──→ pg_pool (max=20) ──→ Postgres
[Worker C] ──┘
              ↑
        Long-running TX가 풀을 잠가버린다
```

워크플로우 한 단계가 외부 API(블록체인 RPC, KYC 벤더)를 호출하면 응답이 30초 걸릴 수 있다. 그동안 트랜잭션을 열어둔 채 row를 `SELECT ... FOR UPDATE`로 잡고 있으면, 동시 워커가 늘수록 [[Connection Pool]]이 폭발한다.

> [!warning] DB를 워크플로우 엔진처럼 쓸 때의 함정
> - **Lock 경쟁**: 동일 워크플로우를 두 인스턴스가 동시에 집어드는 race를 막으려면 `FOR UPDATE SKIP LOCKED` + advisory lock이 필요하다.
> - **폴링 부하**: `WHERE state = 'pending' AND next_run_at < now()`를 N초마다 도는 워커는 인덱스가 있어도 무거운 work load다.
> - **타임아웃 처리**: external call이 멈췄을 때 누가 해당 row를 다시 잡을지 결정하는 reaper를 직접 만들어야 한다.

#### 2. 스키마 변경 부담

플로우가 늘어날 때마다 테이블을 손대야 한다.

| 변경 사유 | 필요한 작업 |
|---|---|
| 새 단계 추가 (`fraud_check` 도입) | `state` enum에 값 추가 + 모든 워커 재배포 |
| 분기 조건 변경 | `context` JSONB 스키마 변경, 기존 row 마이그레이션 고민 |
| Saga 보상 단계 추가 | 새 컬럼 `compensation_state`, 기존 row 백필 |
| 새 워크플로우 타입 | 테이블 하나 또 만들거나 polymorphic JSONB로 |

**결국 비즈니스 로직(코드)과 영속화 스키마(DB)가 양쪽에서 같이 흔들린다.** 코드만 바꿔도 되는 변경이, DB 마이그레이션을 수반하게 된다.

#### 3. 재시작 후 복구 로직을 직접 짜야 함

```ts
// 부팅 시 — 누락된 워크플로우를 누가 줍는가?
async onModuleInit() {
  const stuck = await this.repo.find({
    where: { state: In(['broadcasting', 'confirming']), updated_at: LessThan(...) }
  });
  for (const wf of stuck) {
    await this.resumeOrFail(wf);  // ← 이 로직 자체가 워크플로우 엔진의 일부다
  }
}
```

이 "복구 워커(reaper/janitor)"는 결국 [[Temporal]] 같은 엔진의 worker 구현을 손으로 다시 짜는 일이다.

### 선택지 2 — 워크플로우 엔진에 맡기기

[[Temporal]], [[Cadence]], [[AWS Step Functions]], [[Conductor]] 같은 워크플로우 엔진은 위 세 가지 부담을 **인프라 계층으로 흡수**한다.

```
┌─────────────────────────────────────────────────────────┐
│  애플리케이션 코드 (당신이 쓰는 부분)                   │
│  ──────────────                                         │
│  @WorkflowMethod                                        │
│  async withdraw(req: WithdrawReq) {                     │
│    await activities.runKyc(req);                        │
│    await activities.runAml(req);                        │
│    const txHash = await activities.broadcast(req);      │
│    await activities.waitForConfirm(txHash);             │
│  }                                                      │
└─────────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────────┐
│  Temporal Worker SDK (라이브러리)                       │
│  - await 지점마다 자동 체크포인트                       │
│  - 재시작 시 event history를 replay 해서 state 복원     │
└─────────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────────┐
│  Temporal Server (인프라)                               │
│  - History DB (Cassandra/Postgres/MySQL)                │
│  - Task Queues                                          │
│  - Timer Service                                        │
│  - Visibility (검색용 별도 인덱스)                      │
└─────────────────────────────────────────────────────────┘
```

> [!tip] 엔진이 흡수하는 것들
> - **상태 저장**: 매 `await` 마다 event를 append. 코드에서 직접 INSERT/UPDATE 안 함.
> - **커넥션**: 앱은 Temporal gRPC 하나만 쓰면 끝. DB 커넥션 풀과 분리됨.
> - **재시도/타임아웃**: activity 옵션으로 선언. retry/backoff 정책을 코드 외부에서 관리.
> - **타이머**: `await sleep('24h')` — 워커가 죽어도 24시간 뒤 누군가 깨워준다.
> - **스키마**: 새 단계는 그냥 코드에 `await` 한 줄 추가. 마이그레이션 없음.

#### 같은 출금 워크플로우를 Temporal로 쓰면

```ts
// workflow.ts — 순차 코드처럼 보이지만 각 await가 체크포인트다
export async function withdrawWorkflow(req: WithdrawReq) {
  await runKyc(req);                       // 체크포인트 1
  await runAml(req);                       // 체크포인트 2
  const txHash = await broadcast(req);     // 체크포인트 3 (Outcome Unknown 처리는 [[deposit-request]] 노트 참조)
  await waitForConfirm(txHash, { startToCloseTimeout: '2h' });
  await notify(req.userId);                // 체크포인트 5
}
```

이 코드가 실행되는 도중 워커가 죽어도, 새 워커가 같은 workflow ID를 받아 들면 **Temporal이 event history를 replay** 해서 마지막 체크포인트까지의 상태를 메모리에 복원해주고, 그 다음 `await` 부터 이어서 실행한다.

### 둘 다 쓰는 현실적인 선택 — Outbox + 자체 상태 머신

스타트업 규모에선 Temporal을 도입하는 운영 비용(Cassandra cluster, observability 셋업)이 과할 수 있다. 그래서 많은 팀이 **하이브리드**를 쓴다.

| 패턴 | 상태 저장 | 트리거 | 적합한 경우 |
|---|---|---|---|
| **DB-driven state machine** | Postgres row + JSONB context | cron polling | 워크플로우 수 < 5, 단계 < 10 |
| **Outbox + Queue** | DB(current state) + [[Redis]]/[[Kafka]] (next step) | Queue consumer | 분기 적당, 비동기 많음 |
| **Temporal/Cadence** | Engine이 관리 | SDK | 장기 실행, saga, 다수 워크플로우 |
| **AWS Step Functions** | Engine이 관리 | EventBridge/SQS | AWS 깊게 쓰는 팀 |

> [!example] mvlchain류 핀테크에서 흔한 절충안
> - **Current State Table**: Postgres에 `withdrawal_request` row 하나 유지 (UI에서 "지금 어디까지 갔는지" 보여줘야 하므로).
> - **Event Log Table**: 같은 DB에 append-only event 테이블 (감사 + 재처리용 — 다음 [[이벤트 소싱]] 섹션에서 다룬다).
> - **Queue**: [[BullMQ]]/[[Redis]]로 단계 간 트리거.
> - 결국 "워크플로우 엔진을 가볍게 자체 구현" 하는 셈이지만, **상태가 DB에 있다는 사실은 동일**하다.

핵심은: **워크플로우 엔진을 쓴다고 DB를 안 쓰는 게 아니다.** Temporal도 내부적으로 Cassandra/Postgres를 쓴다. 다만 그 DB를 **당신이 직접 운영/마이그레이션하지 않는다**는 점에서 부담이 옮겨갈 뿐이다. 트레이드오프는 늘 "내가 관리하는 코드/스키마 양 vs. 외부 의존성과 운영 복잡도" 사이에 있다.

## 이벤트 소싱이 해결하는 것 — Current State Table + Event Log

[[워크플로우 상태]]를 관리하는 테이블이 하나뿐이면, 플로우가 늘어날 때마다 컬럼이 부풀어 오르고, 매 단계마다 `UPDATE`로 덮어쓰면서 "왜 이 상태가 됐는지"는 사라진다. [[이벤트 소싱]](Event Sourcing)이 풀려는 문제는 정확히 이 두 가지다 — **스키마 변경 부담**과 **추적·재생 가능성**.

### 핵심 아이디어 — 상태를 "쌓고", 현재값은 "투영"한다

전통적인 CRUD는 `state = f(latest UPDATE)`다. 이벤트 소싱은 뒤집어서 `state = fold(events)`로 본다. 일어난 일(이벤트)은 추가만 가능한 로그에 적재하고, 현재 상태는 그 로그를 접어서 만든 [[프로젝션]](projection) — 즉 **Current State Table**이다.

```
            ┌──────────────────────────────┐
   command  │  Handler (NestJS Service)    │
  ────────▶ │  - validate                  │
            │  - decide next event(s)      │
            └──────┬───────────────────────┘
                   │ append (immutable)
                   ▼
            ┌──────────────────────────────┐
            │  events  (append-only log)   │  ◀── 진실의 원천
            │  pk: (aggregate_id, seq)     │
            └──────┬───────────────────────┘
                   │ project (apply)
                   ▼
            ┌──────────────────────────────┐
            │  deposit_request  (current)  │  ◀── 빠른 조회용 캐시
            │  pk: id                      │
            └──────────────────────────────┘
```

> [!note] 진실의 원천은 항상 [[events 테이블]]이다
> Current State Table은 "지금까지의 이벤트를 빠르게 보기 위한 캐시"다. 잃어버려도 events에서 다시 만들 수 있어야 한다. 이게 [[재생 가능성]](replayability)의 출발점.

### 테이블 구조 — 두 개를 어떻게 잡는가

[[CQRS]] 결을 따르면, 쓰는 쪽(write model)과 읽는 쪽(read model)을 분리한다.

**(1) Event Log Table — append-only, 좁고 길게**

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | bigserial | 전역 순서 보장용 |
| `aggregate_type` | text | `'deposit_request'`, `'withdraw_request'` … |
| `aggregate_id` | uuid | 어떤 인스턴스의 이벤트인가 |
| `seq` | int | aggregate 내 순번 (낙관적 동시성용) |
| `event_type` | text | `'DepositRequested'`, `'TxBroadcasted'` … |
| `payload` | jsonb | 이벤트별 가변 필드 |
| `metadata` | jsonb | `actor`, `correlation_id`, `causation_id`, `idempotency_key` |
| `occurred_at` | timestamptz | 발생 시각 |

**(2) Current State Table — 좁고 평평하게, 자주 바뀜**

```sql
CREATE TABLE deposit_request (
  id              uuid PRIMARY KEY,
  user_id         uuid NOT NULL,
  asset           text NOT NULL,
  amount          numeric(38,18) NOT NULL,
  state           text NOT NULL,         -- 'pending' | 'broadcasted' | 'confirmed' | 'failed'
  tx_hash         text,
  last_event_seq  int NOT NULL,          -- 어디까지 투영했는지
  updated_at      timestamptz NOT NULL
);
```

> [!tip] `last_event_seq`가 멱등 투영의 열쇠
> 같은 이벤트가 재처리돼도 `seq <= last_event_seq`면 무시. 덕분에 [[프로젝터]](projector)가 at-least-once로 돌아도 안전하다.

### 스키마 변경 부담을 줄이는 방식

새로운 플로우 — 가령 [[KYC 재검사 단계]] — 가 추가됐다고 하자.

**단일 상태 테이블만 있을 때:**

```sql
ALTER TABLE deposit_request ADD COLUMN kyc_recheck_started_at timestamptz;
ALTER TABLE deposit_request ADD COLUMN kyc_recheck_result text;
ALTER TABLE deposit_request ADD COLUMN kyc_recheck_attempts int DEFAULT 0;
-- 매 플로우마다 컬럼이 우후죽순 …
```

테이블이 60개 컬럼짜리 괴물로 성장하고, 옛 row는 전부 NULL이며, 마이그레이션은 락을 잡는다.

**이벤트 로그 + 투영 구조에서는:**

```ts
// 새 이벤트만 정의하면 끝. 스키마 변경 0줄.
type KycRecheckRequested = {
  type: 'KycRecheckRequested';
  payload: { reason: string; required_level: 'L2' | 'L3' };
};
```

새 필드는 `payload` jsonb에 들어가고, 그 이벤트를 본 [[프로젝터]]만 Current State에 의미 있는 컬럼(예: `state = 'kyc_recheck'`)으로 반영한다. **Current State 테이블은 "지금 라이브 플로우가 쓰는 필드"만 유지**하면 되고, 죽은 컬럼은 종료된 플로우와 함께 정리할 수 있다.

> [!example] 스키마 진화의 비대칭성
> - **이벤트**: 추가 only, 절대 수정 금지 (불변 사실). 새 버전이 필요하면 `v2` 이벤트 타입을 새로 만든다.
> - **현재 상태**: 자유롭게 재구성. 날려도 events에서 `REPLAY`로 재생성된다.

### 재생(Replay)과 추적(Audit)

`deposit_request 4f2a…`가 왜 `failed`가 됐는지 추적하려면 events를 시간순으로 펼치면 된다.

```sql
SELECT seq, event_type, payload, metadata->>'actor', occurred_at
FROM events
WHERE aggregate_type = 'deposit_request'
  AND aggregate_id = '4f2a...'
ORDER BY seq;
```

```
seq  event_type           payload (요약)                         occurred_at
─── ─────────────────── ───────────────────────────────────── ─────────────────
 1   DepositRequested    amount=1.5 ETH, user=u_91             10:01:03.211
 2   NonceAllocated      nonce=482                             10:01:03.450
 3   TxBroadcasted       tx_hash=0xab…, raw_tx=0xf86…          10:01:04.002
 4   TxOutcomeUnknown    reason="rpc timeout 30s"              10:01:34.018
 5   TxReceiptFetched    status=0 (reverted)                   10:02:11.880
 6   DepositFailed       reason="reverted: insufficient gas"   10:02:11.901
```

> [!tip] [[재생 가능성]]이 살리는 시나리오
> - **버그 수정 후 과거 재계산**: 수수료 산정 로직 버그를 고친 뒤, 영향받은 aggregate들의 events를 다시 fold해서 Current State를 재생성.
> - **신규 read model 추가**: "사용자별 일일 입금 합계" 같은 새 화면을 만들 때, 기존 events에서 새 프로젝션을 빌드. 운영 DB에 새 컬럼 안 만들어도 된다.
> - **포렌식 / 감사**: "이 row가 왜 이런 값이 됐는가?"에 시간순 답을 제공. [[컴플라이언스]] 요구가 있는 도메인(자산 이동, 결제)에 필수.

### 동시성과 멱등성 — `(aggregate_id, seq)`의 역할

같은 aggregate에 두 요청이 동시에 이벤트를 쓰려고 하면 `UNIQUE(aggregate_id, seq)` 제약이 한 쪽을 떨어뜨린다. 이게 [[낙관적 동시성 제어]](optimistic concurrency)다. 핸들러는

```ts
const current = await load('deposit_request', id);   // events fold
const next = decide(current, command);                // 순수 함수
await appendEvents(id, current.seq, next.events);     // seq+1, +2, ...
```

이 `appendEvents`가 `seq` 충돌로 실패하면 재시도 — 동일한 [[idempotency_key]] metadata로 들어왔다면 그 자체가 안전망이 된다.

> [!warning] 이벤트 소싱이 공짜는 아니다
> - **읽기 복잡도**: aggregate를 매번 fold하면 비싸다 → 스냅샷 + Current State Table로 보완.
> - **이벤트 버저닝**: payload 스키마가 바뀔 때 옛 이벤트를 어떻게 읽을지(upcaster) 설계 필요.
> - **모든 도메인에 어울리진 않음**: CRUD가 충분한 곳에 강제로 끼우면 오버엔지니어링. "왜 이 상태가 됐는지"를 사후에 묻는 도메인(금융, [[Treasury]], 주문)에서 빛난다.

## Datadog 로그 vs 이벤트 테이블 — 왜 따로 두는가

처음 보면 둘 다 "시간순으로 쌓이는 append-only 기록"처럼 보여서 "DD로 통일하면 안 되나?" 싶다. 하지만 **목적이 근본적으로 다르고, 보장 수준도 다르다.** 둘은 보완재이지 대체재가 아니다.

### 한눈에 보는 차이

| 축 | Datadog 로그 | 이벤트 테이블 (event log) |
|---|---|---|
| **목적** | 디버깅, 모니터링, 알림 | 감사, 재처리, 상태 복구 |
| **소유자** | SRE/운영 관점 | 비즈니스 도메인 관점 |
| **신뢰도** | best-effort (드롭 OK) | ACID, 트랜잭션 보장 |
| **보존** | 7~30일 (비용 압박) | 영구 (법규/감사) |
| **스키마** | 비/반정형 텍스트 | 강타입, 버전 관리 |
| **수정성** | 로테이션/삭제 가능 | 절대 불변 (immutable) |
| **쿼리** | 풀텍스트, 메트릭 집계 | aggregate_id 기준 정렬 |
| **재생 가능성** | 상태 재구성 불가 | 임의 시점 상태 재구성 가능 |
| **진실의 원천** | 관측 결과 (derived) | 권위 (authoritative) |

### 보장 수준이 다르다

> [!warning] DD는 로그가 드롭되어도 비즈니스가 멈추지 않아야 정상이다
> [[Datadog]] agent가 죽거나 네트워크가 끊기면 로그는 버퍼에서 넘쳐 드롭된다. 그래도 OK — 그게 관측 시스템의 성질이다. 반대로 `deposit_request_events` 테이블에 INSERT가 실패하면 **그 입금은 일어나지 않은 것**이어야 한다.

이벤트 테이블은 보통 비즈니스 상태와 **같은 트랜잭션** 안에서 쓴다:

```sql
BEGIN;
  UPDATE deposit_request SET status='PROCESSING' WHERE id = $1;
  INSERT INTO deposit_request_events (deposit_request_id, type, payload)
    VALUES ($1, 'StatusChanged', '{"from":"PENDING","to":"PROCESSING"}');
COMMIT;
```

DD는 이런 보장을 못 한다 — `logger.info(...)` 호출은 fire-and-forget 이고, agent → 인덱서 → 보관소 사이 어디서든 메시지가 사라질 수 있다.

### 재생 가능성 (Replayability)

이게 가장 큰 차이다. **이벤트 테이블은 상태를 다시 만든다. DD 로그는 못 만든다.**

```
이벤트 테이블이 있으면:
   events ──fold──▶ 현재 상태
                 ──filter──▶ 특정 시점 상태
                 ──replay──▶ 새 read model

DD만 있으면:
   logs ──grep──▶ "아 이때 뭐가 깨졌나 보네" (가설 검증용)
```

예: read model을 새 컬럼이 추가된 스키마로 마이그레이션할 때, 이벤트 테이블을 처음부터 재생하면 정확한 새 상태가 만들어진다. DD 로그로는 절대 불가능 — 로그 라인은 사람이 읽기 쉬운 자유 텍스트이지, 도메인 이벤트의 캐논 표현이 아니다.

> [!example] 입금 재처리 시나리오
> [[deposit_request]] 처리 중 외부 PG가 응답이 늦어서 우리 워커가 타임아웃을 봤다. 이때 상태는 [[Outcome Unknown]]. 30분 뒤 콜백이 도착한다.
> - 이벤트 테이블이 있으면: `TxSent`, `TimeoutObserved`, `CallbackReceived` 이벤트를 순서대로 가지고 정확히 복원 가능.
> - DD만 있으면: 어딘가에 `error: timeout` 라인은 있지만, 그게 어떤 deposit_request에 대응되는지 파싱해서 끌어오기까지 손작업이 필요하고, 그마저도 보존 기간이 지나면 사라진다.

### 쿼리 패턴이 다르다

- **DD**: "지난 1시간 동안 latency p95가 튀었는데 왜?" — 시계열, 풀텍스트, 트레이스 ID 조인.
- **이벤트 테이블**: "deposit_request_id = `abc-123` 의 모든 상태 전이를 시간순으로 보여줘" — `WHERE aggregate_id = ? ORDER BY sequence_no ASC`.

전자는 분석/관측 워크로드, 후자는 OLTP에 가까운 점 조회. 같은 시스템에 욱여넣으면 둘 다 어색해진다.

### 보존 기간과 비용

- DD는 인덱싱된 로그 기준 GB당 비용이 비싸서 7~30일 보존이 보통. 90일 이상은 cold storage로 빠진다.
- 이벤트 테이블은 보통 도메인 DB(Postgres 등)에 들어가서 영구 보존. 입금 같은 도메인은 **법적으로** 수년치 감사 흔적이 필요할 수 있다.

### 그럼 DD는 왜 쓰나?

이벤트 테이블이 못 하는 걸 한다:
- 시스템 메트릭 (CPU, 메모리, 네트워크)
- 외부 호출 latency 분포
- 알림(alert)과 on-call 인테그레이션
- 분산 트레이싱 (여러 서비스를 가로지르는 호출)
- 자유 텍스트 검색 ("auth middleware에서 raise된 에러 다 보여줘")

이건 모두 **운영자**의 도구다. 비즈니스 로직이 의존하면 안 되는 것들.

> [!tip] 멘탈 모델
> - **DD = "지금 시스템이 어떻게 동작하고 있나"의 관측 (운영자용, ephemeral)**
> - **이벤트 테이블 = "이 도메인 엔티티에 무슨 일이 있었나"의 권위 있는 기록 (비즈니스용, immutable)**
>
> 둘은 서로 다른 질문에 답한다. 한쪽으로 합치려 하면 둘 다 잃는다.

### 안티패턴

- **DD를 감사 로그로 쓴다**: 보존 기간 끝나면 증거가 사라진다. 컴플라이언스 사고.
- **이벤트 테이블을 디버그 로그처럼 쓴다**: 스키마가 자유 텍스트로 변질되고, 이벤트 타입이 폭증하며, 재생 시 의미를 잃는다.
- **이벤트 테이블 INSERT를 fire-and-forget으로**: 트랜잭션 밖으로 빼면 비즈니스 상태와 이벤트가 어긋난다 → [[이벤트 소싱]]의 모든 보장이 무너진다.

## 비동기 워크플로우의 핵심 개념 — deposit_request·Idempotency·Outcome Unknown

### 1. `deposit_request` — "요청을 1급 엔티티로 승격시킨다"

크립토/금융 백엔드에서 흔히 보이는 `deposit_request`, `withdraw_request`, `swap_request` 같은 테이블은 단순한 "로그용 테이블"이 아니다. **요청 자체를 하나의 도메인 엔티티(Aggregate)로 다루기 위한 장치**다.

순진하게 생각하면 출금은 그냥 함수 호출이다.

```ts
// ❌ 순진한 버전
async function withdraw(userId, amount, toAddress) {
  await chain.send(userId, amount, toAddress)
  await db.balance.decrement(userId, amount)
}
```

그러나 실제로는 다음 문제들이 동시에 터진다.

- 사용자가 "Submit" 버튼을 두 번 눌렀다 → **중복 송금**
- 체인에 트랜잭션을 쐈는데 RPC가 타임아웃 → **성공인지 실패인지 모름**
- 운영자가 큰 금액에 대해 수동 승인을 해야 한다 → **여러 단계의 상태**
- 컴플라이언스 팀이 KYC 재검토를 요구한다 → **플로우 도중 일시 정지**
- 며칠 후 "어제 이 출금 뭐냐"고 추적해야 한다 → **감사 가능성**

이 모든 요구를 만족시키려면 "출금 함수"가 아니라 "출금 요청이라는 객체"가 있어야 한다.

```sql
CREATE TABLE deposit_request (
  id              UUID PRIMARY KEY,        -- Request ID
  idempotency_key TEXT UNIQUE,             -- 클라이언트가 보낸 고유 키
  user_id         UUID NOT NULL,
  asset           TEXT NOT NULL,
  amount          NUMERIC(38,18) NOT NULL,
  to_address      TEXT NOT NULL,

  status          TEXT NOT NULL,           -- pending / signing / broadcasting / mined / confirmed / failed / outcome_unknown
  raw_tx          BYTEA,                   -- 서명까지 끝난 직렬화 트랜잭션
  nonce           BIGINT,                  -- 이 요청이 점유한 nonce
  tx_hash         TEXT,                    -- broadcasting 직후 계산해서 저장
  block_number    BIGINT,
  confirmations   INT,

  created_at      TIMESTAMPTZ DEFAULT now(),
  updated_at      TIMESTAMPTZ
);
```

> [!note] 핵심 관점
> `deposit_request`는 "사용자가 무엇을 원했는지(intent)"와 "지금 그 의도가 어디까지 진행됐는지(progress)"를 동시에 표현한다. [[이벤트 소싱]]에서는 이게 [[Current State Table]] 역할을 하고, 단계별 변화는 [[Event Log]]에 따로 쌓인다.

### 2. Idempotency Key·Request ID·txHash — 세 단계의 추적 키

비동기 플로우에서 "같은 요청"을 식별하는 키는 한 종류가 아니다. **계층별로 다른 키를 쓴다.**

| 계층 | 키 | 발급 주체 | 충돌 시 동작 | 수명 |
|------|-----|-----------|---------------|------|
| 클라이언트 → API | `Idempotency-Key` 헤더 | 클라이언트(혹은 SDK) | 같은 응답을 반환 (재실행 X) | 보통 24h |
| API → 내부 시스템 | `request_id` (UUID) | 서버가 INSERT 시 발급 | 절대 충돌 안 함 | 영구 |
| 백엔드 → 체인 | `tx_hash` | 서명된 raw tx의 keccak256 | 같은 nonce면 같은 hash | 영구 (체인에 기록) |

```
[Client]                  [API Gateway]                [Worker]                 [Chain]
   |                           |                          |                       |
   |  POST /withdrawals        |                          |                       |
   |  Idempotency-Key: abc123  |                          |                       |
   |-------------------------->|                          |                       |
   |                           | SELECT ... WHERE         |                       |
   |                           |   idempotency_key='abc'  |                       |
   |                           | --found? return cached   |                       |
   |                           | --new? INSERT request    |                       |
   |                           |   id=req_42, status=pend |                       |
   |  202 Accepted             |                          |                       |
   |  { request_id: req_42 }   |                          |                       |
   |<--------------------------|                          |                       |
   |                           |  enqueue(req_42)         |                       |
   |                           |------------------------->|                       |
   |                           |                          | nonce=lock(addr)      |
   |                           |                          | rawTx = sign(...)     |
   |                           |                          | tx_hash = keccak(rawTx)|
   |                           |                          | UPDATE request        |
   |                           |                          |   SET raw_tx, nonce,  |
   |                           |                          |       tx_hash,        |
   |                           |                          |       status='broad'  |
   |                           |                          | sendRawTransaction()  |
   |                           |                          |---------------------->|
   |                           |                          |   (timeout? ERR? OK?) |
```

> [!tip] 왜 굳이 세 단계인가
> - **Idempotency Key**는 "사용자의 재시도"를 흡수한다. 같은 키 = 같은 결과.
> - **Request ID**는 "내부 로그·메시지·이벤트"를 묶는 trace key다. 큐 메시지·이벤트 로그·Datadog 로그가 전부 이걸로 join된다.
> - **txHash**는 "온체인 진실"이다. 우리 DB가 뭐라 적혀 있든, 체인이 가진 hash가 정답이다.

---

### 3. Outcome Unknown — "성공도 실패도 아닌" 3상태

전통적인 동기 API는 결과가 `success | failure` 이지선다다. 그러나 **외부 시스템에 쓰기(write)를 보냈는데 응답이 끊겼을 때**는 그렇지 않다.

```ts
try {
  const txHash = await provider.sendRawTransaction(rawTx)
  // -> 여기 오면 broker가 받았다는 의미. 단 mining 보장은 아님.
} catch (e) {
  // -> 여기 오는 경우가 함정이다.
  // 1) RPC 노드가 아예 못 받음 (네트워크 끊김)
  // 2) RPC는 받았는데 응답이 우리한테 도착하기 전에 타임아웃
  // 3) mempool에는 들어갔는데 우리가 모름
  // 4) replacement tx가 먼저 mining 됨
  // 모두 같은 exception으로 보인다.
}
```

이 "catch에 들어왔지만 진짜로 실패한 건지는 모름" 상태를 [[Outcome Unknown]] 이라고 부른다. Temporal 문서에서 종종 "the third outcome" 으로 언급된다.

> [!warning] 안티패턴
> Outcome Unknown을 그냥 `status = 'failed'` 로 적어 버리면, 잠시 후 같은 nonce·같은 rawTx가 체인에 mining되어도 우리 DB는 영원히 "failed"라고 거짓말을 하게 된다. 이중 송금의 가장 흔한 원인이다.

### 올바른 처리 — `outcome_unknown` 명시적 상태

```
       ┌─ confirmed   ← receipt 조회 성공 + 충분한 confirmations
       │
broadcasting ── outcome_unknown ── (reconciler가 주기적으로 폴링)
       │              │
       │              ├─ tx_hash로 receipt 발견 → confirmed / reverted
       │              └─ N블록 지나도 mempool에도 없음 → safe to retry
       │
       └─ failed (signing 실패 등, 체인에 아예 안 나간 게 확실한 경우)
```

핵심 규칙:

1. **`sendRawTransaction` 호출 직전에 `tx_hash`와 `raw_tx`를 먼저 DB에 저장**한다.
2. 호출 결과와 무관하게, `tx_hash`만 있으면 나중에 `eth_getTransactionByHash`로 진실을 확인할 수 있다.
3. 타임아웃·에러는 무조건 `outcome_unknown` 으로 적고, **별도의 reconciler(또는 [[Treasury Queue]] 워커)** 가 주기적으로 체인을 폴링해서 진짜 상태로 수렴시킨다.

```ts
// ✅ 안전한 패턴 의사코드
async function broadcast(req: DepositRequest) {
  const nonce  = await nonceManager.reserve(req.fromAddress) // 동일 주소 직렬화
  const rawTx  = signer.sign({ ...req, nonce })
  const txHash = keccak256(rawTx)

  await db.update(req.id, { raw_tx: rawTx, nonce, tx_hash: txHash,
                            status: 'broadcasting' })

  try {
    await provider.sendRawTransaction(rawTx)
    await db.update(req.id, { status: 'mined_pending' })
  } catch (err) {
    // ❗ 절대 'failed'로 적지 않는다.
    await db.update(req.id, { status: 'outcome_unknown',
                              last_error: serialize(err) })
  }
}
```

### 4. Nonce Manager·rawTx 저장·Treasury Queue — 묶음 패턴

위 흐름이 동작하려면 세 가지가 한 세트로 움직여야 한다.

> [!example] 묶음 패턴
> **(a) Nonce Manager**
> 같은 sender 주소에 대한 트랜잭션은 nonce가 순차여야 한다. Redis나 DB row lock으로 "이 요청은 nonce=42를 점유한다"를 *DB에 쓰기 전에* 확정한다. 그래야 같은 nonce를 두 번 쓰는 일이 없다.
>
> **(b) raw_tx 저장**
> 서명된 직렬화 트랜잭션을 컬럼에 박아 둔다. RPC가 죽었어도, 워커가 죽었다 살아나도, **같은 raw_tx를 같은 hash로 다시 broadcast** 할 수 있다. (체인은 동일 tx를 중복 제출해도 한 번만 mining한다 — 멱등이다.)
>
> **(c) Treasury Queue**
> "출금 큐"는 단순 FIFO가 아니라 **sender 주소별로 직렬화된 큐**다. 같은 핫월렛 주소에서 동시에 두 트랜잭션이 나가면 nonce 경쟁이 나기 때문에, 주소를 partition key로 잡아 워커 하나가 한 번에 하나씩만 처리한다. Outcome Unknown이 있으면 그게 풀릴 때까지(=reconciler가 confirmed/reverted/expired로 정리할 때까지) 다음 트랜잭션을 막는다.

```
        deposit_request (status=pending)
                │
                ▼
        ┌───────────────────┐
        │  Treasury Queue   │   partition by from_address
        │  ┌─────┐ ┌─────┐  │
        │  │addr1│ │addr2│  │   각 파티션은 단일 워커
        │  └──┬──┘ └──┬──┘  │
        └─────┼───────┼─────┘
              ▼       ▼
        Nonce Manager (per-address lock)
              │
              ▼
        sign → save raw_tx, tx_hash → broadcast
              │
              ├─ ok            → mined_pending → (reconciler) → confirmed
              └─ timeout/err   → outcome_unknown ─┐
                                                  ▼
                                          Reconciler polls chain
                                          by tx_hash, 결정 내림
```

> [!note] 결국 이 셋은 같은 문제를 푼다
> "체인이라는 외부 시스템에 대해 **at-least-once로 보내되 결과는 정확히 한 번** 반영한다" — 즉 **exactly-once effect**를 흉내내는 것. Idempotency Key(클라이언트 측), Request ID(내부 trace), tx_hash(외부 진실)가 layered idempotency를 만들고, Outcome Unknown 상태와 reconciler가 그 사이를 메운다.

## English

### TL;DR

In a backend, "taking a different flow when the request needs something extra" is the problem of **[[오케스트레이션 orchestration]]**. As branching, retries, and timeouts multiply, the standard answer is to model the flow as *data* using a **[[상태 머신 state machine]]** (e.g. [[XState]]) or a **[[워크플로우 엔진 workflow engine]]** ([[Temporal]], [[AWS Step Functions]]). That state must live somewhere — but a single `status` column only tells you *where* the workflow is, not *why* or *when* it got there. The gap is filled by **[[이벤트 소싱 event sourcing]]**, which pairs a **[[Current State Table]]** with an **[[Event Log Table]]**. Even with [[Datadog]] in place, you keep a dedicated event table because *logs are for observability while events are the source of truth for domain state*. The difference becomes decisive in async calls with uncertain results — the **[[Outcome Unknown]]** problem, e.g. tracking `txHash` from `sendRawTransaction` on a blockchain, or retrying [[deposit_request]] safely via an **[[Idempotency Key]]**.

> [!note] One-liner
> **Orchestration is the question of "how to branch"; state machines / engines answer "how to express that branching in code"; event sourcing answers "how to preserve every one of those decisions without loss."** The three are not competitors — they are *layers*.

```
┌────────────────────────────────────────────────────────────┐
│  Orchestration (who conducts branching, retry, timeout?)   │
│     │                                                      │
│     ▼                                                      │
│  State Machine / Workflow Engine (XState, Temporal …)      │
│     │  ← code model                                        │
│     ▼                                                      │
│  Persistence Layer                                         │
│     ├─ Current State Table   ← "where am I now"            │
│     └─ Event Log Table       ← "how I got here" (ES)       │
│           │                                                │
│           ▼                                                │
│  Observability (Datadog, Sentry) ← side view, not truth    │
└────────────────────────────────────────────────────────────┘
```

> [!tip] How to read this note
> The sections below trace the diagram top-down: *branching patterns → code expression ([[XState]]) → where state lives → event sourcing → contrast with logs → async / [[Idempotency]] in practice*.

### What is Orchestration? — Patterns for Branching Flows

"A deposit request comes in, but KYC isn't done → so it diverts to the KYC flow → then comes back to process the deposit." When **one business request weaves through several sub-flows conditionally**, that's broadly called [[workflow-orchestration|orchestration]]. The two core questions are:

1. **Who decides what runs next?** (central conductor vs. each service for itself)
2. **How do you track where the request is now?** (memory / DB / event log)

The patterns split along those two axes.

### Orchestration vs Choreography — Who Holds the Flow

> [!note] Two big families
> - **Orchestration**: a central controller explicitly calls "next is B, then C". The flow lives in one place in code.
> - **Choreography**: each service emits events; others subscribe and react on their own. Loosely coupled, but "what the overall flow looks like" isn't written down anywhere in code.

```
[Orchestration]                          [Choreography]
                                                            
   ┌──────────────┐                       ServiceA ── event ──▶ Bus
   │ Orchestrator │                                          │
   └───┬──────┬───┘                              ┌───────────┼───────────┐
       │      │                                  ▼           ▼           ▼
       ▼      ▼                              ServiceB    ServiceC    ServiceD
   ServiceA ServiceB
```

On traceability, [[orchestration-pattern|Orchestration]] almost always wins. "Where did this request get stuck?" needs only one controller file. Choreography quickly becomes a debugging hell in production.

### Pattern-by-Pattern Comparison

The four canonical implementation patterns for branching flows:

| Pattern | How branching is expressed | State storage | Fits complexity | Traceability |
|---|---|---|---|---|
| **Pipeline / Chain of Responsibility** | `if/else`, early return | usually in-memory (request lifetime) | Low (linear + 1–2 branches) | Low (logs only) |
| **State Machine ([[xstate]], statecharts)** | transitions declared per state | memory + external persist | Medium (10–50 states) | Medium (current state explicit) |
| **Saga (Choreography-based)** | events + compensating actions | event log + each service's local DB | Mid–high (distributed) | Low (needs event-tracking tooling) |
| **[[temporal|Workflow Engine]] (Temporal, Cadence, AWS Step Functions)** | written as code, engine persists | engine auto-persists (event sourced) | High (workflows lasting days–months) | Very high (replayable) |

#### 1. Pipeline — the simplest starting point

```typescript
async function handleDeposit(req: DepositRequest) {
  await validateRequest(req)
  if (!await isKycComplete(req.userId)) {
    await startKycFlow(req.userId)
    return { status: 'PENDING_KYC' }
  }
  await reserveBalance(req)
  await submitOnChain(req)
  return { status: 'SUBMITTED' }
}
```

> [!tip] Where Pipeline breaks down
> Fine with 2–3 branches. But once steps multiply and each becomes async over days — e.g. deposit → wait for KYC → wait for compliance approval → wait for on-chain confirmation → settle — it no longer fits in a single function call. If the process dies between steps, there's no way to recover where it was.

#### 2. State Machine — making state a first-class citizen

You **declare as data** what events in each state cause which transitions. [[xstate]] is the canonical example.

```
        ┌──────────┐  KYC_OK   ┌──────────┐  COMPLIANCE_OK  ┌─────────────┐
   ───▶ │ created  │──────────▶│ kyc_done │────────────────▶│ ready_to_tx │
        └────┬─────┘           └────┬─────┘                 └──────┬──────┘
             │ KYC_FAIL              │ COMPLIANCE_FAIL              │ SUBMIT
             ▼                       ▼                              ▼
         ┌───────┐               ┌─────────┐                   ┌──────────┐
         │rejected│               │rejected │                   │submitted │
         └───────┘               └─────────┘                   └────┬─────┘
                                                                    │ CONFIRMED
                                                                    ▼
                                                                ┌────────┐
                                                                │settled │
                                                                └────────┘
```

> [!example] Where the state machine wins
> "This payment is in `rejected` — how did it get there?" Because transitions are explicit, the possible paths are finite. And when someone adds a new state, code review can ask "did you handle every event reachable in this state?"

That said, plugging [[xstate]] into NestJS means **you handle persistence yourself** — XState knows only what state the in-memory machine is in; it doesn't make the machine resume from the same spot after a process restart. The next section ([[nest-xstate-workflow]]) digs into this.

#### 3. Saga — compensating pattern that mimics distributed transactions

When a transaction spans services and you need "all succeed or all roll back", but distributed reality precludes real 2PC. **Define a compensating action for each step**, and if something fails downstream, you unwind backwards.

```
Forward:    reserveBalance ──▶ deductFee ──▶ submitOnChain ──▶ markSettled
                                                │
                                                │ FAIL
                                                ▼
Compensate:                       refundFee ◀── releaseBalance
```

> [!warning] Saga's trap
> If a compensating action isn't idempotent, the rollback can run twice. And actions that already left the system (an email sent, an on-chain transaction broadcast) can't truly be undone — you have to issue a separate compensating transaction and reconcile bookkeeping-wise.

#### 4. Workflow Engine — written as code, persisted by the engine

[[temporal|Temporal]], Cadence, AWS Step Functions, Airflow, that family. The core magic:

```typescript
// This function can live for days. Even if the process dies and restarts, it resumes at the same spot.
async function depositWorkflow(req: DepositRequest) {
  await activities.validate(req)

  if (!await activities.isKycComplete(req.userId)) {
    await workflow.executeChildWorkflow(kycWorkflow, req.userId) // may wait days
  }

  const txHash = await activities.submitOnChain(req)
  await workflow.condition(() => activities.isConfirmed(txHash), '1 hour')

  return { status: 'SETTLED', txHash }
}
```

> [!note] How is this possible?
> The workflow engine **records the result of every `await` to an event log**. When the process dies, on restart it replays the code from the top — any `await` already in the log returns its recorded value, and only the un-executed tail actually runs. This is a direct application of [[event-sourcing|event sourcing]] — covered in detail in a later section.

### How to Choose

> [!tip] Decision guide
> - **1–2 branches, synchronous, single process**: just Pipeline. Don't over-engineer.
> - **5+ states with clear transitions in the domain** (orders, KYC, billing): [[xstate|XState]] + DB persistence. The big payoff is code and diagram staying in sync.
> - **Steps that span days + external callback waits + complex retry/timeout logic**: seriously evaluate engines like [[temporal|Temporal]]. Rolling your own ends up as a half-baked Temporal.
> - **A transaction crossing many microservices owned by different teams**: Saga + event bus. But pair it with tracing ([[opentelemetry|OpenTelemetry]] traces) or debugging becomes impossible.

**Complexity / traceability tradeoff at a glance**:

```
Complexity ─────────────────────────────────────────▶
Pipeline  <  State Machine  <  Saga  <  Workflow Engine

Traceability cost-effectiveness
                 State Machine  (the sweet spot)
                       ▲
                       │
Pipeline ──────────────┴──────────────── Workflow Engine
  (low invest, low return)         (high invest, very high return)
                 Saga
                 (high invest, loses without tracing tooling)
```

In fintech/crypto domains — **money moves, external systems (chains, banks, card networks) respond asynchronously, and audits are required** — you almost always need to climb at least to [[state-machine|state machines]]. And once you do, the next question naturally follows: "where do we store the state?" — which is the topic of the next section.

### NestJS + XState — Modeling Workflows as Code

The honest reason to reach for [[XState]] inside a [[NestJS]] backend is **"I want to lift my if/else hell into a specified state machine."** Multi-step flows that wait on external callbacks — payments, KYC, withdrawals — become untraceable as branches accumulate inside handlers. XState declares states, events, guards, actions, and `invoke`d services as an object tree, and computes transitions as **pure functions**, which slots naturally on top of Nest's DI/providers.

### Real use case — a Withdrawal machine

> [!example] Scenario
> User requests withdrawal → internal policy check → fetch a nonce from the [[nonce manager]] → sign rawTx → `sendRawTransaction` → receive txHash → wait for confirmation → done/failed. Any step can land in [[Outcome Unknown]].

```ts
// withdrawal.machine.ts
import { setup, assign } from 'xstate';

export const withdrawalMachine = setup({
  types: {
    context: {} as {
      requestId: string;        // same role as deposit_request — an idempotency key
      txHash?: string;
      rawTx?: string;
      lastError?: string;
      retries: number;
    },
    events: {} as
      | { type: 'POLICY_OK' }
      | { type: 'POLICY_REJECT'; reason: string }
      | { type: 'SIGNED'; rawTx: string }
      | { type: 'BROADCASTED'; txHash: string }
      | { type: 'BROADCAST_TIMEOUT' }
      | { type: 'CONFIRMED' }
      | { type: 'REVERTED' },
  },
  actors: {
    runPolicyCheck: undefined as any,
    signRawTx:      undefined as any,
    broadcastTx:    undefined as any,
    waitConfirm:    undefined as any,
  },
  guards: {
    canRetry: ({ context }) => context.retries < 3,
  },
}).createMachine({
  id: 'withdrawal',
  initial: 'policyCheck',
  context: { requestId: '', retries: 0 },
  states: {
    policyCheck: {
      invoke: { src: 'runPolicyCheck', onDone: 'signing', onError: 'rejected' },
    },
    signing: {
      invoke: { src: 'signRawTx', onDone: { target: 'broadcasting',
        actions: assign({ rawTx: ({ event }) => event.output }) } },
    },
    broadcasting: {
      invoke: {
        src: 'broadcastTx',
        onDone: { target: 'confirming',
          actions: assign({ txHash: ({ event }) => event.output }) },
        onError: 'outcomeUnknown',          // sendRawTransaction timeout
      },
    },
    outcomeUnknown: {                       // the load-bearing state
      on: {
        BROADCASTED: { target: 'confirming',
          actions: assign({ txHash: ({ event }) => event.txHash }) },
        BROADCAST_TIMEOUT: { target: 'broadcasting',
          guard: 'canRetry',                // reuse the same rawTx/nonce
          actions: assign({ retries: ({ context }) => context.retries + 1 }) },
      },
    },
    confirming: {
      invoke: { src: 'waitConfirm',
        onDone: 'completed', onError: 'reverted' },
    },
    completed: { type: 'final' },
    rejected:  { type: 'final' },
    reverted:  { type: 'final' },
  },
});
```

```
       ┌───────────┐  POLICY_OK   ┌─────────┐  SIGNED   ┌──────────────┐
 start │policyCheck│─────────────▶│ signing │──────────▶│ broadcasting │
       └─────┬─────┘              └─────────┘           └──────┬───────┘
             │ POLICY_REJECT                                   │ timeout
             ▼                                                 ▼
        ┌────────┐                                       ┌──────────────┐
        │rejected│                                       │outcomeUnknown│◀──BROADCAST_TIMEOUT (retry, canRetry)
        └────────┘                                       └──────┬───────┘
                                                                │ BROADCASTED(txHash)
                                                                ▼
                                                          ┌────────────┐ CONFIRMED  ┌──────────┐
                                                          │ confirming │───────────▶│ completed│
                                                          └─────┬──────┘            └──────────┘
                                                                │ REVERTED
                                                                ▼
                                                            ┌──────────┐
                                                            │ reverted │
                                                            └──────────┘
```

### How it fits into Nest

> [!note] Integration pattern
> - **Machine definitions** live in pure modules (`*.machine.ts`), no DI.
> - **Actor execution** lives in an `@Injectable()` service like `WithdrawalOrchestrator` that calls `createActor(machine)` and wires `invoke` actors to Nest providers (repos, RPC, queues).
> - **Persistence** happens right after each transition: `actor.getPersistedSnapshot()` is written to a workflow row in DB, or appended to the [[Event Log]].
> - **Inbound events** — controllers/listeners translate external callbacks (e.g. node RPC webhooks) into `actor.send({ type: 'BROADCASTED', txHash })`.

```ts
@Injectable()
export class WithdrawalOrchestrator {
  constructor(
    private repo: WorkflowRepo,
    private signer: SignerService,
    private rpc: RpcService,
    private nonce: NonceManager,
  ) {}

  async resume(requestId: string) {
    const row = await this.repo.find(requestId);
    const actor = createActor(withdrawalMachine.provide({
      actors: {
        signRawTx:   fromPromise(() => this.signer.sign(requestId)),
        broadcastTx: fromPromise(() => this.rpc.sendRaw(row.rawTx!)),
        // ...
      },
    }), { snapshot: row.snapshot });   // ← rehydrate

    actor.subscribe((s) => this.repo.save(requestId, s));
    actor.start();
    return actor;
  }
}
```

### Upsides

| Item | Effect |
|---|---|
| Visualization | The [[Stately]] editor/Inspector renders the machine as-is. PR reviews become diagram reviews. |
| Testability | Guards/actions are pure → unit tests against `transition(state, event)` cover branching 100%, no infra needed. |
| Specification | "In this state, only these events are accepted" is enforced by code. Invalid events are ignored or errored — an [[invariant]] guarantee. |
| Model checking | `@xstate/test` can generate path coverage and surface unreachable/dead states ahead of time. |
| Incremental adoption | You can machine-ify just one domain (withdrawals) and leave the rest as plain Nest handlers. No infra footprint like Temporal. |

### Drawbacks / sharp edges

> [!warning] What XState alone won't give you
> - **Persistence is on you.** Where snapshots live and how conflicts merge is your problem → you need a [[Current State Table]] + [[Event Log]] pattern.
> - **Timers and retries are on you.** `after: { 5000: ... }` is an in-memory timer that dies with the process. You'll still need an external scheduler ([[BullMQ]], [[Redis]] delayed jobs, cron).
> - **No distributed locking.** Two instances spinning actors with the same `requestId` will both progress. You must serialize with a row lock or an [[Outbox]].
> - **Long-running workflows are heavy.** You can't hold a 30-minute confirmation in memory; the canonical cycle is "event arrives → hydrate → one step → persist → release."
> - **Schema migrations are tricky.** If you change the machine but DB still holds old snapshots, you'll hit unknown-state errors. Store a `machineVersion` alongside.

### Comparison with external engines like Temporal

| Axis | XState (inside NestJS) | [[Temporal]] / [[AWS Step Functions]] / [[Cadence]] |
|---|---|---|
| Where it runs | Inside your Nest process | A separate cluster (workers are clients) |
| State storage | You own it (DB / Event Log) | The engine owns it (built-in Event History) |
| Determinism | Encouraged, not enforced | Workflow code **must** be deterministic (replay-based) |
| Timers / retries | DIY | Durable timers & retries provided |
| Visualization | Stately Inspector | Temporal Web UI (per-execution traces) |
| Operational cost | Near zero (it's a library) | Cluster + DB + UI + metrics to operate |
| Observability / audit | You design the [[Event Log]] | Every event auto-recorded in Event History |
| Expressiveness | Declarative machine tree | Imperative code + `await activity()` |
| Sweet spot | One service, 1–3 domains | Company-wide, dozens of domains, very long runs |

> [!tip] One-line summary
> [[XState]] is **"a library that pins a workflow as a specification inside your code,"** while [[Temporal]] is **"a runtime that outsources workflow execution to an external system."** When you genuinely need replay, durable timers, and cross-team visibility, you graduate to Temporal — until then, XState + Nest + DB covers 70–80%.

> [!note] Field rule of thumb
> - If a single domain waits on **3+ external callbacks** or has a **TTL of 30 min+**, it's worth splitting into an XState machine.
> - If **money moves**, runs are **long-lived**, and **multiple teams share** workflows, evaluate Temporal. XState is the insurance policy on the way there.
> - Either way, anchor on an [[Idempotency Key]] ([[requestId]] / [[deposit_request]] id) — wherever the machine runs, the same input key must yield the same outcome.

### Where to Store Workflow State — DB vs Workflow Engine

Workflows are intrinsically **long-running**. From the moment a user clicks "withdraw," the system runs KYC → AML → blockchain broadcast → confirmation wait → notification — taking seconds to hours. In between, servers restart, containers OOM, and Kubernetes reschedules pods. Any [[XState]] instance held in memory **vanishes the instant that happens**.

> [!note] Why state persistence is fundamentally required
> If "where is this request right now?" isn't written down outside the process, the system forgets the request even exists after a restart. Whether it's a workflow engine or a database — **someone has to put it on disk**.

### Option 1 — Manage it directly in the DB

The most intuitive approach: create a workflow table in a [[Relational Database]] like PostgreSQL.

```sql
CREATE TABLE withdrawal_workflow (
    id              UUID PRIMARY KEY,
    user_id         BIGINT NOT NULL,
    amount          NUMERIC(36, 18),
    state           TEXT NOT NULL,  -- 'kyc_pending', 'aml_pending', 'broadcasting', ...
    context         JSONB NOT NULL, -- XState context snapshot
    tx_hash         TEXT,
    retry_count     INT DEFAULT 0,
    next_run_at     TIMESTAMPTZ,
    updated_at      TIMESTAMPTZ DEFAULT now()
);
```

This looks clean at first. A [[NestJS]] service reads the row via [[TypeORM]]/[[Prisma]], runs the transition, and UPDATEs the new state. But in production, **three burdens** accumulate.

#### 1. Connection pool pressure

```
[Worker A] ──┐
[Worker B] ──┼──→ pg_pool (max=20) ──→ Postgres
[Worker C] ──┘
              ↑
       Long-running TX locks up the pool
```

A single workflow step may call an external API (blockchain RPC, KYC vendor) that takes 30 seconds to respond. If you keep a transaction open and hold the row with `SELECT ... FOR UPDATE` during that time, the [[Connection Pool]] explodes as concurrent workers grow.

> [!warning] Pitfalls of using a DB as a workflow engine
> - **Lock contention**: To prevent two instances from picking up the same workflow, you need `FOR UPDATE SKIP LOCKED` + advisory locks.
> - **Polling load**: A worker scanning `WHERE state = 'pending' AND next_run_at < now()` every N seconds is heavy even with indexes.
> - **Timeout handling**: When an external call stalls, you must write your own reaper that decides who re-claims the row.

#### 2. Schema-change burden

Every time the flow grows, you touch the table.

| Reason for change | Required work |
|---|---|
| Add a new stage (`fraud_check`) | Add value to `state` enum + redeploy all workers |
| Change branching logic | Modify `context` JSONB schema, plan migration of existing rows |
| Add saga compensation step | New column `compensation_state`, backfill existing rows |
| New workflow type | Make another table or use polymorphic JSONB |

**Business logic (code) and persistence schema (DB) end up shifting in lockstep.** Changes that should be code-only now drag a DB migration along.

#### 3. You have to write recovery logic yourself

```ts
// On boot — who picks up the dropped workflows?
async onModuleInit() {
  const stuck = await this.repo.find({
    where: { state: In(['broadcasting', 'confirming']), updated_at: LessThan(...) }
  });
  for (const wf of stuck) {
    await this.resumeOrFail(wf);  // ← this logic IS part of a workflow engine
  }
}
```

This "recovery worker (reaper/janitor)" is, in effect, you hand-rolling a worker implementation that [[Temporal]] already provides.

### Option 2 — Hand it off to a workflow engine

Workflow engines like [[Temporal]], [[Cadence]], [[AWS Step Functions]], and [[Conductor]] **absorb those three burdens into the infrastructure layer**.

```
┌─────────────────────────────────────────────────────────┐
│  Application code (the part you write)                  │
│  ──────────────                                         │
│  @WorkflowMethod                                        │
│  async withdraw(req: WithdrawReq) {                     │
│    await activities.runKyc(req);                        │
│    await activities.runAml(req);                        │
│    const txHash = await activities.broadcast(req);      │
│    await activities.waitForConfirm(txHash);             │
│  }                                                      │
└─────────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────────┐
│  Temporal Worker SDK (library)                          │
│  - Auto-checkpoints at every await                      │
│  - Replays event history on restart to restore state    │
└─────────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────────┐
│  Temporal Server (infra)                                │
│  - History DB (Cassandra/Postgres/MySQL)                │
│  - Task Queues                                          │
│  - Timer Service                                        │
│  - Visibility (separate search index)                   │
└─────────────────────────────────────────────────────────┘
```

> [!tip] What the engine absorbs
> - **State persistence**: Every `await` appends an event. You don't write INSERT/UPDATE in code.
> - **Connections**: The app speaks only gRPC to Temporal. Decoupled from your DB connection pool.
> - **Retries/timeouts**: Declared as activity options. Retry/backoff policy lives outside business code.
> - **Timers**: `await sleep('24h')` — even if the worker dies, something wakes it 24 hours later.
> - **Schema**: A new stage is just one more `await` line. No migration.

#### The same withdrawal workflow with Temporal

```ts
// workflow.ts — looks like sequential code, but each await is a checkpoint
export async function withdrawWorkflow(req: WithdrawReq) {
  await runKyc(req);                       // checkpoint 1
  await runAml(req);                       // checkpoint 2
  const txHash = await broadcast(req);     // checkpoint 3 (see [[deposit-request]] for Outcome Unknown)
  await waitForConfirm(txHash, { startToCloseTimeout: '2h' });
  await notify(req.userId);                // checkpoint 5
}
```

Even if the worker dies mid-execution, a new worker picking up the same workflow ID makes **Temporal replay the event history**, restoring in-memory state to the last checkpoint, and resumes from the next `await`.

### A pragmatic middle ground — Outbox + your own state machine

At startup scale, the operational cost of Temporal (Cassandra cluster, observability setup) can be excessive. Many teams use a **hybrid**.

| Pattern | State storage | Trigger | Fits when |
|---|---|---|---|
| **DB-driven state machine** | Postgres row + JSONB context | cron polling | Workflows < 5, stages < 10 |
| **Outbox + Queue** | DB (current state) + [[Redis]]/[[Kafka]] (next step) | Queue consumer | Moderate branching, lots of async |
| **Temporal/Cadence** | Engine-managed | SDK | Long-running, saga, many workflows |
| **AWS Step Functions** | Engine-managed | EventBridge/SQS | Teams deep in AWS |

> [!example] Common compromise in mvlchain-style fintech
> - **Current State Table**: One `withdrawal_request` row in Postgres (the UI needs to show "where am I right now?").
> - **Event Log Table**: An append-only event table in the same DB (for audit + replay — covered in the next [[Event Sourcing]] section).
> - **Queue**: [[BullMQ]]/[[Redis]] to trigger between stages.
> - This is essentially "rolling your own lightweight workflow engine," but **state still lives in the DB**.

The key point: **using a workflow engine doesn't mean you stop using a DB.** Temporal itself runs on Cassandra/Postgres internally. The difference is that **you don't operate and migrate that DB by hand** — the burden shifts. The tradeoff is always between "code/schema I personally maintain" and "external dependencies and operational complexity."

### What Event Sourcing Solves — Current State Table + Event Log

If [[workflow state]] lives in a single table, every new flow grows the schema, and every `UPDATE` overwrites the answer to "why is this row in this state?" [[Event Sourcing]] attacks exactly these two pains: **schema-change burden** and **traceability / replay**.

### The core idea — append events, project current state

Classic CRUD is `state = f(latest UPDATE)`. Event sourcing flips it to `state = fold(events)`. What happened (events) goes to an append-only log; the current snapshot is a [[projection]] of that log — the **Current State Table**.

```
            ┌──────────────────────────────┐
   command  │  Handler (NestJS Service)    │
  ────────▶ │  - validate                  │
            │  - decide next event(s)      │
            └──────┬───────────────────────┘
                   │ append (immutable)
                   ▼
            ┌──────────────────────────────┐
            │  events  (append-only log)   │  ◀── source of truth
            │  pk: (aggregate_id, seq)     │
            └──────┬───────────────────────┘
                   │ project (apply)
                   ▼
            ┌──────────────────────────────┐
            │  deposit_request  (current)  │  ◀── fast-read cache
            │  pk: id                      │
            └──────────────────────────────┘
```

> [!note] The [[events 테이블]] is always the source of truth
> The Current State Table is a cache built for fast reads. If you drop it, you must be able to rebuild it from events. That's where [[재생 가능성]] (replayability) begins.

### Table layout — how the two are shaped

Following the [[CQRS]] grain, the write model and read model are separated.

**(1) Event Log Table — narrow, append-only, long-lived**

| Column | Type | Purpose |
|---|---|---|
| `id` | bigserial | Global ordering |
| `aggregate_type` | text | `'deposit_request'`, `'withdraw_request'` … |
| `aggregate_id` | uuid | Which instance of the aggregate |
| `seq` | int | Per-aggregate sequence (for optimistic concurrency) |
| `event_type` | text | `'DepositRequested'`, `'TxBroadcasted'` … |
| `payload` | jsonb | Event-specific variable fields |
| `metadata` | jsonb | `actor`, `correlation_id`, `causation_id`, `idempotency_key` |
| `occurred_at` | timestamptz | When it happened |

**(2) Current State Table — narrow, flat, mutates often**

```sql
CREATE TABLE deposit_request (
  id              uuid PRIMARY KEY,
  user_id         uuid NOT NULL,
  asset           text NOT NULL,
  amount          numeric(38,18) NOT NULL,
  state           text NOT NULL,         -- 'pending' | 'broadcasted' | 'confirmed' | 'failed'
  tx_hash         text,
  last_event_seq  int NOT NULL,          -- how far the projector has applied
  updated_at      timestamptz NOT NULL
);
```

> [!tip] `last_event_seq` is the key to idempotent projection
> If the same event is reprocessed and its `seq <= last_event_seq`, ignore it. This lets the [[projector]] run at-least-once safely.

### How it reduces schema-change burden

Say a new flow — a [[KYC 재검사 단계]] (KYC recheck step) — is added.

**With only a single state table:**

```sql
ALTER TABLE deposit_request ADD COLUMN kyc_recheck_started_at timestamptz;
ALTER TABLE deposit_request ADD COLUMN kyc_recheck_result text;
ALTER TABLE deposit_request ADD COLUMN kyc_recheck_attempts int DEFAULT 0;
-- One column burst per new flow…
```

The table balloons to 60 columns, old rows are all NULL, migrations take locks.

**With event log + projection:**

```ts
// Just define the new event. Zero schema migration.
type KycRecheckRequested = {
  type: 'KycRecheckRequested';
  payload: { reason: string; required_level: 'L2' | 'L3' };
};
```

The new fields live in the `payload` jsonb. Only the [[projector]] that sees this event needs to reflect it in Current State — e.g. set `state = 'kyc_recheck'`. **The Current State Table holds only the fields live flows actually use**; dead columns can be retired with the flow.

> [!example] Asymmetry of schema evolution
> - **Events**: append-only, never modified (immutable facts). If you need a new shape, introduce a `v2` event type.
> - **Current State**: free to restructure. Drop it and `REPLAY` rebuilds it from events.

### Replay and audit

To explain why `deposit_request 4f2a…` ended up `failed`, unfold its events in order:

```sql
SELECT seq, event_type, payload, metadata->>'actor', occurred_at
FROM events
WHERE aggregate_type = 'deposit_request'
  AND aggregate_id = '4f2a...'
ORDER BY seq;
```

```
seq  event_type           payload (summary)                     occurred_at
─── ─────────────────── ───────────────────────────────────── ─────────────────
 1   DepositRequested    amount=1.5 ETH, user=u_91             10:01:03.211
 2   NonceAllocated      nonce=482                             10:01:03.450
 3   TxBroadcasted       tx_hash=0xab…, raw_tx=0xf86…          10:01:04.002
 4   TxOutcomeUnknown    reason="rpc timeout 30s"              10:01:34.018
 5   TxReceiptFetched    status=0 (reverted)                   10:02:11.880
 6   DepositFailed       reason="reverted: insufficient gas"   10:02:11.901
```

> [!tip] Scenarios [[재생 가능성]] (replayability) unlocks
> - **Fix-then-recompute**: After patching a fee calculation bug, re-fold the affected aggregates' events to regenerate Current State.
> - **New read model**: Want a "daily deposit total by user" screen? Build a fresh projection from existing events — no new columns on the live DB.
> - **Forensics / audit**: Answers "why did this row end up here?" in chronological order. Essential for domains under [[컴플라이언스]] pressure (asset movement, payments).

### Concurrency and idempotency — the role of `(aggregate_id, seq)`

If two requests try to append to the same aggregate, the `UNIQUE(aggregate_id, seq)` constraint drops one — this is [[낙관적 동시성 제어]] (optimistic concurrency). The handler shape is:

```ts
const current = await load('deposit_request', id);   // fold events
const next = decide(current, command);                // pure function
await appendEvents(id, current.seq, next.events);     // seq+1, +2, ...
```

If `appendEvents` loses the race, retry — and if the caller carried the same [[idempotency_key]] metadata, that itself is the safety net.

> [!warning] Event sourcing is not free
> - **Read complexity**: folding every read is expensive → mitigate with snapshots + the Current State Table.
> - **Event versioning**: when payload shapes change, you need a strategy (upcasters) to read old events.
> - **Not for every domain**: forcing it onto plain CRUD is overkill. It shines where "why did this state happen?" matters after the fact — finance, [[Treasury]], orders.

### Datadog Logs vs Event Table — Why Both?

At first glance both look like "append-only time-ordered records," so you'd be tempted to consolidate onto Datadog. But **their purposes and guarantees are fundamentally different.** They are complements, not substitutes.

### Side-by-side

| Axis | Datadog logs | Event table |
|---|---|---|
| **Purpose** | Debugging, monitoring, alerting | Audit, replay, state recovery |
| **Owner** | SRE / ops perspective | Business domain perspective |
| **Reliability** | best-effort (drops OK) | ACID, transactional |
| **Retention** | 7–30 days (cost pressure) | Permanent (regulatory/audit) |
| **Schema** | Un/semi-structured text | Strongly typed, versioned |
| **Mutability** | Rotation/deletion allowed | Strictly immutable |
| **Query** | Full-text, metric aggregation | By aggregate_id, ordered |
| **Replayability** | Cannot rebuild state | Can rebuild state at any point |
| **Source of truth** | Observed (derived) | Authoritative |

### Guarantees differ

> [!warning] DD dropping logs must not stall the business
> If the [[Datadog]] agent dies or the network drops, logs overflow buffers and get dropped. That's fine — that is what an observability system is. By contrast, if an INSERT into `deposit_request_events` fails, **that deposit did not happen**.

The event table is written in the **same transaction** as business state:

```sql
BEGIN;
  UPDATE deposit_request SET status='PROCESSING' WHERE id = $1;
  INSERT INTO deposit_request_events (deposit_request_id, type, payload)
    VALUES ($1, 'StatusChanged', '{"from":"PENDING","to":"PROCESSING"}');
COMMIT;
```

DD cannot give you this — `logger.info(...)` is fire-and-forget, and the message can vanish anywhere between the agent, the indexer, and storage.

### Replayability

This is the biggest one. **The event table reconstructs state. DD logs cannot.**

```
With event table:
   events ──fold──▶ current state
                 ──filter──▶ state at point in time
                 ──replay──▶ new read model

With only DD:
   logs ──grep──▶ "ah, something broke around then" (hypothesis only)
```

Example: migrating a read model to add a new column. Replay events from the beginning and you get the exact new state. With DD logs this is impossible — log lines are human-readable free text, not the canonical representation of a domain event.

> [!example] Deposit retry scenario
> A [[deposit_request]] is in flight; the external PG is slow and our worker times out — state is [[Outcome Unknown]]. 30 minutes later the callback arrives.
> - With an event table: `TxSent`, `TimeoutObserved`, `CallbackReceived` events arrived in order — replay restores everything exactly.
> - With only DD: somewhere there's an `error: timeout` line, but you must hand-correlate it to the deposit_request, and even that disappears after retention expires.

### Query patterns differ

- **DD**: "p95 latency spiked in the last hour, why?" — time-series, full-text, trace ID joins.
- **Event table**: "show me every state transition for deposit_request `abc-123` in order" — `WHERE aggregate_id = ? ORDER BY sequence_no ASC`.

The first is an analytics/observability workload; the second is closer to OLTP point lookups. Crammed into one system, both feel awkward.

### Retention and cost

- DD charges per indexed GB and most setups keep only 7–30 days; >90 days falls to cold storage.
- The event table sits in the domain DB (Postgres etc.) and is kept indefinitely. Domains like deposits may **legally** require multi-year audit trails.

### Then what is DD for?

Things the event table cannot do:
- System metrics (CPU, memory, network)
- External-call latency distributions
- Alerts and on-call integration
- Distributed tracing across services
- Free-text search ("show me every error raised in auth middleware")

These are all **operator** tools. Business logic must not depend on them.

> [!tip] Mental model
> - **DD = "how is the system behaving right now?" observation (for operators, ephemeral)**
> - **Event table = "what happened to this domain entity?" authoritative record (for business, immutable)**
>
> They answer different questions. Trying to fold one into the other loses both.

### Anti-patterns

- **Using DD as your audit log**: when retention ends, evidence is gone. Compliance incident.
- **Using the event table as a debug log**: schema rots into free text, event types explode, replay loses meaning.
- **Writing the event table outside the transaction (fire-and-forget)**: business state and events diverge → every [[이벤트 소싱]] guarantee collapses.

### Core Concepts of Async Workflows — deposit_request · Idempotency · Outcome Unknown

### 1. `deposit_request` — "promoting the request to a first-class entity"

In crypto/finance backends, tables like `deposit_request`, `withdraw_request`, `swap_request` are not "logging tables". They exist to **treat the request itself as a domain entity (an Aggregate)**.

The naive view treats a withdrawal as just a function call:

```ts
// ❌ Naive version
async function withdraw(userId, amount, toAddress) {
  await chain.send(userId, amount, toAddress)
  await db.balance.decrement(userId, amount)
}
```

But in reality all of the following hit at once:

- The user double-clicked "Submit" → **double-spend**
- We fired the tx but the RPC timed out → **success or failure unknown**
- Large amounts need manual operator approval → **multi-step state**
- Compliance asks for a KYC re-check → **pause mid-flow**
- Days later somebody asks "what was this withdrawal?" → **auditability**

To satisfy all of these you cannot have a "withdraw function"; you need a "withdraw request object".

```sql
CREATE TABLE deposit_request (
  id              UUID PRIMARY KEY,        -- Request ID
  idempotency_key TEXT UNIQUE,             -- unique key sent by the client
  user_id         UUID NOT NULL,
  asset           TEXT NOT NULL,
  amount          NUMERIC(38,18) NOT NULL,
  to_address      TEXT NOT NULL,

  status          TEXT NOT NULL,           -- pending / signing / broadcasting / mined / confirmed / failed / outcome_unknown
  raw_tx          BYTEA,                   -- the signed, serialized tx
  nonce           BIGINT,                  -- the nonce this request reserved
  tx_hash         TEXT,                    -- computed right before broadcast
  block_number    BIGINT,
  confirmations   INT,

  created_at      TIMESTAMPTZ DEFAULT now(),
  updated_at      TIMESTAMPTZ
);
```

> [!note] The key viewpoint
> `deposit_request` expresses both "what the user wanted (intent)" and "where that intent has progressed to (progress)" at the same time. In [[이벤트 소싱]] this plays the role of the [[Current State Table]], while each step change is appended separately to the [[Event Log]].

---

### 2. Idempotency Key · Request ID · txHash — three layered tracking keys

In an async flow there is no single key that identifies "the same request". **Different layers use different keys.**

| Layer | Key | Issued by | On collision | Lifetime |
|-------|-----|-----------|--------------|----------|
| Client → API | `Idempotency-Key` header | Client (or SDK) | Return the cached response (do NOT re-execute) | ~24h |
| API → internals | `request_id` (UUID) | Server on INSERT | Never collides | Permanent |
| Backend → chain | `tx_hash` | keccak256 of the signed raw tx | Same nonce ⇒ same hash | Permanent (on-chain) |

```
[Client]                  [API Gateway]                [Worker]                 [Chain]
   |                           |                          |                       |
   |  POST /withdrawals        |                          |                       |
   |  Idempotency-Key: abc123  |                          |                       |
   |-------------------------->|                          |                       |
   |                           | SELECT ... WHERE         |                       |
   |                           |   idempotency_key='abc'  |                       |
   |                           | --found? return cached   |                       |
   |                           | --new? INSERT request    |                       |
   |                           |   id=req_42, status=pend |                       |
   |  202 Accepted             |                          |                       |
   |  { request_id: req_42 }   |                          |                       |
   |<--------------------------|                          |                       |
   |                           |  enqueue(req_42)         |                       |
   |                           |------------------------->|                       |
   |                           |                          | nonce=lock(addr)      |
   |                           |                          | rawTx = sign(...)     |
   |                           |                          | tx_hash = keccak(rawTx)|
   |                           |                          | UPDATE request        |
   |                           |                          |   SET raw_tx, nonce,  |
   |                           |                          |       tx_hash,        |
   |                           |                          |       status='broad'  |
   |                           |                          | sendRawTransaction()  |
   |                           |                          |---------------------->|
   |                           |                          |   (timeout? ERR? OK?) |
```

> [!tip] Why three layers
> - **Idempotency Key** absorbs *user retries*. Same key ⇒ same outcome.
> - **Request ID** is the *internal trace key* tying queue messages, the event log, and Datadog logs together.
> - **txHash** is the *on-chain truth*. No matter what our DB says, the hash the chain holds is the source of truth.

### 3. Outcome Unknown — the "neither success nor failure" third state

A traditional synchronous API has a binary outcome: `success | failure`. But the moment you **write to an external system and the response drops**, that binary breaks down.

```ts
try {
  const txHash = await provider.sendRawTransaction(rawTx)
  // -> Reaching here means the broker received it. Does NOT mean mined.
} catch (e) {
  // -> This is the trap.
  // 1) The RPC node never received it (network dropped)
  // 2) RPC received it, but the response timed out before reaching us
  // 3) It made it into the mempool but we don't know
  // 4) A replacement tx was mined first
  // All of these look like the same exception.
}
```

This "we entered the catch block, but we don't actually know whether it failed" condition is called [[Outcome Unknown]]. Temporal docs sometimes call it "the third outcome".

> [!warning] Anti-pattern
> Writing `status = 'failed'` on an Outcome Unknown will permanently lie: the same nonce / same raw tx may still mine later, while your DB insists "failed". This is the single most common cause of double-send in crypto backends.

### Correct handling — an explicit `outcome_unknown` state

```
       ┌─ confirmed   ← receipt found + enough confirmations
       │
broadcasting ── outcome_unknown ── (reconciler polls periodically)
       │              │
       │              ├─ receipt found by tx_hash → confirmed / reverted
       │              └─ N blocks pass, not in mempool either → safe to retry
       │
       └─ failed (signing failure etc. — definitely never left the box)
```

Key rules:

1. **Persist `tx_hash` and `raw_tx` to the DB *before* calling `sendRawTransaction`.**
2. Regardless of the call result, as long as we have `tx_hash` we can ask `eth_getTransactionByHash` for the truth later.
3. Timeouts/errors always write `outcome_unknown`, and a **separate reconciler (or [[Treasury Queue]] worker)** periodically polls the chain to converge it to its real state.

```ts
// ✅ Safe pattern (pseudocode)
async function broadcast(req: DepositRequest) {
  const nonce  = await nonceManager.reserve(req.fromAddress) // serialize per sender
  const rawTx  = signer.sign({ ...req, nonce })
  const txHash = keccak256(rawTx)

  await db.update(req.id, { raw_tx: rawTx, nonce, tx_hash: txHash,
                            status: 'broadcasting' })

  try {
    await provider.sendRawTransaction(rawTx)
    await db.update(req.id, { status: 'mined_pending' })
  } catch (err) {
    // ❗ Never write 'failed' here.
    await db.update(req.id, { status: 'outcome_unknown',
                              last_error: serialize(err) })
  }
}
```

---

### 4. Nonce Manager · raw_tx persistence · Treasury Queue — the combo pattern

For the flow above to actually work, three pieces have to move together.

> [!example] Combo pattern
> **(a) Nonce Manager**
> All transactions from the same sender address must have sequential nonces. Use a Redis/DB row lock to commit "this request reserves nonce=42" *before writing it to the DB*. That guarantees no nonce is ever issued twice.
>
> **(b) raw_tx persistence**
> Store the signed serialized tx in a column. If the RPC died, if the worker crashed and restarted, you can **rebroadcast the exact same raw_tx with the exact same hash**. The chain treats duplicate submissions of the same tx as a no-op — it's idempotent.
>
> **(c) Treasury Queue**
> The "withdrawal queue" is not a single FIFO; it is **per-sender-address serialized**. If two transactions race from the same hot wallet, nonces collide — so the address is the partition key and one worker handles one tx at a time. While an Outcome Unknown is open, the next tx is blocked until the reconciler resolves it to confirmed/reverted/expired.

```
        deposit_request (status=pending)
                │
                ▼
        ┌───────────────────┐
        │  Treasury Queue   │   partition by from_address
        │  ┌─────┐ ┌─────┐  │
        │  │addr1│ │addr2│  │   each partition = single worker
        │  └──┬──┘ └──┬──┘  │
        └─────┼───────┼─────┘
              ▼       ▼
        Nonce Manager (per-address lock)
              │
              ▼
        sign → save raw_tx, tx_hash → broadcast
              │
              ├─ ok            → mined_pending → (reconciler) → confirmed
              └─ timeout/err   → outcome_unknown ─┐
                                                  ▼
                                          Reconciler polls chain
                                          by tx_hash and decides
```

> [!note] All three solve the same problem
> "Deliver to the chain (an external system) **at-least-once, but reflect the effect exactly-once**" — i.e. simulate **exactly-once effect**. Idempotency Key (client side), Request ID (internal trace), and tx_hash (external truth) form layered idempotency, and the Outcome Unknown state plus the reconciler fill the gaps between them.
