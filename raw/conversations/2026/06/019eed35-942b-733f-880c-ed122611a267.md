# OIDC (OpenID Connect) 완벽 가이드

OIDC는 OAuth 2.0 위에 구축된 인증(Authentication) 프로토콜이다.

핵심 구분:
- OAuth 2.0 = 인가(Authorization), "이 앱이 내 리소스에 접근해도 되는가?"
- OIDC = 인증(Authentication), "이 사용자는 누구인가?"

한 줄 요약: OIDC = OAuth 2.0 + ID Token(신원 정보) + 표준화된 사용자 정보 조회 방법.

왜 필요했나: OAuth 2.0의 Access Token은 '이 토큰을 가진 사람이 리소스에 접근 가능'이라는 의미만 가지며 '누가' 발급받았는지 검증 가능한 정보가 없어 신원 위조가 가능. OIDC는 ID Token(JWT)을 도입해 발급자(issuer)와 대상(audience)을 암호학적으로 검증 가능하게 만들어 해결.

구성 요소:
- 역할: End User, Relying Party(RP, 클라이언트 앱), OpenID Provider(OP, Google/Apple/Auth0/Keycloak/Okta 등)
- 토큰: ID Token(JWT, 사용자 신원), Access Token(API 접근), Refresh Token(갱신)

ID Token 구조(JWT) — 검증 필수 클레임: iss(발급자), sub(사용자 고유 ID), aud(대상=client_id), exp(만료), iat(발급시각), nonce(replay 방지). 추가로 email, name 등. sub는 OP 내 변하지 않는 고유 식별자라 사용자 식별 기준은 iss+sub 조합을 사용.

동작 흐름(Authorization Code Flow): 로그인 시작 → /authorize 리다이렉트(client_id, redirect_uri, scope=openid, state, nonce, PKCE code_challenge) → 사용자 로그인&동의 → authorization code 반환 → /token으로 code 교환 → ID Token+Access Token 수령 → ID Token 검증(서명/iss/aud/exp/nonce) → 로그인 완료.

Flow 비교: Authorization Code + PKCE가 현재 권장. Implicit Flow는 사용 금지(deprecated, OAuth 2.1에서 제거). Hybrid는 특수 케이스. Client Credentials는 서버-서버용.

표준 메커니즘: Discovery(/.well-known/openid-configuration), JWKS(jwks_uri 공개키), UserInfo 엔드포인트, Scopes&Claims(openid 필수, profile, email, offline_access 등).

보안 핵심: state 검증(CSRF), nonce 검증(replay), ID Token 서명 검증(JWKS), aud/iss 검증, PKCE 사용, redirect_uri 정확 매칭, HTTPS 필수, Refresh Token 안전 보관(HttpOnly Cookie).

OAuth vs OIDC: OIDC는 OAuth를 대체하지 않고 확장. 로그인 필요→OIDC, API 접근 위임→OAuth 2.0, 둘 다→OIDC 흐름 한 번으로 ID Token+Access Token 동시 획득.

실사용: 소셜 로그인, SSO, B2B 인증.

# Assistant

1. Access Token은 OAuth 2.0 개념, ID Token은 OIDC 개념 — 맞다.

토큰 정리:
- Access Token: OAuth 2.0이 정의, 목적=리소스(API) 접근, 형식 무관(불투명 or JWT)
- ID Token: OIDC가 정의, 목적=사용자 신원 증명, 항상 JWT(명세 강제)
- Refresh Token: OAuth 2.0, 토큰 갱신, 불투명

중요 포인트 ① Access Token 형식은 명세상 정해져 있지 않음(불투명/JWT 둘 다 가능). 클라이언트는 Access Token 내용을 들여다보면 안 됨(리소스 서버용임). ② ID Token은 반드시 JWT. 따라서 'ID Token으로 JWT를 사용한다'보다 'ID Token은 그 자체가 JWT다'가 더 정확. JWT는 ID Token이 따르는 포맷.

JWT란: Header.Payload.Signature 3부분. Header=알고리즘, Payload=Claims(sub/iss/exp/email 등), Signature=OP 비밀키로 서명→위변조 검증 가능.

OAuth 2.0 Authorization Code Flow(예: 내 앱이 사용자의 Google Drive 접근):
- 역할: Resource Owner(사용자), Client(앱), Authorization Server(인증서버), Resource Server(API서버)
- 단계: ①연동 시작 ②/authorize 리다이렉트(client_id, redirect_uri, scope=drive.readonly, state) ③로그인+동의 ④authorization code 발급(일회용) ⑤/token으로 code+client_secret 교환 ⑥Access Token(+Refresh Token) 수령 ⑦Access Token으로 API 호출(Authorization: Bearer) ⑧리소스 반환
- 핵심: OAuth 2.0의 결과물은 권한(Access Token)이지 사용자가 누구인지가 아님.

OAuth vs OIDC 흐름 차이: 모양은 거의 동일, 차이는 무엇을 요청/받느냐. OAuth는 scope=drive.readonly→Access Token. OIDC는 scope=openid profile email→Access Token+ID Token. 즉 OIDC는 OAuth 흐름에 scope=openid를 추가하고 ID Token을 하나 더 받는 것.

시그니처는 어떻게 생성하고 검증하길래 안전해? 그리고 뭐로 서명해?

<!-- kh:msg assistant -->
# Assistant

JWT의 안전성은 전적으로 서명(Signature)에 달려 있다.

1. JWT는 암호화가 아니라 서명: Header/Payload는 단순 Base64URL 인코딩(암호화 아님)이라 누구나 디코드해서 읽을 수 있음. 민감 정보 넣으면 안 됨. JWT가 보장하는 건 기밀성이 아니라 무결성(Integrity)+진위성(Authenticity).

2. 무엇을 서명하나: signing_input = base64url(Header) + '.' + base64url(Payload). Signature = 서명알고리즘(signing_input, 키). Header+Payload 전체를 대상으로 서명하므로 한 글자만 바꿔도 깨짐.

3. 서명 방식 2가지:
- 대칭키(HMAC, HS256): 하나의 secret으로 서명+검증. 서명자와 검증자가 같은 키 공유. 빠르지만 검증하려면 secret을 알아야 하고 secret을 아는 자는 위조도 가능. 발급=검증이 같은 주체일 때 사용(자체 세션 토큰).
- 비대칭키(RSA/ECDSA, RS256/ES256): 키 쌍. 개인키=서명(OP만 보유), 공개키=검증(누구나 가능, 위조 불가). OIDC 기본. 구글 토큰을 전세계 앱이 검증해야 하므로 공개키만 배포하면 위조 원천 불가.

4. 검증 과정(RS256): ①Header에서 alg/kid 확인 ②jwks_uri에서 kid 일치 공개키 획득(캐싱) ③RSA-Verify(signing_input, signature, 공개키) ④Claims 검증(iss/aud/exp/nonce).

5. 공격 시나리오: Payload 변조→서명 깨짐. 토큰 위조→개인키 없어 실패. alg:none 공격→허용 알고리즘 화이트리스트로 방어. 알고리즘 혼동(RS256→HS256)→알고리즘을 코드에서 고정. 격언: 'alg는 헤더에서 읽지 말고 검증 측에서 기대 알고리즘을 못박아라.'

알고리즘: HS256(대칭, secret), RS256(비대칭, RSA, OIDC 기본), ES256(비대칭, ECDSA, 짧고 빠름), none(절대 금지).

요약: OIDC는 개인키로 서명하고 OP의 공개키(JWKS)로 검증. 개인키 없이는 유효한 서명을 못 만들고 공개키로는 검증만 가능(위조 불가)하므로 발급자와 검증자가 분리돼도 신뢰 성립.

네, 맞다. 토큰 기반 인증의 가장 근본적 약점.

1. Bearer Token(소지자 토큰): '이 토큰을 들고 있는 자가 곧 권한자'. 현금과 같음. 서버는 '진짜 너인지'가 아니라 '유효한 토큰이 첨부됐는지'만 봄. 그래서 탈취당하면 원 주인 행세 가능.

2. 서명이 있는데도 못 막는 이유: 서명은 내용 변조/가짜 토큰 생성은 막지만, 토큰 통째로 복사해 사용하는 것과 '누가 들고 있는가'는 못 막음. 탈취된 토큰은 완벽하게 유효한 진짜 토큰.

3. 방어 4가지 축:
- 짧은 수명: Access Token 5분~1시간(짧게), Refresh Token 며칠~몇 주(길게, 안전 보관). 탈취돼도 곧 만료.
- 전송·저장 보호: HTTPS(도청 방지), HttpOnly Cookie(XSS 탈취 방지), localStorage 지양, Secure/SameSite Cookie.
- 토큰 바인딩: DPoP(클라이언트 키로 매 요청 증명), mTLS(인증서 바인딩) — 훔쳐도 키 없으면 무용지물. 근본 해결책이나 구현 복잡.
- 탐지&무효화: Refresh Token Rotation, 이상 탐지, 블랙리스트/폐기.

4. JWT 무효화 어려움: JWT는 자체 완결적이라 서버가 매번 DB를 안 봄(장점)이지만 탈취 시 exp 전까지 막기 어려움. 짧은 수명, 블랙리스트(Redis), 재인증(step-up)으로 대응.

요약: Bearer Token은 소지=권한이라 그대로 악용됨. 방어는 여러 겹 — 탈취 자체 막기, 피해 최소화(짧은 수명), 못 쓰게(DPoP/mTLS), 빠른 대응(Rotation/탐지/폐기). 철학: '탈취를 0%로 만들 수 없으니 피해 최소화+빠른 무효화.'

# Assistant

Refresh Token Rotation = 'Refresh Token을 사용할 때마다 쓴 토큰은 폐기하고 새 토큰으로 바꿔주는' 방식.

1. Refresh Token 복습: Access Token(짧음, API 사용), Refresh Token(김, 갱신용). Access Token 만료 시 재로그인 대신 Refresh Token으로 새 Access Token 발급. 문제: Refresh Token이 탈취되면 오랫동안 새 Access Token을 계속 찍어낼 수 있음(가장 위험).

2. Rotation 없을 때(고정 RT): 같은 RT 계속 재사용. 공격자가 훔치면 만료 전까지 무한 발급, 서버는 탈취 탐지 불가.

3. Rotation 있을 때: RT_AAA 사용→새 Access Token+RT_BBB, AAA 폐기 / RT_BBB 사용→RT_CCC, BBB 폐기... 각 RT는 일회용.

4. 탈취 탐지(Reuse Detection): 공격자가 RT_BBB로 RT_CCC 발급받음(BBB 폐기). 이후 정상 사용자가 RT_BBB 사용 시도→'이미 폐기된 토큰이 또 쓰임!'→탈취 의심→해당 사용자 토큰 체인(family) 전부 무효화→재로그인 요구. 폐기된 RT 재등장 = 두 명이 같은 체인 사용 = 탈취 신호.

5. 함께 쓰는 개념: Token Family(한 로그인에서 파생된 RT 묶음, 탈취 시 family 전체 폐기), 저장소 필요(Redis/DB에 RT 상태 추적).

요약: Rotation은 Refresh Token을 일회용으로 만들어 탈취당한 토큰이 다시 쓰이는 순간을 포착해 전체를 무효화하는 방어 기법.

# Assistant

JWKS(JSON Web Key Set) = '서명 검증에 쓸 공개키들을 JSON 형식으로 모아 공개해 놓은 것'.

1. 왜 필요: 비대칭(RS256) 검증 시 앱이 OP의 공개키를 구해야 함. 하드코딩하면 키 회전 시 깨짐. OP가 표준 URL에 공개키를 공개하고 앱이 가져옴 = JWKS(공개키 배포 표준).

2. 위치: Discovery 문서(/.well-known/openid-configuration)의 jwks_uri 필드(예: https://www.googleapis.com/oauth2/v3/certs).

3. 모습: keys 배열에 공개키들. 각 키(JWK)는 kid(Key ID), kty(RSA), use(sig), alg(RS256), n(modulus), e(exponent). JWK=키 1개, JWKS=JWK들의 집합. n과 e로 RSA 공개키 복원해 검증.

4. kid가 핵심: JWKS에 키가 여러 개(키 회전). 토큰 Header의 kid와 JWKS의 kid를 매칭해 올바른 공개키 선택.

5. Key Rotation: OP가 개인키를 주기적 교체. 하드코딩 시 전세계 앱이 깨지지만, JWKS는 새 키 추가(옛 키도 잠시 유지)→앱이 새 kid에 맞는 키를 자동으로 가져와 검증→코드 수정 불필요.

6. 앱 실전 동작: Header에서 kid 추출→캐시에 있으면 사용, 없으면 jwks_uri에서 새로 가져와 캐싱→서명 검증→클레임 검증. 캐싱 중요(매 요청 호출 X), 모르는 kid 오면 캐시 갱신. jwks-rsa 등 라이브러리가 자동 처리.

요약: JWKS는 OP가 공개한 서명 검증용 공개키 카탈로그. kid로 토큰과 키를 매칭하고 키 회전에 자동 대응하는 표준.

# Assistant

1. Discovery(OIDC Discovery): OP가 자신의 모든 설정 정보를 정해진 URL에 JSON으로 공개해 둔 것 → 앱이 읽고 자동으로 OIDC 연동 설정.
- 왜 필요: authorization_endpoint, token_endpoint, userinfo_endpoint, jwks_uri, issuer 등을 수동 하드코딩하면 오타/변경 시 깨짐. Discovery는 OP가 직접 표준 위치에 최신으로 제공.
- 위치: https://{issuer}/.well-known/openid-configuration (.well-known은 RFC로 정해진 약속된 경로). issuer만 알면 설정 전체를 자동 획득.
- 응답 필드: issuer(OP 고유 식별자, ID Token의 iss와 일치), authorization_endpoint(로그인 시작), token_endpoint(코드→토큰 교환), userinfo_endpoint(추가 사용자 정보), jwks_uri(공개키 위치), ..._supported(지원 알고리즘/scope/응답방식).
- 흐름: issuer만 알고 시작→Discovery 조회→엔드포인트/키위치 전부 획득→OIDC 흐름 진행.
- 요약: Discovery = OP의 사용설명서. issuer 하나로 모든 주소·설정·키위치를 자동으로 받아오는 표준 메타데이터.

2. kid(Key ID): '이 토큰이 어떤 공개키로 서명됐는지' 알려주는 키 식별자. 토큰 헤더와 JWKS의 여러 공개키를 연결.
- 왜 필요: JWKS에 공개키가 여러 개(키 회전). 앱이 '어떤 키로 검증할지' 알아야 함. 토큰이 'abc123 키로 서명됨'이라고 알려줌 = kid.
- 두 곳에서 매칭: ID Token Header { alg:RS256, kid:abc123 } 와 JWKS의 { kid:abc123, n, e }. 토큰 Header의 kid === JWKS의 키 kid → 그 공개키로 검증.
- 키 회전에서: OP가 키 교체 시 새 토큰은 새 kid를 달고 나옴→앱이 캐시에 없으면 JWKS 다시 가져와 새 kid 키로 검증. 코드 수정 없이 회전 대응.

3. 관계(전체 그림): ①Discovery로 시작(issuer→jwks_uri 알아냄) ②jwks_uri에서 JWKS 획득(키마다 kid) ③ID Token 받아 Header의 kid 확인 ④kid로 JWKS에서 맞는 공개키 선택 ⑤서명 검증→로그인 완료.
