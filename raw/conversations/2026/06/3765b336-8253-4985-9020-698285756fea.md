# User

namespaces와 cgroups 설명해줘

<!-- kh:msg assistant -->
# Assistant

namespaces=시야 격리(PID/NET/MNT/UTS/USER/IPC). PID: 호스트 5678이 컨테이너 안 PID 1. NET: 각자 네트워크 스택, 둘 다 3000 써도 충돌 없음. cgroups=자원 격리(CPU/메모리/IO, --memory/--cpus, OOM kill). 둘 합치면 컨테이너.

<!-- kh:msg user -->
# User

각 서비스가 3000 써도 컨테이너 내부적으론 괜찮다는 거구나? 포트를 다르게 할당하는 건가?

<!-- kh:msg assistant -->
# Assistant

포트 바꿔치기 아니라 둘 다 진짜 3000 쓴다. NET namespace가 달라 서로 다른 세상의 3000(아파트 101호/102호 1번방). PID와 포트는 별개 namespace. 충돌은 호스트로 꺼낼 때만 → [3010:3000]처럼 호스트 번호만 다르게.

<!-- kh:msg user -->
# User

net namespace는 정확히 뭐고 실제 포트 할당은 어떻게?

<!-- kh:msg assistant -->
# Assistant

NET namespace=네트워크 스택 통째 복사본(인터페이스/IP/포트테이블/라우팅/iptables). 포트 할당: app.listen(3000)→bind() 시스템콜→커널이 해당 namespace 포트장부 확인→비었으면 기록, 차면 EADDRINUSE. 바깥 접속: veth pair(가상 랜선), docker0(가상 스위치), iptables DNAT(-p가 생성).

# User

OSI 7계층에서 각각 어느 계층?

<!-- kh:msg assistant -->
# Assistant

L7 nginx/HTTP/curl, L4 포트(80/8080)/bind()/TCP, L3 IP/iptables NAT(DNAT/MASQUERADE), L2 veth/docker0/MAC, L1 veth 가상랜선. iptables NAT=L3(IP)+L4(포트) 양다리. OSI 밖: PID namespace/cgroups(OS 격리). NET namespace=L2~L4 스택 통째 복제하는 그릇. 캡슐화: 보낼 때 위→아래 봉투 싸기, 받을 때 아래→위 벗기기.

<!-- kh:msg user -->
# User

dnat 조작하면 다른 프로그램 망가지겠네? 어떤 명령어?

<!-- kh:msg assistant -->
# Assistant

NAT 테이블 쥔 자가 행선지 장악(root 특권). 명령어 `iptables -t nat -I DOCKER 1 ! -i docker0 -p tcp --dport 8080 -j DNAT --to-destination <B_IP>:80`. 발견: 맥 localhost:8080은 여전히 A(OrbStack docker-proxy가 iptables 우회), VM_IP:8080→B(하이재킹 성공, PREROUTING→DOCKER DNAT 경로). DNAT 조작은 그 경로가 iptables를 실제 통과할 때만 트래픽 가로챔. -D로 정확히 삭제해 복구.

<!-- kh:msg assistant -->

본질: 경로(라우팅/NAT/주소해석) 장악=트래픽 장악. 공격: 악성 특권 컨테이너 사이드카 MITM, Docker 소켓 노출, 클라우드 메타데이터 하이재킹, ARP 스푸핑(L2), Rogue DHCP, DNS 스푸핑, BGP 하이재킹(L3), Evil Twin AP. 블록체인은 BGP/DNS 하이재킹으로 지갑/DEX 가짜 사이트(MyEtherWallet 2018). 방어 3축: ①경로 장악 막기(no --privileged, --cap-drop=ALL, K8s NetworkPolicy/Calico, DAI/DHCP Snooping, RPKI) ②장악당해도 무력화(end-to-end TLS, mTLS/서비스메시, 인증서 피닝 — 가장 강력) ③탐지(iptables 변경 감사, Falco). 실무: 내부 서비스 간 mTLS + NetworkPolicy + 특권 컨테이너 금지.

<!-- kh:msg assistant -->
# Assistant

MEW 2018-04-24: 1단계 BGP 하이재킹(L3, AWS Route53 DNS IP 대역 more-specific 광고로 DNS 트래픽 탈취) → 2단계 DNS 스푸핑(myetherwallet.com→러시아 공격자 IP) → 3단계 피싱→개인키 탈취(~215 ETH/~$150,000). 핵심: 가짜 사이트는 유효 TLS 인증서가 없어 브라우저 경고 → 경고 무시하고 '그래도 진행' 누른 사람만 털림. TLS 인증서 검증이 마지막 방어선.

TLS 코드 데모: openssl로 인증서 3종 — (1) 루트 CA(req -x509, 신뢰의 뿌리) (2) 정품 서버(bank.local CSR을 CA가 서명 → issuer=MyTrustedRootCA) (3) 공격자(자체서명, -x509, issuer=bank.local=주체와 동일). 도메인명은 위조 가능하지만 CA 서명은 위조 불가(CA 개인키 없음). nginx 두 서버 겉보기 동일(listen 443 ssl, server_name bank.local), 인증서만 다르게 마운트. 클라이언트 curl: `--resolve bank.local:443:$IP`(DNS/BGP 하이재킹 시뮬레이션, 도메인이 가리키는 IP 바꿔치기), `--cacert /ca.crt`(이 CA만 신뢰=방어선), URL은 항상 진짜 bank.local. 결과: 1)정상(정품IP+CA신뢰)→OK 2)하이재킹(가짜IP+CA신뢰)→curl (60) self-signed certificate, 연결 거부=우회당해도 차단! 3)피해자(가짜IP+-k 검증끔)→STOLEN. 시나리오2가 MEW 교훈: 트래픽 완벽 우회당해도 공격자는 신뢰 CA 서명 위조 불가→연결 거부. 하이재킹은 '어디로'(경로) 속이지만 TLS는 '상대가 진짜인지'(신원)를 CA 서명으로 검증. 단 사용자가 경고 무시(-k) 안 하는 한. 실무에선 mTLS로 이 검증을 자동·강제화.
