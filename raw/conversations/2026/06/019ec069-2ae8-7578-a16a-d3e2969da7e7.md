<!-- kh:msg assistant -->
# Assistant

이건 학습 목적의 설명 요청이네요. 실제 이 monorepo의 docker-compose와 Dockerfile을 근거로 port/volume/network 세 개념을 설명.

큰 그림: 컨테이너는 격리된 작은 컴퓨터. 자기만의 파일시스템/네트워크/프로세스. 기본적으로 host(맥북)와 단절. 그 벽에 구멍을 뚫는 세 장치가 port/volume/network.
- port: 컨테이너↔외부(host). 바깥에서 컨테이너로 들어가는 출입구.
- volume: 컨테이너↔디스크. 컨테이너가 죽어도 살아남는 저장 공간.
- network: 컨테이너↔컨테이너. 컨테이너끼리 부르는 내부 전화망.

1. Port — postgres의 '5431:5432'는 HOST_PORT:CONTAINER_PORT. 컨테이너 안 postgres는 항상 5432에서 듣고, host에서는 5431로 접속(로컬 postgres 충돌 회피). redis는 '6378:6379'. user-service는 3000:3000(충돌 없어서 동일). 콜론 왼쪽=내가 접속할 번호(바꿔도 됨), 오른쪽=컨테이너가 실제 듣는 번호(못 바꿈). Dockerfile의 EXPOSE 3000은 포트를 여는 게 아니라 문서/메타데이터일 뿐. 실제 출입구는 docker-compose의 ports:.

2. Volume — 컨테이너 파일시스템은 컨테이너 지우면 사라짐. (a) named volume: 'postgres:/var/lib/postgresql/data' — 왼쪽이 이름이면 docker가 관리하는 저장소, 컨테이너 재생성해도 데이터 유지. redis:/data도 동일. 파일 맨 아래 volumes:에 이름 등록. (b) bind mount: './docker/nginx.conf:/etc/nginx/nginx.conf', './db-dumps:/dumps' — 왼쪽이 ./나 /로 시작하는 경로면 host 실제 파일을 컨테이너에 꽂음. 구분법: 콜론 왼쪽이 경로면 bind mount, 이름이면 named volume.

3. Network — docker-compose는 한 파일의 모든 서비스를 자동으로 같은 가상 네트워크에 넣고, 서비스 이름이 곧 DNS 호스트명이 됨. user-service 안에서는 postgres:5432, redis:6379로 접속. 즉 누가 접속하느냐에 따라 주소가 다름: 맥북에서 DB툴=localhost:5431(port 매핑), 컨테이너에서=postgres:5432(network 내부 이름+컨테이너 포트). depends_on은 시작 순서일 뿐 통신과 무관. extra_hosts: 'host.docker.internal:host-gateway'는 컨테이너에서 host 자체로 연결해주는 설정.

클라우드 매핑: ports→로드밸런서, volumes→EBS/EFS/PV, 자동network→service discovery/내부DNS.

<!-- kh:msg assistant -->
# Assistant

nginx.conf를 보니 이 repo는 의도된 선택을 함: nginx의 모든 upstream이 host.docker.internal:PORT로 돼 있음. 즉 컨테이너끼리가 아니라 컨테이너→host→다시 서비스로 한 바퀴 돈다.

Part 1. docker-compose 네트워킹 내부 = network namespace + veth pair + bridge + iptables + embedded DNS.
(1) network namespace = 격리의 정체. 각 namespace는 자기만의 인터페이스/라우팅테이블/iptables/hosts·resolv.conf. 컨테이너 하나당 namespace 하나.
(2) veth pair = namespace끼리 잇는 가상 랜선. 양 끝 한 쌍. 한쪽에 들어간 패킷이 반대쪽으로 나옴. 한쪽은 컨테이너 eth0, 한쪽은 host vethXXXX.
(3) bridge = veth들의 host쪽 끝을 묶는 소프트웨어 L2 스위치. compose가 프로젝트당 <프로젝트명>_default bridge 자동 생성(host에서 br-xxxxx). 서브넷(172.18.0.0/16) 할당, 각 컨테이너에 IP. bridge 자신도 IP(172.18.0.1)=컨테이너들의 gateway.
(4) embedded DNS 127.0.0.11 = 각 컨테이너 namespace 안에 내장 DNS. /etc/resolv.conf가 nameserver 127.0.0.11. postgres resolve하면 docker가 172.18.0.2로 응답, 모르는 이름은 host DNS로 forwarding. 단 user-defined network에서만 동작, default bridge(docker0)에선 안 됨. compose는 항상 user-defined라 항상 됨.
(5) 외부 인터넷 나갈 때 = iptables MASQUERADE(SNAT). 출발지를 host IP로 바꾸고 conntrack이 응답을 원래 컨테이너로 되돌림.

Part 2. 외부→nginx→서비스→역방향.
(A) ports: 80:80 = port publishing. 브라우저 localhost→host:80→iptables DNAT→nginx컨테이너:80. macOS는 Docker Desktop이 LinuxKit VM 돌리고 gvisor/vpnkit이 VM 안으로 포워딩.
(B) nginx L7 라우팅: location들을 위에서부터 매칭. /activity→activity-service, /v1/fee→정규식으로 clutch-service, 나머지/→user-service.
(C) 이 repo의 반전: upstream이 server host.docker.internal:3000(컨테이너 이름 아님). nginx는 host.docker.internal을 host IP로 resolve해서 host:3000으로 보냄. host:3000은 (1)컨테이너면 ports:3000:3000으로 DNAT되어 컨테이너 도착, (2)yarn dev면 host의 Node 프로세스. 왜? docker-compose 주석대로 '각 서비스를 local에서 그냥 띄워도 접속 가능하게'. server user-service:3000(내부DNS)을 썼다면 반드시 컨테이너여야만 했음. host.docker.internal로 우회해서 컨테이너든 host 프로세스든 동작.
(D) 역방향: TCP는 양방향, conntrack이 NAT 변환을 기록해서 응답 패킷에 역변환 자동 적용. nginx는 클라이언트↔nginx 연결과 nginx↔upstream 연결 두 개를 들고 중개.

Part 3. extra_hosts host.docker.internal:host-gateway = 컨테이너 /etc/hosts에 한 줄 추가(이름:IP). host-gateway는 매직 키워드로 docker가 런타임에 컨테이너에서 본 host IP(보통 bridge gateway 172.18.0.1)로 치환. Docker Desktop(맥/윈)은 host.docker.internal 자동 제공, 리눅스는 기본 제공 안 돼서 이 줄이 이식성 보장.

# Assistant

Q1 conntrack: 네, 정확. 커널 메모리의 테이블(해시맵). 패킷 처음 나갈 때 5-tuple(프로토콜,출발지IP,출발지포트,목적지IP,목적지포트)을 키로 엔트리 생성. NAT면 원래→바뀐 값 변환정보+예상 응답의 역방향 tuple도 미리 기록. 응답 도착하면 역방향 tuple로 조회해 자동 역변환. conntrack -L 또는 /proc/net/nf_conntrack으로 확인 가능.

Q2 user-defined network: bridge에 두 종류. (a) default bridge(docker0): docker run에서 네트워크 지정 안 하면 자동 진입. IP로는 통신되나 이름(DNS)으로는 못 찾음. 옛날엔 --link 필요. (b) user-defined network: docker network create나 compose가 자동 생성. 내장 DNS가 이름→IP 매핑 해줌. compose 쓰면 항상 user-defined라 항상 됨. 단독 docker run은 안 됨.

Q3 핵심 오해 정정: 이 repo의 nginx는 분기하지 않음. 컨테이너든 로컬이든 항상 host.docker.internal:3000으로만 보냄. docker 내부 DNS(서비스 이름)는 아예 안 씀. nginx.conf의 'user-service'는 docker DNS 이름이 아니라 upstream 블록의 라벨일 뿐. proxy_pass http://user-service/의 user-service는 그 upstream 블록 내부 참조 → 펼치면 host.docker.internal:3000. 분기는 nginx가 아니라 host:3000에 누가 listen 중이냐에서 갈림. 경우1 컨테이너: ports:3000:3000으로 host:3000→컨테이너 DNAT. 경우2 yarn dev: Node가 host:3000 직접 점유. 둘 다 host:3000 도착까지 동일, nginx는 구분 안 함. 만약 server user-service:3000(docker DNS)을 썼다면 컨테이너→컨테이너 직행(더 빠름)이지만 yarn dev 프로세스는 못 찾음. 이 repo는 유연함을 위해 host 우회 택함.

# Assistant

두 군데서 앞 정정이 원래 오해로 돌아감. 첫째: '타깃이 3001'이 모호. 입구 두 가지 — 경우A nginx 경유는 외부가 포트 80으로 옴(http://host/activity), 3001은 nginx가 URL 경로 보고 내부적으로 고르는 값. 경우B 3001로 직접(activity-service도 ports:3001:3001 published)이면 nginx 아예 안 거치고 곧장 컨테이너로. nginx 이야기하려면 진입은 포트 80.

둘째 핵심 재정정: nginx는 bridge 타고 activity 컨테이너로 가지 않음. upstream activity-service { server host.docker.internal:3001; }. 같은 bridge에 activity 컨테이너가 빤히 있어도 그쪽 직접 안 가고 맥 호스트로 빠져나갔다 published 포트로 되돌아옴(헤어핀). veth/bridge로 옆 컨테이너 직행 아님. server activity-service:3001로 썼다면 bridge 직행했을 것.

정확한 트레이스(외부→/activity): 1.외부→맥:80(입구 80, 3001 아님) 2.Docker Desktop gVisor/vpnkit이 VM 안으로 3.VM iptables DNAT: VM:80→nginx컨테이너:80(veth/bridge) 4.nginx L7: /activity 매칭→upstream=host.docker.internal:3001→맥:3001로 새 연결 5.nginx→VM 밖→Desktop 포워딩→맥:3001 6.맥:3001은 published(ports:3001:3001)→Desktop이 다시 VM 안으로→activity-service 컨테이너:3001 7.응답은 conntrack 역변환으로 되감김.

채점: nginx가 iptables 분석=❌(iptables 아니라 HTTP location/proxy_pass L7로 판단). veth/bridge 3001 직행=❌(host.docker.internal로 맥 거쳐 헤어핀).

<!-- kh:msg assistant -->
# Assistant

둘 다 맞음. 단 '라우팅'이 두 레이어에서 다른 의미로 쓰임. (1)L2/L3 전송·포워딩: veth+bridge+iptables(커널), IP·포트 기준, '이 주소로 어떻게 물리적으로 보낼까'. (2)L7 라우팅: nginx 프로세스, URL 경로(/activity) 기준, '내용 보고 어느 백엔드에'. veth+bridge=패킷이 오갈 물리적 통로(L2 스위치), 토대. iptables=그 통로 위에서 목적지IP/포트 바꾸고 어디로 보낼지 정하는 L3/L4 라우팅. nginx location/proxy_pass=nginx 도착 후 HTTP URL 읽고 결정하는 L7 라우팅. 즉 'L7에서 라우팅'이 아니라 L3 라우팅(커널)으로 nginx까지 데려다 놓은 뒤 L7 라우팅(nginx) 시작되는 2단 구조.

VM 진입 시퀀스: 1.패킷 VM 도착(목적지 VM인터페이스:80) 2.iptables nat PREROUTING DNAT로 목적지→nginx컨테이너IP:80 재작성(L3/L4) 3.VM 커널 라우팅: 그 컨테이너IP는 bridge 너머→bridge→veth→nginx eth0(L2 전송) 4.nginx가 :80 수신, HTTP 파싱, location /activity 매칭→proxy_pass(L7 시작). 당신 문장 '+vm 오면 iptables가 nginx로 보내고 거기서 L7 시작'이 정확히 이 흐름.
