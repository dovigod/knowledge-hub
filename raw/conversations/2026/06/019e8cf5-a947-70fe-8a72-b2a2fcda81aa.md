# OIDC (OpenID Connect)

OIDC는 **OAuth 2.0 위에 구축된 인증(Authentication) 레이어**입니다. OAuth 2.0이 "권한 부여(Authorization)"를 다룬다면, OIDC는 "이 사용자가 누구인지"를 확인하는 표준 프로토콜입니다.

## 핵심 개념

### OAuth 2.0과의 차이
- **OAuth 2.0**: "이 앱이 내 Google Drive에 접근해도 되나요?" → 권한 위임
- **OIDC**: "지금 로그인한 사람이 정말 justin인가요?" → 신원 확인

OAuth 2.0만으로 로그인을 구현하면 access token이 "누구"를 나타내는지 표준화된 방법이 없어서, OIDC가 이를 보완하기 위해 만들어졌습니다.

### 주요 구성 요소

**1. ID Token (핵심)**
- JWT 형식으로 발급되는 토큰
- 사용자 신원 정보(claims)를 담고 있음:
  ```json
  {
    "iss": "https://accounts.google.com",  // 발급자
    "sub": "110169484474386276334",        // 사용자 고유 ID
    "aud": "my-client-id",                 // 토큰 수신 대상 (내 앱)
    "exp": 1717400000,                     // 만료 시간
    "iat": 1717396400,                     // 발급 시간
    "email": "justin@example.com",
    "name": "Justin Seo"
  }
  ```
- 서명되어 있어서 위변조 검증 가능 (발급자의 공개키로 검증)

**2. 역할(Roles)**
- **OP (OpenID Provider)**: 인증을 수행하는 서버 (Google, Auth0, Keycloak 등)
- **RP (Relying Party)**: 인증 결과를 신뢰하는 앱 (내 서비스)
- **End User**: 로그인하는 사용자

**3. 엔드포인트**
- `/authorize` — 인증 요청 시작
- `/token` — code를 token으로 교환
- `/userinfo` — 추가 사용자 정보 조회
- `/.well-known/openid-configuration` — OP의 메타데이터 자동 발견 (Discovery)
- `/jwks` — 토큰 서명 검증용 공개키 목록

## 대표적인 플로우: Authorization Code Flow

```
사용자          내 앱(RP)              OP (예: Google)
  │   로그인 클릭   │                      │
  │ ─────────────> │                      │
  │                │  /authorize 리다이렉트  │
  │ <───────────────────────────────────> │  ← 사용자가 Google에서 로그인
  │                │                      │
  │                │ <─ code 전달 (redirect_uri로)
  │                │                      │
  │                │  code + client_secret │
  │                │ ────────────────────> │  /token
  │                │ <──────────────────── │
  │                │  ID Token + Access Token
  │                │                      │
  │                │  ID Token 검증 후 세션 생성
```

핵심 단계:
1. 앱이 사용자를 OP로 리다이렉트 (`scope=openid profile email` — `openid` scope가 OIDC를 활성화하는 트리거)
2. 사용자가 OP에서 인증
3. OP가 authorization code를 앱으로 전달
4. 앱이 백엔드에서 code를 **ID Token + Access Token**으로 교환
5. ID Token의 서명, `iss`, `aud`, `exp`, `nonce`를 검증한 후 로그인 처리

## 보안 관련 핵심 포인트

- **`nonce`**: replay attack 방지 — 요청 시 보낸 값이 ID Token에 그대로 돌아오는지 확인
- **`state`**: CSRF 방지
- **PKCE**: public client(SPA, 모바일)에서 code 탈취 공격 방지 — 현재는 모든 클라이언트에 권장
- **ID Token 검증 필수 항목**: 서명(JWKS 공개키), `iss` 일치, `aud`가 내 client_id인지, `exp` 만료 여부

## 실무에서 자주 보는 활용

| 사례 | 설명 |
|---|---|
| 소셜 로그인 | "Google로 로그인", "Kakao로 로그인" 등 |
| SSO | 사내 여러 서비스를 하나의 IdP(Okta, Keycloak)로 통합 인증 |
| CI/CD 인증 | GitHub Actions → AWS의 OIDC federation (시크릿 없이 클라우드 인증) |
| Kubernetes | kubectl 사용자 인증을 OIDC provider에 위임 |

특히 최근에는 **GitHub Actions ↔ AWS/GCP OIDC federation**처럼, 장기 시크릿(access key) 없이 단기 토큰으로 클라우드에 인증하는 패턴이 보안 모범 사례로 자리잡았습니다.

요약하면: **OIDC = OAuth 2.0 + ID Token(JWT) + 표준화된 사용자 신원 검증 절차**입니다. "로그인"을 구현해야 한다면 OAuth 2.0을 직접 쓰지 말고 OIDC를 쓰는 것이 정석입니다.

# `state`와 `nonce`의 동작 원리

둘 다 "**내가 보낸 값이 그대로 돌아오는지 확인**"하는 메커니즘인데, **검증되는 위치와 막는 공격이 다릅니다.**

---

## 1. `state` — CSRF 방지

### 동작 방식

```
1. 앱: state = 랜덤값 생성 (예: "xK9f2...")
   → 사용자 세션(쿠키/서버 세션)에 저장
   → /authorize?...&state=xK9f2... 로 리다이렉트

2. OP: 인증 후 redirect_uri로 돌려보낼 때 state를 그대로 echo
   → https://myapp.com/callback?code=AUTH_CODE&state=xK9f2...

3. 앱: 콜백 수신 시
   세션에 저장한 state == 콜백으로 받은 state ?
   → 불일치하면 거부
```

핵심은 **state가 사용자의 브라우저 세션에 바인딩**되어 있다는 점입니다.

### 막는 공격: CSRF (로그인 세션 주입)

`state`가 없으면 이런 공격이 가능합니다:

```
1. 공격자가 자기 계정으로 OIDC 로그인을 시작해서
   자기 명의의 callback URL을 획득:
   https://myapp.com/callback?code=공격자의_CODE

2. 이 URL을 피해자에게 클릭하게 만듦 (이메일, 이미지 태그 등)

3. 피해자의 브라우저가 콜백을 호출
   → 앱이 code를 교환 → 피해자의 브라우저 세션이
   "공격자 계정으로 로그인"된 상태가 됨

4. 피해자가 이를 모르고 카드 등록, 파일 업로드 등을 하면
   전부 공격자 계정에 저장됨 → 공격자가 나중에 열람
```

`state`가 있으면 3번에서 막힙니다:
- 피해자의 세션에는 **공격자가 받은 state에 대응하는 값이 없음** (피해자는 로그인 플로우를 시작한 적이 없으니까)
- 콜백의 state ≠ 피해자 세션의 state → 거부

즉, **"이 콜백이 정말 이 브라우저에서 시작한 플로우의 응답인가?"** 를 확인하는 겁니다.

---

## 2. `nonce` — ID Token replay 방지

### 동작 방식

`state`와 비슷하게 시작하지만, **돌아오는 경로가 다릅니다**:

```
1. 앱: nonce = 랜덤값 생성 → 세션에 저장
   → /authorize?...&nonce=aB3x9...

2. OP: 인증 후 ID Token을 발급할 때
   nonce를 ID Token의 claim 안에 넣어서 서명함:
   {
     "iss": "https://accounts.google.com",
     "sub": "1101694...",
     "nonce": "aB3x9...",   ← 토큰 내부에 포함
     ...
   }

3. 앱: ID Token 서명 검증 후
   token.nonce == 세션에 저장한 nonce ?
   → 불일치하면 거부
```

차이점:
- `state`는 **URL 파라미터로** 돌아옴 → 콜백 요청 자체를 검증
- `nonce`는 **서명된 ID Token 내부에** 들어가서 돌아옴 → **토큰 자체를 검증**

### 막는 공격: ID Token 재사용(replay) / 토큰 주입

ID Token은 서명도 유효하고, `iss`/`aud`/`exp`도 전부 통과하는 **"진짜 토큰"이지만 다른 맥락에서 발급된 것**일 수 있습니다:

```
시나리오: 토큰 탈취 후 재사용
1. 공격자가 어딘가에서 (로그 유출, 다른 앱, 과거 세션 등)
   유효한 ID Token을 입수
2. 이 토큰을 진행 중인 인증 플로우에 주입
3. 서명 OK, iss OK, aud OK, exp 아직 안 지남 → 통과?

→ nonce 검증에서 막힘:
   탈취한 토큰의 nonce는 "그 토큰이 발급된 과거 플로우"의 값이지,
   지금 이 세션이 생성한 nonce가 아님
```

즉, **"이 토큰이 정말 지금 이 세션의 인증 요청에 대한 응답으로 발급된 것인가?"** 를 토큰 내용으로 증명하는 겁니다.

특히 implicit flow(`response_type=id_token`)처럼 토큰이 브라우저 프론트 채널로 직접 전달되던 시절엔 토큰 주입이 쉬웠기 때문에 nonce가 필수였습니다.

---

## 3. 왜 둘 다 필요한가? (역할 비교)

| | `state` | `nonce` |
|---|---|---|
| 어디에 실려 돌아오나 | 콜백 URL 쿼리 파라미터 | 서명된 ID Token claim 내부 |
| 무엇을 바인딩하나 | 브라우저 세션 ↔ 인증 **요청/응답 왕복** | 브라우저 세션 ↔ **발급된 토큰** |
| 막는 공격 | CSRF (남의 code를 내 세션에 주입) | 토큰 replay (과거/타 맥락의 토큰 주입) |
| 검증 시점 | 콜백 도착 즉시 | code → token 교환 후, ID Token 파싱 시 |
| OP가 서명하나 | ❌ (그냥 echo) | ✅ (토큰에 포함되어 서명됨) |

`state`는 콜백 단계를, `nonce`는 토큰 단계를 지킵니다. `state`만 있으면 콜백은 정상이어도 교환 과정에서 바꿔치기된 토큰을 못 잡고, `nonce`만 있으면 ID Token이 없는 플로우 단계(code 주입)를 못 잡습니다.

---

## 4. 보안이 성립하는 전제 조건

이 메커니즘들이 작동하려면:

1. **예측 불가능한 랜덤값**이어야 함 — CSPRNG로 충분한 엔트로피(128bit+) 생성. `state=1234` 같은 값이면 공격자가 그냥 맞춰서 보내면 끝
2. **세션에 안전하게 저장** — 보통 `HttpOnly` + `SameSite` 쿠키나 서버 세션. 공격자가 피해자의 저장된 state를 읽거나 쓸 수 있으면 무력화됨
3. **일회용** — 검증 후 즉시 폐기. 재사용 허용하면 replay 방지 의미가 없음
4. **반드시 검증할 것** — 의외로 많은 구현이 state를 보내기만 하고 콜백에서 비교를 안 합니다. 그러면 그냥 장식임

참고로 요즘은 **PKCE**가 code 바꿔치기까지 막아주면서 state의 CSRF 방어 역할 상당 부분을 겸하게 되었지만 (code_verifier도 세션 바인딩이므로), OAuth 2.1 / OIDC 모범 사례는 여전히 **PKCE + state + nonce를 모두 사용**하는 것을 권장합니다 — 각자 커버하는 단계가 미묘하게 다르기 때문입니다.

# Redis가 단일 쓰레드인데도 빠른 이유

결론부터: **"in-memory라서 빠른 것"이 절반, "단일 쓰레드가 오히려 유리한 워크로드라서"가 나머지 절반**입니다. 그리고 그냥 애플리케이션 메모리(HashMap)에 저장하는 것과는 **다른 물건**입니다.

---

## 1. 병목이 CPU가 아니다

Redis 작업의 시간 구성을 보면:

```
명령 하나 처리 = 네트워크 I/O ≫ 명령 파싱 > 실제 메모리 연산
```

- `GET key` 같은 연산은 해시 테이블 룩업 → **수백 나노초**
- 반면 네트워크 왕복, 소켓 read/write가 대부분의 시간을 차지

즉, **CPU 연산이 병목이 아니므로 쓰레드를 늘려도 의미가 없습니다.** 디스크를 안 거치고(in-memory), 연산 자체가 O(1)~O(logN)으로 짧으니, 진짜 문제는 "수만 개의 클라이언트 소켓을 어떻게 효율적으로 처리하느냐"가 됩니다.

## 2. I/O Multiplexing + 이벤트 루프

Redis는 클라이언트마다 쓰레드를 만들지 않고, **epoll(Linux) / kqueue(macOS)** 기반의 단일 이벤트 루프로 모든 소켓을 처리합니다:

```
while (true) {
  events = epoll_wait()        // 읽을 데이터가 있는 소켓들만 OS가 알려줌
  for (event of events) {
    명령 파싱 → 실행 → 응답 버퍼에 기록
  }
}
```

- 10,000개 연결이 있어도 **실제로 데이터가 도착한 소켓만** 깨워서 처리
- Nginx, Node.js와 같은 모델입니다

## 3. 단일 쓰레드가 오히려 주는 이점

멀티 쓰레드였다면 치러야 할 비용이 전부 사라집니다:

| 멀티 쓰레드 비용 | Redis 단일 쓰레드 |
|---|---|
| lock/mutex 경합 | **락이 아예 없음** — 모든 자료구조가 락 프리 |
| 컨텍스트 스위칭 | 없음 |
| 캐시 라인 무효화 (false sharing) | 없음 — CPU 캐시 효율 극대화 |
| 동기화 버그 | 없음 |

부수 효과로 **모든 명령이 원자적(atomic)** 입니다. `INCR`, `LPUSH` 등이 동시성 걱정 없이 안전한 이유, `MULTI/EXEC`나 Lua 스크립트가 격리 보장되는 이유가 바로 단일 쓰레드 실행 모델 덕분입니다.

## 4. 최적화된 자료구조

같은 "메모리 저장"이라도 구현이 다릅니다:

- **SDS (Simple Dynamic String)**: C 문자열 대신 길이를 헤더에 저장 → `strlen` O(1), 버퍼 미리 할당으로 재할당 최소화
- **listpack/ziplist**: 작은 컬렉션은 포인터 덩어리 대신 연속된 메모리 블록에 압축 저장 → 캐시 친화적, 메모리 절약
- **skiplist + hashtable** (Sorted Set): 점수 범위 검색 O(logN) + 멤버 룩업 O(1) 동시 지원
- **점진적 rehashing**: 해시 테이블 확장 시 한 번에 다 옮기지 않고 요청마다 조금씩 이동 → 단일 쓰레드인데도 latency spike 없음

## 5. "단일 쓰레드"의 정확한 범위

사실 요즘 Redis는 완전한 단일 쓰레드가 아닙니다:

- **명령 실행**: 단일 쓰레드 (이게 핵심 불변량)
- **Redis 6.0+ I/O threads**: 소켓 read/write와 프로토콜 파싱을 멀티 쓰레드로 분산 가능 (`io-threads` 설정) — 단, 명령 실행은 여전히 메인 쓰레드
- **백그라운드 쓰레드**: RDB/AOF 저장은 `fork()`, 큰 키 삭제(`UNLINK`), fsync 등은 별도 쓰레드

# "그냥 in-memory 저장"과 뭐가 다른가?

애플리케이션 안의 `HashMap`/`dict`와 비교하면:

| | 앱 내 HashMap | Redis |
|---|---|---|
| 속도 (단일 프로세스 내) | **더 빠름** (네트워크 없음, ns 단위) | 네트워크 왕복 비용 있음 (보통 sub-ms) |
| 여러 프로세스/서버 간 공유 | ❌ 불가능 | ✅ 핵심 존재 이유 |
| 앱 재시작 시 | 데이터 소멸 | RDB/AOF로 **영속성** 옵션 |
| 동시성 | 직접 락 관리해야 함 | 모든 명령 원자적 |
| 자료구조 | 직접 구현 | List, Set, Sorted Set, Hash, Stream, HyperLogLog, Bitmap... |
| 만료/축출 | 직접 구현 | TTL, LRU/LFU eviction 내장 |
| 부가 기능 | — | Pub/Sub, 분산 락, 트랜잭션, Lua, 복제, 클러스터 |

중요한 역설:

> **로컬 HashMap이 Redis보다 빠릅니다.** 네트워크를 안 타니까요.

Redis를 쓰는 이유는 "로컬 메모리보다 빨라서"가 아니라:

1. **여러 서버가 같은 상태를 공유**해야 할 때 (세션, 캐시, 분산 락, rate limiter)
2. 앱 프로세스와 **생명주기를 분리**하고 싶을 때 (배포해도 캐시 유지)
3. 풍부한 자료구조 + 원자적 연산을 네트워크 너머에서 쓰고 싶을 때

즉 Redis의 정확한 포지션은 **"네트워크로 접근 가능한, 자료구조 서버(data structure server)"** 이고, 그 네트워크 서버를 디스크 기반 DB 대비 압도적으로 빠르게 만든 비결이 ① in-memory ② epoll 이벤트 루프 ③ 락 없는 단일 쓰레드 실행 ④ 최적화된 자료구조의 조합입니다.

단일 서버 기준 보통 **10만+ ops/sec** (pipelining 쓰면 100만+)이 나오는데, 이건 "메모리라서"만이 아니라 위 설계 전부가 합쳐진 결과입니다.
