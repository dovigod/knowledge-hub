# Assistant

1) 디폴트 시 보증 수수료: 디폴트 여부가 아니라 투자자 이익 여부가 기준. guaranteeFee=totalProfit×fee%, 이익이 0보다 클 때만(purchase-fee.service.ts:75). redeem 시 FractionsRedeemed 이벤트의 guarantorFeeUsdc를 받아 적음. 정상 상환=보증인 수수료만 챙김(보험사). 디폴트+보상=보상금 지급(수수료보다 지출 클 수 있음). 디폴트+부분회수(투자자 손실)=이익 0 이하라 fee 0. 핵심: 보증인=보험사, '사고 났냐'가 아니라 '투자자가 이익 봤냐'가 기준. 2) 여러 투자자 분배: 나누는 게 아니라 각자 자기 구매건(PurchaseTransaction)마다 자기 이익에 비례해 독립 계산(purchase-investor.usecase.ts:357). 조각=지분이라 이익도 수수료도 지분만큼 자동 분배. 3) partial 4종: A. 남은 조각보다 많이 사려 함→availableCount 체크로 거부 400(:193). B. 일부만 팔림→정상 PARTIALLY_FUNDED, 나머지 계속 판매(:404). C. 상환 시 적게 받음→PARTIAL_REDEEM(redemptionAmount<expectedAtomic, redeem-investor:280), 디폴트+보증부족/비보증 시. D. 온체인 검증 실패→VERIFICATION_FAILED(count/금액 불일치).

그럼 invoice에서 현금으로 redeem가능하다 했을때, escrow는 뭘써? 그리고 buyer는 만기때 어떻게 받아?

<!-- kh:msg assistant -->
# Assistant

통화 3분리: currencyOriginal(원래 빚 USD/USDC/JPYC), listingCurrency(투자자 거래 통화→토큰 매핑), redemptionCurrency(만기 수령, 실제 redeem 로직선 미사용). 핵심: USD도 USDC 토큰으로 매핑(invoice-onchain.service.ts:162: case USDC/USD→USDC 주소, JPYC→JPYC). 1) escrow: 통화 무관 동일 온체인 Escrow(USDC 기준)—Purchase Escrow/Payback Escrow/Guarantor Vault. '현금 전용 escrow' 없음. 채무자가 진짜 현금으로 갚으면 은행으로, 운영자가 paybackFiat 기록+USDC를 Payback Escrow에 충당. 2) buyer 수령: 100% 온체인. 만기→창구 OPEN→투자자가 자기 지갑으로 redeem 트랜잭션→컨트랙트가 USDC 지급(정상=Payback Escrow, 디폴트+보증=Vault)→FractionsRedeemed 이벤트→ar-service 기록. 투자자는 끝까지 USDC만 만짐(지폐 아님).

<!-- kh:msg assistant -->
# Assistant

직접 검증: 투자자가 현금으로 받는 경로는 코드에 없음. redeem 진입점은 POST /ar/purchase/redeem 단 하나(purchase.controller.ts:51), txHash 필수(redeem-investor.dto.ts:11 @IsNotEmpty)→온체인 없이 redeem 불가. payout/disburse/bankTransfer 0건. '현금(USD) invoice'는 채무자가 달러 현금으로 갚는 빚이란 뜻이지 투자자가 현금 받는다는 뜻 아님. escrow는 통화 무관 온체인 USDC Escrow. buyer는 만기에 자기 지갑으로 온체인 redeem해서 USDC 수령. 채무자 현금↔투자자 USDC 간극은 운영자가 충당으로 메움. 비대칭 구조: 채무자만 현금 OK, 투자자는 USDC 전용.

MVP=B, 현금네이티브=A.

<!-- kh:msg assistant -->
# Assistant

'등록'이 만드는 것: ①DB 레코드 status=ACTIVE(즉시) ②온체인 Registry 등록(REGISTER outbox, onchainStatus PENDING→CONFIRMED 비동기). 정정: 상품 생성 전 등록 필요한 건 Seller·Payer(보증이면 Guarantor)뿐, 투자자(buyer)는 전제 아님—generate-invoices.usecase.ts에 investor 참조 0건, 투자자는 POST /ar/investor로 나중에 본인이 등록. '시작한다'=generateInvoices 호출(상품/쪽지 생성)이고 게이트 4개: ①Contract DRAFT ②payerConfirmation=RECEIVED ③Seller ACTIVE ④Payer ACTIVE. 미묘점: generateInvoices는 DB ACTIVE만 확인(onchainStatus CONFIRMED 미확인), 쪽지 DRAFT 생성은 가능하나 나중 SC 등록 땐 온체인 Registry 등록돼 있어야 revert 안 남. Guarantor는 상품 생성 전제 아니고 GuaranteePosition 등록 단계의 전제.
