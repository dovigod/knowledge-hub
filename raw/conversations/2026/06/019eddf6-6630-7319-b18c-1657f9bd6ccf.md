# Assistant

# Point Request 무지갑 대응 — Manual-Wallet Registration 트리거 Revert 여부 의사 결정

## 배경 / Context
Point request 시 사용자의 지갑(privy wallet)이 없는 경우, manual-wallet registration 플로우를 트리거하도록 한 작업(MIP-4299).
이 작업이 현재 발생 중인 **지갑 누락** 및 **지갑 중복 생성** 문제를 완전하게 해결하지 못한다는 점이 걸려 revert를 고민 중.

## 의사 결정 과정 (Q&A 형식의 사고 흐름)

**1. 이 작업이 어떤 트레이드오프를 만드는가?**
- (+) 기존 "지갑이 안 생기는" 이슈는 사라짐.
- (−) Race condition 발생 가능성이 높아짐.

**2. 둘 중 무엇이 더 위중한가?**
- 둘 다 위중함. 둘 중 하나라도 발생하면 **유저는 코인을 받지 못함** (동일한 최종 피해).

**3. 둘 다 기존부터 있던 문제인가?**
- Race condition은 기존에도 존재했음.
- 현재 방식은 race condition을 **새로 만든 게 아니라, 발생 가능성을 늘릴 뿐**.

**4. 발생 가능성은 무엇이 더 높은가?**
- **지갑 누락**의 가능성이 더 높음.

**5. 이미 report를 받은 상태인가?**
- 예. (지갑 누락에 대한 report 접수됨)

## 핵심 결론 / Decision Principle

> **가장 중요한 것은 문제 인식이다.**

- 진짜 문제는 **"지갑이 생성되지 않은 것"**.
- 따라서 태스크의 결과로 **지갑은 무조건 생성되도록** 보장해야 한다.
- 그렇다면 **"왜 안 생겼는가?"**, **"누구의 책임(role)인가?"** 를 규명해야 한다.
- 규명 후 **제안을 던지고 티키타카(논의)** 한다.

> **상급자가 고민하지 않게 하는 것 — 질문이 아니라 답을 제시하는 것이 가장 중요하다.**

## 정리
- Revert 자체가 목적이 아님. 핵심은 "지갑 생성 보장"이라는 본질적 문제 해결.
- Race condition(가능성 증가)과 지갑 누락(가능성 높음·이미 report됨) 모두 코인 미수령으로 귀결 → 둘 다 잡아야 함.
- 책임 소재(role)를 규명하고, 답(해결안)을 들고 상급자/관련자와 논의하는 방향으로 진행.
