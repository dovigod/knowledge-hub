# Docker 완벽 가이드

## 1. Docker의 역사

문제의 시작 — '내 컴퓨터에선 됐는데?' 2000년대까지 소프트웨어 배포는 환경 차이(OS 버전, 라이브러리 버전, 설정값) 때문에 악몽이었다.

연대기: ~2000년대 VMware 등 가상 머신(VM)으로 격리(무겁고 느림) → 2008 Linux 커널에 cgroups + namespaces 추가 → 2013 dotCloud의 Solomon Hykes가 Docker 발표(커널 기능을 쉽게 포장) → 2015 OCI 표준 제정, Kubernetes 등장 → 현재 컨테이너가 배포의 사실상 표준.

핵심: Docker는 새 기술 발명이 아니라 Linux 커널에 이미 있던 격리 기술(cgroups, namespaces)을 누구나 쉽게 쓰게 만든 것.

## 2. Docker는 어떻게 작동하는가

VM vs 컨테이너: VM은 각자 OS 전체(수 GB)를 가짐(부팅 수십 초, 무거움). 컨테이너는 호스트의 커널을 공유하고 앱+필요한 라이브러리만 격리(시작 1초 이내, 수십~수백 MB).

핵심 3요소: Dockerfile(이미지를 만드는 레시피) → 이미지(실행에 필요한 모든 것을 담은 불변 스냅샷) → 컨테이너(이미지를 실행한 인스턴스). 이미지가 클래스라면 컨테이너는 객체. (Dockerfile=레시피, Image=붕어빵 틀, Container=붕어빵)

격리는 Linux 커널의 두 기능으로: namespaces(프로세스가 '내 것'만 보게 함), cgroups(CPU/메모리 사용량 제한).

## 3. 로컬 직접 설치 vs Docker

이 레포의 `yarn up:infra`가 redis/postgres/rabbitmq를 docker로 한 번에 띄우는 예시. 환경 일관성, 버전 충돌 없음, 깨끗한 설치/삭제, 빠른 시작, 프로덕션 동일성. 핵심 가치: 'Build once, run anywhere'.

## 4. 네트워크 포트 매핑

중요: 포트 매핑은 Dockerfile에 없다. Dockerfile의 EXPOSE는 단순 문서/메모일 뿐, 실제 매핑은 `docker run -p` 또는 docker-compose.yml에서 한다.

컨테이너는 격리된 자기만의 네트워크 공간을 가져서 외부에서 내부 포트가 안 보인다(벽으로 막힌 방). 포트 매핑은 그 벽에 창문을 뚫는 것.

`docker run -p 8080:3000 my-service` → 왼쪽 8080=호스트(맥북) 포트, 오른쪽 3000=컨테이너 내부 포트. localhost:8080 접속 → 컨테이너의 3000번 앱으로 연결. `왼쪽:오른쪽` = `호스트:컨테이너`.

# namespaces와 cgroups — 컨테이너 격리의 두 기둥

namespaces = '무엇을 볼 수 있는가'(시야 격리), cgroups = '무엇을 얼마나 쓸 수 있는가'(자원 격리). 아파트 비유: namespaces는 방마다 벽을 세워 서로 못 보게, cgroups는 각 방에 전기/수도 사용량 한도.

## 1. namespaces — 시야 격리

종류: PID(프로세스 ID), NET(네트워크), MNT(파일시스템/마운트), UTS(호스트명), USER(사용자 ID), IPC(프로세스 간 통신).

PID namespace 예시: 호스트에서 node가 PID 5678이어도 컨테이너 안에서 ps aux 하면 자기 프로세스만 보이고 PID 1로 보인다. NET namespace 예시: 각 컨테이너가 자기만의 네트워크 스택을 가져서 둘 다 3000번 포트를 써도 충돌하지 않는다. namespaces는 일방향 거울로 둘러싸인 방.

## 2. cgroups — 자원 한도

시야만 격리하면 한 컨테이너가 자원을 다 먹어 다른 컨테이너가 굶을 수 있다. cgroups가 CPU/메모리/디스크 I/O/네트워크 대역폭을 제한. 예: `docker run --memory="512m" --cpus="1.5"`. 메모리 초과 시 OOM kill. cgroups는 각 방의 두꺼비집(전기 차단기).

## 3. 둘을 합치면 = 컨테이너

namespaces(시야 격리) + cgroups(자원 격리) = 격리되고 제한된 독립 실행 환경. Docker는 둘을 자동으로 쉽게 묶어주는 도구.

딱 한 군데가 거꾸로다. 오해: '다른 포트를 할당할 테니'가 아니라, 두 컨테이너가 진짜로 똑같이 3000번을 쓴다. 포트를 바꿔치기하는 게 아니라 둘 다 3000번을 쓰는데도 충돌이 안 난다. 이유는 각 컨테이너가 자기만의 NET namespace를 가져서 같은 '3000번'이라도 서로 다른 세상의 3000번이기 때문. 아파트 101호 1번 방과 102호 1번 방 같은 것.

PID와 포트는 별개: PID namespace(프로세스 번호 격리)와 NET namespace(네트워크/포트 격리)는 다른 namespace. 'PID가 달라서 포트가 괜찮은' 게 아니라 'NET namespace가 따로라서 포트가 괜찮은' 것.

충돌은 언제? 컨테이너 안에서는 안 나지만 호스트(맥북) 바깥으로 포트를 꺼낼 때 충돌 가능. 그래서 포트 매핑에서 호스트 번호만 다르게: user-service ports ["3000:3000"], clutch-service ports ["3010:3000"]. 컨테이너 안(오른쪽)은 둘 다 3000 그대로, 맥북 쪽(왼쪽)만 다르게.

# NET namespace의 정체와 실제 포트 할당 메커니즘

## 1. NET namespace = 네트워크 스택 통째로 복사본

네트워크 스택 부품: 네트워크 인터페이스(eth0, lo), IP 주소, 포트 테이블('어떤 포트를 누가 쓰는지' 장부), 라우팅 테이블, 방화벽 규칙(iptables). 보통 리눅스는 이 세트가 하나라 모든 프로세스가 공유 → 한 프로세스가 3000을 잡으면 다른 건 못 잡음. NET namespace를 만든다 = 이 세트를 통째로 새로 하나 더 복사. 포트 테이블이 namespace마다 따로라 각자 자기 장부에 '3000 사용 중'이라 적어도 충돌 없음.

## 2. 실제 포트 할당

앱이 app.listen(3000) 호출 → 내부적으로 bind(socket, port=3000) 시스템 콜. 커널이: (1) 이 프로세스가 속한 NET namespace 확인 (2) 그 namespace의 포트 테이블 확인 (3) 비어있으면 장부에 기록, 차있으면 EADDRINUSE 에러. 커널은 그 프로세스가 속한 namespace의 포트 테이블만 확인하므로 서로의 존재를 모름. 포트 할당 = 커널이 해당 namespace 포트 장부에 '이 번호는 이 프로세스 것'이라 적는 행위.

## 3. 바깥에서 접속하는 법

(a) veth pair = 두 namespace를 잇는 가상 랜선 한 쌍. 한쪽 끝은 컨테이너(eth0), 다른 쪽은 호스트(vethXXX). docker0는 가상 스위치(브리지)로 여러 veth가 꽂힘. (b) 포트 포워딩(NAT): `-p 3010:3000` → iptables에 '맥북 3010으로 온 패킷은 컨테이너의 3000으로 전달' 규칙 추가. 흐름: 맥북 localhost:3010 → iptables NAT → docker0 → veth → 컨테이너 eth0 → 3000번 앱.

# veth pair, docker0 bridge, iptables NAT 상세

출발점: 컨테이너는 외딴 섬. NET namespace는 네트워크 스택 통째 복사본이라 기본 상태로는 바깥과 연결할 통로가 0개. 누군가 물리적으로 선을 연결해줘야 함 = veth pair.

조각1 veth pair = 양 끝이 뚫린 마법의 랜선. virtual ethernet. 항상 쌍으로 생기고 한쪽 끝에 들어간 데이터는 무조건 반대쪽으로 나온다. 끝A=컨테이너의 eth0, 끝B=호스트의 vethXXXX. eth0@if13의 @if13 = '내 랜선 반대쪽 끝은 호스트의 13번 인터페이스'.

조각2 docker0 bridge = 여러 랜선을 꽂는 가상 스위치(멀티탭). 컨테이너끼리 통신시켜주고(IP로 서로 호출), 자신도 IP(게이트웨이)를 가짐.

조각3 두 방향 트래픽: ① 나가는 트래픽(컨테이너→인터넷): 쉬움, 자동. 호스트가 출발지 주소를 자기 IP로 바꿈(masquerade NAT). ② 들어오는 트래픽(맥북→컨테이너): 어려움, -p 필요. 컨테이너 IP는 호스트 안에서만 아는 사설 주소+기본 차단. `-p 3010:3000` → iptables DNAT 규칙: '목적지가 호스트:3010인 패킷이 오면 목적지를 컨테이너IP:3000으로 갈아끼워라'. DNAT=Destination NAT(목적지 주소 갈아끼우기).

핵심 3줄: veth pair=컨테이너 벽에 뚫은 랜선, docker0=랜선 꽂는 가상 스위치, iptables NAT=주소 번역기(나갈 때 자동 masquerade, 들어올 때 -p로 DNAT). veth+bridge는 배선, iptables NAT은 주소 번역.

# OSI 7계층 매핑

L7 응용: nginx, HTTP, curl, HTTP 200(메시지). L6 표현: 평문 HTTP라 거의 없음(HTTPS면 TLS 암호화). L5 세션: TCP/IP에선 L4에 흡수. L4 전송: 포트 80/8080, bind(), TCP LISTEN, 포트 매핑의 '포트' 부분(세그먼트/포트번호). L3 네트워크: IP 192.168.215.2, 게이트웨이, iptables NAT(DNAT/MASQUERADE)(패킷/IP주소). L2 데이터링크: veth pair, docker0 브리지(스위치), MAC 주소(프레임/MAC). L1 물리: veth의 가상 랜선 자체(비트).

핵심: veth=가상 NIC(랜선 비유는 L1이지만 MAC 박힌 프레임 다루니 L2, link/ether=L2 증거). docker0=가상 스위치(L2 장비, 단 IP도 가져 L3 게이트웨이 겸함). iptables NAT=L3(IP)+L4(포트) 양다리. 포트 매핑 8080:80=순수 L4.

패킷 캡슐화 여정: 보낼 때 위→아래로 봉투 싸기(L7 HTTP→L4 TCP/포트→L3 IP→L2 Eth/MAC→L1 비트), 경로 중간 NAT이 L3 dst IP와 L4 dst port 갈아끼움, docker0가 L2 MAC 보고 veth로 전달, 받을 때 아래→위로 봉투 벗기기.

OSI에 안 들어가는 것: PID namespace(OS 프로세스 격리, 네트워크 아님), cgroups(자원 제한, 네트워크 아님). NET namespace는 단일 계층이 아니라 L2~L4 스택을 통째 복제하는 그릇. 그래서 같은 80번 포트(L4)도 충돌 없이 쓸 수 있었던 것. 네트워크 부품(OSI 안)과 격리 부품(OSI 밖)이 두 갈래.

## MyEtherWallet 2018 BGP 하이재킹 사건

2018년 4월 24일: 1단계 BGP 하이재킹(L3) - 공격자가 라우터들에게 'Amazon Route53 DNS 서버 IP 대역은 우리 것'이라고 more-specific 경로를 BGP 광고 → AWS DNS로 갈 트래픽을 공격자에게. 2단계 DNS 스푸핑(L7) - 가로챈 DNS가 'myetherwallet.com → 러시아 공격자 IP' 거짓 응답. 3단계 피싱 - 진짜 주소 쳤는데 가짜 사이트 → 개인키 탈취. 피해 약 215 ETH(~$150,000).

핵심: 가짜 사이트는 유효한 TLS 인증서가 없어 브라우저가 경고를 띄웠고, 경고를 무시하고 '그래도 진행'을 누른 사람만 털렸다. BGP도 DNS도 뚫렸지만 TLS 인증서 검증이 마지막 방어선.

## TLS 방어 코드 데모

인증서 3종(컨테이너 내 openssl): (1) 루트 CA - `openssl req -x509 -newkey rsa:2048 -nodes -keyout ca.key -out ca.crt -days 3650 -subj /CN=MyTrustedRootCA`. (2) 정품 서버 - bank.local CSR 생성 후 CA가 서명(`openssl x509 -req -in server.csr -CA ca.crt -CAkey ca.key -out server.crt -extfile san.ext`) → issuer=MyTrustedRootCA. (3) 공격자 - 자체서명(-x509, issuer=bank.local=주체와 동일). 도메인명은 위조 가능하지만 신뢰 CA 서명은 위조 불가(CA 개인키 없음).

nginx 설정 두 서버 겉보기 동일(listen 443 ssl, server_name bank.local), 어떤 인증서를 마운트했느냐만 다름. 클라이언트 curl: `--resolve bank.local:443:$IP`(DNS/BGP 하이재킹 시뮬레이션, 도메인이 가리키는 IP 바꿔치기), `--cacert /ca.crt`(이 CA만 신뢰=방어선), URL은 항상 진짜 bank.local.

세 시나리오: 1)정상(정품 IP+CA신뢰)→OK 진짜 서버. 2)하이재킹(가짜 IP+CA신뢰)→curl: (60) SSL certificate ... self-signed certificate, 연결 거부=우회당해도 차단(MEW 브라우저 경고). 3)피해자(가짜 IP+`-k` 검증 끔)→STOLEN 가짜 서버 연결=경고 무시.

시나리오2가 MEW 교훈: 트래픽 완벽 우회당해도 공격자는 신뢰 CA 서명 위조 불가 → 클라이언트가 연결 거부. 시나리오3(-k)이 '그래도 진행' 누른 사람. 큰 그림: 하이재킹은 '어디로 보낼지'(경로)를 속이지만 TLS는 '상대가 진짜인지'(신원)를 CA 서명으로 검증. 경로 100% 장악당해도 막히지만 단 사용자가 인증서 경고를 무시(-k)하지 않는 한. 실무에선 mTLS로 이 검증을 자동·강제화. 데모 후 컨테이너+임시파일 삭제로 원상복구.
