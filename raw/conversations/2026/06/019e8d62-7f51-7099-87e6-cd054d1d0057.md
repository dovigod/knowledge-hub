## TL;DR

DNS의 MX 레코드(이메일을 받을 서버를 알려주는 주소록), 이메일 발송 IP 평판(메일이 스팸함에 가지 않게 하는 신뢰 점수), 그리고 비트코인 트랜잭션 처리 과정(돈을 동전(UTXO)처럼 쪼개 쓰고, 채굴자가 블록에 담아 확정하는 방식)을 차례로 배운 대화입니다.

## Key takeaways

- > [!summary] MX 레코드는 "이 도메인의 이메일은 이 서버로 보내세요"라고 알려주는 DNS 주소록입니다. 앞의 숫자(우선순위)가 낮을수록 먼저 시도됩니다 — 줄서기 번호표 같은 것이에요.
- 이메일 IP 평판(reputation)은 발신 IP의 신뢰 점수입니다. 스팸 신고율, 바운스율(없는 주소로 보낸 비율), 블랙리스트 등재 여부로 결정되며, 점수가 나쁘면 메일이 스팸함으로 갑니다.
- 새 IP로 메일을 보낼 땐 워밍업(warming)이 필요합니다 — 첫날 50~100통부터 시작해 4~8주에 걸쳐 천천히 늘립니다. 새 운동을 시작할 때 몸을 푸는 것과 같아요.
- > [!tip] 요즘은 IP보다 도메인 평판이 더 중요합니다. SPF/DKIM/DMARC 인증 설정은 필수이고, 마케팅 메일은 서브도메인으로 분리해 중요한 메일(영수증 등)의 평판을 보호하는 게 정석입니다.
- 비트코인에는 계좌 잔고가 없고 UTXO(미사용 출력)라는 "디지털 동전"만 있습니다. 5만 원권으로 3만 원을 내면 거스름돈을 받듯, UTXO를 통째로 쓰고 거스름돈을 자기 주소로 돌려받습니다.
- 비트코인 트랜잭션은 1) 지갑이 동전(UTXO)을 골라 서명 → 2) 네트워크에 전파되어 멤풀(대기실)에서 대기 → 3) 채굴자가 수수료 높은 순으로 골라 블록에 포함 → 4) 블록이 6개 쌓이면 사실상 확정, 순서로 처리됩니다.
- 비트코인 수수료는 따로 적는 칸이 없고 "넣은 돈 − 보낸 돈"의 차액이 자동으로 수수료가 됩니다. 블록 공간이 한정돼 경매처럼 수수료 경쟁이 일어납니다.

DNS 셋팅관련해서

# Assistant

아, DNS 얘기였군요. **MX (Mail eXchanger) 레코드**는 상태값이라기보다는 DNS 레코드 타입 중 하나로, **해당 도메인의 이메일을 수신할 메일 서버를 지정**하는 레코드입니다.

구조는 이렇습니다:

```
example.com.    3600    IN    MX    10 mail1.example.com.
example.com.    3600    IN    MX    20 mail2.example.com.
```

- **우선순위 (Priority)** — 앞의 숫자 (10, 20). **낮을수록 먼저 시도**되고, 같은 값이면 부하 분산됩니다. 위 예시에선 mail1이 죽었을 때만 mail2로 갑니다.
- **메일 서버 호스트명** — 반드시 A/AAAA 레코드로 해석되는 호스트명이어야 하고, CNAME이나 IP 직접 지정은 표준 위반입니다.

흔한 사용 예:

| 서비스 | MX 값 |
|---|---|
| Google Workspace | `smtp.google.com` (우선순위 1) |
| Microsoft 365 | `<도메인>.mail.protection.outlook.com` (0) |

확인 방법:

```bash
dig MX example.com +short
# 또는
nslookup -type=MX example.com
```

참고로 메일 관련 DNS 셋팅은 보통 MX만으론 부족하고, 발신 인증을 위해 **SPF**(TXT), **DKIM**(TXT), **DMARC**(`_dmarc` TXT)도 같이 설정해야 스팸 처리를 피할 수 있습니다.

혹시 지금 특정 도메인 MX 설정 중이시면 (예: mvlchain.io 관련) 어떤 메일 서비스에 연결하려는지 알려주시면 구체적으로 도와드릴게요.

## IP Reputation이란

이메일 발송 시 **발신 IP 주소에 대한 신뢰도 점수**입니다. Gmail, Outlook 같은 수신 측 메일 서버(ISP)가 "이 IP에서 오는 메일을 받아줄까, 스팸함에 넣을까, 아예 거부할까"를 결정하는 핵심 기준이에요.

## 평가 요소

- **스팸 신고율 (complaint rate)** — 수신자가 "스팸 신고" 버튼을 누르는 비율. 보통 0.1% 이상이면 위험, Gmail은 0.3% 넘으면 사실상 차단
- **바운스율 (hard bounce)** — 존재하지 않는 주소로 보내는 비율. 리스트 품질이 나쁘다는 신호
- **스팸트랩 적중** — ISP가 심어놓은 미끼 주소로 발송하면 즉시 평판 급락
- **발송량 패턴** — 갑자기 대량 발송하면 의심. 평소 안 보내던 IP가 하루에 수만 통 쏘면 차단됨
- **인증 여부** — SPF / DKIM / DMARC 정합성
- **블랙리스트 등재** — Spamhaus, Barracuda 등 RBL에 올라가 있는지
- **수신자 반응 (engagement)** — 열람, 답장 vs 읽지 않고 삭제

## 공유 IP vs 전용 IP

| | 공유 IP (Shared) | 전용 IP (Dedicated) |
|---|---|---|
| 평판 | 같은 IP 쓰는 다른 발송자들과 **공유** | 내 발송 품질이 곧 내 평판 |
| 적합 | 소량 발송 (월 수만 통 이하) | 대량 발송 (월 10만+ 통, 꾸준한 볼륨) |
| 리스크 | 남이 스팸 쏘면 같이 피해 | 볼륨이 적거나 불규칙하면 오히려 평판 형성이 안 됨 |

SendGrid, AWS SES, Mailgun 같은 서비스가 공유 IP 풀 평판을 관리해주는 게 핵심 가치 중 하나입니다.

## IP Warming (워밍업)

새 IP는 평판이 없어서 **처음부터 대량 발송하면 바로 차단**됩니다. 그래서:

1. 첫날 50~100통 → 며칠마다 2배씩 증가 → 4~8주에 걸쳐 목표 볼륨 도달
2. 워밍업 기간엔 **engagement 높은 수신자**(최근 열람한 유저)에게 먼저 발송
3. AWS SES 등은 자동 워밍업 기능 제공

## 확인 도구

```
- Google Postmaster Tools  — Gmail 기준 IP/도메인 평판, 스팸률 (필수)
- Microsoft SNDS           — Outlook/Hotmail 기준
- Sender Score (Validity)  — 0~100 점수, 80+ 양호
- MXToolbox Blacklist Check — RBL 등재 여부 일괄 확인
- Spamhaus Lookup          — 가장 영향력 큰 블랙리스트
```

## 참고: 요즘은 Domain Reputation이 더 중요

2024년 이후 Gmail/Yahoo 대량발송자 정책 강화로, IP보다 **발신 도메인 평판** 비중이 커졌습니다. IP를 바꿔도 도메인 평판이 나쁘면 소용없어요. 그래서:

- SPF + DKIM + DMARC(`p=none` 이상) 설정은 이제 대량 발송자 **필수 요건**
- 마케팅 메일은 `marketing.example.com` 같은 **서브도메인으로 분리**해서 트랜잭션 메일(영수증, 인증 메일)의 평판을 보호하는 게 정석
- 원클릭 수신거부 헤더 (`List-Unsubscribe`) 필수

특정 서비스(SES, SendGrid 등) 도입 검토 중이거나, 지금 메일이 스팸함으로 가는 문제를 겪고 계시면 상황 알려주시면 그에 맞춰 더 구체적으로 설명드릴게요.

## 비트코인 트랜잭션 처리 흐름

### 1. UTXO 모델 — 계좌 잔고가 아닌 "동전" 개념

비트코인엔 "계좌 잔고"라는 게 없습니다. 대신 **UTXO (Unspent Transaction Output, 미사용 출력)** 의 집합이 있어요.

- 내 지갑의 "잔고" = 내 주소로 잠긴 UTXO들의 합
- 트랜잭션은 기존 UTXO를 **통째로 소비(input)** 하고, 새 UTXO를 **생성(output)** 하는 행위

```
[내 UTXO: 0.5 BTC] ──┐
                      ├─→ Input ──→ Output 1: 0.3 BTC (상대방 주소)
                      │            Output 2: 0.1999 BTC (내 거스름돈 주소)
                      └─           (차액 0.0001 BTC = 수수료, 명시 안 됨)
```

현금과 비슷합니다 — 5만 원권으로 3만 원을 내면 거스름돈을 받듯, UTXO는 쪼개 쓸 수 없어서 **거스름돈(change) output**을 자기 주소로 돌려보냅니다.

### 2. 트랜잭션 생성과 서명

1. **지갑이 input 선택 (coin selection)** — 보낼 금액 + 수수료를 충당할 UTXO들을 고름
2. **output 구성** — 받는 사람 주소에 잠금 스크립트(locking script, `scriptPubKey`) 설정. "이 공개키 해시에 대응하는 서명을 제시해야 쓸 수 있음"이라는 조건
3. **디지털 서명** — 각 input에 대해 개인키로 ECDSA(또는 Taproot 이후 Schnorr) 서명. "이 UTXO의 정당한 소유자"임을 증명하는 해제 스크립트(unlocking script)
4. 서명된 raw transaction이 완성됨

### 3. 전파 (Broadcast) 와 멤풀

- 트랜잭션을 연결된 노드에 전송 → 각 노드가 **검증** 후 P2P 네트워크로 가십(gossip) 전파
- 검증 항목: 서명 유효성, input UTXO가 실제 존재하고 미사용인지(이중지불 방지), input 합 ≥ output 합, 스크립트 실행 성공 등
- 검증 통과한 트랜잭션은 각 노드의 **멤풀(mempool)** 에 대기 — "블록에 담기길 기다리는 대기실"

### 4. 채굴과 블록 포함

- 채굴자는 멤풀에서 **수수료율(sat/vByte)이 높은 순**으로 트랜잭션을 골라 블록(최대 ~4MB weight)을 구성
- PoW(작업증명) 수행: 블록 헤더의 nonce를 바꿔가며 목표 난이도 이하의 SHA-256 해시를 찾음 (평균 10분)
- 성공하면 블록을 전파 → 다른 노드들이 검증 후 체인에 추가
- 이때 트랜잭션이 **1 confirmation** 획득

### 5. 컨펌 (Confirmation)

| 컨펌 수 | 의미 |
|---|---|
| 0 (멤풀) | 미확정 — 이중지불 위험 있어 신뢰 금물 |
| 1 | 블록에 포함됨 — 소액 결제 수준 |
| 3 | 일반적인 입금 인정 기준 |
| 6 | 사실상 되돌릴 수 없음 (거래소 표준) |

블록이 위에 쌓일수록 해당 트랜잭션을 되돌리려면 그 이후 모든 블록의 PoW를 다시 해야 하므로 기하급수적으로 어려워집니다.

### 6. 수수료 메커니즘

- **수수료 = input 합 − output 합** (명시적 필드가 없음!)
- 블록 공간이 한정돼 있어 **경매 시장**처럼 작동 — 혼잡할 때 수수료율 낮으면 며칠씩 대기
- 트랜잭션이 안 들어갈 때 구제책:
  - **RBF (Replace-By-Fee)**: 같은 input으로 수수료 올린 트랜잭션으로 교체
  - **CPFP (Child-Pays-For-Parent)**: 거스름돈 output을 높은 수수료로 다시 써서 부모까지 같이 채굴되게 유도

### 7. 주요 업그레이드

- **SegWit (2017)** — 서명(witness) 데이터를 분리해 트랜잭션 가변성(malleability) 해결 + 실질 블록 용량 증가. 주소 `bc1q...`
- **Taproot (2021)** — Schnorr 서명 도입. 다중서명/복잡한 조건도 단일 서명처럼 보여 프라이버시·효율 향상. 주소 `bc1p...`
- **Lightning Network** — 온체인 처리량 한계(~7 TPS)를 우회하는 L2. 채널을 열고 오프체인으로 무수히 거래 후 정산만 온체인 기록

### 정리: 전체 생애주기

```
지갑: UTXO 선택 → output 구성 → 서명
  → 노드 전파 → 각 노드 검증 → 멤풀 대기
  → 채굴자가 수수료순 선택 → PoW → 블록 포함 (1 conf)
  → 블록 누적 (6 conf ≈ 최종 확정)
```

특정 부분(스크립트 동작 원리, coin selection 알고리즘, Lightning 구조 등)을 더 깊게 파고 싶으시면 말씀해주세요.
