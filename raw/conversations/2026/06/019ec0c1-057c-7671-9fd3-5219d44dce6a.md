docker에 대한 이해는 햇는데 kubernetes에 대해 알고싶어 이게 뭐고 왜 필요한거야?

<!-- kh:msg assistant -->
# Assistant

Docker는 이해했다니 거기서부터 자연스럽게 이어서 설명할게.

## Docker만으로는 부족한 순간

Docker는 "컨테이너 1개를 만들고 실행"하는 도구야. 근데 실제 서비스를 운영하다 보면 이런 상황이 생겨:

- 트래픽이 몰리면 컨테이너를 10개로 늘려야 해 (그리고 한가하면 다시 줄여야 함)
- 컨테이너가 죽으면 누군가 다시 살려야 해 (새벽 3시에도)
- 컨테이너 10개가 여러 서버에 흩어져 있으면 어느 서버에 띄울지 정해야 함
- 새 버전 배포할 때 서비스 중단 없이 하나씩 교체해야 함
- 컨테이너끼리 서로 찾아서 통신해야 함 (IP가 계속 바뀌는데)

이걸 사람이 손으로, 혹은 셸 스크립트로 다 하기엔 너무 많고 실수가 나. 이 "여러 컨테이너를 자동으로 관리"하는 일을 컨테이너 오케스트레이션(orchestration)이라고 부르고, Kubernetes(쿠버네티스, 줄여서 k8s)가 그 표준이야.

비유하자면, Docker는 "악기 한 대", Kubernetes는 "오케스트라 지휘자"야. 연주자(컨테이너)가 아무리 많아도 지휘자가 누가 언제 무엇을 연주할지 조율해줌.

## Kubernetes가 해주는 핵심 일

- 자가 치유 (Self-healing): 컨테이너가 죽으면 자동으로 다시 띄움
- 오토스케일링: 부하에 따라 컨테이너 개수를 자동으로 늘리고 줄임
- 스케줄링: 여러 서버 중 자원이 남는 곳에 컨테이너를 알아서 배치
- 롤링 업데이트: 무중단으로 새 버전 배포, 문제 생기면 자동 롤백
- 서비스 디스커버리 / 로드밸런싱: 컨테이너끼리 이름으로 찾고 트래픽을 고르게 분배
- 선언적 관리: "컨테이너 3개 떠 있어야 함"이라고 원하는 상태를 선언하면, k8s가 알아서 그 상태를 유지

마지막 "선언적 관리"가 핵심 철학이야. Docker는 "이거 해, 저거 해"라고 명령(절차)하는 느낌이라면, k8s는 "최종 상태가 이래야 해"라고 선언하면 현재 상태와 비교해서 알아서 맞춰줘. (YAML 파일로 작성)

## 핵심 개념 몇 가지

- Pod: k8s의 최소 배포 단위. 컨테이너 1개(또는 몇 개)를 묶은 것
- Deployment: "이 Pod를 몇 개 유지해줘"를 선언하는 객체 (스케일링/롤링 업데이트 담당)
- Service: 흩어진 Pod들에 접근하는 고정 진입점 (로드밸런서 역할)
- Node: Pod가 실제로 돌아가는 서버(머신). 여러 Node를 묶은 게 Cluster

## 그래서 언제 필요한가?

솔직히 말하면 항상 필요한 건 아니야.
- 서비스 1~2개, 트래픽 적음 → Docker Compose만으로 충분
- 마이크로서비스 15개+, 여러 서버, 무중단 배포, 트래픽 변동 큼 → Kubernetes가 빛을 발함

이 모노레포처럼 NestJS 마이크로서비스가 15개 이상이고 blockchain/mobility/gaming 도메인이 나뉘어 있는 구조면, 운영 환경(production)에서는 거의 확실히 k8s 같은 오케스트레이션 위에서 돌아가고 있을 거야.

# Assistant

## 1. "nginx 띄우면 되는 거 아냐?"

반은 맞아. nginx는 로드밸런싱(여러 백엔드에 트래픽 분배)은 잘 해. 근데 문제는 그 백엔드 목록을 누가 갱신하느냐야.

nginx 설정은 upstream에 IP를 사람이 손으로 박아넣은 거야. 그런데:
- 컨테이너 하나가 죽고 새로 뜨면 → IP가 바뀜 → nginx는 아직 죽은 IP로 트래픽을 보냄
- 오토스케일링으로 3개 → 10개가 되면 → 새로 생긴 7개를 nginx가 모름

즉 nginx는 "분배"는 하지만, "지금 살아있는 컨테이너가 누구인지"를 스스로 알아내지 못해. 누군가 설정 파일을 다시 쓰고 nginx -s reload 해줘야 하는데, 컨테이너가 수시로 죽고 살아나는 환경에선 그걸 사람이 못 따라가.

그래서 빠진 퍼즐 조각이 "서비스 디스커버리(service discovery)"야: "이름표(예: user-service)를 주면, 지금 이 순간 살아있는 컨테이너들의 IP 목록을 자동으로 알려주는 시스템"

직접 만들려면 nginx + Consul(또는 etcd) + consul-template 같은 걸 조합해야 함. Kubernetes는 이걸 내장으로 줘: Service 객체를 만들면 user-service라는 고정 이름(DNS)이 생기고, 뒤에 붙은 Pod들이 죽고 살아나도 k8s가 목록을 실시간으로 자동 갱신. 다른 컨테이너는 http://user-service:3000로 부르면 알아서 살아있는 Pod로 연결됨. (외부 트래픽 받을 땐 k8s에서도 nginx를 Ingress 형태로 같이 씀)

## 2. "여러 서버에 흩어져 있으면 어느 서버에 띄울지 정해야 함"

이건 스케줄링(scheduling) 이야기야. 서버(머신)가 3대 있고 각각 CPU/RAM이 한정돼 있어. 컨테이너 10개(각각 자원 소비)를 어느 서버에 어떻게 나눠 배치할까? 한 서버에 몰면 터지고 나머지는 놀고, 골고루 분산하려면 기준이 필요해. 이게 "짐을 여러 트럭에 효율적으로 싣는(bin-packing)" 문제와 같아.

Docker만 쓰면 네가 직접 각 서버 SSH 접속해서 docker run을 손으로 결정/실행해야 함. Kubernetes의 스케줄러가 이걸 자동으로 해: "이 Pod는 CPU 2코어, RAM 4GB 필요해"라고 선언만 하면 자원 남는 서버를 찾아 배치하고, "이 두 Pod는 같은 서버에 두지 마" 같은 규칙도 줄 수 있어.

두 질문 다 결론은 같아: 규모가 작으면 nginx + 수동 배포로 충분한데, 컨테이너가 수십~수백 개가 되고 수시로 죽고 살아나면 사람이 못 따라가서 자동화 시스템(k8s)이 필요해진다.

# Assistant

## 1. "팟 늘어나면 라우팅 시스템 재시작이 필요한가?" ← 가장 중요

아니, 재시작 안 해. 이 지점이 nginx 수동 방식과 k8s의 결정적 차이야.

nginx 방식은 설정 파일 수정 → nginx -s reload(재적용 필요). reload는 무중단이긴 하지만 "설정을 다시 읽는 행위"가 명시적으로 일어나야 함.

k8s는 구조가 달라. 핵심은 Endpoints(엔드포인트) 객체야. Service는 고정 가상 IP를 갖고, 그 뒤 실제 Pod 목록(Endpoints)을 k8s가 실시간 자동 갱신해. 새 Pod가 뜨면 컨트롤러가 감지해 Endpoints에 자동 추가하고, 각 노드의 kube-proxy가 라우팅 규칙(iptables/IPVS)을 즉시 갱신해. 이 갱신은 프로세스 재시작이 아니라 커널 규칙 테이블만 수정하는 거라 무중단.

비유: nginx는 "전화번호부를 새로 인쇄해서 배포", k8s는 "교환원이 실시간으로 연결을 바꿔주는" 느낌. 그래서 오토스케일링으로 Pod가 3개→50개가 되어도 아무것도 재시작 안 하고 트래픽이 퍼져.

## 2. Docker Compose vs Kubernetes 비교

- 대상 범위: Compose=한 대 머신 / k8s=여러 머신(클러스터)
- 용도: Compose=로컬 개발 / k8s=운영 대규모
- 컨테이너 죽으면: Compose=restart:always 단순 재시작 / k8s=자가치유+다른 서버 재배치
- 스케일링: Compose=수동 한 머신 안 / k8s=자동 여러 서버 분산
- 로드밸런싱: Compose=거의 없음 / k8s=Service 내장
- 무중단 배포: Compose=직접 스크립트 / k8s=롤링 업데이트+자동 롤백 내장
- 학습 난이도: Compose=쉬움 / k8s=어려움

한 줄: Docker Compose=한 대 컴퓨터에서 컨테이너 여러 개 띄우는 도구 / Kubernetes=여러 대 컴퓨터를 묶어 컨테이너 수백 개를 자동 운영하는 시스템. Compose에도 같은 네트워크 안 이름 기반 디스커버리는 있지만 한 머신 안에서만 동작.

## 3. "서버=컴퓨터인가? 로컬엔 대응 없겠군"

맞아, 서버=컴퓨터(물리 서버든 클라우드 가상머신이든). k8s 용어로 Node. 여러 Node를 묶은 게 Cluster. 다만 "로컬엔 대응 없다"는 반만 맞아 — minikube, kind, Docker Desktop(Enable Kubernetes)으로 노트북 1대를 1-Node 클러스터처럼 만들 수 있어. Node가 1개뿐이라 분산 스케줄링의 묘미는 못 보지만 Pod/Service/Deployment/자가치유/롤링 업데이트 개념은 똑같이 실습 가능.

# Assistant

## 전체 그림: 컨트롤 플레인(두뇌) + 워커 노드(일꾼)

컨트롤 플레인: API Server(정문), etcd(상태 저장 DB), Controllers(상태 감시/조정), Scheduler(배치 결정). 각 워커 노드: kubelet(Pod 생사 관리), kube-proxy(라우팅 규칙 관리), Pod들.

## 1단계: 새 Pod 뜨면 컨트롤러가 Endpoints에 자동 추가

선언적 상태 관리. replicas:3 같은 원하는 상태가 etcd에 저장되고, 컨트롤러는 리컨실리에이션 루프(원하는 상태 vs 현재 상태 비교 → 다르면 조정)를 무한 반복해. 새 Pod가 IP를 받으면 kubelet이 Ready를 API Server에 보고 → EndpointSlice 컨트롤러가 엔드포인트 목록에 자동 추가. 핵심은 watch(감시) 메커니즘: 폴링이 아니라 "바뀌면 알려줘" 구독이라 밀리초 단위 통보.

## 2단계: kube-proxy가 변화 감지 → 라우팅 규칙 갱신

각 노드의 kube-proxy도 API Server에 watch를 걸어둠. EndpointSlice가 바뀌면 즉시 통보받아 자기 노드의 라우팅 규칙을 다시 씀.

## 3단계: 커널 레벨 규칙 테이블 수정 — iptables의 정체

Service IP는 어디에도 실제로 존재하지 않는 가상 IP(VIP)야. 컨테이너가 VIP로 요청하면 리눅스 커널 netfilter/iptables 규칙이 진짜 Pod IP로 바꿔치기 = DNAT(목적지 NAT). kube-proxy가 만든 규칙은 "목적지가 VIP면 1/3 확률로 Pod1, 1/3 Pod2..."처럼 동작. 로드밸런싱이 애플리케이션이 아니라 커널 패킷 처리 단계에서 일어남.

왜 재시작 불필요? nginx는 user space 프로세스라 설정을 reload해야 하지만, iptables 규칙은 커널이 든 테이블(데이터)일 뿐이라 줄 하나 추가/삭제하면 다음 패킷부터 새 규칙대로 처리. "다시 읽는 행위" 자체가 없음. 비유: nginx reload=메뉴판 새로 인쇄/배포, iptables 갱신=화이트보드 한 줄 고치기.

참고(IPVS): 규칙이 수천 개로 늘면 iptables는 선형 탐색이라 느려져 대규모는 IPVS(해시 테이블 기반) 사용. 원리는 같고 성능만 좋아진 버전.

## "도커에서 노드는 물리 컴퓨터 한 대?"

노드(Node)는 Docker 단독 개념이 아니라 오케스트레이터 개념이야. 그냥 docker run은 "노드"라는 말을 거의 안 씀(머신 1대). Docker Swarm/Kubernetes에서 머신 1대=1 노드. 답: 노드=컨테이너가 도는 머신 한 대가 맞지만, 물리 컴퓨터로 한정 X(클라우드 가상머신일 수도, 실무에선 가상머신이 더 흔함). 단독 Docker엔 노드 개념이 굳이 필요 없고, 여러 머신을 묶는 오케스트레이터가 등장해야 "노드1, 노드2" 이름표가 의미 생김.

완전 정확한 직감이야. k8s 네트워킹은 Docker가 쓰는 리눅스 기능들을 그대로 물려받아 확장한 거라 닮은 게 당연해.

## 공통 뿌리: network namespace + veth + iptables

이 셋은 리눅스 커널 기능이지 Docker/k8s 발명품이 아님. network namespace(netns)=네트워크 스택(인터페이스, 라우팅 테이블, iptables 규칙)을 통째로 격리한 독립 공간. veth pair=두 namespace를 잇는 가상 랜선. iptables=각 namespace마다 독립적으로 존재하는 규칙 테이블. iptables는 netns에 종속되므로 netns가 다르면 iptables도 별개.

## Docker의 네트워크 구조

컨테이너마다 자기 netns(안에 eth0=고유 IP). 각 eth0은 veth pair로 호스트의 docker0 브리지(가상 스위치)에 연결. 외부로 나갈 때 호스트 iptables가 SNAT(MASQUERADE)로 출발지를 호스트 IP로 변환. -p 8080:80 포트 매핑은 DNAT. ← Docker도 이미 DNAT/SNAT을 iptables로 쓰고 있던 거야.

## k8s가 올린 세 가지 변화

변화1: 컨테이너가 아니라 Pod 단위 netns. Pod 1개=netns 1개, 안의 컨테이너들이 netns 공유(pause 컨테이너가 netns를 들고 있고 앱 컨테이너가 얹힘 → Pod 안 컨테이너는 localhost로 통신).

변화2: docker0 브리지 대신 CNI 플러그인(Calico/Flannel 등). 머신이 여러 대라 단일 브리지로 부족 → CNI가 "Pod는 노드가 달라도 서로의 Pod IP로 직접 통신 가능"이라는 평평한 네트워크 모델 구현.

변화3: Service VIP의 DNAT은 호스트(root) netns의 iptables에서 일어남. kube-proxy가 규칙을 써넣는 곳이 거기. Pod의 netns 안 iptables는 보통 거의 비어있고, 호스트 netns iptables에 KUBE-SERVICES/KUBE-SVC/KUBE-SEP 체인이 들어감. 패킷 여정: Pod A netns에서 VIP로 출발 → veth 타고 호스트 root netns 진입 → 여기서 iptables DNAT으로 실제 Pod IP로 변경 → CNI 타고 목적지 Pod 도착(다른 노드여도 OK).

한 문장: 둘 다 같은 리눅스 원시 기능(netns+veth+iptables DNAT)을 쓰는데, Docker는 한 머신에서 컨테이너 격리+포트 매핑까지만, k8s는 그 위에 (1)Pod 단위 netns (2)여러 노드를 잇는 CNI (3)kube-proxy가 호스트 iptables에 써넣는 동적 Service 로드밸런싱을 얹은 것.

# 봉우리 1: CNI가 노드 간 Pod 통신을 어떻게 구현하나

## 왜 문제인가
Pod IP(10.244.x.x)는 k8s 내부 가상 대역. 노드를 잇는 물리 네트워크(스위치/라우터)는 이 대역을 모름(노드 실제 IP 192.168.1.x만 앎). 이 간극을 메우는 게 CNI 임무. 두 갈래: 오버레이 vs 라우팅.

## 방식 A: 오버레이(VXLAN) — 봉투에 넣어 부치기
대표: Flannel(기본), Calico VXLAN. 물리망이 모르는 Pod 패킷을 물리망이 아는 노드 패킷으로 한 번 감싸서(encapsulation) 보냄. 패킷 이중 포장: [원본 10.244.1.5→10.244.2.7]을 [바깥 192.168.1.10→192.168.1.20 + UDP(8472) + VXLAN 헤더]로 감쌈. Node1의 flannel.1(VXLAN 장치)이 가로채 "10.244.2.7은 Node2" 조회(FDB) → UDP 봉투에 넣어 발송 → Node2 flannel.1이 개봉 → Pod B 전달. 장점: 물리망이 멍청해도 무조건 작동, 클라우드 VPC 넘나듦. 단점: 캡슐화 CPU 오버헤드, MTU 감소(~50바이트), 디버깅 어려움.

## 방식 B: 라우팅(L3/BGP) — 길 안내판 세우기
대표: Calico BGP, Cilium, Flannel host-gw. 봉투 없이, 각 노드가 자기 Pod 대역을 광고해 라우팅 테이블로 직접 보냄. 라우팅 테이블에 "10.244.2.0/24 → via 192.168.1.20" 경로. BGP(Calico는 BIRD 데몬)로 노드끼리 경로 자동 동기화. 패킷은 봉투 없이 원본 그대로. 장점: 거의 네이티브 속도, MTU 문제 없음, 디버깅 쉬움. 단점: 물리 네트워크가 똑똑해야 함(L3 도달성/BGP 지원), 다른 서브넷 흩어지면 설정 까다로움.

한 줄: 둘 다 "물리망이 모르는 Pod IP를 노드 간 전달" 문제를 푸는데, 오버레이는 포장해서 우회, 라우팅은 길 알려줘 직행.

# 봉우리 2: kube-proxy의 iptables 체인 해부

## 전체 계층
패킷 진입(PREROUTING/OUTPUT) → KUBE-SERVICES(어느 Service인가 분류) → KUBE-SVC-XXX(로드밸런싱: 확률 분배) → KUBE-SEP-YYY(실제 DNAT). SVC=Service, SEP=Service EndPoint(Pod 하나).

## ① KUBE-SERVICES — 교통정리
모든 Service VIP가 한 줄씩: -d 10.96.0.10/32 -p tcp --dport 3000 -j KUBE-SVC-ABC. 어느 Service 행이냐만 판별해 분기.

## ② KUBE-SVC-XXX — 로드밸런서(확률 분배)
statistic 모듈로 확률: 첫 줄 probability 0.33333→KUBE-SEP-001, 둘째 0.5→SEP-002, 마지막 무조건 SEP-003. 확률이 0.33→0.5→1.0로 변하는 이유: 순차적으로 걸러지기 때문(첫 줄 1/3, 남은 2/3 중 1/2=전체 1/3, 마지막 1/3) → 정확히 3등분.

## ③ KUBE-SEP-YYY — 실제 DNAT
SEP 하나=Pod 하나. (a) -s PodIP -j KUBE-MARK-MASQ (헤어핀 대비 SNAT 표시) (b) -p tcp -j DNAT --to-destination 10.244.1.5:3000 ← 가상 IP→진짜 Pod IP 바꿔치기 실물.

## 빠진 조각 2개
(1) KUBE-MARK-MASQ/KUBE-POSTROUTING(SNAT): DNAT로 목적지만 바꾸면 응답이 엉뚱한 데로 갈 수 있어(헤어핀, 클러스터 밖 출발) 마킹 후 KUBE-POSTROUTING에서 MASQUERADE. (2) conntrack(연결 추적): 갈 때 DNAT한 걸 커널이 기억해 응답 패킷이 오면 자동 역변환(Pod IP→VIP 출발지). DNAT은 첫 패킷에만, 나머지는 conntrack 처리 → 빠르고 세션 일관성.

두 봉우리가 만나는 지점: KUBE-SEP에서 DNAT으로 목적지=다른 노드 Pod IP가 정해지면, 실제 운반은 봉우리1의 CNI(오버레이/라우팅). iptables=어느 Pod로 보낼지 정하고 주소 변환, CNI=정해진 Pod까지 물리적 배달.

# 1. Probe — Pod 생사·준비 판정

## 두 가지 다른 질문
- liveness: "살아있어?" 실패→컨테이너 죽이고 재시작
- readiness: "트래픽 받을 준비됐어?" 실패→Service 엔드포인트에서 제외(재시작 X)
- startup: "다 켜졌어?" 실패→켜질 때까지 위 둘 보류
liveness≠readiness 구분이 핵심.

## readiness probe — 미뤄둔 그것
앞서 "Pod가 떠도 진짜 준비됐는지 확인하고 엔드포인트 추가"의 그 확인. 컨테이너가 떠도 DB 풀/캐시/설정 로딩에 시간 걸려 즉시 처리 불가. readinessProbe(httpGet /health/ready, periodSeconds, failureThreshold)로 막음. 연결: readiness 통과→kubelet Ready 보고→EndpointSlice 컨트롤러가 Pod IP 엔드포인트 추가→kube-proxy iptables KUBE-SVC 추가→트래픽 흐름. readiness 실패→엔드포인트 제거→iptables에서 삭제→트래픽 안 감(컨테이너는 안 죽임). 즉 readiness=엔드포인트 명단 입출입 스위치. 롤링 업데이트 무중단 이유도 이것.

## liveness probe
"좀비 됐냐"(데드락 등). 실패→kubelet이 컨테이너 죽이고 재시작(반복되면 CrashLoopBackOff).

## startup probe
부팅 2분 걸리는 무거운 앱에 liveness 걸면 부팅 중 영원히 재시작 루프. startup은 다 켜질 때까지 liveness/readiness 비활성화하는 보호막(failureThreshold×periodSeconds로 최대 대기). 성공하면 그때부터 나머지 가동.

## probe 방식 4가지
httpGet(200~399 성공), tcpSocket(포트 열리면), exec(명령 exit 0), grpc.

## 실무 흔한 사고
1. liveness에 의존성 체크 넣음: DB 잠깐 느려질 때 멀쩡한 컨테이너 줄줄이 재시작(cascading failure). liveness는 "나 자신이 좀비냐"만, 의존성은 readiness로. 2. probe 없이 배포: 준비 안 된 Pod로 트래픽 가서 에러. 3. initialDelay/threshold 너무 빡빡: 정상인데 오판.

# 2. eBPF 기반 Cilium

## 왜 iptables를 버리나
1. 선형 탐색 O(n): KUBE-SERVICES를 위에서부터 하나씩 비교. Service 수천 개면 규칙 수만~수십만 줄. 2. 갱신 비용: Pod 하나 바뀌면 체인 재작성 무거움. 3. user/kernel 경계, conntrack 오버헤드. 작은 클러스터는 OK, 수천 서비스에서 병목.

## eBPF란
"커널 안에서 안전하게 돌릴 수 있는 작은 프로그램" = 커널을 위한 JavaScript. 재컴파일/재부팅 없이 커널 hook에 검증된 프로그램 꽂음. 특성: 커널 안 실행(빠름), verifier가 무한루프/메모리 안전 강제 검사(안전), eBPF map(해시 테이블)에 "VIP→Pod" 저장해 O(1) 조회, hook 지점(XDP/tc/socket).

## Cilium이 하는 일
kube-proxy 통째 대체. 기존 iptables(O(n) 선형 탐색→확률 분배→DNAT) 대신 eBPF가 map에서 O(1) 해시 조회로 즉시 목적지 선택, 규칙 수 무관, map 한 줄만 갱신. 특히 socket 레벨 로드밸런싱: 내부(east-west) 통신은 connect() 시스템 콜 단계에서 목적지를 바로 Pod IP로 꽂아 패킷마다 DNAT 불필요, conntrack 부담 감소, 거의 오버헤드 0.

## 장점 정리
O(1) 해시맵, 규모 무관 일정, map 항목 1줄 수정, 소켓 레벨 LB(연결당 1회), Identity(라벨) 기반 보안(Pod IP 바뀌어도 정책 유지, L7까지), Hubble 관측성. 단점: 비교적 최신 커널 필요.

## 봉우리 1과 관계
Cilium은 CNI 역할+kube-proxy 역할+NetworkPolicy를 전부 eBPF로 한 번에 처리하는 올인원.

한 줄: iptables는 규칙을 선형으로 훑는 옛 방식이라 대규모에서 느려진다. eBPF는 커널 안에서 해시맵으로 O(1) 처리하고 소켓 레벨에서 LB하며, Cilium이 이걸로 kube-proxy+CNI+보안을 한 번에 대체한다.
