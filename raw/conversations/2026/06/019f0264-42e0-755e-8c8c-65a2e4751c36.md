# Assistant

코드를 직접 확인했습니다. sign-service의 two-party signing은 **Lindell 방식의 2-party ECDSA**이고, Paillier 암호화는 그 중 "s 값을 두 서버가 협력해서 계산"하는 단계에서만 쓰입니다. 원리를 단계별로 설명드리겠습니다.

## 1. 먼저 일반 ECDSA 서명 복습

개인키 `x`, 메시지 해시 `hm`, 1회용 난수 `k`가 있을 때 서명 `(r, s)`는:

```
r = (k·G).x  mod n          // k·G 점의 x좌표
s = k⁻¹·(hm + r·x)  mod n
```

핵심은 **`x`(개인키)와 `k`(난수)가 한 곳에 모여야 `s`를 계산**할 수 있다는 점입니다. 이걸 한 서버가 다 갖지 않게 쪼개는 게 2PC의 목표입니다.

## 2. 비밀을 "곱셈으로" 둘로 쪼갠다

개인키와 난수를 두 서버(main=player1, sub=player2)가 나눠 갖습니다. **덧셈이 아니라 곱셈** 분할입니다:

```
x = key1 · key2   (mod n)    ← 진짜 개인키는 어디에도 통째로 존재하지 않음
k = k1   · k2     (mod n)    ← 1회용 난수도 마찬가지
```

- **공개키 Q 생성** (`two-party-player.ts:59-66`)
  - main: `partialQ = key1·G`
  - sub: `Q = partialQ·key2 = key1·key2·G` → 즉 `Q = x·G` ✓
  - 두 서버가 각자 Q를 독립 계산해 일치하는지 검증 후 저장 (`create-signer.usecase.ts`)

- **r 계산** (`returnPartialR`, `returnR` — `two-party-player.ts:71-84`)
  - main: `k1·G`, sub: `k2·G`를 교환
  - main: `r = (k1·(k2·G)).x = (k1·k2·G).x mod n` ✓

여기까지는 그냥 점 곱셈이라 암호화가 필요 없습니다. 문제는 `s`입니다.

## 3. 왜 Paillier가 필요한가 — `s` 계산의 딜레마

`s`를 분할된 비밀로 풀어쓰면:

```
s = k⁻¹·(hm + r·x)
  = (k1·k2)⁻¹ · (hm + r·key1·key2)
```

여기서 `r·key1·key2` 항이 문제입니다. **`key1`은 main만, `key2`는 sub만** 알고 있는데 둘을 곱해야 합니다. 그렇다고 서로 평문으로 주고받으면 개인키가 노출됩니다.

→ 이때 **Paillier 동형암호(homomorphic encryption)** 가 등장합니다. Paillier는 암호문 상태에서 다음 두 연산이 가능합니다:

```
Enc(a) ⊕ Enc(b) = Enc(a + b)      // 덧셈 동형
Enc(a) ⊗ b      = Enc(a · b)      // 평문 스칼라 곱
```

이걸 이용하면 **sub가 key1을 평문으로 보지 못한 채** `s`의 일부를 계산할 수 있습니다.

## 4. 실제 흐름 (코드 기준)

**① main이 자기 키 조각을 자기 Paillier 키로 암호화** (`returnCKey`, `:89-92`)
```
cKey = Enc_pk1(key1)        // main의 Paillier 공개키로 암호화
```
main은 `cKey`, 자기 Paillier 공개키(`pk1`), `r`, `hm`을 sub에게 보냅니다 (`return-partial-s.usecase.ts` → `/v1/signer/get-part-s`).

**② sub가 암호문 위에서 partial-S를 계산** (`returnPartialS`, `:94-112`)
```
result1 = k2⁻¹·hm
eResult1 = Enc_pk1(k2⁻¹·hm)                       // 새로 암호화

result2 = k2⁻¹·r·key2                              // sub는 자기 key2를 평문으로 사용
eResult2 = pk1.multiply(cKey, result2)             // Enc_pk1(key1) ⊗ (k2⁻¹·r·key2)
         = Enc_pk1(k2⁻¹·r·key1·key2)               // ← 동형 곱! key1은 암호문 상태

partialS = pk1.addition(eResult1, eResult2)        // 동형 덧셈
         = Enc_pk1( k2⁻¹·hm + k2⁻¹·r·key1·key2 )
```
> 포인트: sub는 `key1`을 **암호문 `cKey`로만** 다룹니다. 평문 `key1`을 절대 못 봅니다.

**③ main이 복호화해서 s 완성** (`returnS`, `:114-121`)
```
dec = Dec_sk1(partialS) = k2⁻¹·hm + k2⁻¹·r·key1·key2   // main만 가진 Paillier 개인키로 복호화
s   = dec · k1⁻¹ mod n
    = (k1·k2)⁻¹·(hm + r·key1·key2)
    = k⁻¹·(hm + r·x)                                    // ← 정확히 ECDSA의 s ✓
```

`r`은 이미 계산했으니 `(r, s)` 서명 완성. (`s > n/2`면 canonical form 위해 재시도 — `two-party-evm-signer.ts:188-237`)

## 5. 그래서 무엇이 보장되는가

- **어느 서버도 전체 개인키 `x = key1·key2`를 가진 적이 없습니다.** main은 `key1`만, sub는 `key2`만 압니다.
- sub가 main의 키 조각을 만지긴 하지만 **항상 Paillier 암호문 상태**입니다. main의 Paillier 개인키(`sk1`)가 없으면 복호화 불가.
- main이 마지막에 복호화해서 얻는 값은 `k2⁻¹·hm + k2⁻¹·r·key1·key2` 하나의 식인데, 여기엔 미지수 `key2`와 `k2`가 섞여 있어 `key2`를 역산할 수 없습니다.
- 결론: **한 서버가 털려도 단독으로는 서명도, 개인키 복원도 불가능**합니다. 이게 main/sub 두 인스턴스로 운영하는 이유입니다.

참고로 `TwoPartyPlayer` 생성자(`:20-28`)의 `while` 루프는, Paillier 모듈러스 `n`이 secp256k1 곡선 차수보다 충분히 커야 동형 연산 중 mod 오버플로가 안 생기므로(`n.bitLength()*2`) 조건을 만족하는 Paillier 키가 나올 때까지 반복 생성하는 부분입니다.

# Assistant

## 1. G 와 n 이 뭔가 (코드: `ec.ts:8-9`)

이 서비스는 **secp256k1** 타원곡선을 씁니다 (비트코인/이더리움과 동일).

타원곡선 위의 "점들"은 특별한 덧셈 규칙을 가진 하나의 **그룹(group)**을 이룹니다. 여기서:

- **`G` (Generator, 생성원)**: 모두가 약속해서 공유하는 곡선 위의 고정된 한 점. "시작점"이라고 보면 됩니다.
- **점 곱셈 `k·G`**: G를 k번 더한 점 (`G + G + ... + G`). 단순 숫자 곱이 아니라 곡선 위 점들의 덧셈입니다.
- **`n` (order, 차수)**: `n·G = O`(무한원점, 항등원)가 되는 가장 작은 수. 즉 점 곱셈의 지수는 `mod n`으로 돌아갑니다. secp256k1에서 n은 약 2²⁵⁶의 소수.

**왜 이게 암호의 핵심이냐** — 일방향성 때문입니다:
```
k 를 알면 → k·G  계산은 쉬움  (빠름)
k·G 만 보고 → k  역산은 불가능  (이산로그 문제, ECDLP)
```
이게 키쌍의 토대입니다: **개인키 = `x` (그냥 큰 숫자), 공개키 = `Q = x·G` (점)**. Q를 공개해도 x는 못 구합니다.

## 2. 그래서 r, s 가 왜 이렇게 생겼나

ECDSA 서명의 진짜 목적은 이겁니다:

> "나는 `x`를 안다(=이 지갑 주인이다)는 걸, `x`를 공개하지 않고 증명한다."

이걸 검증식에서 거꾸로 보면 이해가 쉽습니다. **검증자(verifier)** 는 공개키 `Q`, 해시 `hm`, 서명 `(r, s)`만 가지고 다음을 계산합니다:

```
u1 = hm·s⁻¹
u2 = r ·s⁻¹
P  = u1·G + u2·Q        ← 점 계산
서명 유효 ⟺  P.x mod n == r
```

이 식이 성립하려면 `s`가 어떻게 만들어졌어야 하는지 거꾸로 따라가 봅시다.

**① r 의 정체**

서명자는 1회용 난수 `k`로 점 `R = k·G`를 만들고 그 **x좌표만** 뽑아 `r`로 씁니다:
```
r = (k·G).x mod n
```
즉 `r`은 "내가 이번 서명에 쓴 비밀 난수 k에 대응하는 공개 흔적"입니다. k 자체는 숨기고 흔적 r만 공개. (k가 유출되거나 재사용되면 개인키가 털립니다 — 그래서 매번 새 난수.)

**② s 를 그렇게 정의하면 검증식이 닫힌다**

검증식의 P를 전개해 보면 왜 `s = k⁻¹·(hm + r·x)`여야 하는지 나옵니다:

```
P = u1·G + u2·Q
  = (hm·s⁻¹)·G + (r·s⁻¹)·Q
  = (hm·s⁻¹)·G + (r·s⁻¹)·(x·G)      ∵ Q = x·G
  = s⁻¹·(hm + r·x)·G
```

여기서 만약 서명자가 `s = k⁻¹·(hm + r·x)` 로 정의했다면 `s⁻¹ = k·(hm + r·x)⁻¹` 이므로:

```
P = k·(hm + r·x)⁻¹·(hm + r·x)·G
  = k·G                              ← (hm + r·x) 항이 깔끔히 소거됨
  = R
```

따라서 `P.x mod n = (k·G).x mod n = r` → **검증 통과** ✓

즉 `s`의 모양은 임의가 아니라, **검증식에서 `(hm + r·x)`가 약분되어 `P = k·G = R`로 되돌아오게** 정확히 역으로 설계된 겁니다.

## 3. 각 항의 역할 직관

`s = k⁻¹·(hm + r·x)` 한 줄에 세 가지가 묶여 있습니다:

| 항 | 역할 |
|---|---|
| `hm` | **무엇에** 서명했는지 (메시지 해시). 메시지가 바뀌면 s도 바뀜 → 위변조 탐지 |
| `r·x` | **누가** 서명했는지. 개인키 `x`가 들어가지만, r과 묶이고 `k⁻¹`로 가려져 직접 노출 안 됨 |
| `k⁻¹` | **재사용 방지 + 은닉**. 매번 다른 k가 곱해져 같은 메시지도 매번 다른 서명이 나오고, x를 숨김 |

세 개를 한 식에 묶어, 검증자는 `Q`만으로 "이 사람이 `x`를 알고 이 `hm`에 서명했다"를 확인할 수 있되 `x`도 `k`도 알아낼 수는 없습니다.

## 4. 다시 2PC 로 연결

이제 앞 대화가 더 명확해집니다. 일반 ECDSA에선 한 명이 `x`와 `k`를 다 갖고 `s = k⁻¹·(hm + r·x)`를 한 번에 계산합니다. 

2PC에선 `x = key1·key2`, `k = k1·k2`로 쪼갰기 때문에 그 한 줄이:
```
s = (k1·k2)⁻¹·(hm + r·key1·key2)
```
가 되고, `key1·key2` 교차 곱셈을 평문 노출 없이 해내려고 **Paillier 동형암호**를 끌어들인 것입니다. 즉 G/이산로그가 키쌍의 토대, ECDSA 검증식이 s의 형태를 강제, 그 s를 둘로 나눠 계산하려는 필요가 Paillier를 부르는 — 한 줄기로 이어지는 구조입니다.

검증식 전개나 secp256k1 파라미터(p, a, b 등 곡선 정의), 혹은 k 재사용 공격 같은 부분 더 파볼까요?

맞아요, 거기서 갑자기 `x`랑 `Q`가 튀어나오면 헷갈리죠. 천천히 쌓아서 설명드릴게요.

## 1. 가장 먼저: 개인키 `x`는 그냥 "엄청 큰 숫자"

거창한 게 아닙니다. 개인키 `x`는 **1부터 n 사이에서 고른 무작위 정수 한 개**입니다.

코드에서도 그냥 랜덤 바이트로 숫자를 뽑습니다 (`two-party-player.ts:39-41`):
```
private generateKey() {
  return new BN(randomBytes(n.byteLength() / 2));   // 그냥 큰 랜덤 숫자
}
```

예를 들어 (실제론 256비트지만 작게 비유):
```
x = 27   ← 이게 개인키. 절대 공개 안 함.
```

## 2. 공개키 `Q`는 그 숫자로 "점을 만든 결과"

앞에서 `G`(생성원, 모두가 공유하는 곡선 위 고정된 점)와 점 곱셈 `k·G`을 봤죠. 공개키는 **개인키 숫자만큼 G를 곱한 점**입니다:

```
Q = x · G
```

`x=27`이면 `Q = 27·G` = "G를 27번 더한 점". 이 `Q`(곡선 위의 한 점)를 세상에 공개합니다. 이게 지갑 주소의 근원이에요.

코드에서 정확히 이 한 줄 (`two-party-player.ts:59-61`):
```
public returnPartialQ(): curve.base.BasePoint {
  return G.mul(this.key);     //  Q(조각) = key · G
}
```

## 3. 왜 이게 "키 쌍"으로 안전한가 — 한쪽 방향만 쉬움

핵심은 점 곱셈의 **비대칭성**입니다:

```
x 를 알면  →  Q = x·G  계산:  쉬움 ✅  (컴퓨터가 순식간에)

Q 만 보고  →  x  역산:        불가능 ❌  (n이 2²⁵⁶라 우주가 끝날 때까지 못 풂)
```

이걸 **이산로그 문제(ECDLP)** 라고 합니다. 곱셈은 쉽지만 나눗셈(역산)은 사실상 불가능.

> 비유: 페인트 두 색을 섞는 건 쉽지만, 섞인 색을 보고 원래 두 색 비율을 알아내는 건 불가능한 것과 비슷합니다.

그래서:
- **개인키 `x`** = 나만 아는 비밀 숫자 (서명할 때 씀)
- **공개키 `Q`** = `x`로 만든 점, 공개해도 안전 (남들이 서명 검증할 때 씀)

`Q`를 아무리 공개해도 거기서 `x`를 거꾸로 못 구하기 때문에 "공개"키인 거예요.

## 4. 둘이 서명/검증에서 만나는 지점

앞 대화의 검증식을 다시 보면 `x`와 `Q`가 왜 같이 등장했는지 보입니다:

```
서명자: s = k⁻¹·(hm + r · x)        ← 비밀 x 로 만든다
검증자: P = u1·G + u2·Q              ← 공개 Q 로 확인한다
```

검증식 전개 중 `Q = x·G`를 대입하는 순간 `x`가 식 안으로 들어와서:
```
u2·Q = u2·(x·G)
```
서명자가 `x`로 넣은 것과 검증자가 `Q`로 넣은 것이 **곡선 위에서 정확히 맞물려** 서명이 검증됩니다. 즉:

> 서명자는 비밀 `x`로 잠그고, 검증자는 공개 `Q`로 "그 사람이 진짜 `x`를 안다"는 사실만 확인한다. **`x` 자체는 절대 전달되지 않음.**

## 5. 그래서 2PC 에서 쪼갠다는 게 무슨 뜻이었나

이제 앞 얘기가 깔끔히 연결됩니다.

일반 지갑: `x` 한 개를 한 서버가 통째로 보관 → 그 서버 털리면 끝.

2PC 지갑: `x`라는 숫자를 둘로 쪼갭니다.
```
x = key1 · key2        (key1은 main만, key2는 sub만 보관)
```
- main: `partialQ = key1·G`
- sub:  `Q = partialQ·key2 = key1·key2·G = x·G`   ← 공개키는 정상적으로 나옴 ✓

**하지만 `x = key1·key2`라는 곱은 어디서도 실제로 만들어진 적이 없습니다.** 두 조각이 곡선 위 점 곱셈으로만 합쳐져 `Q`가 되고, 진짜 숫자 `x`는 둘 다 모릅니다. 그래서 한 서버가 털려도 개인키 전체를 알 수 없는 거예요.

---

정리하면:
- **`x`** = 무작위로 고른 비밀 숫자 (개인키)
- **`Q = x·G`** = 그 숫자로 만든 곡선 위의 점 (공개키)
- 곱셈은 쉽고 역산은 불가능 → 그래서 Q를 공개해도 x는 안전

타원곡선에서 "점을 더한다"는 게 구체적으로 어떤 연산인지(기하학적 의미), 아니면 Q에서 실제 지갑 주소가 어떻게 만들어지는지 더 볼까요?

## 1. G — 애초에 "털린다"는 개념이 없음 (공개 상수)

G는 비밀이 아닙니다. **secp256k1 표준에 박혀서 전 세계가 똑같이 쓰는 공개 상수**예요. 비트코인, 이더리움, 이 sign-service 전부 동일한 G를 씁니다. 코드에도 그냥 라이브러리에서 가져옵니다 (`ec.ts:9`):
```
export const G = ec.g;   // 누구나 아는 값
```

G를 안다고 안전이 깨지지 않아요. 왜냐하면 보안은 "G를 모르는 것"이 아니라 **"Q = x·G에서 x를 역산 못 하는 것"(이산로그)** 에 있기 때문입니다. G는 처음부터 공개를 전제로 설계됐습니다.

> 비유: 자물쇠 브랜드(G)는 누구나 알아도 됩니다. 비밀은 열쇠(x)지 자물쇠 모델명이 아니죠.

## 2. k — 이건 진짜 치명적. 한 번만 새도 개인키 복원됨

`k`(1회용 난수, nonce)는 정반대입니다. **k가 새면 개인키 `x`가 즉시 계산됩니다.**

서명식이 이거였죠:
```
s = k⁻¹·(hm + r·x)
```
공격자는 서명을 보면 `s, r, hm`을 이미 압니다(다 공개됨). 여기서 `k`까지 알면 미지수가 `x` 하나뿐이라 그냥 풀려요:
```
x = r⁻¹·(s·k − hm)   mod n
```
끝. 개인키 탈취 완료.

### 더 무서운 것: k를 "재사용"만 해도 털림

k 값 자체를 몰라도, **같은 k로 두 번 서명하면** 공격자가 두 식을 빼서 k를 구하고, 그걸로 x까지 구합니다:
```
서명1:  s1 = k⁻¹·(hm1 + r·x)
서명2:  s2 = k⁻¹·(hm2 + r·x)     ← 같은 k라 r도 동일
─────────────────────────────
s1 − s2 = k⁻¹·(hm1 − hm2)
  → k = (hm1 − hm2)·(s1 − s2)⁻¹
  → 그다음 위 식으로 x 복원
```

이게 실제로 일어난 사건들:
- **2010년 소니 PS3** — 모든 서명에 고정된 k를 써서 마스터 개인키가 통째로 털림
- 초기 안드로이드 비트코인 지갑들 — 난수 생성기 결함으로 k 중복 → 코인 도난

그래서 코드에서 **매 서명마다 새 k를 무작위로** 뽑습니다 (`two-party-player.ts:47-49`):
```
public createRandomK() {
  this.k = new BN(randomBytes(n.byteLength() / 2)).umod(n);  // 매번 새 난수
}
```

## 3. 그런데 이 서비스(2PC)는 k 위험도 한 단계 더 막아둠

여기가 2PC의 또 다른 장점입니다. 일반 지갑은 한 서버가 `k` 전체를 갖지만, 이 서비스는 `k`도 쪼개져 있어요:
```
k = k1 · k2     (k1은 main만, k2는 sub만)
```

- main의 RNG가 고장 나서 k1이 새거나 중복돼도, **sub의 k2를 모르면 진짜 k를 못 구합니다.**
- 한 서버가 털려도 그쪽 조각(k1 또는 k2)만 노출 → 개인키 복원 불가.
- sub의 nonce는 Redis에 `(walletAddress, randomRequestId)` 키로 잠깐 저장됐다 partial-S 단계에서 쓰고 버려서, 세션 간 재사용도 구조적으로 막습니다 (`return-partial-r/s.usecase.ts`).

## 정리

| 값 | 털리면? | 이유 |
|---|---|---|
| **G** | 괜찮음 ✅ | 원래 공개 상수. 보안은 G가 아니라 이산로그 난해성에 의존 |
| **Q** (공개키) | 괜찮음 ✅ | 공개 전제. Q→x 역산 불가 |
| **k** (nonce) | 치명적 ❌ | 한 번 누출/재사용 → 개인키 x 즉시 복원 |
| **x** (개인키) | 끝장 ❌ | 말 그대로 개인키 |

→ 즉 **"비밀로 지켜야 하는 건 x와 k"**, G·Q·r·s·hm은 다 공개돼도 됩니다. 그리고 2PC는 x와 k **둘 다** 한 곳에 모이지 않게 쪼개서, 한 서버 탈취만으로는 어느 쪽도 복원 못 하게 만든 설계입니다.

k 재사용 공격을 실제 숫자로 한번 따라가 볼까요, 아니면 결정론적 nonce(RFC 6979) 같은 추가 방어책이 이 코드에 있는지 확인해 볼까요?

> 참고: Paillier 키쌍은 **DB에 저장 안 합니다.** 서명 요청마다 `TwoPartyPlayer` 생성자에서 새로 만들고 메모리에서만 쓰고 버립니다.

## B. 요청이 오면 어떻게 서명하나 (런타임 흐름)

`POST /v1/transaction/transfer`가 왔다고 하면, main 서버 기준으로:

**1단계 — 자기 조각 로드 & 복호화** (`key.repository.ts:25-75`)
```
DB에서 암호문 privateKey 읽기 → KMS.decrypt() → key1 (평문, 메모리에만)
```
이걸로 메모리에 `TwoPartyPlayer(key1)`를 만듭니다. 이때 Paillier 키쌍도 새로 생성. (캐시 적중하면 KMS 호출 생략)

**2단계 — r 만들기 위해 sub에 1차 요청** (`POST /v1/signer/get-part-r`)
- main: 자기 난수 `k1` 생성 → `k1·G` 보유
- sub: 자기 난수 `k2` 생성 → `k2·G`를 응답으로 돌려줌. **이때 sub는 자기 `k2`를 Redis에 잠깐 저장** (`return-partial-r.usecase.ts`, `randomRequestId` 키로)
- main: `r = (k1·(k2·G)).x = (k1·k2·G).x mod n` 계산 ✓

**3단계 — s 만들기 위해 sub에 2차 요청** (`POST /v1/signer/get-part-s`)
- main이 sub에 보내는 것: 자기 `key1`을 **자기 Paillier 키로 암호화한 `cKey`**, Paillier 공개키, `r`, 메시지 해시 `hm`
- sub: Redis에서 아까 저장한 `k2`를 꺼내 자기 player 복원 → 동형암호 연산으로 **암호화된 partial-S** 계산해서 응답
  - 이 과정에서 sub는 `key1`을 암호문으로만 만짐 (앞 대화의 Paillier 부분)
- main: 받은 암호문을 **자기 Paillier 개인키로 복호화** → `s` 완성 (`returnS`)

**4단계 — 서명 조립 & 브로드캐스트** (`two-party-evm-signer.ts`, `evm.service.ts:215-247`)
```
(r, s, v) → 0x{r}{s}{v} 서명 생성
→ publicClient.sendRawTransaction()  // 실제 체인에 전송
→ 영수증(receipt) 받아서 응답 반환
```
`s > n/2`거나 `r=0`/`s=0`이면 canonical form 위해 2~3단계를 새 `k`로 재시도합니다.

| 네트워크에 흐르는 것 | 절대 안 흐르는 것 |
|---|---|
| `k1·G`, `k2·G` (점, 공개) | 평문 `key1`, `key2` |
| Paillier로 암호화된 `cKey`, partial-S | Paillier 개인키 |
| `r`, `hm`, 요청 ID (공개) | 완성된 개인키 `x`, 난수 `k` |

→ **한 줄 요약:** sign-service는 지갑마다 "개인키의 절반 조각을 KMS로 암호화해" 각자 다른 서버·DB에 저장하고, 서명 요청이 오면 main이 자기 조각을 복호화한 뒤 **sub와 2번의 HTTP 왕복(get-part-r, get-part-s)**으로 협력해서 `(r,s)`를 만들어 체인에 쏩니다. 그 과정 어디서도 완전한 개인키나 평문 키 조각이 한 곳에 모이거나 네트워크를 타지 않습니다.

## 먼저: 누가 뭘 아는지 정확히

```
main 만 안다:  key1, k1, (자기 Paillier 키쌍)
sub  만 안다:  key2, k2
```

그리고 진짜 난수는 `k = k1 · k2`인데 — **이 곱(완전한 k)은 main도 sub도, 아무도 모릅니다.** key랑 똑같아요. 한쪽도 전체 k를 못 가집니다.

## 트릭 1 — r 계산: "점으로 합치면 스칼라는 안 새어나간다"

r은 `(k·G).x = (k1·k2·G).x`가 필요하죠. 그런데 main은 `k2`를 모릅니다. 어떻게?

sub가 main에게 보내는 건 **숫자 `k2`가 아니라 점 `k2·G`** 입니다 (`returnPartialR`). 그러면 main은:
```
r = (k1 · (k2·G)).x        // 내 k1을 "점에 곱한다"
  = (k1·k2·G).x  ✓
```

여기서 결정적인 건 앞에서 배운 **이산로그**예요:
```
점 k2·G 를 받아도  →  k2 는 역산 불가 ❌
하지만 그 점에 내 k1 을 곱하는 건 가능 ✅
```

> 비유: 상대가 잠긴 상자(`k2·G`)를 보내요. 나는 그 상자 안의 숫자(`k2`)는 못 봐도, 상자째로 내 배율(`k1`)만큼 키울 수는 있어요. 결과 상자는 정확히 `k1·k2`짜리가 됩니다.

sub 입장도 대칭입니다. sub는 `k1` 자체가 아예 필요 없어요. partial-S 계산엔 자기 `k2`랑 공개값 `r`만 쓰거든요. 그래서 sub도 `k1`을 볼 일이 없습니다.

## 트릭 2 — s 계산: "각자 자기 k⁻¹만 곱하면 합쳐진다"

s의 정체는:
```
s = (k1·k2)⁻¹ · (hm + r·x) = k1⁻¹ · k2⁻¹ · (hm + r·x)
```

`k1⁻¹`과 `k2⁻¹`이 둘 다 들어가야 하죠. 근데 이걸 **한 번에 곱하지 않고, 두 단계로 나눠서** 각자 자기 것만 곱합니다:

**sub 단계** (자기 `k2`만 사용, `returnPartialS`):
```
partialS = Enc( k2⁻¹·hm  +  k2⁻¹·r·key1·key2 )    ← k2⁻¹ 곱함. k1은 등장 안 함
```
**main 단계** (자기 `k1`만 사용, `returnS`):
```
s = 복호화한 값 · k1⁻¹
  = k1⁻¹·k2⁻¹·(hm + r·key1·key2)
  = (k1·k2)⁻¹·(hm + r·x)  ✓
```

즉 `k1⁻¹ · k2⁻¹ = (k1·k2)⁻¹ = k⁻¹`이 되는데, 이 곱셈이 **두 서버의 서로 다른 계산 단계에 흩어져서** 일어납니다. 누구도 `k`를 조립한 적이 없어요. (key1·key2 교차항은 Paillier가 암호문으로 날라준 거고요 — 앞 대화 내용.)

## 그래서 "1회용 생성 후 폐기"가 왜 괜찮나

- main은 한 번의 `signHash` 호출 동안 메모리에 `k1`만 들고 있다 끝나면 버립니다.
- sub는 get-part-r → get-part-s가 **HTTP 2번**으로 나뉘니까, 그 사이에만 자기 `k2`를 Redis에 잠깐 저장했다가 (`randomRequestId` 키) get-part-s 끝나면 폐기합니다.
- **둘은 서로의 k를 저장할 필요도, 알 필요도 없습니다.** 각자 자기 절반만 만들고 자기 절반만 폐기하면 됨.

## 그리고 이게 사실 "보안 기능"이다

여기가 반전인데 — main이 **상대 k를 몰라야 오히려 안전**합니다. 만약 main이 완전한 `k = k1·k2`를 알았다면, 공개된 서명 `(r,s)`만 있으면:
```
x = r⁻¹·(s·k − hm)
```
로 전체 개인키를 복원할 수 있어요 (앞에서 본 k 유출 공격). 그래서 k도 x처럼 **한쪽에 절대 모이면 안 되는** 값이고, 2PC는 그걸 구조적으로 막은 겁니다.

이 "점으로 합치면 스칼라가 안 샌다"는 게 r 만들 때 실제 좌표 숫자로 어떻게 맞아떨어지는지 작은 숫자 예시로 따라가 볼까요?

좋은 질문이에요. 식을 또 전개하기보다, **r과 s가 각각 "무슨 역할을 하는 물건인지"** 의미부터 잡고, 그래서 왜 그 꼴일 수밖에 없는지로 가겠습니다.

## 큰 그림: 서명은 "증명"이다

ECDSA 서명 `(r, s)`는 사실 하나의 **증명(proof)** 입니다. 서명자가 검증자에게 이렇게 말하는 거예요:

> "나는 이 공개키 `Q`에 대응하는 비밀 `x`를 안다. 그리고 **바로 이 메시지** `hm`에 대해 그걸 안다. 단, `x`는 절대 안 보여준다."

이런 종류의 증명은 보통 **3박자 구조**(커밋 → 챌린지 → 응답)를 가집니다. ECDSA도 변형이긴 하지만 이 틀로 보면 r과 s의 정체가 깔끔하게 드러납니다:

- **r = 커밋(commitment)** — "이번 한 번의 서명을 위한 임시 흔적"
- **s = 응답(response)** — "그 흔적 + 내 비밀 + 메시지를 한 식에 묶은 증거"

## r 의 의미: "1회용 임시 공개키"

서명자는 매번 난수 `k`를 뽑고 점 `R = k·G`를 만듭니다. 그런데 이 `R`이 뭐냐면 — **이번 서명에만 쓰는 1회용 임시 키쌍의 공개키**예요. (`k`가 임시 개인키, `R = k·G`가 임시 공개키.)

`r`은 그 `R`의 **x좌표만** 떼어낸 값입니다:
```
r = R.x = (k·G).x mod n
```

의미론적으로 r은 **"내가 이번에 어떤 난수 k를 골랐는지에 대한 공개 약속(커밋)"** 입니다.
- `k` 자체는 숨기지만 (숨겨야 함, 안 그러면 개인키 털림),
- `k`에 대응하는 흔적 `r`은 공개해서 "나 이거 골랐다"고 못 박아 둡니다.
- 나중에 검증자가 계산으로 이 커밋이 진짜 맞는지 확인할 수 있게 하는 닻 역할.

> 왜 점 전체가 아니라 x좌표만? 256비트로 압축하려는 것 + DSA 계보의 설계입니다. 핵심 정보는 x좌표에 다 들어있어요.

## s 의 의미: "비밀·메시지·커밋을 묶은 봉인"

`s = k⁻¹·(hm + r·x)` — 이 한 줄에 **세 가지가 묶여** 있습니다. 각 항이 하는 일이 다 다릅니다:

| 조각 | 의미론적 역할 | 빠지면? |
|---|---|---|
| `hm` | **무엇에** 서명했나 (메시지 바인딩) | 메시지를 안 묶으면 → 같은 서명을 아무 메시지에나 갖다 붙임 (위조) |
| `r·x` | **누가** 서명했나 (신원 바인딩) + 커밋과 연결 | `x` 없으면 아무나 서명, `r` 없으면 커밋과 안 묶여 검증식이 안 닫힘 |
| `k⁻¹` | **은닉 + 일회성** (블라인딩) | 없으면 `x`가 그대로 노출 / 매번 같은 서명 |

그래서 s는 의미상 **"내 비밀 `x`를, 이번 커밋 `r`과 이 메시지 `hm`에 맞물려, 1회용 난수 `k`로 가린 응답값"** 입니다. 세 가지를 한 식에 봉인해서, 셋 중 하나라도 바뀌면 s가 깨지게 만든 거예요.

## 왜 "하필 그 꼴"인가 — 검증식이 닫혀야 하니까

s의 모양은 임의로 정한 게 아니라, **검증자가 r(커밋)을 다시 복원할 수 있어야 한다**는 제약에서 역으로 강제됩니다.

검증자가 가진 건 `Q, hm, r, s`뿐. 검증자가 하는 일은 결국 "**커밋 R = k·G를 내가 다시 만들어낼 수 있나?**"를 확인하는 겁니다:
```
P = s⁻¹·(hm + r·x)·G          // Q=x·G 를 대입해 전개한 결과
```
여기서 s를 `k⁻¹·(hm + r·x)`로 정의했기 때문에 `s⁻¹ = k·(hm + r·x)⁻¹`이고:
```
P = k·(hm + r·x)⁻¹·(hm + r·x)·G = k·G = R   ✓
```
→ `(hm + r·x)` 항이 **통째로 약분**되면서 커밋 `R`이 정확히 되살아나고, `P.x == r`이면 통과.

즉 s의 형태는:
- `(hm + r·x)`를 곱셈 덩어리로 묶고 → 검증 때 `s⁻¹`로 약분돼 사라지게,
- `k⁻¹`을 앞에 둬서 → 약분 후 `k·G = R`(커밋)이 남게

**"검증 시 커밋이 깨끗이 복원되도록" 거꾸로 설계된 결과**입니다. 다른 모양이면 이 약분이 안 일어나서 검증이 닫히지 않아요.

## "유일한" 꼴은 아니다 — Schnorr와 비교하면 명확

s가 굳이 이 모양인 건 ECDSA(=DSA 계보)의 선택이지, 서명의 본질은 아닙니다. **Schnorr 서명**은 같은 목적을 훨씬 깔끔하게 합니다:
```
ECDSA:    s = k⁻¹·(hm + r·x)      // 곱셈·역원 사용
Schnorr:  s = k + e·x   (e = H(R,m))  // 덧셈만, 선형
```
둘 다 "커밋 + 비밀·메시지 바인딩 + 난수 블라인딩"이라는 **의미는 동일**합니다. 다만 ECDSA는 `r`을 좌표에서 뽑고 `k⁻¹`을 쓰는 비선형/역원 구조라 2PC 할 때 까다로워지고(그래서 Paillier 동원), Schnorr는 선형이라 멀티파티가 훨씬 쉽습니다. 이 서비스가 Paillier까지 끌어온 이유도 결국 **ECDSA의 이 `k⁻¹·(...)` 곱셈 꼴 때문**이에요.

---

**한 줄 요약:**
- **r** = "이번 1회용 난수에 대한 공개 커밋"(임시 공개키의 x좌표).
- **s** = "내 비밀 x를, 그 커밋 r과 메시지 hm에 묶어, 난수 k로 가린 응답".
- 그 꼴인 이유 = **검증할 때 `(hm+r·x)`가 약분돼 커밋 `R=k·G`가 정확히 되살아나도록** 역설계됐기 때문. (Schnorr처럼 덧셈 꼴도 가능하지만 ECDSA는 곱셈/역원을 택했고, 그게 2PC에서 Paillier가 필요한 근본 원인.)

## P = 검증자가 다시 만들어보는 점 (= 커밋 R을 재현하려는 시도)

검증자가 가진 재료는 **공개값뿐**입니다: 공개키 `Q`, 메시지 해시 `hm`, 서명 `(r, s)`. **`x`도 `k`도 모릅니다.**

검증자가 하는 일은 딱 하나: 이 재료들로 점을 하나 조립해보고, 그게 서명자의 커밋 `R = k·G`와 같은지 확인하는 것. 그 **조립해서 나온 점이 `P`** 입니다.

검증자는 실제로 이렇게 계산합니다 (여기엔 x가 없어요, 공개값만 씀):
```
u1 = hm · s⁻¹
u2 = r  · s⁻¹
P  = u1·G + u2·Q        ← 이게 검증자가 실제로 계산하는 P
```
`G`는 공개 상수, `Q`는 공개키, `u1·u2`는 공개값으로 계산 가능 → **검증자 혼자 P를 만들 수 있습니다.** 비밀 없이.

## 그럼 제가 쓴 "P = s⁻¹·(hm + r·x)·G"는 뭐냐

그건 검증자가 계산하는 식이 **아니라**, 위 P가 사실은 무엇과 같은지 보려고 종이 위에서 전개한 것입니다. `Q = x·G`라는 사실을 대입하면:

```
P = u1·G + u2·Q
  = (hm·s⁻¹)·G + (r·s⁻¹)·Q
  = (hm·s⁻¹)·G + (r·s⁻¹)·(x·G)      ← Q를 x·G로 바꿔치기
  = s⁻¹·(hm + r·x)·G                  ← G로 묶음
```

> 중요: `x`는 검증자가 모릅니다. 이 전개는 "검증자가 모르는 진실까지 포함하면 P가 실제로 어떤 점인지" 증명하려고 **우리가** 칠판에서 하는 거예요. 검증자는 `u1·G + u2·Q`만 계산하지, `x`를 쓰지 않습니다.

## 그래서 P가 결국 무엇과 같아지나

이제 `s = k⁻¹·(hm + r·x)`(서명자가 만든 값)를 대입하면 `s⁻¹ = k·(hm + r·x)⁻¹`이므로:

```
P = s⁻¹·(hm + r·x)·G
  = k·(hm + r·x)⁻¹·(hm + r·x)·G
  = k·G
  = R                  ← 서명자의 1회용 커밋과 정확히 같아짐!
```

즉:
- **서명자**가 만든 커밋: `R = k·G`, 그 x좌표가 `r`.
- **검증자**가 공개값만으로 조립한 점: `P = u1·G + u2·Q`.
- 서명이 진짜면 이 둘이 **같은 점**이 됩니다 → 그래서 검증자는 `P.x mod n == r` 인지만 확인하면 끝.

## 직관 한 줄

P는 **"검증자가 공개키 Q를 가지고 서명자의 1회용 커밋 R을 거꾸로 재현해 본 점"** 입니다.
- 서명자가 `x`를 진짜 알고 올바르게 s를 만들었으면 → `P`가 `R`로 딱 떨어져서 x좌표가 `r`과 일치.
- 가짜라면 → `P`가 엉뚱한 점이 되어 x좌표가 `r`과 안 맞음 → 검증 실패.

그래서 검증자는 `x`를 한 번도 안 보고도 "이 사람이 `x`를 안다"를 확인합니다. (`x`는 `Q` 안에 점으로 숨어 있고, 위 전개에서 `s`가 약분되며 사라지니까요.)

정리하면 **P = 검증자가 `u1·G + u2·Q`로 만든 점이고, 올바른 서명이면 그게 곧 `R = k·G`** 입니다. 작은 숫자로 P를 실제로 계산해서 `R`과 같아지는 걸 눈으로 따라가 볼까요?

## u1, u2 가 정확히 뭔가

앞에서 검증자는 `x`도 `k`도 모른 채 점 `P`를 만든다고 했죠. 그 P를 만드는 식이:
```
P = u1·G + u2·Q
```
여기서 **u1, u2는 "G와 Q를 각각 얼마만큼 곱해서 더할지"를 정하는 배율(계수)** 입니다. 정의는:
```
u1 = hm · s⁻¹   (mod n)
u2 = r  · s⁻¹   (mod n)
```
전부 공개값(`hm`, `r`, `s`)으로만 계산 → 검증자 혼자 만들 수 있음.

### 왜 하필 이렇게 정의하나

s의 정의 `s = k⁻¹·(hm + r·x)`를 거꾸로 풀면 `k`가 이렇게 나옵니다:
```
s = k⁻¹·(hm + r·x)
→ k = s⁻¹·(hm + r·x)
→ k = s⁻¹·hm  +  s⁻¹·r·x
     └──┬──┘    └──┬──┘
       u1          u2 의 x배
```

즉 `k = u1 + u2·x` 라는 관계가 나옵니다. 이제 양변에 `G`를 곱하면(점으로 올리면):
```
k·G = (u1 + u2·x)·G
    = u1·G + u2·(x·G)
    = u1·G + u2·Q          ← x·G = Q 라서 Q로 바뀜
    = P
```

→ 그래서 `P = u1·G + u2·Q = k·G = R` 이 됩니다.

**핵심 아이디어:** 진짜 `k`는 `u1 + u2·x`로 쪼갤 수 있는데, 검증자는 `x`를 모르니 숫자로는 못 구합니다. **하지만 `x` 대신 점 `Q(=x·G)`를 쓰면, x를 몰라도 같은 계산을 "점 위에서" 할 수 있어요.** u1은 `G`에 직접 곱하는 몫, u2는 `Q`에 곱하는(=숨겨진 x에 곱하는) 몫인 거죠.

### 직관

- `u1` = "G 자체에 얼마나 기여하는가" (메시지 `hm`에서 온 부분)
- `u2` = "공개키 Q(숨은 x)에 얼마나 기여하는가" (커밋 `r`에서 온 부분)
- 둘을 `P = u1·G + u2·Q`로 합치면 → 서명이 올바를 때만 정확히 커밋 `R = k·G`이 재현됨.

`s⁻¹`이 양쪽에 공통으로 곱해져 있는 이유는, s 정의에 있던 `k⁻¹`을 "풀어서" k를 복원하려는 것 — `s⁻¹`이 `k⁻¹`을 상쇄해 다시 `k` 쪽으로 되돌리는 역할입니다.

---

**한 줄 요약:** u1, u2는 검증자가 **공개값만으로** "숨겨진 k = u1 + u2·x"라는 관계를 점 위에서 재현하기 위한 두 배율입니다. `u1 = hm·s⁻¹`은 G에 곱하고, `u2 = r·s⁻¹`은 Q에 곱해서 더하면, 올바른 서명일 때 정확히 커밋 점 `R`이 되살아나고 그 x좌표가 `r`과 일치 → 검증 성공.

이제 기호가 다 모였으니, 작은 숫자(작은 곡선)로 키생성→서명→검증 전 과정을 직접 숫자로 한 번 돌려볼까요? 그러면 r, s, u1, u2, P가 실제로 어떻게 맞아떨어지는지 눈으로 확인됩니다.

## 왜 이게 의미 있나 (직관)

```
k·G = u1·G + u2·x·G
```
이 식을 보면:
- 왼쪽 `k·G`는 서명자가 만든 커밋 `R`.
- 오른쪽은 검증자가 만들 수 있는 것 — 단, `x·G` 부분이 문제입니다. 검증자는 `x`를 모르니까요.
- **그런데 `x·G`는 통째로 `Q`(공개키)다!** 검증자는 `x`는 몰라도 `Q`는 압니다.

그래서 검증자는 `x`를 모른 채로 `u2·x·G` 대신 `u2·Q`를 계산하면 똑같은 점이 나옵니다. 이게 바로 "**x를 몰라도 점 위에서는 같은 계산을 할 수 있다**"는, 우리가 계속 봐온 그 트릭이에요.

정리하면 세 단계:
1. s 정의에서 → `k = u1 + u2·x` (숫자 등식)
2. 양변에 G 곱하고 분배 → `k·G = u1·G + u2·(x·G)`
3. `x·G = Q` 대입 → `k·G = u1·G + u2·Q`

검증자는 오른쪽(`u1·G + u2·Q`, 전부 공개값)을 계산 → 그게 왼쪽 `k·G = R`과 같아지면 → x좌표가 `r`과 일치 → 서명 진짜.

혹시 `x`를 모르는데 어떻게 `u2·Q`가 `u2·x·G`와 "정확히 같은 점"이 되는지, 그 부분(`u2·Q = u2·(x·G) = (u2·x)·G`, 스칼라 곱의 결합법칙)이 더 걸리면 거기를 짚어드릴까요? 아니면 이제 작은 숫자로 전 과정을 한 번 돌려볼까요?

## 1. 어디에 끼어드나 — 문제 지점부터

2PC에서 만들어야 하는 s는:
```
s = (k1·k2)⁻¹ · (hm + r · key1·key2)
                          └────┬────┘
                          이게 문제의 교차항
```

- `key1` = main만 앎
- `key2` = sub만 앎
- 그런데 `key1·key2`를 곱해야 함 → **서로 자기 비밀을 평문으로 주면 개인키 노출.**

이 "남의 비밀과 내 비밀을 곱해야 하는데, 평문 교환은 안 됨" 딱 한 군데를 풀려고 Paillier가 들어옵니다. (r, hm, 점 계산엔 Paillier 안 씀 — 오직 이 곱셈 때문.)

## 2. Paillier의 두 가지 초능력

Paillier는 **암호문 상태로** 두 연산이 됩니다 (`Enc`=암호화):
```
① 덧셈:      Enc(a) ⊕ Enc(b) = Enc(a + b)      // 암호문끼리 곱하면 평문은 더해짐
② 평문곱:    Enc(a) ⊗ b      = Enc(a · b)      // 암호문을 b제곱하면 평문에 b 곱해짐
```
코드의 `publicKey.addition(...)`이 ①, `publicKey.multiply(cipher, scalar)`가 ②입니다 (`two-party-player.ts:106-111`).

→ 이걸로 sub는 **`key1`을 암호문으로만 만지면서** `key1·(자기가 아는 것)`을 계산할 수 있습니다.

## 3. 기호로 본 흐름 (코드 그대로)

**main** (`returnCKey`): 자기 key1을 자기 Paillier 공개키로 암호화
```
cKey = Enc_pk1(key1)
```
이걸 sub에 보냄 (+ pk1, r, hm).

**sub** (`returnPartialS`, 자기 k2·key2만 평문으로 사용):
```
result1 = k2⁻¹·hm                         (평문)
eResult1 = Enc_pk1(result1)               ← 새로 암호화
result2 = k2⁻¹·r·key2                      (평문, sub 자기 것만)
eResult2 = cKey ⊗ result2 = Enc_pk1(key1·result2) = Enc_pk1(k2⁻¹·r·key1·key2)   ← 초능력②
partialS = eResult1 ⊕ eResult2 = Enc_pk1(k2⁻¹·hm + k2⁻¹·r·key1·key2)            ← 초능력①
```
이 암호문을 main에 돌려줌. **sub는 key1을 끝까지 평문으로 못 봄.**

**main** (`returnS`): 자기 Paillier 개인키로 복호화 후 자기 k1⁻¹ 곱함
```
dec = Dec_sk1(partialS) = k2⁻¹·hm + k2⁻¹·r·key1·key2
s   = dec · k1⁻¹ = (k1·k2)⁻¹·(hm + r·key1·key2)  ✓
```

```
N > nc²  필요  →  코드: generateRandomKeysSync(nc.bitLength() * 2)
```

즉 곡선 차수의 **2배 비트수**로 Paillier 키를 만들어 `N ≈ nc²`을 확보하고, `nc ≤ N`을 만족할 때까지 `while` 루프를 돕니다 (`two-party-player.ts:20-28`). 실제 곡선은 `nc≈2²⁵⁶`이라 `N≈2⁵¹²`. 제 예시(N=143 > 11²=121)도 이 조건을 지켜서 39가 안 잘린 거예요.

## 1. 먼저 왜 "이항정리"가 등장하나

Paillier에서 `g = N+1`을 쓰면, 암호화(설명용 난수 r=1)는:
```
Enc(m) = gᵐ mod N² = (1 + N)ᵐ mod N²
```
즉 모든 암호문이 `(1+N)`의 거듭제곱 꼴입니다. 그래서 `(1+N)`의 거듭제곱을 풀려면 **이항정리**가 필요한 거예요.

여기서 `cKey = Enc(3) = (1+N)³ = 1 + 3N = 430`. (N=143 → 1+429=430)

## 2. 핵심 보조정리: `(1+N)ᵃ ≡ 1 + aN (mod N²)`

이항정리로 `(1+N)ᵃ`를 펼치면:
```
(1+N)ᵃ = Σ C(a,k)·Nᵏ
       = C(a,0)·N⁰ + C(a,1)·N¹ + C(a,2)·N² + C(a,3)·N³ + ...
       = 1 + aN + C(a,2)N² + C(a,3)N³ + ...
```
이제 **mod N²** 를 취하면 — `k ≥ 2`인 모든 항은 `Nᵏ`을 품고 있고, `Nᵏ = Nᵏ⁻²·N²`이라 **N²의 배수 → 0으로 사라집니다.**
```
(1+N)ᵃ ≡ 1 + aN   (mod N²)
```
이게 Paillier가 작동하는 근본 이유예요. "N² 모듈러 세계에선 `(1+N)`의 지수가 곧 평문이 된다."

## 3. 우리 경우: `430¹⁰ = (1 + 3N)¹⁰`

`430 = 1 + 3N` 이므로 (`3N`을 한 덩어리로 보고) 이항정리 전개:
```
(1 + 3N)¹⁰ = Σ C(10,k)·(3N)ᵏ
  = C(10,0)·(3N)⁰ + C(10,1)·(3N)¹ + C(10,2)·(3N)² + ...
  = 1 + 10·(3N) + 45·(3N)² + ...
  = 1 + 30N + 45·9·N² + ...
```
**mod N²** 취하면 `N²` 이상 항 전부 소멸:
```
(1 + 3N)¹⁰ ≡ 1 + 30N   (mod N²)
```

숫자 대입:
```
= 1 + 30·143 = 1 + 4290 = 4291
```

그리고 `4291 = 1 + 143·30 = Enc(30)`. ✓

## 4. 그래서 이게 "초능력 ② (평문 곱)"의 정체

방금 한 게 정확히 `Enc(a)ᵇ = Enc(a·b)`입니다:
```
cKey^10 = ((1+N)³)¹⁰ = (1+N)³ˣ¹⁰ = (1+N)³⁰ ≡ 1 + 30N = Enc(30)
          └── Enc(3) ──┘                        └ Enc(3·10) ┘
```
지수 법칙 `(gᵃ)ᵇ = gᵃᵇ` 때문에, **암호문을 b제곱하면 평문이 a → a·b로 곱해집니다.** 이게 sub가 `key1`(암호문 430) 을 평문 `10`만큼 곱해 `Enc(30)`을 만든 원리예요 — key1=3을 끝까지 평문으로 안 보고도.

## 5. 검산 (이항정리 안 쓰고 직접)

믿기 어려우면 그냥 거듭제곱해도 됩니다. `430² mod 20449`부터:
```
430² = 184900;  184900 mod 20449 = 184900 - 20449·9(=184041) = 859
```
`859 = 1 + 6·143 = Enc(6) = Enc(3·2)` ✓ (제곱 → 평문 2배)
계속 제곱·곱셈으로 10제곱까지 가면 결국 `4291`이 나옵니다 — 이항정리는 그 과정을 한 줄로 점프한 것뿐이에요.
