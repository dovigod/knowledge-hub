# Assistant

# Docker 완벽 가이드

## 1. 역사
'내 컴퓨터에선 됐는데?' 환경 차이 문제. 2000년대 VM(무겁고 느림) → 2008 Linux 커널 cgroups+namespaces → 2013 Solomon Hykes가 Docker 발표(커널 기능을 쉽게 포장) → 2015 OCI 표준+Kubernetes → 현재 표준. 핵심: 새 기술 발명이 아니라 기존 커널 격리 기술을 쉽게 만든 것.

## 2. 작동
VM(각자 OS 전체, 수GB, 부팅 수십초) vs 컨테이너(커널 공유, 앱+라이브러리만, 수십~수백MB, 1초). Dockerfile(레시피)→이미지(불변 스냅샷)→컨테이너(실행 인스턴스). 격리=namespaces+cgroups.

## 3. 로컬 vs Docker
yarn up:infra가 redis/postgres/rabbitmq 한번에. 환경 일관성, 버전 충돌 없음, 깨끗한 설치/삭제, 프로덕션 동일성. 'Build once, run anywhere'.

## 4. 포트 매핑
Dockerfile에 없음(EXPOSE는 문서용). 실제는 -p/compose. `-p 8080:3000`=호스트:컨테이너. 격리된 벽에 창문 뚫기.

# User

namespaces와 cgroups 설명해줘

<!-- kh:msg assistant -->
# Assistant

namespaces=시야 격리(PID/NET/MNT/UTS/USER/IPC). PID: 호스트 5678이 컨테이너 안 PID 1. NET: 각자 네트워크 스택, 둘 다 3000 써도 충돌 없음. cgroups=자원 격리(CPU/메모리/IO, --memory/--cpus, OOM kill). 둘 합치면 컨테이너.

<!-- kh:msg user -->
# User

각 서비스가 3000 써도 컨테이너 내부적으론 괜찮다는 거구나? 포트를 다르게 할당하는 건가?

<!-- kh:msg assistant -->
# Assistant

포트 바꿔치기 아니라 둘 다 진짜 3000 쓴다. NET namespace가 달라 서로 다른 세상의 3000(아파트 101/102호 1번방). PID와 포트는 별개 namespace. 충돌은 호스트로 꺼낼 때만 → [3010:3000]처럼 호스트 번호만 다르게.

<!-- kh:msg user -->
# User

net namespace는 정확히 뭐고 실제 포트 할당은 어떻게?

<!-- kh:msg assistant -->
# Assistant

NET namespace=네트워크 스택 통째 복사본(인터페이스/IP/포트테이블/라우팅/iptables). 할당: app.listen(3000)→bind() 시스템콜→커널이 해당 namespace 포트장부 확인→비었으면 기록, 차면 EADDRINUSE. 바깥 접속: veth pair, docker0, iptables DNAT.

<!-- kh:msg user -->
# User

맥에서는 어떻게?

<!-- kh:msg assistant -->
# Assistant

맥에 Linux 없음→OrbStack/Docker Desktop이 Linux VM 띄움. Client=darwin/arm64, Server=linux/arm64. 맥 호스트에선 iptables 안 보임(VM 안). 데모: nginx 2개 내부 80 LISTEN 충돌 없음, ps aux nginx PID 1, eth0@if13, 맥 8001→.2/8002→.3. 치트시트: 맥(docker ps/inspect/exec -it sh), 컨테이너 안(ps/ip addr/netstat), VM(orb 진입→iptables).

veth/bridge/NAT 상세히

<!-- kh:msg assistant -->
# Assistant

veth pair=양 끝 뚫린 마법의 랜선(한쪽 들어가면 반대쪽 나옴). 끝A=컨테이너 eth0, 끝B=호스트 vethXXX. docker0=가상 스위치/게이트웨이. 나갈 때 자동 masquerade(출발지→호스트 IP), 들어올 때 -p로 DNAT(목적지→컨테이너IP:포트). veth+bridge=배선, iptables NAT=주소 번역.

# User

osi 7계층에서 각각 어느 계층?

<!-- kh:msg assistant -->
# Assistant

L7 nginx/HTTP, L4 포트/bind()/TCP, L3 IP/iptables NAT(DNAT/MASQUERADE), L2 veth/docker0/MAC, L1 veth 가상랜선. iptables NAT=L3+L4 양다리. OSI 밖: PID namespace/cgroups(OS 격리). NET namespace=L2~L4 스택 통째 복제. 캐프슐화: 보낼 때 위→아래 봉투 싸기, 받을 때 아래→위 벗기기.

# User

dnat 조작하면 다른 프로그램 망가지겠네? 명령어는?

<!-- kh:msg assistant -->
# Assistant

NAT 테이블 쥔 자가 행선지 장악(root 특권). `iptables -t nat -I DOCKER 1 ! -i docker0 -p tcp --dport 8080 -j DNAT --to-destination <B_IP>:80`. 발견: 맥 localhost:8080은 여전히 A(OrbStack docker-proxy가 iptables 우회), VM_IP:8080→B(하이재킹 성공, PREROUTING→DOCKER DNAT). DNAT 조작은 그 경로가 iptables 실제 통과할 때만 가로채다. -D로 복구.

<!-- kh:msg user -->
# User

실생활 공격과 방어는?

<!-- kh:msg assistant -->
# Assistant

본질: 경로 장악=트래픽 장악. 공격: 특권 컨테이너 사이드카 MITM, docker.sock 노출, 메타데이터 하이재킹, ARP/DHCP/DNS/BGP 스푸핑, Evil Twin. 블록체인은 BGP/DNS로 지갑/DEX 가짜 사이트(MEW 2018). 방어 3축: ①경로 장악 막기(no --privileged, cap-drop=ALL, NetworkPolicy/Calico, DAI/DHCP Snooping, RPKI) ②장악당해도 무력화(TLS/mTLS/서비스메시/인증서 피닝, 최고 강력) ③탐지(iptables 감사/Falco). 실무: mTLS+NetworkPolicy+특권 금지.

MyEtherWallet 2018 BGP 하이재킹 사건과 TLS로 막히는 걸 코드로 보여주고 줄별 설명

<!-- kh:msg assistant -->
# Assistant

MEW 2018-04-24: BGP 하이재킹(AWS Route53 DNS 대역 more-specific 광고로 DNS 트래픽 탈취)→DNS 스푸핑(myetherwallet.com→공격자 IP)→피싱→개인키 탈취(~215 ETH). 핵심: 가짜 사이트는 유효 TLS 인증서 없어 브라우저 경고→무시한 사람만 털렸다. TLS가 마지막 방어선.

TLS 데모: openssl 인증서 3종 — 루트 CA(req -x509), 정품 서버(bank.local CSR을 CA가 서명, issuer=MyTrustedRootCA), 공격자(자체서명, issuer=bank.local). 도메인명은 위조 가능하지만 CA 서명은 위조 불가(CA 개인키 없음). nginx 두 서버 겉보기 동일(listen 443 ssl, server_name bank.local), 인증서만 다르게. curl --resolve(DNS 하이재킹 시뮬레이션), --cacert(CA 신뢰=방어선). 결과: 1)정품+CA신뢰→OK, 2)가짜+CA신뢰→curl(60) self-signed certificate 연결거부(우회당해도 차단!), 3)가짜+-k(검증끔)→STOLEN. 시나리오2가 MEW 교훈: 완벽 우회당해도 공격자는 CA 서명 위조 불가→연결 거부. 하이재킹=경로 속임, TLS=신원 검증. 실무 mTLS로 자동·강제화.
