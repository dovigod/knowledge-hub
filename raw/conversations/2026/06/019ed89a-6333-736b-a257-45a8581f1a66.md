## 1. CNI로서 Cilium의 기본 원리 (eBPF)

Cilium은 iptables 기반 kube-proxy를 대체하는 **eBPF 기반 CNI**입니다.

- Pod가 뜨면 cilium-agent가 veth를 만들고, **커널 eBPF 프로그램**을 네트워크 훅(tc/XDP)에 붙입니다.
- 라우팅·정책·로드밸런싱을 iptables 룰 체인이 아니라 **eBPF 맵 lookup**으로 처리 → 커널을 안 거치고 빠르게 패킷 판단.
- "identity" 개념: IP가 아니라 **Pod label 기반 보안 ID**로 정책을 적용합니다.

핵심은 **Cilium = 데이터플레인 그 자체**라는 점. kube-proxy 같은 보조가 아니라 패킷이 지나가는 길 자체를 Cilium이 만듭니다. 그래서 cilium-agent가 못 뜨면 노드 네트워킹 전체가 죽습니다(=당신이 본 cascade).

## 2. ztunnel이 뭔가 — 사이드카 없는 노드 프록시

ztunnel("zero-trust tunnel")은 원래 **Istio Ambient Mesh**의 L4 데이터플레인입니다.

전통적 service mesh: Pod마다 Envoy 사이드카 주입 → 무겁고 리소스 낭비.
ztunnel 모델: **노드당 프록시 하나(DaemonSet)**가 그 노드의 모든 Pod 트래픽을 가로채서 처리.

ztunnel이 하는 일:
- **mTLS 암호화/복호화** (L4, HBONE 터널 = HTTP/2 CONNECT 위에 mTLS)
- **워크로드 신원(identity) 부여** — SPIFFE 형식 `spiffe://cluster.local/ns/<ns>/sa/<sa>`
- L7은 안 함(그건 Istio의 waypoint proxy 몫). ztunnel은 순수 L4 + mTLS만.

## 3. Cilium + ztunnel mTLS가 실제로 도는 방식

```
Pod A (node1)                          Pod B (node2)
   │ 평문                                  ▲ 평문
   ▼                                       │
[cilium eBPF: 트래픽 redirect]      [cilium eBPF]
   │                                       ▲
   ▼                                       │
ztunnel(node1) ──── mTLS HBONE 터널 ────► ztunnel(node2)
   암호화                  네트워크          복호화
```

1. **트래픽 가로채기**: Cilium의 eBPF가 Pod에서 나가는 패킷을 노드의 ztunnel로 redirect (사이드카 주입 없이 커널 레벨에서).
2. **신원 확인 + mTLS**: ztunnel이 `cilium-ztunnel-secrets`의 CA로 발급받은 인증서로 상대 노드 ztunnel과 mTLS 핸드셰이크. 서로의 SPIFFE ID(`O = cluster.local`)를 검증.
3. **터널링**: 암호화된 트래픽이 노드 간 네트워크를 건너감. IPsec/WireGuard 대신 ztunnel의 mTLS 터널이 그 역할.
4. **복호화 + 전달**: 상대 노드 ztunnel이 복호화 → eBPF가 목적지 Pod로 전달.

## 4. 왜 시크릿이 "옵션"이 아니라 "부트스트랩 전제"인가

당신이 정리한 게 정확합니다. 보강하자면:

- `encryption.type: ztunnel`이므로 ztunnel이 **데이터플레인의 필수 구성요소**가 됨. cilium-agent는 ztunnel 인증서 볼륨을 `optional: false`로 마운트 → 시크릿 없으면 agent Pod가 ContainerCreating에서 멈춤.
- CA(`ca-root.crt`/`ca-private.key`)는 **워크로드 인증서 발급용 루트**, bootstrap 인증서는 ztunnel **기동 시 자기 자신을 증명**하는 초기 신뢰 앵커.
- agent 안 뜸 → CNI 없음 → 노드 `NotReady` → 클러스터 cascade.

그래서 **35 클러스터 신규 구성 시 `scripts/ztunnel_generate_secret.sh`로 시크릿을 가장 먼저** 만들어줘야 하는 chicken-and-egg 부트스트랩 문제입니다.

## 한 줄 요약

> Cilium(eBPF CNI)이 패킷을 노드별 ztunnel 프록시로 redirect하고, ztunnel이 `cilium-ztunnel-secrets` CA로 발급한 인증서로 노드 간 트래픽을 mTLS 자동 암호화한다. 사이드카가 없으니 가볍고, CA가 데이터플레인의 신뢰 뿌리라서 없으면 네트워킹 전체가 안 뜬다.

mTLS = **mutual TLS** (상호 TLS). 한마디로 "TLS인데 양쪽 다 인증서로 신원을 증명하는 것"입니다.

## 일반 TLS vs mTLS

평소 HTTPS(브라우저 ↔ 웹서버)에서 쓰는 TLS는 **한쪽만** 인증합니다.

```
일반 TLS (단방향)
브라우저 ──"넌 진짜 naver.com이야?"──► 서버
         ◄── 서버 인증서 제출 ──        (서버만 증명)
브라우저는? 신원 증명 안 함 (그냥 익명 손님)
```

mTLS는 **양쪽 다** 인증서를 제출해서 서로를 검증합니다.

```
mTLS (양방향)
A ──"넌 누구야?"──► B   B가 인증서 제출
A ◄──"너는 누구야?"── B   A도 인증서 제출
둘 다 상대 인증서를 CA로 검증한 뒤에야 통신 시작
```

## 무엇을 보장하나

| 보장 | 설명 |
|---|---|
| **암호화** | 중간에서 패킷 까봐도 내용 못 봄 (일반 TLS도 됨) |
| **상호 신원 인증** | "상대가 진짜 그 워크로드가 맞는가"를 **양쪽 다** 확인 (mTLS만) |
| **위변조 방지** | 가짜 Pod가 끼어들어 트래픽 가로채기 불가 |

## 왜 클러스터 내부 통신에 쓰나 (zero-trust)

전통적 보안은 "방화벽 안쪽 = 안전"이라고 믿었지만, zero-trust는 **내부 트래픽도 못 믿는다**가 전제입니다.

- 일반 TLS는 클라이언트가 익명이라 → 클러스터 안에서 악성 Pod가 다른 서비스로 위장 접속 가능.
- mTLS는 **양쪽 다 인증서가 있어야** 연결되니까, 인증서 없는(=신원 없는) Pod는 아예 통신 자체가 안 됨.

## 우리 클러스터 맥락

ztunnel이 노드 간 통신할 때 바로 이 mTLS를 씁니다:

```
ztunnel(node1) ◄── 서로 인증서 제출 & 검증 ──► ztunnel(node2)
       │                                          │
   cilium-ztunnel-secrets의 CA로 발급받은 인증서
       │                                          │
   SPIFFE ID 검증: spiffe://cluster.local/...
```

- 각 ztunnel은 `cilium-ztunnel-secrets`의 **CA로 발급받은 인증서**를 들고 있음.
- 노드 간 연결할 때 서로 인증서를 교환 → "너 진짜 같은 cluster.local 신뢰 도메인 소속 맞아?" 확인.
- 그래서 그 **CA(`ca-root.crt`/`ca-private.key`)가 mTLS 전체의 신뢰 뿌리** → 없으면 인증서 발급 자체가 안 되고 mTLS가 성립 못 함.

## 한 줄 요약

> TLS = 한쪽(서버)만 신원 증명. mTLS = 양쪽이 서로 인증서로 신원 증명. 클러스터 안에서 "신원 없는 Pod는 통신 불가"를 강제하는 zero-trust의 핵심 메커니즘이고, 그 인증서를 발급하는 CA가 우리가 찾은 시크릿이다.

# Assistant

CNI = **Container Network Interface** (컨테이너 네트워크 인터페이스). 한마디로 **"쿠버네티스에서 Pod에게 네트워크를 붙여주는 표준 규격(플러그인 인터페이스)"**입니다.

## 왜 필요한가 — 문제부터

쿠버네티스 자체는 **네트워킹을 직접 구현하지 않습니다.** 대신 규칙(요구사항)만 정해놓습니다:

- 모든 Pod는 고유 IP를 가진다
- 모든 Pod는 NAT 없이 서로 통신할 수 있어야 한다
- 노드도 Pod와 통신할 수 있어야 한다

"이걸 실제로 어떻게 구현할지는 너희(플러그인)가 알아서 해" → 그 **플러그인을 끼우는 표준 구멍이 CNI**입니다.

```
쿠버네티스 (kubelet)
      │  "Pod 떴다. 네트워크 좀 붙여줘"
      ▼
 [ CNI 인터페이스 ]  ← 표준 규격(구멍)
      │
      ▼
 CNI 플러그인  ← 실제 구현체 (Cilium / Calico / Flannel ...)
```

## 동작 흐름

Pod가 생성될 때:

1. kubelet이 새 Pod를 위한 **network namespace** 생성
2. kubelet이 **CNI 플러그인 호출** (`ADD` 명령)
3. CNI 플러그인이:
   - veth(가상 케이블) 만들어 Pod ↔ 노드 연결
   - Pod에 **IP 할당** (IPAM)
   - 라우팅·정책 설정
4. Pod 삭제되면 `DEL` 호출 → 정리

즉 CNI는 "Pod가 뜰 때마다 네트워크를 꽂아주고, 죽을 때 뽑아주는" 표준화된 약속입니다.

## CNI 플러그인 종류 (구현체들)

| 플러그인 | 방식 | 특징 |
|---|---|---|
| Flannel | VXLAN 오버레이 | 단순, 정책 없음 |
| Calico | iptables / BGP | 네트워크 정책 강력 |
| **Cilium** | **eBPF** | iptables 대체, 고성능, L7 정책, 암호화 |

## Cilium이 CNI로서 특별한 이유 (eBPF)

대부분 CNI는 **iptables 룰 체인**으로 라우팅·정책을 처리합니다. 룰이 많아지면 선형 탐색이라 느려지죠.

Cilium은 **eBPF**(커널 안에서 동작하는 작은 프로그램)를 씁니다:

```
일반 CNI:  패킷 → iptables 룰 1 → 룰 2 → ... → 룰 5000  (느림)
Cilium:    패킷 → eBPF 맵 lookup (해시 조회 1번)         (빠름)
```

- 룰을 체인으로 안 거치고 **커널 eBPF 맵에서 즉시 조회**
- IP가 아니라 **Pod label 기반 identity**로 정책 적용
- kube-proxy(iptables 기반 서비스 LB)도 eBPF로 대체 가능

## 우리 클러스터 맥락에서 왜 중요한가

앞서 본 cascade 문제의 핵심이 여기 있습니다:

> Cilium = CNI = **데이터플레인 그 자체**

Cilium은 kube-proxy 같은 보조 도구가 아니라, **패킷이 지나가는 길 자체를 만드는 주체**입니다. 그래서:

```
cilium-agent 못 뜸 (ztunnel 시크릿 없음)
     ▼
CNI 동작 안 함
     ▼
Pod에 네트워크 못 붙임 → 노드 NotReady
     ▼
클러스터 전체 cascade
```

다른 CNI라면 "네트워크 일부 기능 문제" 정도지만, Cilium은 CNI가 곧 전체 데이터플레인이라 **없으면 클러스터가 통째로 멈추는** 것입니다.

## 한 줄 요약

> CNI = 쿠버네티스가 Pod에 네트워크를 붙이는 표준 규격. 쿠버네티스는 규칙만 정하고 실제 구현은 플러그인에 맡기는데, Cilium은 그 구현을 iptables 대신 eBPF로 해서 빠르고 강력하다. 그리고 Cilium에선 CNI가 곧 데이터플레인 전체라 없으면 클러스터가 죽는다.

좋아요, 비유로 풀어볼게요. 핵심 질문은 **"왜 Pod마다 프록시(사이드카) 대신 노드당 하나(ztunnel)냐?"** 입니다.

## 먼저 "프록시가 왜 필요한가" — 경비원 비유

Pod끼리 그냥 통신하면 "암호화·신원확인·접근제어"를 각 앱이 직접 코드로 짜야 합니다. 귀찮고 실수 많죠.

그래서 **각 통신 앞에 "경비원"을 세웁니다.** 이 경비원이 대신:
- 트래픽 암호화(mTLS)
- "넌 누구야?" 신원 확인
- 출입 통제

앱은 평문으로 보내기만 하면, 경비원이 알아서 암호화·검문을 해줍니다. 이 경비원이 **프록시**예요.

## 옛날 방식 (사이드카) — "방마다 경비원 1명"

전통적 service mesh(Istio 기본 모드)는 **Pod마다 Envoy 프록시를 하나씩 붙입니다.**

```
사이드카 모델 = 아파트 모든 집 현관마다 경비원 배치

[Pod A][경비원]   [Pod B][경비원]   [Pod C][경비원]
[Pod D][경비원]   [Pod E][경비원]   [Pod F][경비원]
```

문제:
- **경비원 100명** (Pod 100개면 프록시 100개) → 메모리·CPU 낭비 엄청남
- 집(앱)을 새로 단장(배포)할 때마다 **경비원도 같이 재배치** → 앱 업데이트하면 프록시도 재시작
- 작은 집(가벼운 Pod)에도 똑같이 무거운 경비원이 붙음 → 배보다 배꼽

## 새 방식 (ztunnel) — "건물 1층 로비에 경비실 하나"

ztunnel은 **노드(서버 한 대)당 프록시를 딱 하나만** 둡니다 (DaemonSet).

```
ztunnel 모델 = 아파트 1동에 공동 경비실 하나

       ┌─── 노드(아파트 1동) ───┐
       │ [Pod A] [Pod B] [Pod C] │
       │ [Pod D] [Pod E] [Pod F] │
       │                         │
       │   [ztunnel 경비실 1개]  │ ← 이 동의 모든 출입을 관리
       └─────────────────────────┘
```

이 동의 모든 Pod가 드나드는 트래픽을 **공동 경비실 하나가 담당**합니다.

## 그래서 왜 필요한가 — 3가지 이득

| | 사이드카 (방마다 경비원) | ztunnel (동마다 경비실) |
|---|---|---|
| **리소스** | Pod 100개 = 프록시 100개 (무거움) | 노드 5개 = 프록시 5개 (가벼움) |
| **배포 영향** | 앱 배포 시 프록시도 재시작 | 앱 따로, 프록시 따로 (앱 배포해도 경비실 안 건드림) |
| **운영** | 프록시 100개 관리·버전업 | 노드당 하나만 관리 |

특히 두 번째가 큽니다. 사이드카는 **앱과 보안이 한 몸**이라 앱 건드릴 때마다 보안 레이어도 흔들립니다. ztunnel은 **보안 인프라를 앱에서 떼어내서** 노드 레벨로 내림 → 앱 개발자는 보안을 신경 안 써도 됨.

## 단, 트레이드오프 — "공동 경비실의 한계"

방마다 경비원이 있으면 그 집 사정(L7, HTTP 경로·헤더 같은 세밀한 내용)까지 다 압니다. 공동 경비실(ztunnel)은 **누가 드나드는지(L4: 출발지·목적지·암호화)만** 압니다. 세밀한 L7 검문은 못 해요.

그래서 Istio Ambient에선 역할을 나눕니다:
- **ztunnel** = 공동 경비실 (L4, mTLS 암호화·신원확인) ← 기본
- **waypoint proxy** = 필요한 동에만 추가로 두는 "정밀 검문소" (L7) ← 옵션

우리 클러스터는 **Cilium 암호화용으로 ztunnel의 L4 mTLS 기능만** 쓰는 거라, "노드 간 트래픽 자동 암호화 경비실" 역할이면 충분합니다.

## 한 줄 요약

> 사이드카는 "Pod마다 경비원" → 100개면 100명이라 무겁고, 앱 배포할 때마다 같이 흔들림. ztunnel은 "노드마다 공동 경비실 하나" → 가볍고, 보안을 앱에서 떼어내 따로 관리. 대신 세밀한 L7 검문은 못 하고 출입·암호화(L4)만 한다. 우리는 그 암호화 기능만 쓰는 거다.

CNI 플러그인 3개가 **"Pod 간 통신을 실제로 어떻게 구현하느냐"**에서 갈립니다. 핵심은 두 가지 질문이에요:

2. **정책·서비스 처리를 무엇으로 하나?** (iptables vs eBPF)

## 1. Flannel — "택배 상자에 넣어 보내기" (VXLAN 오버레이)

가장 단순한 CNI. 노드 간 통신을 **오버레이(overlay)** 방식으로 합니다.

### 문제 상황
노드1의 Pod(10.244.1.5)가 노드2의 Pod(10.244.2.8)로 보내려는데, 물리 네트워크는 그 Pod IP들을 모릅니다. 물리망은 노드 IP(192.168.x.x)만 알아요.

### VXLAN의 해결법 — "상자 안에 상자"
```
원본 패킷:        [출발 Pod IP → 목적 Pod IP][데이터]
                          │ VXLAN이 통째로 감쌈
                          ▼
캡슐화된 패킷:   [노드1 IP → 노드2 IP][ {원본 패킷} ]
                  └─ 물리망이 아는 주소 ─┘
```

**비유:** 회사 내부 사서함 주소(Pod IP)로는 우체국이 배달 못 하니까, **회사 건물 주소(노드 IP)가 적힌 큰 택배 상자에 원래 편지를 넣어** 보냅니다. 받는 회사(노드2)가 상자를 뜯어서 내부 사서함(Pod)으로 전달.

- **장점:** 물리 네트워크가 뭐든 상관없이 동작 (어디서나 됨)
- **단점:** 매번 포장/개봉(캡슐화/디캡슐화) → 오버헤드, 약간 느림
- **정책:** 없음. "누가 누구랑 통신 가능한가" 제어 기능이 없음 → 보안 약함

---

## 2. Calico — "진짜 주소로 직접 배달" (BGP 라우팅) + iptables 정책

Flannel과 두 가지가 다릅니다.

### (a) 전달 방식 — 오버레이 안 쓰고 "라우팅"
Calico는 상자에 안 넣고 **라우터에게 Pod IP로 가는 길을 직접 알려줍니다.** 이때 쓰는 게 **BGP**(라우터끼리 "이 IP 대역은 나한테 보내" 하고 길 정보를 교환하는 프로토콜).

```
Flannel: 포장해서 보냄         (오버레이, 느림)
Calico:  라우터가 Pod IP 길을 이미 알아서 그냥 직접 보냄  (네이티브 라우팅, 빠름)
```

**비유:** Flannel이 "택배 상자에 포장"이라면, Calico는 **우체국(라우터)에 모든 사서함 주소를 미리 등록**해놔서 포장 없이 바로 배달. 단, 우체국(물리망)이 협조해줘야 함(BGP 지원).

### (b) 정책·서비스 처리 — iptables
Calico는 "누가 누구랑 통신 가능한가"(NetworkPolicy)를 **iptables 룰**로 구현합니다.

```
패킷 도착 → iptables 룰 체인을 위에서부터 검사
  룰1: A→B 허용?  아니오 ↓
  룰2: C→D 차단?  아니오 ↓
  ...
  룰5000: ...      (룰 많아지면 선형 탐색 → 느려짐)
```

- **장점:** 네트워크 정책이 강력하고 성숙함, 오버레이 없어서 빠름
- **단점:** 정책 많아지면 iptables가 길어져 성능 저하, BGP 설정이 물리망에 의존적

---

## 3. Cilium — "커널에 직접 프로그램 심기" (eBPF)

앞의 둘은 **리눅스가 원래 주는 도구(VXLAN, iptables)**를 조합한 거라면, Cilium은 **커널 안에 직접 작은 프로그램(eBPF)을 심어서** 패킷을 처리합니다.

### eBPF가 뭔가
커널을 재컴파일하거나 모듈을 안 만들고도, **커널 안에서 안전하게 도는 프로그램을 동적으로 꽂는** 기술. 패킷이 들어오는 그 지점(네트워크 카드 근처)에서 즉시 판단합니다.

```
Calico(iptables):  패킷 → 룰1 → 룰2 → ... → 룰5000   (체인 선형 탐색)
Cilium(eBPF):      패킷 → eBPF 맵 해시 조회 1번        (즉시 결정)
```

**비유:** iptables가 **"규정집을 첫 장부터 한 줄씩 읽어 내려가며 검문"**이라면, eBPF는 **"입구에서 바코드 한 번 찍으면 즉시 통과/차단 판정"**. 규정이 5000개로 늘어도 속도가 안 떨어집니다(해시 조회라서).

### Cilium이 추가로 하는 것들
| 기능 | 설명 |
|---|---|
| **iptables 대체** | kube-proxy(서비스 로드밸런싱)까지 eBPF로 대체 → 더 빠름 |
| **고성능** | 룰 수와 무관하게 일정한 속도 |
| **L7 정책** | IP/포트(L4)뿐 아니라 HTTP 경로·메서드(L7)까지 제어 ("`GET /api`는 허용, `DELETE`는 차단") |
| **identity 기반** | IP가 아니라 **Pod label**로 정책 적용 (IP가 바뀌어도 정책 유지) |
| **암호화** | IPsec/WireGuard/**ztunnel** mTLS 내장 ← 우리 클러스터가 쓰는 것 |

---

## 세 개 비교 — 한눈에

```
                Flannel          Calico            Cilium
노드 간 전달    택배 포장        직접 배달         직접 배달
                (VXLAN)          (BGP 라우팅)      (eBPF 라우팅)
정책 엔진       없음             iptables          eBPF
정책 수준       —                L3/L4            L3/L4/L7
속도            보통             빠름              가장 빠름(룰↑무관)
암호화          ✕                제한적            IPsec/WG/ztunnel
복잡도          낮음             중간              높음
```

**진화의 흐름:**
- Flannel = "되게만 하자" (단순, 오버레이)
- Calico = "정책도 제대로, 오버레이 빼서 빠르게" (iptables + BGP)
- Cilium = "iptables 한계를 eBPF로 넘자, L7·암호화까지" (커널 레벨 재설계)

---

## 우리 클러스터가 Cilium인 이유

```
Cilium 선택 = eBPF 성능 + L7 정책 + ztunnel mTLS 암호화를 한 번에
                                          │
                            앞서 본 cilium-ztunnel-secrets가
                            바로 이 "암호화" 기능의 신뢰 뿌리(CA)
```

다른 CNI였으면 별도 메시(Istio 등)를 또 깔아야 mTLS가 됐을 텐데, Cilium은 **CNI 안에 암호화까지 통합**되어 있어서 ztunnel 방식으로 노드 간 트래픽을 자동 암호화하는 겁니다.

## 한 줄 요약

> Flannel은 패킷을 노드 IP 상자에 포장해 보내는 단순 오버레이(정책 없음). Calico는 BGP로 Pod IP 길을 알려 직접 배달하고 iptables로 정책 처리. Cilium은 iptables 대신 eBPF를 커널에 심어 룰이 많아도 빠르고, L7 정책·mTLS 암호화까지 통합 — 그래서 우리가 ztunnel 암호화를 쓸 수 있는 것이다.

# User

L7정책은 왜 좋은거야? L4나 이하 레이어정책은 없는거야?

<!-- kh:msg assistant -->
# Assistant

좋은 질문이에요. **L4 이하 정책도 당연히 있습니다.** 오히려 그게 기본이고, L7은 "그 위에 추가로 더 세밀하게"입니다. 레이어별로 무엇을 보는지부터 봅시다.

## 네트워크 레이어와 "각 레이어에서 볼 수 있는 것"

```
L7 (애플리케이션)  HTTP 경로·메서드·헤더    "GET /api/users"
L4 (전송)          포트·프로토콜            "TCP 8080"
L3 (네트워크)      IP 주소                  "10.0.0.5 → 10.0.0.8"
L2 (데이터링크)    MAC 주소
L1 (물리)          전기 신호·케이블
```

위로 갈수록 **"내용에 가까운 정보"**, 아래로 갈수록 **"배달 경로에 가까운 정보"**입니다.

네트워크 정책은 보통 **L3/L4** 기준입니다. L7은 거기에 얹는 거고요.

## 같은 통신을 레이어별 정책으로 표현하면

상황: "프론트엔드 → 백엔드 API 통신을 제어하고 싶다"

### L3 정책 (IP 기준)
```
"10.0.1.0/24 대역에서 오는 트래픽만 허용"
```
→ "이 동네 사람만 출입 가능"

### L4 정책 (포트/프로토콜 기준) ← 가장 흔함
```
"TCP 8080 포트로 오는 것만 허용, 나머지 포트 차단"
```
→ "정문(8080)으로만 들어와, 다른 문은 잠김"

### L7 정책 (HTTP 내용 기준)
```
"GET /api/products 는 허용
 DELETE /api/users 는 차단
 Header에 valid-token 있는 것만 허용"
```
→ "들어오는 건 되는데, **무슨 용건이냐**까지 보고 통과/차단"

## L7이 왜 좋은가 — L4의 한계 때문

L4 정책의 결정적 한계: **포트는 열거나 닫거나 둘 중 하나**입니다.

```
L4의 세계: 8080 포트 = 열림 ✅  또는  닫힘 ❌
           → 한번 열면 그 포트로 오는 "모든 요청"이 통과
```

문제는, **같은 포트(8080)로 안전한 요청과 위험한 요청이 섞여 들어온다**는 것:

```
TCP 8080 (전부 같은 포트)
   ├─ GET  /api/products   ← 정상 조회 (허용하고 싶음)
   ├─ GET  /api/users      ← 개인정보 조회 (제한하고 싶음)
   └─ DELETE /api/users/*  ← 계정 삭제 (절대 막고 싶음)
```

**L4로는 이걸 구분 못 합니다.** 8080을 열면 셋 다 통과, 닫으면 셋 다 차단. 전부 아니면 전무.

**L7이면** 같은 포트 안에서 "조회는 허용, 삭제는 차단"처럼 **용건 단위로** 세밀하게 자릅니다.

### 비유
- **L4 = 건물 정문 경비** — "출입증(포트) 있으면 들어가세요." 일단 들어오면 건물 안 어디든 감.
- **L7 = 각 사무실 앞 검문 + 용무 확인** — "당신 열람실은 가도 되는데, 서버실은 안 됩니다." 들어온 사람의 **행동 하나하나**를 통제.

## 그럼 L4는 필요 없나? — 아니요, 둘 다 씁니다

L7만 쓰는 게 아니라 **계층적으로 겹쳐서** 씁니다:

```
1차 (L3/L4): "그 동네(IP)에서, 정문(8080)으로만"   ← 굵은 필터, 빠름
2차 (L7):    "그중에서도 GET만, DELETE는 차단"      ← 정밀 필터
```

이유:
- **성능**: L7 검사는 패킷 내용까지 까봐야 해서 비쌈. L4로 먼저 대부분 걸러내고, 통과한 것만 L7로 정밀 검사하는 게 효율적.
- **적용 범위**: 모든 트래픽이 HTTP는 아님. DB 연결, gRPC 등은 L4 정책이 더 적합.
- **방어 심층화(defense in depth)**: 여러 겹으로 막아야 한 겹 뚫려도 다음 겹이 막음.

## Cilium에서의 의미

대부분 CNI(Calico 등)는 **L3/L4 정책까지만** 됩니다. iptables 기반이라 HTTP 내용을 들여다보기 어렵거든요.

Cilium은 **eBPF로 패킷 내용까지 커널에서 파싱**할 수 있어서 L7 정책이 가능합니다:

```
Calico:  L3/L4 정책 (IP, 포트까지)
Cilium:  L3/L4 + L7 정책 (HTTP 경로·메서드, gRPC, Kafka 토픽까지)
```

그래서 "L7 정책"이 Cilium의 차별점으로 꼽히는 거예요. **L4 정책이 없어서가 아니라, L4는 기본으로 다 되고 거기에 L7까지 더 된다**는 뜻입니다.

## 한 줄 요약

> L4 이하 정책(IP·포트)은 기본이고 모든 CNI가 합니다. 문제는 L4는 "포트 열림/닫힘"이라 같은 포트로 들어오는 정상 요청과 위험 요청을 못 가른다는 것. L7은 "GET은 허용, DELETE는 차단"처럼 용건 단위로 자릅니다. 실무는 L4로 굵게 거르고 L7로 정밀하게 거르는 식으로 겹쳐 쓰며, Cilium은 eBPF 덕에 그 L7까지 된다는 게 강점입니다.

데이터플레인(data plane)은 **"실제로 패킷(데이터)이 지나다니는 길"**입니다. 짝이 되는 개념인 **컨트롤플레인(control plane)**과 같이 봐야 이해가 쉬워요.

## 두 개의 플레인 — 핵심 구분

```
컨트롤플레인 (Control Plane)  =  "결정하는 뇌"
   → 어떻게 라우팅할지, 누가 통신 가능한지 규칙을 정함

데이터플레인 (Data Plane)     =  "실제로 나르는 손발"
   → 그 규칙대로 실제 패킷을 전달함
```

**비유: 우체국**
- **컨트롤플레인** = 배송 계획을 짜는 관제실. "이 지역 우편물은 3번 트럭이, 저 지역은 5번 트럭이 나른다"는 **경로표(라우팅 테이블)를 만듦.** 편지를 직접 만지진 않음.
- **데이터플레인** = 실제로 편지를 싣고 달리는 **트럭들.** 관제실이 정한 경로표를 보고 편지를 목적지로 나름.

관제실이 잠깐 멈춰도 트럭들은 기존 경로표로 계속 배달할 수 있지만, **트럭이 멈추면 배달 자체가 멈춥니다.** 이게 핵심 차이예요.

## 네트워크에서

| | 컨트롤플레인 | 데이터플레인 |
|---|---|---|
| 역할 | 규칙·경로 **결정** | 패킷 **전달** |
| 빈도 | 가끔 (정책 바뀔 때) | 항상 (패킷마다) |
| 속도 요구 | 덜 중요 | **매우 중요** (모든 패킷이 지나감) |
| 예시 | 라우팅 프로토콜, 정책 계산 | 패킷 포워딩, 암호화/복호화 |

## Cilium에서의 데이터플레인

Cilium도 이 둘로 나뉩니다:

```
컨트롤플레인:  cilium-operator, 정책 계산, identity 관리
              "Pod label X는 Pod Y와 통신 가능" 같은 규칙을 계산해서
              eBPF 맵에 써넣음

데이터플레인:  커널의 eBPF 프로그램들
              실제 패킷이 지나갈 때 그 맵을 조회해서 즉시 전달/차단
```

eBPF 프로그램이 **"패킷이 실제로 흐르는 길"** = Cilium의 데이터플레인입니다.

## 우리 클러스터 맥락 — 왜 "Cilium = 데이터플레인 그 자체"라고 했나

앞에서 제가 이렇게 말했죠:

> Cilium = CNI = 데이터플레인 그 자체

그 의미는:

```
일반 환경:
  네트워킹 = 컨트롤플레인(쿠버네티스) + 데이터플레인(여러 도구가 분담)
  → 일부 죽어도 나머지로 버팀

Cilium 환경:
  데이터플레인을 Cilium의 eBPF가 통째로 담당
  → 패킷이 지나가는 길 자체가 Cilium
```

그리고 우리 클러스터는 `encryption.type: ztunnel`이라 **ztunnel의 mTLS 암호화도 데이터플레인의 일부**입니다:

```
데이터플레인 = eBPF 포워딩 + ztunnel mTLS 암호화
                                    │
                  cilium-ztunnel-secrets가 없으면
                  cilium-agent가 못 뜸
                                    │
                  데이터플레인 전체가 안 만들어짐
                  = 패킷 길 자체가 없음
                  = 노드 NotReady → 클러스터 cascade
```

즉 "트럭(데이터플레인)이 멈추면 배달 전체가 멈춘다"는 그 상황이, 시크릿이 없어서 cilium-agent(데이터플레인 주체)가 못 떴을 때 벌어진 일입니다.

## 한 줄 요약

> 컨트롤플레인 = 경로·규칙을 정하는 뇌, 데이터플레인 = 그 규칙대로 실제 패킷을 나르는 손발(우체국 트럭). Cilium에선 eBPF가 데이터플레인이고, 우리 클러스터는 ztunnel mTLS 암호화까지 그 데이터플레인에 포함되어 있어서, CA 시크릿이 없으면 데이터플레인 자체가 안 떠서 클러스터가 멈춘 것이다.

# Assistant

솔직히 말하면 제가 앞에서 **gRPC를 DB랑 같이 묶은 건 부정확했습니다.** 정정하면서 설명할게요.

## 정정: gRPC는 사실 L7 정책 가능

gRPC는 **HTTP/2 위에서** 도는 프로토콜입니다. 그래서 Cilium은 gRPC도 L7 정책을 걸 수 있어요 (`POST /package.Service/Method` 형태로 메서드 단위 제어 가능). 제가 DB와 한 묶음으로 "L4가 적합"이라 한 건 틀렸습니다.

**진짜 L4가 적합한 건 "프록시가 내용을 못 읽는 트래픽"**입니다. 그게 무슨 뜻인지가 핵심이에요.

## L7 정책이 성립하려면 — "내용을 읽을 수 있어야" 함

L7 정책은 "`GET /api/users` 차단"처럼 **패킷 내용을 파싱해서 의미를 이해**해야 가능합니다. 그러려면 두 조건:

1. 그 프로토콜을 프록시가 **해석할 줄 알아야** 함 (HTTP, gRPC, Kafka 등)
2. 트래픽이 **평문**이거나, 프록시가 **복호화할 수 있어야** 함

이 조건이 안 되면 L7은 불가능하고, **L4(IP·포트)로만** 제어할 수 있습니다.

## L4가 적합한(혹은 L4밖에 안 되는) 경우들

### (1) 프록시가 모르는/해석 못 하는 프로토콜 — DB가 대표적

PostgreSQL, MySQL, Redis 같은 **DB는 각자 고유한 바이너리 프로토콜**을 씁니다. HTTP처럼 표준화된 "경로/메서드" 개념이 없어요.

```
HTTP:   GET /api/users  ← 텍스트, 구조가 명확, 파싱 쉬움
PostgreSQL 와이어 프로토콜:  0x51 00 00 00 1a 53 45 4c...  ← DB 전용 바이너리
```

Cilium의 L7 파서는 HTTP/gRPC/Kafka/DNS 정도만 이해합니다. **PostgreSQL 쿼리를 파싱해서 "SELECT는 허용, DROP TABLE은 차단" 같은 걸 못 해요** (그 프로토콜 파서가 없으니까). 그래서 DB 트래픽은 사실상 **L4로 "이 Pod만 5432 포트 접속 허용"** 정도가 최선입니다.

### (2) 암호화된 트래픽 — 내용이 안 보임

TLS로 암호화된 트래픽은 프록시가 까봐도 **암호문**입니다.

```
[암호화된 페이로드]  ← 프록시 입장에선 그냥 의미 없는 바이트 덩어리
```

내용을 못 보니 "무슨 요청인지" 판단 불가 → L7 정책 못 검. 보이는 건 **L4 정보(목적지 IP·포트)뿐** → L4 정책만 가능. (mTLS로 암호화된 우리 ztunnel 트래픽이 딱 이 경우.)

### (3) 애초에 L7 구분이 의미 없는 통신

```
- DB 커넥션 풀:  "DB에 붙는다/안 붙는다"가 전부. 세부 경로 개념이 없음
- Redis:        키-값 명령 단위라 HTTP식 경로 정책이 안 맞음
- 단순 TCP 스트림: 구조 자체가 없음
```

이런 건 **"누가(IP) 어디(포트)에 붙느냐"**만 통제하면 충분 → L4가 더 자연스럽고 적합.

### (4) 성능 — 굳이 까볼 필요 없을 때

L7 검사는 패킷 내용을 파싱하는 비용이 듭니다. DB처럼 대량·고빈도 연결인데 L7로 얻을 게 없다면, **L4로 가볍게 거르는 게 효율적**입니다.

## 정리하면 — "적합"의 기준

| 트래픽 | L7 가능? | 왜 |
|---|---|---|
| HTTP | ✅ | 표준 텍스트, 파싱 쉬움 |
| gRPC | ✅ | HTTP/2 기반 (← 정정한 부분) |
| Kafka, DNS | ✅ | Cilium에 전용 파서 있음 |
| PostgreSQL/MySQL/Redis | ❌ → L4 | 전용 바이너리, 파서 없음 |
| TLS 암호화 트래픽 | ❌ → L4 | 내용이 암호문이라 못 읽음 |
| 일반 TCP/UDP 스트림 | ❌ → L4 | 구조 자체가 없음 |

핵심 원리:

> **L7 정책은 "프록시가 그 프로토콜을 평문으로 읽고 이해할 수 있을 때만" 가능하다.** 그게 안 되는 트래픽(DB 바이너리 프로토콜, 암호화된 트래픽, 구조 없는 스트림)은 내용을 못 보니까 IP·포트(L4)로만 제어할 수밖에 없고, 그래서 L4가 "더 적합"한 게 아니라 **"L4가 유일하게 가능한 선택"**인 경우가 많다.

## 한 줄 요약

> gRPC는 제가 틀렸고 L7 가능합니다(HTTP/2 기반). 진짜 L4가 적합한 건 DB(PostgreSQL 등 전용 바이너리 프로토콜이라 프록시가 파싱 못 함)나 암호화 트래픽(내용이 암호문이라 못 읽음)처럼 **프록시가 내용을 이해할 수 없는 경우**다. 이럴 땐 "누가 어느 포트에 붙냐"는 L4 제어가 가능한 전부다.
